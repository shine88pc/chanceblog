# PR 만들고 병합하는 방법 (운영자용)

> AI가 GitHub 화면을 쓸 수 없을 때(내장 브라우저가 `github.com` 을 막은 동안) 운영자가 **직접** 병합하는 방법입니다. GitHub에 로그인된 브라우저 하나면 됩니다(휴대폰 브라우저도 됩니다). 마지막 갱신: 2026-10-27 밤, 갱신자: Claude
>
> **병합할 PR 은 텔레그램 요청(`병합 부탁`)에 적힌 제목의 것 하나뿐입니다.** 2026-11-02 부터 요청에는 **링크 주소를 쓰지 않고**, 병합할 PR 의 **제목**을 `[R-045] …` 처럼 맨 앞에 요청 번호를 붙여(텔레그램 맨 위의 `r045` 와 같은 번호이고 PR 제목에는 저장소 쪽 표기 `R-045` 로 적힙니다) 눈에 띄게 적습니다(비슷한 제목이 여러 개라 실수하기 쉽다는 운영자 지적, 병합은 휴대폰의 PC 버전 GitHub 에서 하십니다). 제목이 **글자까지 같은 하나만** 병합하고 다른 제목은 병합하지 않습니다. **병합하셨는지는 AI 가 공개 정보로 직접 확인하니 따로 알리지 않으셔도 됩니다.**

> AI 가 텔레그램으로 병합을 부탁하거나 결정을 묻고, 운영자가 이슈 양식으로 답하는 방법은 [`운영자_요청함_사용법.md`](./운영자_요청함_사용법.md) 입니다(병합한 뒤 `했어요` 로 알려 주면 됩니다).

## 한눈에 (3분 + 기다리는 시간)

1. 휴대폰에서 GitHub 를 **PC 버전**으로 열고 저장소 첫 화면(또는 **Pull requests** 탭)에서, 요청에 적힌 **병합할 제목**(`[R-nnn] …`)과 같은 것 **하나**를 찾아 초록 **"Create pull request"** 를 누른다(첫 화면 노란 배너의 "Compare & pull request" 도 같습니다 — 제목은 이미 요청의 제목으로 채워져 있습니다).
2. PR 화면 아래쪽 검사가 **모두 초록 체크**가 될 때까지 기다린다(블로그 저장소는 보통 2분 안팎 — AI 가 같은 검사를 PR 보다 먼저 끝내 초록인 것을 확인하고 부탁을 드리지만, PR 을 만들면 PR 검사가 한 번 더 돕니다).
3. 초록 **"Squash and merge"** 버튼 → **"Confirm squash and merge"** 를 누른다. 끝.
4. 병합하고 5~10분 뒤 저장소의 **Actions** 탭에서 `[공통] 사이트 자동 배포`가 초록인지 본다(AI 도 확인합니다).

## PR 을 만드는 두 가지 방법

| 방법 | 설명 |
|------|------|
| **저장소 첫 화면 노란 배너 또는 Pull requests 탭(2026-11-02~, 권장)** | AI 는 병합할 브랜치를 **커밋 한 개**로 합쳐 올립니다. 그래서 PR 의 기본 제목이 그 커밋 제목 = 요청에 적힌 `[R-nnn] …` 제목입니다. 링크는 드리지 않습니다 |
| 노란 배너가 **여러 개**일 때 | 브랜치 이름이 요청 번호로 시작하는 것(예: `r045…`)을 고릅니다. 제목이 `Ai/claude/…` 처럼 나오면 커밋이 여러 개인 브랜치라는 뜻이니 병합하지 말고 알려 주세요. **같은 브랜치로 PR 을 두 번 만들지 마세요**(2026-10-27 묶음 2 는 #53·#54 로 두 번 만들어졌습니다 — 내용은 같아서 문제는 없었습니다) |
| 먼저 만들어 두신 PR 이 있을 때 | 한글 Blogger 는 구현 브랜치로 #57 을 먼저 만드셨습니다. 이럴 땐 PR 을 새로 만들 필요 없이 **AI 가 같은 브랜치에 충돌을 푼 커밋을 올려** 그 PR 이 병합 대상이 됩니다. 올라오기 전에는 "This branch has conflicts" 가 보이는 것이 정상이니 **병합하지 말고 AI 의 "병합 가능" 안내를 기다려 주세요** |

## 병합하지 말고 닫을 PR

지금은 없습니다. 예전에 구현 브랜치별로 만들어 두신 #48~#52 는 내용이 이미 묶음 1·2 로 병합돼 있었고, 2026-10-28 에 모두 닫힌 것을 확인했습니다. 앞으로 같은 일이 생기면 PR 화면 맨 아래 **"Close pull request"**(삭제가 아니라 닫기)를 눌러 닫고 브랜치는 그대로 둡니다.

## 단계별 설명 (PC·휴대폰 브라우저 공통)

1. **링크를 엽니다.** 로그인 화면이 나오면 GitHub에 로그인합니다. 로그인되어 있으면 "Open a pull request" 화면이 바로 보입니다.
2. **초록 "Create pull request" 를 누릅니다.** 화면이 PR 페이지(주소 끝이 `/pull/숫자`)로 바뀌면 만들어진 것입니다.
3. **검사를 기다립니다.** 페이지 맨 아래쪽 "Checks"(또는 병합 상자)에서 노란 점은 진행 중, 초록 체크는 통과입니다. `검사 (Python 3.10)`, `검사 (Python 3.12)`, `이슈 요청 범위 확인`이 모두 초록이면 **"All checks have passed"** 가 보입니다.
   - 빨간 ✗ 가 하나라도 있으면 **병합하지 말고** 화면을 캡처해 알려 주세요.
   - "This branch has conflicts that must be resolved" 가 보여도 병합하지 말고 알려 주세요.
4. **"Squash and merge" (초록 버튼)** 을 누르고, 제목·본문 칸은 **그대로 둔 채** "Confirm squash and merge" 를 누릅니다. (광고 표면을 바꾸는 PR 은 제목 앞쪽에 `Ad-Surface-Approved: …` 가 들어 있습니다 — 승인 기록이라 **지우지 마세요**.)
5. "Pull request successfully merged and closed" 가 뜨면 병합 완료입니다. **"Delete branch" 버튼은 누르지 마세요**(병합한 브랜치를 지우지 않는 규칙입니다).
6. 병합 5~10분 뒤 **Actions** 탭에서 `[공통] 사이트 자동 배포`가 초록인지 확인합니다. 빨강이면 알려 주세요(AI 도 병합 직후 확인합니다).

## 휴대폰에서 할 때

- 휴대폰 브라우저에서 링크를 열어 같은 순서로 하면 됩니다(GitHub 앱이 설치되어 있으면 앱으로 열릴 수 있고, 앱에서도 "Pull requests"에서 같은 PR을 열어 "Merge pull request → Squash and merge"를 누르면 같습니다).
- 텔레그램 알림이 켜져 있어 새 글·확인 필요 항목이 휴대폰으로 옵니다(알림의 링크 버튼으로 PR·모음 화면을 바로 열 수 있습니다).

## 막혔을 때

| 보이는 것 | 의미·할 일 |
|-----------|-----------|
| "Open a pull request" 대신 이미 PR 이 있다는 안내 | 이미 만들어진 PR 입니다. 그 PR 로 들어가 3번부터 진행 |
| 검사가 20분 넘게 노란 점 | GitHub 지연일 수 있습니다. 기다리다 알려 주세요 |
| 빨간 ✗ / conflicts | 병합하지 말고 캡처해서 알려 주세요(제가 고칩니다) |
| "Squash and merge" 가 안 보이고 "Merge pull request" 만 있음 | 그대로 "Merge pull request" 를 눌러도 내용은 같습니다. 알려 주시면 설정을 확인합니다 |
| 병합했는데 사이트 배포가 빨강 | 제가 공개 정보로 먼저 확인합니다. 캡처가 있으면 같이 주세요 |

## 왜 PR 여러 개가 아니라 묶음인가

PR 여러 개를 차례로 병합하면 두 번째부터 `WORKLOG.md` 맨 위 항목이 겹쳐 "conflicts"가 생기고, 이 충돌은 비개발자가 풀기 어렵습니다(실험으로 확인). 묶음은 제가 미리 충돌을 풀고 합친 결과를 시험한 것이라 한 번의 클릭으로 끝납니다. 구성 요소 각각의 독립 검증 결과와 병합 전 확인 사항은 `WORKLOG.md` 맨 위 항목들에 있습니다.
