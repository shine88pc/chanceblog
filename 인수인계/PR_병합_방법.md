# PR 만들고 병합하는 방법 (운영자용)

> AI가 GitHub 화면을 쓸 수 없을 때(내장 브라우저가 `github.com` 을 막은 동안) 운영자가 **직접** 병합하는 방법입니다. GitHub에 로그인된 브라우저 하나면 됩니다(휴대폰 브라우저도 됩니다). 마지막 갱신: 2026-10-27 밤, 갱신자: Claude
>
> **병합할 PR 은 텔레그램 요청(`병합 부탁`)에 적힌 제목의 것 하나뿐입니다.** 2026-11-02 부터 요청에는 **링크 주소를 쓰지 않고**, 병합할 PR 의 **제목**을 `[R-045] …` 처럼 맨 앞에 요청 번호를 붙여(텔레그램 맨 위의 `r045` 와 같은 번호이고 PR 제목에는 저장소 쪽 표기 `R-045` 로 적힙니다) 눈에 띄게 적습니다(비슷한 제목이 여러 개라 실수하기 쉽다는 운영자 지적, 병합은 휴대폰의 PC 버전 GitHub 에서 하십니다). 제목이 **글자까지 같은 하나만** 병합하고 다른 제목은 병합하지 않습니다. **병합하셨는지는 AI 가 공개 정보로 직접 확인하니 따로 알리지 않으셔도 됩니다.** (2026-11-06 부터 병합 요청은 `🔀 M007 · 병합 요청` 알림이고 그 안의 `PR 제목:` 줄이 **글자 그대로의 실제 PR 제목**입니다 — AI 가 줄이거나 바꾸지 않았으니 같은 제목의 PR 하나만 병합하세요. 이전 방식 요청은 위처럼 요약 안의 「…」 제목입니다.)

> **★ 2026-11-06 바뀐 표기 — 병합 화면에서 `M` 번호로 알아봅니다.** 병합할 PR 의 제목은 `[M004] …` 처럼 **알림 번호(`M…`)로 시작**하고 가지 이름도 `ai/claude/M004-…` 입니다(텔레그램 `🔀 M004 · 병합 요청` 의 번호와 같습니다). **제목 맨 앞에 `M` 번호가 있는 것만 병합하는 것**입니다. 병합하면 안 되는 가지(요청 파일을 올리는 가지 `ai/claude/NO-MERGE-…`·진단용 임시 가지 등)는 이름에 `NO-MERGE` 가 들어 있습니다. 요청 번호(`R-nnn`)는 AI 의 작업 번호라 병합 화면에는 나오지 않습니다(R-175 까지는 `[R-175] …` 꼴이었고 아래 설명의 `[R-nnn]` 은 그 옛 표기입니다).
>
> AI 가 텔레그램으로 병합을 부탁하거나 결정을 묻고, 운영자가 이슈 양식으로 답하는 방법은 [`운영자_요청함_사용법.md`](./운영자_요청함_사용법.md) 입니다(병합한 뒤 `했어요` 로 알려 주면 됩니다).

## 한눈에 (3분 + 기다리는 시간)

1. 휴대폰에서 GitHub 를 **PC 버전**으로 열고 저장소 첫 화면(또는 **Pull requests** 탭)에서, 요청에 적힌 **병합할 제목**(`[M004] …` 꼴 — 텔레그램 알림의 `PR 제목:` 줄)과 같은 것 **하나**를 찾아 초록 **"Create pull request"** 를 누른다(첫 화면 노란 배너의 "Compare & pull request" 도 같습니다 — 제목은 이미 요청의 제목으로 채워져 있습니다).
2. PR 화면 아래쪽 검사가 **이미 끝난 초록 체크**인지 본다(2026-11-04 부터 PR 을 만들 때 새로 도는 검사는 없습니다. AI 가 병합할 브랜치를 올릴 때 이미 끝난 검사가 PR 화면에 그대로 보이고, 초록인 것을 확인한 뒤에 부탁을 드리므로 기다리지 않고 바로 병합하면 됩니다. `Skipped`(건너뜀)로 보이는 줄이 한두 개 있는 것은 해당 없다는 뜻의 정상입니다).
3. 초록 **"Squash and merge"** 버튼 → **"Confirm squash and merge"** 를 누른다. 끝.
4. 병합하고 5~10분 뒤 저장소의 **Actions** 탭에서 `[공통] 사이트 자동 배포`가 초록인지 본다(AI 도 확인합니다). 병합 직후 main 의 검사도 한 번 더 돌고, 실패하면 휴대폰(텔레그램)으로 알립니다.
5. 병합이 끝나면 AI 가 직접 확인하고 텔레그램으로 `[M004] 병합완료 확인 - 정상` **한 줄**을 보냅니다(2026-11-12 부터 — 진행 현황 번호 없이 병합 요청의 `M` 번호를 그대로 씁니다. AI 의 요청 전용 가지가 이 기능이 병합된 `main` 을 합친 뒤부터이고, 그 전에는 예전처럼 `병합완료` 진행 알림으로 올 수 있습니다). 이 줄이 오면 병합이 제대로 된 것이니 따로 답하지 않아도 됩니다. 이상이면 `- 이상` 줄 아래에 무엇이 이상한지 한 줄이 붙고 **요청 열기** 단추가 달립니다.

## ★ PR 이 이미 만들어져 있을 수 있습니다 (병합 부탁 PR 자동 만들기, 2026-11-06~)

AI 가 병합할 가지(`ai/claude/M004-…`)를 올리면 `[공통] 병합 부탁 PR 자동 만들기` 가 그 커밋의 검사가 초록이 된 **뒤에** PR 을 **자동으로** 만들어 둡니다(제목·내용은 노란 배너로 만들 때와 같습니다). 이 워크플로는 **병합하지 않습니다** — 병합은 늘 운영자가 합니다.

1. 텔레그램 병합 부탁의 `PR 제목:` 줄(`[M004] …`)을 확인합니다.
2. 저장소의 **Pull requests** 탭에 같은 제목의 PR 이 **이미 만들어져** 있으면 노란 배너를 누르지 말고 **그 PR 을 열어** 위 '한눈에' 의 2번(초록 확인)부터 진행해 병합합니다.
3. 그 제목이 **없으면** 지금까지처럼 저장소 첫 화면의 노란 `Compare & pull request` 배너로 PR 을 만들면 됩니다(자동 만들기가 아직 꺼져 있거나 이번에는 만들지 못한 것입니다).
4. Pull requests 탭에 `[M###]` PR 이 **둘 이상** 보이면(AI 가 다음 병합 가지를 미리 올려 검사를 돌린 경우 그 가지의 PR 도 자동으로 만들어집니다) **텔레그램 병합 부탁의 `PR 제목:` 줄과 같은 하나만** 병합하고 나머지는 건드리지 마세요(닫아야 하면 AI 가 텔레그램 요청으로 따로 안내합니다).
5. PR 의 제목·내용은 AI 가 올린 **첫 번째 커밋의 제목·내용 그대로 공개**됩니다. 비밀이나 `@이름`(그 사람에게 알림이 갑니다)이 들어 있으면 병합하지 말고 텔레그램으로 알려 주세요(AI 는 커밋 제목·내용에 그런 것을 쓰지 않는 것이 규칙입니다). 같은 가지를 다시 올려 커밋 제목을 바꿔도 **이미 만들어진 PR 의 제목은 바뀌지 않으니**, 텔레그램의 `PR 제목:` 줄과 다르면 PR 화면에서 제목만 직접 고치거나 AI 에게 텔레그램으로 물어보세요.

**켜는 방법(운영자가 한 번만)**: 저장소 **Settings → Actions → General → Workflow permissions → `Allow GitHub Actions to create and approve pull requests`** 에 체크하고 **Save**. 블로그 저장소는 **이미 켜져 있었습니다**(2026-11-07 첫 관측 — 따로 켜지 않았는데도 봇이 PR 을 만들었습니다. 수정안 PR 을 만드는 `[Chance] 이슈 수정 요청 처리(수정안 PR 만들기)` 도 같은 설정을 씁니다). 데스크톱 저장소는 첫 관측을 기다리는 중이라 켜져 있는지 아직 모릅니다. 이 설정은 워크플로가 PR 을 '승인'하는 것도 허용하지만, 자동 만들기 워크플로에는 승인 기능이 없고 시험이 막습니다. 켜지 않아도 불편은 없습니다 — 자동 만들기가 경고만 남기고 끝나고 노란 배너로 만들면 됩니다. PR 이 막 만들어진 몇 초 동안 `병합 부탁 PR 자동 만들기` 줄이 '도는 중'으로 보일 수 있고 곧 초록이 됩니다.

**자동으로 만든 PR 에서만 보일 수 있는 것**: 병합 상자에 `[공통] PR 변경 범위 검사` 가 **'승인 대기'**(`Approve workflows to run` 단추)로 보일 수 있습니다. GitHub 가 봇이 만든 PR 의 검사를 일단 승인 대기로 두는 것이고, AI 가 올린 병합 가지의 PR 은 그 검사가 어차피 건너뛰므로 **승인 단추를 누르지 말고** 위 순서대로 초록 체크(`검사 (Python 3.10)`·`검사 (Python 3.12)`)만 확인해 병합하면 됩니다. 병합하면 그 승인 대기도 사라질 것으로 봅니다(첫 관측 2026-11-07: 병합 직전에 운영자가 그 줄을 승인(또는 재실행)했을 때는 '건너뜀'(할 일 없음)으로 끝났고 병합에는 영향이 없었습니다 — 승인하지 않고 병합했을 때 그 줄이 어떻게 되는지는 아직 못 봤습니다). 텔레그램에 `승인 대기` 알림이 따로 와도 같습니다(눌러 승인하지 않아도 됩니다).

## PR 을 만드는 두 가지 방법

| 방법 | 설명 |
|------|------|
| **저장소 첫 화면 노란 배너 또는 Pull requests 탭(2026-11-02~, 권장)** | AI 는 병합할 브랜치를 **커밋 한 개**로 합쳐 올립니다. 그래서 PR 의 기본 제목이 그 커밋 제목 = 요청에 적힌 `[M###] …` 제목입니다. 링크는 드리지 않습니다 |
| 노란 배너가 **여러 개**일 때 | 가지 이름에 알림 번호가 들어 있는 것(예: `ai/claude/M004-…`)을 고르고 `NO-MERGE` 가 들어 있는 가지는 누르지 않습니다. 제목이 `Ai/claude/…` 처럼 나오면 커밋이 여러 개인 브랜치라는 뜻이니 병합하지 말고 알려 주세요. **같은 브랜치로 PR 을 두 번 만들지 마세요**(2026-10-27 묶음 2 는 #53·#54 로 두 번 만들어졌습니다 — 내용은 같아서 문제는 없었습니다) |
| 먼저 만들어 두신 PR 이 있을 때 | 한글 Blogger 는 구현 브랜치로 #57 을 먼저 만드셨습니다. 이럴 땐 PR 을 새로 만들 필요 없이 **AI 가 같은 브랜치에 충돌을 푼 커밋을 올려** 그 PR 이 병합 대상이 됩니다. 올라오기 전에는 "This branch has conflicts" 가 보이는 것이 정상이니 **병합하지 말고 AI 의 "병합 가능" 안내를 기다려 주세요** |

## 병합하지 말고 닫을 PR

지금은 없습니다. 예전에 구현 브랜치별로 만들어 두신 #48~#52 는 내용이 이미 묶음 1·2 로 병합돼 있었고, 2026-10-28 에 모두 닫힌 것을 확인했습니다. 앞으로 같은 일이 생기면 PR 화면 맨 아래 **"Close pull request"**(삭제가 아니라 닫기)를 눌러 닫고 브랜치는 그대로 둡니다.

## 단계별 설명 (PC·휴대폰 브라우저 공통)

1. **링크를 엽니다.** 로그인 화면이 나오면 GitHub에 로그인합니다. 로그인되어 있으면 "Open a pull request" 화면이 바로 보입니다.
2. **초록 "Create pull request" 를 누릅니다.** 화면이 PR 페이지(주소 끝이 `/pull/숫자`)로 바뀌면 만들어진 것입니다.
3. **검사 결과를 확인합니다.** 페이지 맨 아래쪽 "Checks"(또는 병합 상자)에서 초록 체크는 통과입니다. `검사 (Python 3.10)`, `검사 (Python 3.12)` 가 초록이면 **"All checks have passed"** 가 보입니다 — 이 검사는 AI 가 브랜치를 올릴 때 이미 끝난 것이라 PR 을 만들어도 새로 돌지 않습니다. `실패 알림(main 에 올라간 변경만)`·`이슈 요청 범위 확인` 이 **Skipped(건너뜀)** 로 보이는 것은 해당 없음이라는 뜻의 정상입니다(빠진 검사가 아닙니다). `확인 필요 항목 모으기` 의 건너뜀 한 줄은 PR 을 열 때가 아니라 병합한 직후에 생깁니다. 초록은 AI 가 가지를 올린 시점의 main 기준입니다. 부탁을 받고 한참 뒤 병합하려는데 `This branch has conflicts` 가 보이면 병합하지 말고 알려 주세요(병합 뒤 main 검사가 한 번 더 돌고 실패하면 휴대폰으로 알립니다).
   - 빨간 ✗ 가 하나라도 있으면 **병합하지 말고** 화면을 캡처해 알려 주세요.
   - "This branch has conflicts that must be resolved" 가 보여도 병합하지 말고 알려 주세요.
4. **"Squash and merge" (초록 버튼)** 을 누르고, 제목·본문 칸은 **그대로 둔 채** "Confirm squash and merge" 를 누릅니다. (광고 표면을 바꾸는 PR 은 제목 앞쪽에 `Ad-Surface-Approved: …` 가 들어 있습니다 — 승인 기록이라 **지우지 마세요**.)
5. "Pull request successfully merged and closed" 가 뜨면 병합 완료입니다. **"Delete branch" 버튼은 누르지 마세요**(병합한 브랜치를 지우지 않는 규칙입니다). 브랜치 선택 칸에 PR 번호 같은 글자를 쳐 넣고 **"Create branch"** 를 누르면 그 이름의 빈 브랜치가 생기고 검사가 한 번 돕니다 — 해는 없지만 필요 없는 일이니 누르지 않습니다(실수로 생기면 AI 가 알려 드리고 지웁니다).
6. 병합 5~10분 뒤 **Actions** 탭에서 `[공통] 사이트 자동 배포`가 초록인지 확인합니다. 빨강이면 알려 주세요(AI 도 병합 직후 확인합니다).

## 휴대폰에서 할 때

- 휴대폰 브라우저에서 링크를 열어 같은 순서로 하면 됩니다(GitHub 앱이 설치되어 있으면 앱으로 열릴 수 있고, 앱에서도 "Pull requests"에서 같은 PR을 열어 "Merge pull request → Squash and merge"를 누르면 같습니다).
- 텔레그램 알림이 켜져 있어 새 글·확인 필요 항목이 휴대폰으로 옵니다(알림의 링크 버튼으로 PR·모음 화면을 바로 열 수 있습니다).

## 막혔을 때

| 보이는 것 | 의미·할 일 |
|-----------|-----------|
| "Open a pull request" 대신 이미 PR 이 있다는 안내 | 이미 만들어진 PR 입니다. 그 PR 로 들어가 3번부터 진행 |
| PR 화면에 노란 점(진행 중)이 오래 보임 | 원래 PR 을 만들 때 새로 도는 검사는 없습니다. 몇 분이 지나도 그대로면 알려 주세요 |
| 빨간 ✗ / conflicts | 병합하지 말고 캡처해서 알려 주세요(제가 고칩니다) |
| "Squash and merge" 가 안 보이고 "Merge pull request" 만 있음 | 그대로 "Merge pull request" 를 눌러도 내용은 같습니다. 알려 주시면 설정을 확인합니다 |
| 병합했는데 사이트 배포가 빨강 | 제가 공개 정보로 먼저 확인합니다. 캡처가 있으면 같이 주세요 |

## 왜 PR 여러 개가 아니라 묶음인가

PR 여러 개를 차례로 병합하면 두 번째부터 `WORKLOG.md` 맨 위 항목이 겹쳐 "conflicts"가 생기고, 이 충돌은 비개발자가 풀기 어렵습니다(실험으로 확인). 묶음은 제가 미리 충돌을 풀고 합친 결과를 시험한 것이라 한 번의 클릭으로 끝납니다. 구성 요소 각각의 독립 검증 결과와 병합 전 확인 사항은 `WORKLOG.md` 맨 위 항목들에 있습니다.
