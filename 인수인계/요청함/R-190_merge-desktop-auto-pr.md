# [M011] 병합 부탁 — 병합 부탁 PR 자동 만들기 (데스크톱 저장소)

> **검사는 이미 끝났고 PR 도 이미 만들어져 있습니다 — Pull requests 탭에서 34번 PR 을 열어 병합하시면 됩니다.** **이 병합 부탁은 데스크톱 프로그램 저장소 `chanceblog-desktop` 것입니다**(블로그 저장소 `chanceblog` 가 아닙니다). 방금 병합해 주신 M010(블로그 저장소의 같은 워크플로)과 **같은 기능을 이 저장소에도** 넣는 묶음이고, **앱·화면·저장·서비스는 바뀌지 않습니다** — 워크플로 하나와 그 시험·문서뿐입니다. 워크플로(`.github/`)와 보안 영역에 닿아 보안 등급 T3 라 병합은 운영자 승인으로만 합니다.

## 병합할 제목 (이것 하나만)

- **제목 맨 앞이 `[M…]` 인 것만 병합하는 것입니다.** 이번 것은 `[M011]` 이고 가지 이름은 `ai/claude/M011-auto-pr-desk-1` 입니다(제목·가지 이름의 `M011` 이 위 알림의 번호와 같습니다). `M` 이 없는 제목·가지는 병합하지 않습니다.
- 병합 화면 맨 위의 저장소 이름이 **`chanceblog-desktop`** 이고 변경된 파일이 **5개**인지 봅니다(워크플로 1·시험 1·문서 3).
- 이 병합에는 앱 코드(`src/`)·`ci.yml`·`AGENTS.md`·의존성 파일·`vendor/` 변경이 **없습니다.** 다른 노란 배너(작업 중인 다른 브랜치)는 무시하셔도 됩니다.

## 이번 묶음이 하는 일 (블로그 M010 과 같은 워크플로)
1. **새 워크플로 `[공통] 병합 부탁 PR 자동 만들기`**: 제가 `ai/claude/M###-…` 병합 가지를 올리면, 그 가지의 검사(`CI — 시험` 네 칸)가 **초록으로 끝나고 main 위에 커밋이 한 개뿐일 때만** 같은 제목·본문으로 PR 을 **자동으로 만듭니다.** 그래서 앞으로는 Pull requests 탭에서 `[M###]` PR 을 열어 병합만 하시면 됩니다(지금처럼 직접 PR 을 만드셔도 됩니다 — 이미 PR 이 있으면 워크플로는 아무것도 하지 않습니다).
2. **병합은 자동화하지 않았습니다.** PR 만들기 한 가지만 하고 병합·승인·라벨·코멘트·가지 삭제·설정 변경·다른 워크플로 실행은 하지 않습니다. 권한은 읽기 둘과 PR 쓰기 하나뿐이고, 외부 액션·비밀 값이 없으며, 가지 이름·제목·본문은 안전하게 따옴표 친 값으로만 다룹니다.
3. **블로그 저장소에서의 첫 실제 실행(이미 관측)**: M010 가지를 올린 직후 새 워크플로가 2분 45초 만에 성공했고 **PR 148 을 스스로 만들었습니다**(저장소 설정은 이미 켜져 있었고, 병합 커밋의 작성자가 `github-actions[bot]` 으로 찍혔습니다). 이번 데스크톱 저장소에서는 운영자께서 PR 34 를 먼저 만드셔서 자동 생성은 관측하지 못했습니다.

## 눈에 보이는 변화
- 앱·화면은 그대로입니다. 병합 뒤부터 이 저장소의 병합 가지에 대해 **PR 이 자동으로 만들어질 수 있습니다**(작성자 `github-actions[bot]`).
- 이 저장소의 검사(`CI — 시험`)는 `push` 에서만 돌아서 봇이 만든 PR 에 '승인 대기' 줄이 생기지는 않을 것으로 봅니다(블로그에서는 PR 변경 범위 검사 한 줄이 승인 대기로 보였습니다).
- **(선택, 1분) 저장소 설정 확인**: 이 저장소의 `Settings → Actions → General → Workflow permissions` 에서 **`Allow GitHub Actions to create and approve pull requests`** 가 켜져 있어야 자동 PR 이 만들어집니다(블로그 저장소는 이미 켜져 있었습니다). 꺼져 있어도 워크플로는 경고만 남기고 성공으로 끝나므로 지금처럼 진행하면 됩니다. **켜 두시면 다음 병합 부탁부터 PR 을 직접 만드실 필요가 없어집니다.** 하지 않으셔도 이번 병합에는 영향이 없습니다.
