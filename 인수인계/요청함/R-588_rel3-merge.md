# 병합 요청 M144 — 릴리스 올리기 워크플로(앱, T3 — 운영자 전용 항목)

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M144 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다.) 이 요청은 앱 저장소 `chanceblog-desktop` 의 것이고, PR 제목 맨 앞이 `[M144]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다. 급하지 않습니다(보통). **이 변경은 GitHub Actions 워크플로 파일이라 운영자만 병합하는 항목입니다.**

## 1. 무엇을 바꾸는지
운영자께서 확인 048 ①(이슈 #289)로 승인하신 범위 — 새 워크플로 파일 하나·새 액션 하나·그 구조를 지키는 시험 — 만 들어옵니다. 앱 코드·스위치·의존성·서명 키는 0줄입니다.
- **새 워크플로 `.github/workflows/release.yml`**: 수동 실행 하나(입력칸 없음)·맨 위 권한 전부 차단·잡 둘.
  - `build`(Windows): 읽기 권한과 비밀 없음. 설치 파일·압축 파일·정보 파일을 만듭니다.
  - `sign-and-draft`(Ubuntu): 환경 `release` 의 서명 비밀 하나를 서명 단계에만 받고, 매니페스트를 만들어 서명하고 사후 점검을 거쳐 **초안** 릴리스만 만듭니다. 공개와 태그는 운영자의 'Publish release' 한 번입니다.
  - 액션은 40자리 고정 코드로 묶은 넷(새 액션 `download-artifact` 하나).
- **구조를 지키는 시험·검사기**: 워크플로 글을 구조로 읽어 규칙을 한 줄씩 지키고(권한·시크릿 자리·바깥 접속·허용 명령), 나쁜 글 수백 가지가 걸리는지 확인합니다.
- 바뀐 곳(12개 파일): 워크플로 1·시험 6(새 `test_release_workflow`·도우미와 바뀐 기존 시험)·문서 5.

## 2. 왜 필요한지
앞서 병합된 설치 파일 도구(M142)와 서명 도구(M143)를 GitHub 의 일회용 컴퓨터에서 차례로 부르는 '릴리스 올리기' 흐름이 앱 v1.0 정식 릴리스를 만드는 마지막 조각입니다. 서명 비밀을 다루는 유일한 워크플로라 구조를 시험으로 못박았고, 독립 검증을 두 번 거쳤습니다.

## 3. 사용자가 체감하는 변화
**없습니다.** 워크플로는 수동 실행뿐이라 저절로 도는 것이 없고 앱은 한 줄도 바뀌지 않았습니다.

## 4. 위험과 알려 둔 한계
- **이 병합은 아무것도 실행하지 않습니다.** 첫 실행(`Run workflow` 한 번과 환경 승인 한 번)은 운영자만 하고, AI 는 실행하지 않습니다.
- **첫 실행 전에 해 주실 일 둘**: ① 새 액션 하나의 고정 코드를 공식 태그와 대조(확인 요청 049, 약 3분) ② 환경 `release` 만들기(필수 검토자 본인 한 명·배포 가지 main 만·본인 승인 막기는 끔). 환경이 없는 채로 실행하면 GitHub 가 보호 규칙 없는 환경을 자동으로 만들어 승인 없이 서명 단계가 시작될 수 있습니다.
- 서명 키는 운영자가 오프라인에서 만들어야 하고(AI 는 키를 만들지도 다루지도 않음), 공개키를 앱에 넣는 변경이 병합되기 전의 첫 실행은 '매니페스트 만들기' 단계에서 멈추는 것이 정상입니다.
- 이 흐름이 GitHub 러너에서 끝까지 도는지는 **한 번도 확인하지 못했습니다**(첫 실행의 확인 항목은 문서 8번에 있고, 읽기 전용 한 줄 확인도 넣었습니다).
- 재확인이 짚은 시험 보강·규칙화(숫자 모양 변형·러너 항목 규칙화·`ci_shard` 가중치)는 시험 묶음 후속으로 미뤘습니다. 병합을 막는 것은 아닙니다.
- 운영자께 여쭐 것: 확인 요청 049 하나(새 액션의 고정 코드 대조).
