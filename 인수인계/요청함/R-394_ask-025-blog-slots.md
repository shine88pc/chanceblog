# 확인 요청 025 — 블로그를 어느 사이트든 더 많이 연결할 수 있게 한도를 푸는 일을 시작하시나요

> 이 글은 **질문**입니다. 이슈 양식 '[답변] AI 확인 요청에 답하기' 에 **대상번호 025**(`25` 처럼 써도 됩니다)와 고른 보기(1·2·3·4)를 적어 올려 주세요. **답이 없으면 1(그대로)** 입니다. 3 을 고르시면 바꾸고 싶은 결정 번호와 값을 같이 적어 주세요(예: `3 — 결정 8 은 ②`).

## 한눈에
- 지금은 블로그를 최대 다섯 개(네이버 2·Blogger 2·GitHub Pages 1)까지만 연결할 수 있습니다. 이슈 #207 의 "어느 사이트든" 을 이루려면 저장 형식 판 3 과 엔진 채널 변경이 필요한 대규모 T3 입니다(앞 두 묶음은 화면만 고쳤습니다).
- 추천: 블로그마다 번호표(id)를 주고 옛 다섯 열쇠는 그대로 첫 번호표로 쓰는 방식을 다섯 단계로 나눠 병합합니다. 단계 1에서 3까지는 화면·데이터가 하나도 안 바뀌고(옛 다섯 그대로·옛 형식으로만 저장), 데이터가 바뀌는 '켜는 날'(단계 4)과 일반 블로그 종류(단계 5)는 그때 따로 여쭙니다.
- 데이터가 새 형식으로 바뀌는 날은 '여섯째 이후 블로그를 처음 저장하는 순간' 뿐이고, 직전에 자동 전체 백업과 확인창이 있습니다. 그날 이후 옛 버전 앱은 "업데이트하세요" 로 멈춥니다(데이터는 안 지워지고, 되돌리려면 백업 복원과 새 블로그 자료 포기).
- 소요(추정): 단계 1에서 4까지 약 40에서 62시간, 일반 블로그 종류까지 약 46에서 72시간. 비용 0원·키·계정·네트워크 접속 없음·블로그 저장소 변경 없음.
- 정해 주실 것은 아홉 가지입니다 — 결정 1 은 '시작할지' 이고 결정 2에서 9 는 모두 추천이 기본값이라 '2' 면 추천안 일괄 승인입니다.

## 선택지 (결정 1 — 시작할지)
1. **그대로(기본)** — 아무것도 시작하지 않습니다. 한도(다섯 칸·세 종류)가 계속 남고, 이슈 #207 의 '어느 사이트든' 은 부분 충족으로 남습니다.
2. **추천안 일괄 승인** — 아래 결정 2에서 9 를 모두 추천대로 받고 **단계 1에서 3까지만** 시작합니다. 단계마다 구현·시험·독립 검증·병합 부탁(병합은 운영자)을 합니다.
3. **일부만 승인** — 바꾸실 결정 번호와 값을 적어 주세요. 적지 않은 번호는 추천을 따릅니다.
4. **보류** — 지금은 정하지 않습니다(1 과 같이 두되 다시 묻지 않고 기다립니다).

## 정해 주실 아홉 가지 (추천 = 기본값)
| 번호 | 무엇을 | 추천 | 다른 선택지 |
|---|---|---|---|
| 1 | 한도를 어떻게 풀까 | 블로그 목록 방식을 단계적으로 | 그대로 / 고정 슬롯 늘리기(네이버 5·Blogger 3·GitHub 2 — 같은 판 올림이 필요한데 한도가 남아 비추천) |

## 추천 이유 (짧게)
- 한도를 푸는 비용의 큰 부분(저장 형식 판 3·글 보관함 원고 모델 완화·엔진 보관함 판·엔진 표 정리)이 '조금 늘리기' 와 같고, 그러면서 한도가 남습니다. 목록 방식만 '어느 사이트든' 으로 가는 길입니다.
- 단계 1에서 3까지는 사용자 데이터를 한 바이트도 안 바꾸고(상한 다섯·옛 형식으로만 저장) 시험으로 못박은 뒤에 '켜는 날' 을 따로 여쭙니다 — 틀리면 PR 되돌리기만으로 원래대로입니다.
- 데이터가 바뀌는 순간을 '여섯째 이후 블로그를 처음 저장할 때' 로 미뤄서, 새 블로그를 안 만드는 동안은 옛 버전 앱으로 돌아가도 아무 일이 없습니다.

## 허락하시면 하는 일과 열어 주지 않는 일
- **하는 일(단계 1에서 3)**: 앱 저장소(`shine88pc/chanceblog-desktop`)의 코드·시험·문서 변경, 단계마다 독립 검증 보고서(안전·자료 손실·기존 자료 호환 관점 / 요구·화면·시험 품질 관점), 병합 부탁(앱 자동 검사가 끝난 뒤 한 번에 하나, 병합은 운영자). 데이터·화면 변화는 없습니다.
- **열어 주지 않는 일**: 상한을 풀거나 판 3 으로 실제 저장하는 '켜는 날'(단계 4 — 별도 요청), 일반 블로그 종류(단계 5 — 별도 요청), 블로그 저장소의 파이프라인·레지스트리·워크플로 변경, 외부 접속·설치·내려받기·비용, 키·계정, main 직접 push, 운영자 PC 데이터의 사용(이관 리허설은 운영자가 복사본을 주실 때만).

## 멈추고 다시 여쭙는 조건
- 단계 1 의 '옛 다섯 열쇠 결과가 바이트까지 같음' 시험이 하나라도 달라질 때.
- 단계 2 의 '새 블로그가 없으면 저장 파일이 지금과 바이트까지 같음' 이 깨지거나, 옛 앱 호환 시험에서 "업데이트하세요" 대신 "깨졌다" 안내가 나올 때.
- 단계 3 에서 홈·서랍 지문 시험에 의도하지 않은 변화가 생길 때.
- 실제 데이터를 판 3 으로 쓰게 되는 코드 길이 단계 4 이전에 열려 있다는 것이 발견될 때.
- 독립 검증이 '필수' 지적(병합 전에 반드시 고칠 것)을 남기고 한 번의 수정으로 풀리지 않을 때.
- 정책 충돌(로그인·쿠키·자동 발행 금지 규칙 6, 티스토리 제외·격리 D-01 의 문구)이 보일 때.
- 추정 시간의 두 배를 넘길 때(보고하고 범위를 다시 정합니다).

## 알려 드릴 위험과 못 정한 것 (숨기지 않습니다)
- **옛 Package 로 돌아갈 때**: 켜는 날 이후에는 옛 버전 앱이 새 형식을 못 읽고 "업데이트하세요" 로 멈춥니다(채널 프로필·씨앗·캘린더·엔진 보관함·원고·초안의 읽기 코드는 직접 돌려 확인했고, 옛 앱 화면에 보이는 실제 문장은 코드와 안내 표로만 확인). 데이터는 지워지지 않지만 일부 화면이 막히고, 되돌리려면 자동 백업을 복원하고 새 블로그 자료를 포기해야 합니다. 캘린더·원고·저장한 초안은 안내가 덜 친절하거나 그 줄 하나만 '깨졌다' 로 보입니다.
- **Blogger·GitHub Pages 를 늘려도 앱이 해 주는 일은 적습니다**: 이 빌드는 외부 쓰기가 모두 꺼져 있어 지금 실제로 되는 발행은 네이버의 복사해서 붙여 넣기뿐입니다. 그래서 일반 블로그를 제안했습니다.
- **새 블로그는 읽을 이력이 없습니다**(이력 원천이 옛 다섯에만 있음) — 중복 검사가 약해집니다. **말씨 풀이 둘뿐**이라 셋째 이상 네이버 블로그는 둘 중 하나를 되풀이합니다(추측: 초안이 비슷해짐).
- **정책 확인이 필요합니다**: 일반 블로그가 티스토리 주소를 받아들이면 'D-01 티스토리 제외·격리' 의 문구와 걸립니다(사이트별 기능을 안 만들면 취지와는 맞다고 보지만 운영자 결정 사항입니다). 초안·후보 생성은 지금 '첫 제품은 네이버 A·B'(2026-11-06 확정 답변 9절)로 한정돼 있어 일반 블로그에 열려면 범위를 넓혀야 합니다.
- **추정은 약합니다**: 시간·파일 수는 앞 두 묶음(M079·M080)에서 비례해 잡은 것이고, 운영자 PC 의 실제 데이터 모양과 화면 동작은 못 봤습니다(단계 2 의 이관 리허설을 운영자가 복사본을 주실 때 합니다).
- 이슈 #207 원문은 네트워크 접속이 금지돼 못 읽었고 검증 보고서와 결정 기록의 요약에 기댔습니다.
