## 1. 무엇을 바꾸는지 — 운영자님이 승인하신 변경(확인 039 ①, 이슈 #266)
검사(guardrails)의 한 칸은 10분 안에 끝나야 하는데, 같은 코드가 러너에 따라 3.10 칸 단위 테스트 304–575초로 흔들려(어제 제한에 걸려 취소된 검사 세 건) 시험을 **하나도 지우거나 건너뛰지 않고** 시간을 줄이는 변경입니다.
① **워크플로 한 줄**: `.github/workflows/guardrails.yml` 단위 테스트 단계의 `run:` 한 줄만 `python -m unittest discover -s tests -v` → `python scripts/run_unit_parallel.py --weights tests/unit_test_weights.json`. 권한·시크릿·트리거·`timeout-minutes`·`concurrency`·칸 이름·다른 단계는 그대로입니다.
② **새 파일 셋**: 실행기 `scripts/run_unit_parallel.py`(표준 라이브러리만·셸 없음·저장소 쓰기 없음)·모듈별 예상 초 표 `tests/unit_test_weights.json`·실행기 시험 `tests/test_run_unit_parallel.py`(108개). 실행기는 처음에 모든 시험 이름을 모아 두었다가 실제로 돈 시험과 정확히 견주어 **하나라도 빠지면 전부 통과했어도 빨강**으로 끝납니다(자식이 `os._exit(0)` 로 조용히 끝나는 경우처럼 옛 직렬 흐름은 초록이던 곳도 빨강).
③ **기존 시험 둘**: `tests/test_guardrails_precheck.py`(단위 테스트 줄 단언을 새 줄로·두 파일 존재 단언 추가)·`tests/test_publish_paths.py`(쓰기 길 허용 목록에 실행기 한 항목 — **허용 목록을 넓히는 변경**입니다).

## 2. 사용자가 체감하는 변화
블로그 글·발행·알림은 **그대로**입니다. 달라지는 것은 검사 시간뿐입니다 — 시제품을 진짜 GitHub 러너에서 5번 돌린 단위 테스트 단계는 3.10 칸 126–256초·3.12 칸 124–235초였고(같은 날 직렬은 변경 없는 가지 기준 3.10 칸 304–527초·3.12 칸 253–511초, 어제 병합 뒤 main 검사도 3.10 칸 340–398초·3.12 칸 270–471초), **이 PR 자신의 검사가 최종 실행기의 첫 진짜 실행**입니다: 단위 테스트 단계가 3.10 칸 127초·3.12 칸 110초(칸 전체 146초·127초, 검사 전체 2분 28초 — 직렬일 때는 8–10분)로 끝나 둘 다 초록이었고 시험 id 대조도 통과했습니다.

## 3. 위험과 알려 둔 한계
- **실행기는 새 필수 부품**입니다. 버그가 있으면 검사 전체가 빨개집니다(안전한 방향) — 실행기 시험 108개와 변이 86개(모두 시험이 잡음)로 지켰습니다.
- **알려진 차이 둘(거짓 경보 쪽)**: `setUpClass`/`setUpModule` 에서 건너뜀을 던지는 시험 클래스와, 줄바꿈 없는 글이 시험 줄 앞에 붙는 경우는 옛 직렬 흐름은 초록이고 실행기는 빨강입니다. 오늘 저장소에는 둘 다 없고 문제 글이 이유를 말합니다(설계 글에 기록).
- **실행기 자체의 시간 제한은 없습니다**: 칸 제한(10분)에 걸리면 지금처럼 GitHub 가 '취소' 로 끝내 알림이 조용합니다. 병렬로 칸이 절반 안팎으로 줄어 여유가 생기지만 제한 자체는 그대로이고, 자체 마감을 넣는 일은 후속 작은 변경 후보입니다.
- 묶음 출력은 그 묶음이 끝난 뒤 번호 순서로 나오므로 로그는 **묶음 단위**입니다(맨 끝 요약과 실패 목록에서 찾습니다). 새 시험 일부(진짜 파이프·손자 프로세스·신호를 쓰는 것)는 리눅스에서 이 PR 의 검사가 처음 돌립니다. 시간을 재는 시험 24개 모듈이 병렬에서 흔들리는지는 첫 검사들에서 지켜보겠습니다.
- 가중치 표는 이 PC 에서 잰 값을 맞춘 어림이라 병합 뒤 진짜 CI 로그의 모듈별 시간으로 다시 갱신합니다(작은 후속). CPU 4개 러너를 가정하며 러너 CPU 가 줄면 병렬 수가 자동으로 줄어 이득도 줄어듭니다.
