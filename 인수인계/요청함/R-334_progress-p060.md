## 접수한 내용 (제가 이해한 정책 — 틀린 곳이 있으면 알려 주세요)
1. **방식**: AI 가 알아서 병합하는 것이 아닙니다. AI 가 변경을 쉬운 말로 설명하고(무엇을 바꾸나·왜 필요한가·사용할 때 달라지는 점·기존 기능 영향과 위험·검사와 독립 검증 결과·되돌리는 방법) 운영자가 **병합 번호를 적어 `M075 승인`** 처럼 답하면 AI 가 **그 PR 한 건**만 병합합니다.
2. **승인 문구**: '확인했습니다'·'진행하세요'·'좋아 보입니다'·'기본값대로'·'다음 단계 진행'은 승인이 아닙니다. 승인은 그 PR 한 건에만 유효하고, 승인 뒤 커밋이 늘거나 변경 범위가 달라지면 무효 — 새 설명과 새 승인이 필요합니다.
3. **병합 직전 재확인 8가지**: 승인 번호와 PR 일치 · 승인 뒤 커밋 없음 · 검사 전체 통과 · 독립 검증 통과 · 충돌 없음 · 변경 범위가 설명과 일치 · 비밀 정보 노출 없음 · 되돌리는 방법 확인.
4. **범위**: 일반 코드·일반 UI·시험·문서·로컬 저장·조회·오류 수정·접근성·성능 개선은 AI 병합 가능. **승인하셔도 운영자 직접 병합**: GitHub Actions 워크플로 · 광고·AdSense·ads.txt · 공개 게시물과 고정 페이지 · PIPELINE_PAUSE · 발행 모드와 재개 · Provider 활성화 · 키·시크릿·자격 증명 · 의존성 추가 · 데이터 삭제·마이그레이션 · 자동 게시 활성화 · 외부 비용이 드는 기능 · main 보호 설정.
5. **방식 제한**: 운영자 PC 의 Git 자격 증명으로 main 에 직접 push 하는 것은 금지. 흐름은 'AI 가 PR 작성 → 검사·독립 검증 → 쉬운 병합 설명 발송 → 운영자가 번호 명시 승인 → AI 가 승인된 PR 병합 → main 사후 검사 → 병합 완료 알림'. 사후 검사에 문제가 나오면 추가 변경을 자동 병합하지 않고 되돌리기 요청과 쉬운 원인 설명을 먼저 보냅니다. 완료 알림에는 병합 번호·PR 번호·병합된 커밋·실제 반영된 변화·main 검사 결과·이상 유무·원복 커밋 또는 방법을 넣습니다.
6. **순서**: 정책 문서화·시험 먼저 → 켜는 변경은 **별도 병합 요청, 운영자가 직접 병합** → 첫 운영은 일반 코드·문서 PR 3건 → 3건이 모두 조건(승인받은 PR 만 병합·승인 후 변경 없음·main 검사 전체 통과·원복 0건·오병합 0건·운영자 전용 경로 변경 0건)을 지키면 계속, **한 건이라도 문제면 AI 병합을 즉시 중지하고 운영자 직접 병합으로 복귀**.
