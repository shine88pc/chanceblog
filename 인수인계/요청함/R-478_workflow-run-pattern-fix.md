# 병합 요청 M112 — 알림 워크플로 둘의 시작 실패 수정 (T3)

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M112 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다.) 이 요청은 블로그 저장소 `chanceblog` 의 것이고, PR 제목 맨 앞이 `[M112]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다. 급하지는 않지만 병합 전까지 워크플로가 끝날 때마다 빨간 실행이 계속 쌓입니다(보통).

## 1. 무엇을 바꾸는지
**T3 — `.github/workflows/` 두 파일(`merge-ready-notice.yml`·`merge-confirm-notice.yml`)의 트리거 한 줄(+설명 주석 두 줄)씩**입니다. 확인 031(보기 2)로 승인하신 두 워크플로의 정정이며 권한·시크릿·외부 액션·job 구조·`branches` 필터·켬 상태 파일(`off`)은 그대로입니다.
① **무슨 일이었나**: [M108](11-23 22:11)로 병합한 두 알림 워크플로가 GitHub 에서 **시작 단계에서 거절**돼(`startup_failure`) 병합 뒤 워크플로가 끝날 때마다 빨간 실행이 쌓였습니다(블로그 Actions 의 같은 워크플로 실행 16건). 알림이 꺼진 채라 기능 손실은 없지만 실패 알림 메일이 올 수 있습니다.
② **원인**: 트리거의 `workflows` 칸에 워크플로 이름을 그대로(`[공통] …`) 적었는데 GitHub 는 이 칸을 **이름이 아니라 필터 패턴**으로 읽고 대괄호에는 영문·숫자만 허용합니다. 우리 시험은 이름 글자만 대조해 놓쳤습니다.
③ **고침**: `*병합 부탁 PR 자동 만들기`·`*저장소 규칙·테스트 자동 검사`(`*` 앞붙이 — 문서에 있는 문법)로 바꿨습니다. 검증기에 '항목 모양 검사(대괄호 등 금지)'와 '이 패턴이 저장소 안에서 의도한 워크플로 하나에만 맞는지' 검사를 더하고 시험·문서·결함 기록(D-428)을 맞췄습니다.
④ **미리 확인한 것**: 앱 저장소의 임시 가지(삭제함)에서 같은 필터 문법을 두 번 시험했습니다 — 대괄호 원형은 실패, `*` 앞붙이는 대괄호·공백·한글·가운뎃점이 든 이름에 **실제로 맞았습니다**.

## 2. 왜 필요한지
빨간 실행(실패 알림 메일 가능성)을 멈추고, 알림 자동화를 나중에 켤 수 있는 상태로 만드는 정정입니다. 켜기는 별도 번호 요청입니다.

## 3. 사용자가 체감하는 변화
**지금은 없습니다**(알림은 꺼진 채). 병합하면 워크플로가 끝날 때마다 쌓이던 빨간 실행이 멈추는 것이 달라집니다.

## 4. 위험과 기존 기능에 미치는 영향
- **기존 기능**: 광고 표면·레지스트리·시크릿·권한·켬 상태·의존성은 바뀌지 않았습니다. 검증기 출력은 시작점과 같습니다(오류 0·경고 3). 시크릿을 쥔 job 을 낯선 쪽에 열지 않았습니다 — 판정 코드가 트리거 워크플로의 이름·경로를 읽지 않고 GitHub 에서 다시 읽은 상태만 보며, 이름이 겹치는 워크플로가 새로 생기면 검증기가 오류로 막습니다(독립 검증이 확인).
- **알려 둔 한계**: `workflow_run` 트리거는 기본 가지의 파일만 평가돼 **병합 전에는 직접 시험할 수 없습니다** — 앞 시험은 같은 문법을 쓰는 다른 필터로 한 것입니다. 병합 직후 main 검사가 끝나면 제가 직접 확인합니다(빨간 실행이 사라지고 알림 판정이 `off` 로 곧바로 끝나는지). 패턴이 안 맞으면 알림 워크플로가 깨어나지 않을 뿐이라(꺼진 상태) 영향은 없습니다.
- **운영자께 여쭐 것(이번 병합과 별개)**: 병합 부탁 알림이 나가기 전에 PR 을 병합하시는 경우가 늘었습니다(문제 없음 — 병합 결과는 제가 확인해 알립니다). `.github` 변경(T3)은 이 PR 처럼 알림에 'T3' 를 적어 두겠습니다.
