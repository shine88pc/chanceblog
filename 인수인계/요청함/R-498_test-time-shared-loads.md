# 병합 요청 M118 — 검사(CI) 시험 시간 줄이기 (T1, 시험 코드만)

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M118 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다.) 이 요청은 블로그 저장소 `chanceblog` 의 것이고, PR 제목 맨 앞이 `[M118]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다. 급하지 않습니다(보통).

## 1. 무엇을 바꾸는지
검사(CI)의 파이썬 단위 테스트가 job 제한(10분)에 늘 아슬아슬했습니다(진짜 CI 3.10 칸 시험 본문 약 556초, [M114] 첫 검사는 제한에 걸려 취소됐습니다). **시험을 지우거나 건너뛰지 않고, 같은 입력의 같은 계산을 시험마다 되풀이하던 여섯 곳을 한 번만** 하게 했습니다 — ① 진짜 저장소에 검증기 전체를 돌리는 시험 넷(각 약 7초) ② AI 흐름 스캐너 시험(호출 풀이·같은 소스 분석 반복·구문 트리 보관) ③ 변이 목록 시험의 YAML 다시 쓰기(1,566번 가운데 서로 다른 구조는 519개) ④ Blogger 워크플로 파일 반복 읽기 ⑤ 같은 시드의 가상 글 반복 조립.
시험 id 는 10,463개 → 10,491개(**사라지거나 이름이 바뀐 id 0**, 더해진 28개는 새 도우미 시험)이고 단언·무작위 표본 수·시드·허용 범위는 그대로입니다. 문서는 `docs/ENGINEERING_GUIDE.md` 시험 작성 규칙 7번 한 문단과 결함 D-446 한 행입니다.
**제품 코드·검증기·워크플로·시크릿·광고 표면·레지스트리 값·의존성은 바꾸지 않았습니다**(`tests/` 와 문서 둘만).

## 2. 사용자가 체감하는 변화
**없습니다**(시험 코드만). 병합 뒤 검사(CI) 시간이 진짜 CI 3.10 칸에서 약 47초(8–9%) 줄 것으로 추정합니다(같은 코드도 러너에 따라 최대 1.9배 흔들려 정확한 값은 병합 뒤 측정합니다).

## 3. 위험과 알려 둔 한계
- **나눠 쓰는 값이 시험 사이로 새거나 낡은 값을 주는 위험**: 열쇠는 입력 내용 전체(진짜 저장소 검증기 결과는 파일 내용 해시)이고 받는 쪽이 고쳐도 새지 않게 복사본을 돌려주며, 임시 사본·변이 사본에는 쓰지 않습니다. 독립 확인이 나눠 쓴 값이 새로 계산한 값과 같고 단독·역순·섞은 순서에서도 같음을 직접 확인했습니다.
- **목표(25%)에는 못 미칩니다**(약 8–9%). 남은 시간의 대부분은 제품 코드가 바닥이라 시험 쪽에서 줄일 수 없습니다(퍼징·Fact 검토·조립 시험이 `fact_topics.blocked_in` 을 수십만 번 부름). 제품 쪽 메모(T2)와 job 나누기·병렬 시험 실행기(T3, 진짜 CI 3.10 칸 256초·3.12 칸 235초로 직렬 300–575초보다 짧음)는 이 병합이 아니라 검사 속도 보고서와 함께 별도 변경안으로 올립니다.
- 새 모듈 `test_shared_loads` 는 PyYAML 이 없는 환경에서만 건너뜁니다(검사에는 PyYAML 이 항상 있어 실행됩니다).

## 4. 시험·독립 검증 결과
- 독립 확인 둘(구현자와 다른 AI): 안전 **pass(필수 0·권고 4·참고 7)** — 지워진 시험 정의 0·삭제된 39줄은 모두 같은 단언을 나눠 쓰는 값으로 부르기, 시험 **pass(필수 0·권고 3·참고 6)** — 시험 id 목록 비교·구현자가 못 돌린 변이 다섯을 기준 사본과 머리 양쪽에 넣어 같은 시험이 빨개짐. 권고(열쇠를 내용 해시로·분석 열쇠 단언·메모 전수 대조·변이 목록 전수 비교 등)는 같은 날 반영했고, 반영분(7개 파일)은 제가 직접 읽어 약해진 곳이 없음을 확인했습니다.
- 합친 나무(제가 새 main 위에서 다시 돌림): 바뀐 시험 모듈 열둘의 시험 278개가 파이썬 3.12(PyYAML 있음)·3.10 에서 모두 통과, PyYAML 없는 3.12 에서는 153개 중 79개 통과·74개 건너뜀(기존 68 + 새 모듈 6)·실패 0, 접속 시도 0건, 검증기 오류 0·경고 3(시작점과 같음).
- 검사(CI): 블로그 검사 초록(파이썬 3.10·3.12 두 칸 모두).
