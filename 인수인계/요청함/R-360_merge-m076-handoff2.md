# 병합 요청 M076 — AI 작업 도구와 새 PC 시작 안내의 정본을 저장소로 옮깁니다

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M076 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다 — 켜지는 변경이 운영자 병합으로 들어온 뒤에만.) 이 요청은 블로그 저장소 `chanceblog` 의 것이고, PR 제목 맨 앞이 `[M076]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다.
>
> **급하지 않습니다.** 이 PC 에서는 작업 폴더의 도구를 계속 쓰고 있어 병합이 늦어져도 하는 일에는 지장이 없습니다. 지금 우선인 일은 앱의 래퍼런스 보관함(이슈 #205)입니다.

## 1. 무엇을 바꾸는지
지금까지 이 PC(작업 폴더)에만 있던 AI 작업 도구 — 요청 파일 만들기·병합 부탁 만들기·병합완료 확인·병합 가지 만들기·검사 읽기·감시기·정기 현황 크론 지시문(v3)·양식 둘 — 를 저장소의 `인수인계/도구/work/` 로 옮겨 **정본**으로 삼습니다. 새 PC 에서 처음 시작하는 순서(`setup_workspace.py` 와 도구 README 의 '새 PC 에서 처음 시작하기' 절)와, 그 도구들이 제대로 도는지 지키는 새 자동 시험 파일 `tests/test_handoff_tools.py`(156개)를 더합니다. 또 '도구는 저장소 사본이 최신이 아니고 이 PC 에만 있다'고 적힌 낡은 문장을 사실대로 고칩니다(작업내용·SESSION_START·요청함 README·AGENT_RUNBOOK).

## 2. 왜 필요한지
11-15 새 PC 로 옮길 때 도구 사본이 최신이 아니어서 일부를 처음부터 다시 만들어야 했습니다(새 세션 모의 시험이 '일부만 가능'으로 나온 원인 중 하나). 앞으로 PC 나 세션이 바뀌어도 저장소만으로 같은 도구를 받아 같은 방식으로 이어 가려는 것입니다.

## 3. 사용자가 체감하는 변화
사용하는 분이 느끼는 변화는 없습니다. 블로그 글 발행·앱·Actions 동작은 그대로이고, 이 도구들은 사람이나 AI 세션이 직접 실행하며 저장소의 자동 실행(워크플로·예약)이 부르지 않습니다.

## 4. 위험과 기존 기능에 미치는 영향
- **기존 기능**: 영향이 없습니다. 새 파일 18개(도구·양식·시험)가 더해지고, 기존 파일 16개가 바뀝니다 — 도구 사본 다섯 곳(`make_request.py`·`notice_tools.py`·`wait_ci.py`·`watch_desktop.py`·`watch_light.py`)은 이 PC 에서 이미 쓰던 최신 판으로, 작업 폴더 만들기 도구(`setup_workspace.py`)는 아래 ④ 로, 그 README 는 새 PC 시작 절 추가로, 정기 현황 알림 문서 둘(본보기·옛 프롬프트)은 '옛 판이며 현행은 v3' 안내 한 줄 추가로 바뀌고, 상태 문서 넷과 `WORKLOG.md` 는 문장만 바뀝니다. 글 발행 흐름(`pipeline/`)에서 바뀌는 파일은 `pipeline/egress.py` 하나뿐이고 그 안에서도 외부 접속 목록(장부)과 이유 문장뿐입니다.
- **솔직하게 알려 드릴 점 ① — 새 외부 접속 등록 13건**: 저장소에는 '외부로 나가는 접속 지점을 모두 목록(`pipeline/egress.py`)에 올려야 한다'는 시험이 있습니다. 새 도구가 GitHub 의 공개 주소를 읽거나 `git ls-remote` 를 부르는 곳이 13곳(도구 11개)이라 목록에 올렸고(등록 62→75·호출 지점 72→85곳·37→48개 파일), 모두 '사람이나 AI 세션이 직접 실행하는 도구, 저장소의 워크플로·예약이 부르지 않음'으로 적었습니다. 이 등록은 단순한 시험 숫자 맞춤이 아니라 **새 외부 접속을 목록에 올리는 일**이어서 숨기지 않고 알립니다. 이 한 파일만 되돌릴 수는 없고(도구·시험·숫자 줄이 함께 묶여 있음) 반대하시면 이 병합 전체를 되돌려야 합니다. 글 발행 흐름은 이 도구를 부르지 않아 발행에는 영향이 없습니다. `docs/SOURCE_POLICY.md` 는 같은 숫자 한 줄만 고쳤습니다.
- **① 에 딸린 기존 장부 두 줄의 문구 변경**: 새 등록이 아니라 **이미 있던 설명을 사실대로 고친 것**입니다 — 공통 설명 `_G_TOOL` 은 '사람이 실행하는 도구'에서 '사람이나 AI 세션이 직접 실행하는 도구(저장소의 워크플로·예약이 부르지 않는다 — AI 세션 안의 크론 프롬프트는 일부를 부른다)'로, `wait_ci.py` 항목은 '자기 저장소'에서 '저장소는 첫 인자로 주며 보통 자기 저장소 — 인자로 준 다른 공개 저장소도 읽는다'로 바뀝니다(접속 범위는 그대로이고, 옛 문구가 실제보다 좁게 적혀 있던 것을 고침).
- **② 검사 관문 면제 한 곳**: 병합 부탁 도구는 '그 가지의 자동 검사가 초록'일 때만 요청 파일을 만듭니다. 자동 검사가 없는 루트 홈 저장소(`shine88pc.github.io`) 한 곳만 이 관문에서 면제되고, 그 저장소는 검사 실행 목록이 없거나 읽기가 실패해도 통과합니다(증거는 요청 본문에 사람이 적습니다 — 안전 장치를 푸는 성격이라 알립니다). 블로그·앱 저장소는 면제되지 않는다는 것을 새 시험이 지킵니다.
- **③ 병합 후보 판정 도구**: `merge_guard.py` 는 병합 가지가 'AI 병합 후보 등급'인지 **판정만** 하는 검사 전용 도구입니다(쓰기·푸시 없음). AI 병합은 꺼져 있고 이 도구를 근거로 병합하지 않습니다. 이 도구가 보호 경로 8곳(`privacy.md`·`categories.md`·`robots.txt`·`posts.json`·`pipeline/ai_processor_policy.json`·`pipeline/ops_inbox_policy.json`·`pipeline/egress.py`·`scripts/validate_repo.py`)을 아직 C 등급으로 보지 않는 한계가 있어, AI 병합을 켜는 변경 전에 정책 문서와 맞추겠습니다(새 시험이 이 한계를 못박고 있어 목록이 바뀌면 시험이 알려 줍니다).
- **④ 작업 폴더 만들기 도구의 위험을 고쳤습니다**: 독립 검증자가 '이미 만든 작업 폴더에서 다시 돌리면 푸시 전에 쌓아 둔 요청 파일·커밋이 사라질 수 있다'는 문제를 찾았고, 이미 있으면 가지를 바꾸지 않도록 고친 뒤 실제 git 저장소 시험으로 못박았습니다.
- **⑤ 남은 한계**: 도구가 실제 GitHub 로 clone·push·알림을 보내는 길은 이 환경에서 직접 돌려 보지 않았고 로컬 임시 저장소 시험으로 확인했습니다. 기존 장부 항목 다섯 개(`runs_by_sha`·`run_annotations`·`run_steps_times`·`wait_ci_multi`·`ci_web`)의 이유 글이 아직 '자기 저장소'로 적혀 있고 `egress.py` 안의 옛 주석 한 줄도 그대로입니다 — main 에 있던 줄이라 이번엔 건드리지 않았고 다음 정비에서 고칩니다.
