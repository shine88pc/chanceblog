# 확인 요청 003 — AI 가 직접 병합할 수 있는지 (이슈 #144 의 답)

운영자가 이슈 #144 로 "직접 병합까지 가능한지 한번 더 확인해줘"(진행 범위: 논의·준비까지만)라고 하셔서, 오늘 20시대에 **읽기만 하는 방식**으로 다시 확인했습니다. 아무것도 병합하거나 바꾸지 않았습니다.

## 점검 결과 — 지금 AI 는 직접 병합할 수 없습니다
| 길 | 결과 |
|---|---|
| 내장 브라우저로 GitHub 열어 병합 단추 누르기 | **막힘** — 조직 정책으로 github.com 이 열리지 않습니다 |
| 운영자의 크롬(연결돼 있음)으로 GitHub 열기 | **막힘** — 같은 조직 정책으로 github.com 이 열리지 않습니다 |
| GitHub 명령줄(gh)로 병합 | **안 됨** — 이 PC 에 설치돼 있지 않고, 설치해도 로그인(운영자만 가능)이 필요합니다 |
| API 로 병합 | **안 됨** — AI 에게는 병합 권한이 있는 토큰이 없습니다(가지를 올리는 인증만 있고, 키·토큰을 AI 가 입력하거나 꺼내 쓰지 않는 것이 보안 규칙입니다) |
| `git push` 로 main 에 직접 올리기 | **기술적으로는 가능해 보임**(두 저장소 모두 main 보호 설정이 꺼져 있음) — 그러나 하지 않습니다: PR 기록(제목·검사·번호)이 남지 않고, 블로그 main 은 봇이 계속 올려 충돌 위험이 있고, 예전 main 직접 수정 사고(복구 요청 R-043)가 있었고, 운영자 승인 없는 main 변경은 규칙에 어긋납니다 |

## 병합 단추 누르는 일을 줄이는 방법 (고르실 것)
1. **지금처럼** — AI 가 가지·검사·요청까지 하고 운영자가 폰에서 PR 만들기 → 병합(2~3번 누름). 변경 없음.
2. **PR 만들기만 자동화** — AI 가 병합 가지를 올리면 저장소 자동화가 PR 을 대신 만들어 둡니다. 운영자는 **병합 한 번**만 누릅니다. 병합이 아니라 PR 만드는 일이라 위험이 낮습니다. 필요: 새 워크플로(병합 부탁 1건)와 저장소 설정 한 줄(운영자가 켜야 함).
3. **폰 승인 한 번으로 자동 병합** — 운영자가 병합 부탁에 '병합해 주세요'라고 승인하면 저장소 자동화가 조건을 모두 확인한 뒤 병합합니다(소유자 본인 확인·검사 초록·제목 `[M###]` 와 가지 이름 일치·변경 파일 수 일치·한 커밋·광고 표면·시크릿·워크플로 변경이 든 PR 제외). 운영자는 GitHub 에서 PR 을 만들거나 병합할 필요가 없어집니다. **보안이 걸린 변경(T3)** 이라 독립 검증과 별도 병합 부탁이 필요하고, 승인 신호가 소유자만 보낼 수 있고 정확한 커밋에 묶이도록 설계해야 합니다.
4. **더 알아본 뒤 다시 묻기**.

AI 의 권장: **2번을 먼저**(위험 낮음), 그 뒤 쓰시면서 3번이 필요하면 따로 설계해 독립 검증을 거칩니다. 2·3번을 고르셔도 **이번에는 준비(설계·초안)까지만** 하고, 켜는 것은 병합 부탁으로 따로 드립니다. 어떤 방법이든 '병합해도 된다'는 최종 결정은 운영자께 있습니다.

## 답하는 법 (바꾸고 싶을 때만, 1분)
GitHub **Issues → New issue → `AI 확인 요청에 답하기(대상번호)`** 에서 **대상번호 `003`**, **선택**에서 원하는 번호(①~④)를 고르고 내용은 비워도 됩니다. 답이 없으면 1번(지금처럼)으로 진행합니다.
