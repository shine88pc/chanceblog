# 병합 요청 M115 — 운영자 답 이슈 수정 알림·범위 검사 입력 형식 검사 (T3)

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M115 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다.) 이 요청은 블로그 저장소 `chanceblog` 의 것이고, PR 제목 맨 앞이 `[M115]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다. 급하지 않습니다(보통).

## 1. 무엇을 바꾸는지
**T3 — `.github/workflows/` 두 파일(`operator-reply.yml`·`pr-scope-check.yml`)을 바꿉니다.** 확인 032 ①(이슈 #254)로 승인하신 일곱 건 중 **7번과 8번**입니다.
① **답 이슈 수정 알림(7번)**: 접수 워크플로의 `issues` 트리거에 `edited` 를 더했습니다(`opened` 그대로 + `edited`). 소유자가 연 `[답변]` 이슈를 접수 뒤에 고치면 폰에 '⚠️ 답변이 고쳐졌습니다(이슈 번호)' 알림 **한 통**이 갑니다 — 이슈 번호와 고정 문장뿐이고 본문·제목은 싣지 않습니다. **이 알림은 승인이 아닙니다**(AI 는 접수 코멘트가 되풀이한 값과 지금 본문이 같을 때만 승인으로 읽습니다). GitHub 에는 읽기도 쓰기도 없고, 같은 글로 다시 저장한 편집은 알리지 않습니다. 소유자가 연 이슈가 아니면 알리지 않습니다(접수와 같은 판정).
② **범위 검사 입력 형식(8번)**: `pr-scope-check.yml` 의 수동 입력 `pr_number` 를 **첫 단계**에서 `^[1-9][0-9]{0,8}$` 로 검사합니다(`issue-edit.yml` 과 같은 식 — 맞지 않으면 그 단계에서 실패하고 이후 단계는 돌지 않습니다). 자동 실행(PR 이벤트)의 번호는 늘 통과합니다.
③ 접수 코드·검증기(WF-14 가 `opened`·`edited` 두 종류만 허용)·시험 69개·문서 열한 개의 한계 문장 정정·결함 D-437·D-438.
**권한·시크릿·다른 트리거·광고·레지스트리 값·발행 정지는 바꾸지 않았습니다.**

## 2. 왜 필요한지
접수 뒤에 답변 본문이 고쳐져도(예: `선택 안 함` → 승인 보기) 운영자가 알아챌 길이 없었습니다. AI 의 승인 판독은 이미 막혀 있었지만(접수 대조), 이 알림이 운영자 쪽 눈을 더합니다. 입력 형식 검사는 같은 종류의 다른 워크플로가 하는 일을 이것만 안 하던 틈입니다.

## 3. 사용자가 체감하는 변화
**답변 이슈를 접수 뒤에 고치실 때만** 폰에 알림 한 통이 더 옵니다(평소엔 없음). 짧은 간격으로 여러 번 고치면 최대 두 통, 시간을 두고 고치면 그때마다 한 통입니다. 그 밖은 그대로입니다.

## 4. 위험과 기존 기능에 미치는 영향
- **기존 기능**: 광고 표면·`ads.txt`·시크릿·권한·의존성·레지스트리 값은 바뀌지 않았습니다. 검증기 출력은 시작점과 같습니다(오류 0·경고 3). 접수(`opened`) 경로는 시작점 코드와 한 줄도 다르지 않다고 독립 검증이 5가지 이벤트로 확인했습니다.
- **알려 둔 한계 — GitHub 실제 동작을 한 번도 못 봤습니다**(가짜 이벤트·가짜 서버로만 시험): 병합 뒤 첫 관측 네 가지를 결함 대장에 남겼습니다 — ① `edited` 로 시작 실패가 나지 않는지 ② 이슈 양식으로 새 이슈를 올릴 때 `edited` 실행이 따로 생기지 않는지(생기면 올릴 때마다 가짜 알림 한 통) ③ 실제 `changes` 모양 ④ 짧은 간격으로 두 번 고쳤을 때 접수 실행이 취소되지 않는지. 병합 뒤 제가 실행 목록으로 확인하고, 이상이 있으면 알립니다.
- **알려 둔 한계 — 이 PC 에서 못 돌린 것**: `actionlint`(검사 서버가 돌립니다)·리눅스 bash 로 입력 값 표 돌리기(검사 서버가 돌립니다).
- **이론상의 틈 하나(안전 쪽 실패)**: 이벤트 도착 순서가 뒤바뀌는 드문 경우 대기 중인 접수 실행이 다음 편집에 밀려 취소될 수 있습니다 — 접수 코멘트가 사라질 뿐 승인으로 읽히지는 않습니다. 고치려면 후속 T3 입니다.
