# 병합 요청 M085 — 사이트 자동 배포의 게시 잡이 기본 가지에서만 돌게 합니다(확인 015 의 AP6 F113)

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M085 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다.) 이 요청은 블로그 저장소 `chanceblog` 의 것이고, PR 제목 맨 앞이 `[M085]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다. 급하지 않습니다(보통).

## 1. 무엇을 바꾸는지
사이트 자동 배포 워크플로(`.github/workflows/pages.yml`)의 **게시 잡에 한 줄**을 더합니다: `if: github.ref_name == github.event.repository.default_branch`(지금 실행 중인 가지가 저장소의 기본 가지일 때만 게시). 빌드 잡·권한·트리거·동시성·시크릿·액션 고정값·다른 워크플로·저장소 설정은 한 글자도 안 바꿨습니다.

## 2. 왜 필요한지
운영자님이 확인 015(2026-11-13, 이슈 #195)에서 추천대로 승인하신 열두 가지 중 하나입니다. 지금은 push 로 도는 배포만 `main` 으로 제한돼 있고, 수동 실행과 Chance 두 워크플로의 배포 요청(`gh workflow run pages.yml --ref`)은 **어느 가지에서든 빌드하고 공개 사이트에 게시**할 수 있습니다(결함 D-375). `main` 이 아닌 가지의 내용이 공개 사이트에 올라갈 수 있는 길을 막습니다.

## 3. 사용자가 체감하는 변화
**사이트를 보시는 분이 느끼는 변화는 없습니다.** main 에 push 하는 정상 배포는 그대로 게시됩니다. 달라지는 것은 기본 가지가 아닌 가지에서 수동 실행을 눌렀을 때뿐입니다 — 빌드만 돌고 '게시'와 '반영 확인'은 건너뜁니다.

## 4. 위험과 기존 기능에 미치는 영향
- **가장 큰 위험(거짓 건너뜀)**: 식이 main 에서 정상 배포를 잘못 건너뛰면 사이트가 **조용히 갱신을 멈춥니다**(실행 결론은 성공이라 워치독도 못 봅니다). 근거: push 경로는 이 저장소 안에 관측이 있습니다(`auto-pr.yml` 이 같은 `default_branch` 속성으로 PR #148 을 실제로 만든 기록). **수동 실행(`workflow_dispatch`) 경로는 저장소 안에 관측 증거가 없습니다**(독립 검증자가 GitHub 문서를 기억에 의존해 판단).
- **그래서 병합 뒤 제가 직접 확인합니다**: ① 첫 main push 의 세 잡이 모두 초록이고 건너뜀이 아닌지 ② main 에서 수동 실행을 한 번 눌러 '사이트 게시' 가 건너뜀이 아닌지(잡 단위 확인). 건너뜀이 나오면 즉시 알리고, 복구 길은 **이 병합을 되돌리는 PR 하나**입니다(문서에 적어 둠).
- **일부러 안 한 것**: 같은 `concurrency` 그룹 때문에 다른 가지의 수동 실행이 진행 중인 main 게시를 취소할 수 있는 문제는 승인 밖이라 D-376(열림)으로 남겼습니다.
