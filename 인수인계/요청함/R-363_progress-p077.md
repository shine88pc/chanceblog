# 진행 현황 P077 — 로컬 사진 분석 조사표·시제품 계획 (본문 — 폰에는 싣지 않고 요청 열기로 읽습니다)

> 운영자 지시(11-16 채팅)에 따른 **읽기 전용** 검토입니다. 모델·패키지·저장소를 내려받거나 설치하거나 복제하지 않았고(웹 페이지 읽기만), 코드 병합도 없습니다. GitHub 의 임의 Skill 도 설치하지 않았습니다. 사진은 PC 밖으로 나가지 않고, 비용이 드는 선택지는 쓰지 않았습니다. 조사는 후보마다 독립 조사원 한 명이 공식 저장소·모델 카드·문서를 읽어 [공식 확인]·[제3자]·[추정]·[미확인] 으로 나눠 적게 했고, 근거를 못 찾은 것은 '미확인'으로 두었습니다. 읽기 도구가 페이지를 요약해 돌려주므로 **숫자와 옵션 이름은 시제품 단계에서 원문으로 다시 확인**합니다. 조사 원문은 작업 폴더 `audit6/improve/photolocal/report_*.txt` 에 있습니다.

## 1. 한눈에
- 세 후보 모두 코드·모델이 MIT 또는 Apache-2.0 이라 **라이선스·API·클라우드 비용은 없습니다.** 다만 설치 용량(가상환경)은 후보마다 크게 다릅니다.
- **Florence-2**(장면·객체 설명): 영어 전용 모델이라 한국어 설명은 번역 단계가 필요하고 한글 글자 읽기는 기대하기 어렵습니다. 음식·메뉴·간판 사진에서의 오인식 근거는 찾지 못했습니다(측정 필요).
- **Docling**(문서 구조·글자): 활발히 관리되고 공식 오프라인 방법이 있지만 torch 를 끌고 와 무겁고, 사진(문서 스캔이 아닌) 성능 근거가 없으며, 의존성·모델 라이선스 검증이 가장 어렵습니다. 한국어 글자는 RapidOCR(한국어)·EasyOCR 로 가능합니다.
- **PaddleOCR**(글자): 한국어 모델이 작고(14MB) 한국어 읽기는 가능하지만, 윈도 CPU 에서 알려진 오류(oneDNN)와 큰 사진에서 메모리가 폭증하는 사례가 있고, 기본이 모델 출처 연결 점검(네트워크 요청)이라 '네트워크 0' 은 끄는 설정을 시험으로 확인해야 합니다.
- 결론: **지금 바로 채택할 단계는 아닙니다.** 시제품에서 재야 할 것은 네트워크 0 증명·메모리 상한·한국어 글자 정확도·장면 설명이 수동 입력보다 시간을 줄이는지입니다. 조건이 안 맞으면 로컬 분석은 채택하지 않고 수동 사진 종류·순서·메모만 유지합니다.

| setting | 예 | 예 | 실내·실외·객실·야경 등(사용자 선택) |
| user_subject | 예 | 예 | 사용자가 적은 사진의 대상, 60자 이하(예: 시그니처 냉면) |
| user_note | 예 | 예 | 사진 사이에 넣을 사용자의 한마디·맥락, 300자 이하 |

- **저장하지 않는 것**: EXIF(촬영 위치·기기·시각)·썸네일·원본 사본·분석 원문(캡션 전문·박스 좌표)·얼굴 관련 값 전부. 분석 결과(observed_objects·visible_text)의 영구 저장은 **기본 OFF**.

## 5. 처리 흐름과 플러그인 구조
사진 선택 → 순서·종류 수동 지정 → (선택) 로컬 분석: 사용자가 '분석'을 누를 때만, **별도 프로세스**에서 → 관찰 결과를 '확인 전' 배지로 표시 → 항목별로 고치고 확정 → Manifest 생성 → 초안의 Section·사진 위치에 확정분만 반영.
- UI 멈춤 방지: 분석은 언제나 별도 프로세스(취소 단추·시간 제한·낮은 우선순위). 앱 본체는 무거운 라이브러리를 불러오지 않습니다.
- 플러그인(본체와 분리): 사용자 데이터 폴더 아래 `plugins/photo-local/` — 자체 가상환경·모델 폴더·`plugin.json`(이름·버전·해시·입출력 스키마). 앱은 설치돼 있고 해시가 맞을 때만 '로컬 분석' 단추를 보임. 통신은 표준 입출력 JSON(요청: 파일 하나·작업 종류, 응답: 관찰 결과). 앱은 플러그인 출력을 믿지 않고 스키마·길이·금지 낱말 검사를 거쳐 '확인 전'으로만 보입니다. 본체 Package 의 의존성·크기는 변하지 않고, 플러그인 폴더를 지우면 본체는 그대로 동작합니다.
- 한국어 설명: Florence-2 의 영어 출력은 번역 모델을 더하지 않고 '객체 이름(영어) → 앱 안의 닫힌 한국어 낱말 목록 → 사용자가 고름' 으로 처리하는 길을 먼저 시험합니다(번역 모델은 새 모델이라 별도 승인 대상).

## 6. 시제품 계획 (격리 — 본체와 병합하지 않음)
1. **위치**: 앱 저장소 밖 작업 폴더(예: `C:/work/ai/photolab/`)와 후보별 자체 가상환경. 일반 사용자 권한. 코드는 병합하지 않고 결과 보고서만 남깁니다. 시제품이 끝나면 지워도 되는 구조입니다.
2. **단계(제안)**: 1단계 글자 — PaddleOCR(한국어 v5 모델, 가장 작은 모델 세트) 대 Docling(RapidOCR 한국어)을 메뉴판·화면 캡처·제품 라벨에서 비교. 2단계 장면 — Florence-2(네이티브 + safetensors + 커밋 해시 고정)로 음식·외관·내부·제품 사진 비교. 각 단계는 따로 승인받습니다.
3. **시험 사진**: 운영자가 직접 찍은 사진만(외부 작성자 사진 금지). 음식·메뉴판·매장 외관·매장 내부·제품·화면 캡처 6유형 각 3장에서 5장, 총 20장에서 30장. 사진 폴더는 운영자가 지정하고 저장소에 올리지 않으며 PC 밖으로 나가지 않습니다. 얼굴·번호판·영수증 개인정보가 보이는 사진은 제외하거나 가린 사본을 씁니다. **정답표**(유형별 대상 목록·글자 전사)는 정확도 측정에 필요해 운영자가 고치거나 확인합니다.
4. **비교 3조건**: 수동 분류만 · Florence-2 Base · PaddleOCR 또는 Docling OCR.
5. **측정(운영자 지정 10가지)**: 사진 1장 처리 시간(모델 불러오기와 추론을 나눠 중앙값·최댓값) · 최대 RAM(프로세스 작업 집합 최댓값 표본) · 설치·모델 용량(가상환경과 모델 폴더 크기) · CPU 사용률 · 앱 응답 없음(시제품 창의 UI 타이머 지연 최댓값 — 별도 프로세스 대 같은 프로세스) · 객체 설명 정확도(사진별 정확/부분/오류/지어냄 채점) · OCR 정확도(정답표 대비 글자 오류율, 가격 숫자 정확도) · 한국어 결과 품질 · 잘못된 추론(신원·감정·음식명·브랜드·장소 단정 수) · 사용자 수정 횟수와 확정까지 걸린 시간. 후보별 추가 측정: PaddleOCR 의 oneDNN 오류 재현 여부·긴 변 상한별 메모리, Docling 의 최소 설치 조합과 EXIF 회전, Florence-2 의 원본 대 변환본 출력 비교.
6. **네트워크 0 증명(세 겹)**: ① 준비가 끝난 뒤 네트워크를 끊고(비행기 모드·랜선 분리 — 어댑터 끄기는 관리자 권한이라 운영자 수동) 전 시험 수행 ② 시험 하니스의 소켓 가드(파이썬이 여는 연결 시도를 기록·차단해 0건 확인 — 네이티브 라이브러리는 못 잡으므로 보조) ③ 프로세스별 연결 표본(`Get-NetTCPConnection`·`Get-NetUDPEndpoint` 의 소유 프로세스를 짧은 간격으로 기록해 0건 확인). 각 후보의 오프라인 환경 변수와 텔레메트리 끄기를 모두 적용합니다.
7. **채택 판정표(합격선은 제안 — 조정 가능)**: 일반 사용자 권한(UAC 0) · UI 멈춤 없음(UI 지연 200ms 이하·응답 없음 0) · 네트워크 요청 0(위 세 겹 모두 0) · 외부 전송 0(네트워크 0 + 업로드 코드 경로 없음) · 확인한 Manifest 만 반영(단위 시험) · 시간 절감(수동 대비 총 소요 시간 30% 이상 줄고 수정 횟수가 합리적) · 오인으로 사실 만들지 않음(단정 오류 0) · 새 의존성·모델 라이선스(상업 사용 가능·재배포 조건 확인·AGPL/비상업 0) · 분리 가능한 플러그인 구조(본체 크기·의존성 변화 0). **하나라도 못 채우면 로컬 분석은 채택하지 않고 수동 사진 종류·순서·메모만 유지**합니다.
