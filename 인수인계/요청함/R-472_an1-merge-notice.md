# 병합 요청 M108 — 병합 알림 자동화 워크플로 둘(블로그 AN1)

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M108 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다.) 이 요청은 블로그 저장소 `chanceblog` 의 것이고, PR 제목 맨 앞이 `[M108]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다. 급하지 않습니다(보통). **이 병합에는 새 워크플로 파일 둘이 들어 있습니다(운영자 12항목 중 '워크플로' = 예) — 운영자님이 채팅으로 승인하신 확인 031 보기 2 의 바로 그것이고, 병합돼도 꺼진 채라 지금 알림은 그대로입니다.**

## 1. 무엇을 바꾸는지
운영자님이 개인 PC·무료 AI 한도로 옮기셔도 병합 알림이 끊기지 않게, AI 가 상주해 보내던 두 알림을 GitHub 가 자동으로 보낼 수 있는 길을 **만들기만** 합니다.
① **병합 부탁 자동** — 병합 가지의 검사가 모두 초록이고 PR 이 만들어진 뒤 `[M###] 병합 부탁` 알림 문장을 만듭니다. ② **병합완료 확인 자동** — PR 이 main 에 병합되고 main 검사가 끝난 뒤, 병합 커밋의 부모 수·트리·변경 파일 집합을 PR 과 대조해 `병합완료 확인 - 정상/이상` 문장을 만듭니다.
**꺼진 채**입니다: 켬 상태 파일 `pipeline/auto_notice.json` 이 `{"mode": "off"}` 이고, 켜는 것은 `dry`(판정은 하되 발송은 안 함 — 첫 관측) → `on` 순서로 **각각 별도의 병합 부탁**(T3)으로 올립니다. 앱 저장소용은 텔레그램 시크릿이 없어 만들지 않았습니다.

## 2. 왜 필요한지
확인 031 에서 운영자님이 '추천: 위 워크플로 둘 추가' 로 승인하셨습니다(요청 R-463, 채팅 11-23 13시대). AI 쪽 변경(경제 모드)은 프로그램 완성 뒤부터라는 지시에 따라 지금은 AI 상주 방식을 그대로 두고, 이 길만 먼저 준비합니다.

## 3. 사용자가 체감하는 변화
**지금은 없습니다**(꺼진 채). 알림은 지금처럼 AI 가 보냅니다. 켠 뒤에는 AI 가 꺼져 있어도 병합 부탁·병합완료 확인이 자동으로 옵니다.

## 4. 위험과 기존 기능에 미치는 영향
- **워크플로 안전 설계**: 트리거는 `workflow_run`(completed) 하나뿐, 권한은 읽기만, 가지·PR 의 코드는 체크아웃도 실행도 하지 않고(기본 가지의 믿을 수 있는 코드만), 이벤트의 글은 `env` 로만 받습니다. **job 둘로 분리**했습니다 — 판정 job 에는 시크릿이 없고, 발송 job 은 판정이 '보낸다' 고 했을 때만 시작하며 시크릿은 그 마지막 단계에만 내려갑니다. `off`·`dry` 에서는 발송 job 이 시작도 하지 않아 시크릿이 어떤 러너에도 가지 않습니다. 알림 문장은 base64 한 줄 출력으로만 전달되고 발송 직전에 다시 거릅니다(비밀 모양·주소·멘션·제어 문자·방향 글자).
- **기존 기능**: 기존 워크플로·정책·광고 표면·레지스트리·의존성은 안 바뀌었습니다(변경은 새 워크플로 둘·알림 코드·검증기 규칙(WF-16 — `workflow_run` 은 이 두 파일만 허용)·시험·문서뿐). 검증기 출력은 시작점과 같습니다(오류 0·경고 3).
- **알려 둔 한계(켜기 전에 닫을 작은 후속 다섯 — 이번 병합을 막지 않는 권고·참고)**: ① 검증기가 YAML `on` 키의 변형 표기(`'on'` 문자열 키와 불리언 `on` 을 함께 쓰는 꼴)를 못 읽어 WF-16 을 피할 수 있음 ② 알림의 '검사: 초록' 을 가지 쪽이 꾸밀 수 있다는 사실 등이 문서에 아직 없음 ③ 주소 거르기의 남은 구멍(비영문 도메인 꼬리 등) ④ 외부 접속 스캐너가 새 YAML 읽기 모양을 못 보는 사각지대 ⑤ 검사 상태 판정이 GitHub 쿼리 필터를 믿는 가정을 시험이 못 지킴. 모두 `dry` 관측 전에 닫습니다.
- **운영자께 여쭐 것**: 지금은 없습니다(켜기 단계는 따로 올립니다).
