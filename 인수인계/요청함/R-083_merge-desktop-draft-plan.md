## 무엇이 바뀌나 (쉬운 설명)
요구서(v0.3.1)의 **'입력 없이 후보 → 초안'** 흐름에서 세 번째 순서인 **글 쓰기 전 뼈대 만들기**입니다. 아직 글 문장을 쓰지는 않고, **무엇을 어떤 순서로 쓸지**를 규칙으로 짜 줍니다(AI·인터넷 필요 없음, **읽기만 하고 아무것도 저장하지 않음**).

1. **새 명령 `draft plan`**: 후보 하나와 대상 블로그(네이버 A·B)를 고르면 **제목 후보 3개·권장 목차와 소제목·꼭 넣을 핵심 내용·주의사항·태그·확인 권장**을 보여 줍니다. 선택 입력은 하나도 안 넣어도 됩니다.
2. **선택 입력 11칸**(모두 선택): 전하고 싶은 내용·실제 사용 경험·의견·꼭 넣을 말·뺄 말·독자·글 길이·제목 방향·참고 주소(열어 보지 않고 글자 그대로만 적음)·가격 기준일·결론, 글 유형. 값은 **사용자 입력 → 블로그 프로필 → 글 유형 틀 → 후보 → 공통 기본값** 순서로 적용됩니다.
3. **글 유형 틀 5종**과, 네이버 A·B 가 **서로 다르게** 나오고 너무 비슷하면 경고하는 규칙.
4. **'지어내지 않기' 검사**: 후기·방문·체험처럼 경험이 있어야 쓸 수 있는 글을 **경험 입력 없이** 만들면 경험담을 지어내지 않고 **정보형 안내 글**(위치·이용 정보와 방문 전 확인사항 등)로 바꾸고 그 사실을 '확인 권장' 에 적습니다. 계획 안의 모든 문장은 스스로 이 검사를 통과해야 하고, 직접 사용·방문·구매·수익 같은 경험 주장은 위반으로, 가격·날짜·통계는 '확인 권장'으로 알립니다.
5. **비밀 입력 거절**: 비밀번호·키·토큰처럼 보이는 입력(한글에 바로 붙은 키 포함)은 받지 않고, 오류에도 입력한 글을 적지 않습니다. 참고 주소 안의 비밀 값(`token=…` 같은 인자)도 이름과 값을 함께 보고, 퍼센트 부호로 가려 쓴 것까지 풀어서 거절합니다.

**바뀌지 않는 것:** 기존 명령(후보·네이버 변환·GitHub Pages 올리기 등)의 동작과 출력은 그대로입니다(기존 시험으로 확인). 화면·초안 문장·네이버 데이터 수집은 다음 묶음입니다.

## 보안 코드 한 곳이 바뀝니다 (알려 드립니다)
공유 가리기 규칙(`security/mask.py`)이 **한글이나 밑줄 바로 옆에 붙은 키 모양**까지 알아보도록 경계를 넓혔습니다(독립 검증 중 '키가 한글에 붙으면 가려지지 않는다'가 발견돼 고쳤습니다). **일반 글의 출력은 한 글자도 달라지지 않습니다**(독립 검증자가 3만 9천여 글을 비교). 달라지는 것은 한글·밑줄 바로 옆의 키(이제 가려짐)와, `…_api_key = "…"` 꼴에서 가림 표지가 `[가림: 값]` 에서 `[가림: 키/토큰 할당]` 로 바뀌는 것(비밀은 둘 다 가려지며 비교한 글의 0.6%)뿐이고, 이 규칙을 쓰는 기존 시험 12개 모듈 621개가 모두 통과합니다. 보안 코드라서 독립 검증자가 이 부분을 따로 다시 확인했습니다. 한계: 영문·숫자에 붙은 키(`abcAKIA…`)와 밑줄·하이픈 앞의 JWT 는 기존 규칙처럼 알아보지 못하며 문서에 적었습니다.

## 확인한 것
- 독립 검증 3회(구현자와 다른 AI 가 새 복사본에서). 1차는 중간 6건·낮음 10건이 나와 모두 고쳤고, 2차(`89d83e5` 기준)는 **'조건부 병합 가능'**(높음 0·중간 4·낮음 6)으로 병합 조건 2가지(참고 주소 인자 이름 규칙 되돌리기·문서 정확도 문구 정정)를 구현자가 고쳤으며, 3차로 검증자가 수정분(`55a894a`)만 다시 확인해 **'병합 가능'**(높음 0·중간 3·낮음 6 — 중간 3 은 규칙 정확도로 문서에 한계가 적혀 있는 후속 과제)이라고 판정했습니다. 근거: 참고 주소의 비밀 인자 72개 중 받음 28→0, 정상 주소 94개 오거절 0, 퍼센트로 가려 쓴 21가지 중 20가지 거절(세 겹 퍼센트만 받음 — 비현실적), 거절 오류 글의 입력 조각 0(4,114조합), 한글 옆 키 노출 0, 문서의 수치가 검증자 측정과 일치, 진짜 파이썬 3.10.11 29개 모듈 1351개 OK, 새 코드 변이 33곳 중 32곳 잡힘(생존 1곳은 동작이 맞는 시험 공백); 앞서 진짜 3.10.11 전체 시험 2341개 OK(`223382f` 기준)·한글 붙은 키 노출 153조합→0·일반 글 출력 불변(3만 9천여 글 비교)도 확인했습니다. 남은 것은 문서에 수치로 적은 규칙 정확도 한계(독립 새 예문 기준 위반 미탐 34%·통과 오탐 8%)로 초안 문장 묶음 전의 후속 과제입니다.
- 이 브랜치의 자동 검사: 4칸(Windows·Ubuntu × 파이썬 3.10·3.12) 모두 초록 — 21:23 에 시작해 21:38 에 끝났고 15분 3초 걸렸습니다. PR 화면의 검사도 이 결과를 그대로 보여 줍니다.
- 변경 범위: 파일 27개(새 모듈 5개와 새 시험 파일 8개 포함, 기존 파일은 명령 등록·오류 코드·후보 가져오기·가리기 규칙·문서에 조금씩), 줄 수로는 거의 새로 추가한 것입니다(+6493 −10).

## 솔직한 한계 (병합을 막지 않음)
- '지어내지 않기' 검사는 한국어 낱말 규칙이라 **놓치거나 잘못 걸 수 있습니다.** 독립 검증자가 새로 만든 예문으로 재 보니 경험을 말하는 문장을 놓치는 비율이 34%(24/70), 일반 문장을 잘못 걸어 내는 비율이 8%(6/74), 이용 후기를 청하는 말·조건문 같은 문장을 잘못 거는 비율이 31%(21/67)였고, 프로젝트 문서 1,165문장에서는 잘못 건 것이 5개(0.4%)였습니다. 그래서 문서에는 '구현자 예문 기준 96%' 라고만 쓰지 않고 이 수치를 나란히 적었고, **규칙 정확도 개선은 초안 문장을 쓰는 묶음 전에 하는 후속 과제**로 정했습니다. 높임 없는 구어 질문('써 봤어요?')은 경험을 말하는 문장과 모양이 같아 걸리니 '써 보셨나요?' 로 바꿔 쓰면 됩니다. 한계 목록과 예문은 시험으로 고정해 문서에 적었습니다.
- 안전을 먼저 해서 `password: required` 같은 '이름: 값' 꼴의 일반 글도 비밀로 보여 거절합니다(문장으로 바꿔 쓰면 됩니다).
- 알려 둔 후속 과제(이번에 안 함): 질문 형태로 우회하는 경험 주장('-았죠?'·'-잖아요?' 꼴), 일부 후기 판정 사례, 시험이 못 잡는 변이 11곳, 긴 값이면 아직 받는 참고 주소 인자 이름 일부(`rlkey`·`csrf`·`state` 등 — 검증자가 위험 여부를 판단).
