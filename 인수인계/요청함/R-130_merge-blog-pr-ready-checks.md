# [R-130] 병합 부탁 — 블로그 PR 검사를 '병합만' 가능하게

> **검사는 이미 끝났습니다 — PR 을 만들자마자 병합하셔도 됩니다.** 제가 브랜치를 올린 때 새 검사가 돌아 초록으로 끝났습니다. **이 병합 부탁은 블로그 저장소 `chanceblog` 것입니다**(데스크톱 프로그램 저장소 `chanceblog-desktop` 이 아닙니다). 운영자님이 15:17 채팅과 16:50 채팅으로 요청하신 "병합만 바로 진행할 수 있게"에 대한 구조 개선이며, 블로그 검사가 도는 때가 바뀌므로 **병합이 곧 승인**입니다.

## 병합할 제목 (이것 하나만)
> **[R-130] 블로그 PR 검사를 '병합만' 가능하게 — 가드레일 검사를 push 때 시험 병합으로 돌리고 PR 이벤트 검사는 줄임 [대상: 공통]**

- 맨 앞이 `[R-130]` 인 이 제목 하나만 병합합니다. 다른 번호나 다른 제목은 병합하지 않습니다.
- 병합 화면 맨 위의 저장소 이름이 **`chanceblog`** 인지 확인합니다(`chanceblog-desktop` 이 아닙니다).
- 첫 화면에 노란 배너가 여러 개 보여도(작업 중인 다른 브랜치) 위 제목 하나만 고릅니다.

## 무엇이 바뀌나 (쉬운 설명)
지금은 제가 브랜치를 올릴 때 검사가 한 번 돌고, 운영자님이 PR 을 만들면 **같은 검사가 2~3분 더 돌아** '일부 검사가 도는 중'처럼 보입니다. 이 변경은 **검사를 줄이지 않고 도는 시점만 옮깁니다.** 브랜치를 올릴 때 검사가 'main 의 최신 내용을 그 브랜치에 임시로 합쳐 본 상태'(제 PC 와 GitHub 서버 안에서만 합치고 어디에도 올리지 않음)로 규칙·전체 시험을 돌리므로, PR 을 만들 때쯤에는 이미 끝난 초록이 붙어 있습니다.

| 파일 | 바뀌는 것 |
|---|---|
| 규칙·시험 검사 워크플로 | PR 을 만들 때는 돌지 않고, 어느 브랜치든 올릴 때 돕니다. 올린 브랜치에 main 을 시험 병합한 내용을 검사하고, 충돌이거나 main 을 가져오지 못하면 빨강입니다. 광고 표면 검사의 기준은 '시험 병합 직전의 main 끝'. main 에 올라간 변경·수동 실행·main 검사 실패 때의 텔레그램 알림은 그대로입니다 |
| PR 범위 확인 워크플로 | 제가 올린 브랜치(`ai/claude/…`)에서 만든 PR 은 건너뜁니다(브랜치를 올릴 때 이미 검사가 끝남) |
| 확인 필요 모음 워크플로 | PR 형식 중 `opened`·`reopened` 만 뺐습니다(라벨을 붙이거나 닫을 때의 즉시 갱신은 그대로) |

시험 6개(새 시험 2개 포함)와 문서도 같이 고쳤습니다. **PR 화면 예상**: 초록 3줄(`검사 (Python 3.10)`·`검사 (Python 3.12)`·`요청 알림 보내기`)과 '건너뜀' 2줄(`실패 알림`·`이슈 요청 범위 확인`), 노란 점(진행 중)은 거의 없습니다. 병합하시면 main 에서 검사(약 2분)와 사이트 배포가 한 번 돌고 실패하면 휴대폰으로 알립니다.

**바뀌지 않는 것:** 검사 내용(규칙 검증기·전체 단위 시험·액션 문법 검사·파이썬 3.10/3.12 두 칸·시간 한도 10분), 광고 표면 보호 검사(AD-1·AD-2), 시크릿·권한, 글 생성·발행·사이트.

## 병합하시면 승인하시는 것
1. **검사가 도는 때가 PR 을 만들 때 → 브랜치를 올릴 때로 바뀝니다.** 포크한 저장소에서 온 PR 은 검사가 안 돕니다(이 저장소는 같은 저장소 브랜치로만 일합니다).
2. **초록은 '제가 브랜치를 올린 시점의 main' 기준입니다.** 부탁을 받고 한참 뒤 병합하시는데 화면에 `This branch has conflicts` 가 보이면 **병합하지 말고** 알려 주세요. 글자 충돌 없이 의미만 어긋나는 드문 경우는 병합 직후 main 검사가 한 번 더 잡고 실패하면 휴대폰으로 알립니다.
3. 다른 변화는 없습니다(검사 강도·시크릿·권한 불변).

## 효과와 한계 (과장하지 않습니다)
- **풀리는 것**: 'PR 을 만들자마자 병합하면 일부 검사가 도는 중인 채로 병합하게 되는 것처럼 보이는' 문제. PR 을 만든 뒤 병합까지 기다리던 2~3분이 없어집니다.
- **남는 것**: 건너뜀 2줄은 계속 보입니다(해당 없음이라는 뜻의 정상 표시). 이 변경이 병합되기 전에 만든 옛 브랜치는 옛 검사 파일을 담고 있어 새 main 위에서 다시 만들어야 합니다(제가 합니다). 가지를 지울 때 검사가 새로 생기는지는 공식 문서에 없어 확인 전입니다(생겨도 알림은 없습니다).

## 확인한 것
- 독립 검증(구현자와 다른 AI): **병합 가능**(필수 수정 0, 보안 위험 낮음). 옛 PR 방식과 광고 표면 검사 결과를 12개 시나리오로 견주니 모두 같았고, 일부러 어겨 본 변이 82곳을 시험이 모두 잡았으며, 이상한 브랜치 이름·값 8건에서 새는 것이 없었고, 관련 15개 모듈 1,056개와 무거운 시험 2개가 파이썬 3.12·진짜 3.10.11 에서 통과했습니다. 17개 워크플로의 트리거를 직접 읽어 PR 화면 예측이 맞는지 확인했습니다.
- 검증 뒤 제가 반영한 것(검증자가 다시 읽지는 않음): 권장 문서 고침 2건(운영자 문서에 '초록은 올린 시점의 main 기준·충돌이 보이면 병합하지 말고 알림', 결함 표 관측 항목), R-127 병합으로 겹친 작업 기록·결함 표 두 곳을 새 main 위로 옮기며 풀기(변경 줄은 검증본과 같음), `인수인계/작업내용.md` 갱신. 문서 못박기 12개 모듈 420개와 무거운 시험 43개가 통과했습니다.
- 이 브랜치의 자동 검사: 새 검사(브랜치에 main 을 시험 병합한 내용으로 저장소 규칙·전체 시험, 파이썬 3.10·3.12)가 19:09 에 시작해 초록으로 끝났고 2분 36초 걸렸습니다. PR 화면에서는 이 결과가 그대로 붙어 보입니다.
- **첫 실제 실행 관측**(새 검사가 실제 GitHub 서버에서 도는 첫 번째 때): 이 브랜치를 올린 19:09 에 새 검사가 처음으로 실제 GitHub 서버에서 돌았습니다. 결과: ① 파이썬 3.10·3.12 두 칸 모두 초록(3.10 은 2분 32초, 3.12 는 1분 53초, 전체 2분 36초로 한도 10분 안이고 시험 단계는 129초·98초) ② 시험 병합 단계가 통과했고 광고 표면 검사의 기준이 '시험 병합 직전의 main 끝 1f50c0d' 로 검사 주석에 남았으며 그 값이 그 시각 main 의 끝과 같습니다(이 브랜치는 main 끝에서 바로 갈라져 있어 합칠 것이 없었습니다 — main 이 앞서간 경우의 실제 합치기는 시험 코드로만 확인했고 서버에서는 다음 브랜치부터 관측합니다) ③ 서버의 액션 문법 검사(셸 스크립트 검사 포함)가 새 단계 스크립트에서 지적 0건 ④ main 에서만 도는 실패 알림은 예상대로 건너뜀 ⑤ 같은 푸시로 도는 다른 두 워크플로(요청 알림·텔레그램 수신)도 성공. 검사 요약에 오류 표시 한 줄이 보이는 것은 시험 하나의 설명 문장이 오류 표시 기호로 시작해 생기는 기존 현상(이전 검사에도 있던 표시로 보이며 결과는 초록)이고 별건으로 고치겠습니다.
- 변경 범위: 파일 26개(워크플로 3·시험 6·문서 17), 줄 수는 +1166 −345 입니다.

## 병합 뒤 제가 확인할 것 (관측 목록)
병합 직후 main 검사·사이트 배포 초록과 `확인 필요 항목 모으기` 건너뜀 한 줄, 다음에 만드는 PR 의 화면이 예상대로(초록 3·건너뜀 2·진행 중 없음)인지, 브랜치를 지운 직후 새 실행이 생기는지, 단계별 시간(한도 10분 안)을 읽어 알려 드립니다.

## 솔직한 한계 (병합을 막지 않음)
- 처음 실제 서버에서 도는 시험은 이 브랜치를 올린 때의 한 번뿐입니다(위 관측). 시험 병합이 오래 걸리는 시험을 단위 시험 단계에 더해 단계가 길어졌습니다(한도 10분 안).
- 이 PC 에는 셸 스크립트 검사기(shellcheck)가 없어 새 단계 스크립트는 서버의 액션 문법 검사가 처음 봅니다(위 관측에서 지적 여부를 확인).
- 별건 후속(이번에 넣지 않음): 광고 표면 검사의 이름 바꿈 우회(보호 파일을 보호 목록 밖으로 옮기면 못 잡음 — 옛 방식에도 있던 약점), 검증기의 주입 낱말 보강.

## 위험과 대비
- 최악의 경우도 '검사가 안 돌거나 빨강으로 보이는 것'이고 글·발행·시크릿 경로는 안 건드립니다. 문제가 보이면 병합 한 건을 되돌리는 요청을 드립니다(워크플로 3개가 이전 상태로 돌아갑니다).
- 병합 뒤 제가 직접 확인합니다(병합 상태·내용 일치·main 검사). 병합하신 시각을 알려 주실 필요는 없습니다.

## 하실 일 (병합, 1분)
1. 휴대폰에서 GitHub 를 PC 버전으로 열어 **`chanceblog` 저장소**(블로그, `chanceblog-desktop` 아님) 첫 화면(또는 Pull requests 탭)으로 갑니다.
2. 제목이 위의 **[R-130] 블로그 PR 검사를 '병합만' 가능하게 — 가드레일 검사를 push 때 시험 병합으로 돌리고 PR 이벤트 검사는 줄임 [대상: 공통]** 인 것 하나를 찾아 **Create pull request**(첫 화면 노란 배너의 Compare & pull request)를 누릅니다. 배너가 없으면 Pull requests 탭 → New pull request → 오른쪽(compare) 칸에서 `ai/claude/r130-pr-ready-checks-1` 를 고르면 됩니다.
3. **검사를 기다리지 않으셔도 됩니다**(이미 끝난 초록이 근거). 화면에 초록 3줄과 건너뜀 줄이 보이면 정상입니다. **Merge pull request(또는 Squash and merge) → Confirm**. **Delete branch·Update branch·Re-run 은 누르지 않습니다.**
- 위 '병합하시면 승인하시는 것' 중 마음에 걸리는 것이 있으면 **병합하지 말고** [답하기]로 알려 주세요.

## 안 될 때
빨간 ✗ 이거나 'conflicts' 가 보이면 병합하지 말고, [답하기] → 요청 번호 **r130**(하이픈이 있어도 없어도 됩니다) → 답변 '문제' 를 고르고 메모에 화면에 보이는 문구를 적어 주세요.
