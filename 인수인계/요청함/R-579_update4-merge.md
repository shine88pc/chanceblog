# 병합 요청 M141 — 업데이트 적용 설치 도구 어댑터와 복구 경로 보강(앱, T3)

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M141 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다.) 이 요청은 앱 저장소 `chanceblog-desktop` 의 것이고, PR 제목 맨 앞이 `[M141]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다. 급하지 않습니다(보통).

## 1. 무엇을 바꾸는지
운영자께서 확인 038 ①로 승인하신 '앱 업데이트' 중 **받은 설치 파일을 적용하는 부분**을 구현했습니다. 앱이 새 판의 설치 파일(Inno Setup)을 받아 서명·해시를 확인한 뒤, 앱을 끝내고 설치 도구를 조용히 실행하는 코드이고, **스위치가 모두 꺼진 채** 들어갑니다.
- **설치 도구를 띄우는 곳은 한 함수뿐**: 인자는 고정 목록(`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP- /CLOSEAPPLICATIONS` 와 고정 이름의 기록 파일)이고 셸을 거치지 않으며, 띄우기 직전에 파일을 다시 해시해 확인합니다. 소스 전체에서 이 호출이 이 한 곳뿐임을 시험이 지킵니다(별칭으로 돌려 쓰는 우회도 막음).
- **Velopack 감지 삭제**: 설치 종류는 Inno·휴대용·소스 셋으로 정리하고, 옛 `velopack` 은 읽기만 하고 적용은 거절합니다.
- **받은 파일과 확인 결과의 일치 확인**: 백업·잠금보다 앞에서 파일의 경로·모양·판을 확인해 어긋나면 아무것도 건드리지 않고 거절합니다. 폴더에서 확인한 결과로는 인터넷 요청이 나가지 않게 막았습니다.
- **복구 경로 보강**: 복구 설치 파일을 띄운 뒤 그것이 조용히 실패해도 다음 시작이 알아보도록 '띄웠다'와 '됐다'를 나눠 기록합니다.
- 바뀐 곳(29개 파일): 소스 8(`update/{apply,install_kind,manifest,recovery,state}.py`·`service/update_flow.py`·`ui/core/updates.py`·`errors/catalog.py`)·시험 새 둘(`test_update_inno`·`test_update_guards`)과 바뀐 기존 시험 9·문서 9.

## 2. 왜 필요한지
앱 v1.0 의 '새 판 확인 → 받기 → 적용' 흐름 중 마지막 조각입니다. 이 코드가 있어야 정식 설치 파일로 앱이 스스로 새 판으로 바뀔 수 있습니다. 설치 도구를 실행하는 위험한 부분이라 켜기 전에 독립 검증을 두 번(안전·시험) 거쳤습니다.

## 3. 사용자가 체감하는 변화
**없습니다.** 업데이트 적용 스위치가 꺼져 있어 앱은 설치 도구를 한 번도 실행하지 않습니다.

## 4. 위험과 알려 둔 한계
- **켜는 일은 이 병합에 없습니다.** 업데이트 적용 스위치는 독립 검증 뒤 새 번호로 따로 승인받습니다.
- 진짜 설치 파일로만 확인할 수 있는 것은 켜기 전 실기 단계로 남깁니다: `/CLOSEAPPLICATIONS` 의 실제 효과, 공백이 든 폴더의 기록 파일 이름 읽기, `/SP-` 가 꼭 필요한지.
- 재확인 권고 셋(경로 글에 널 문자·아주 긴 글이 들면 생 오류가 새는 길, 이름 규칙 세부 시험, 새 업데이트가 낡은 안내를 비우는 줄의 시험)은 병합을 막지 않는 시험 한두 줄의 틈이라 시험 묶음 후속으로 미룹니다.
- 상태 파일에 허용 안내 값이 하나 늘었습니다(옛 판은 새 상태 파일을 손상으로 봄 — 업데이트 기능이 처음 켜지는 판이 이 코드를 가지므로 닿지 않음). 데이터 폴더를 네트워크 경로에 둔 사용자는 업데이트가 거절됩니다(닫는 쪽).
- 운영자께 여쭐 것은 없습니다.
