# 병합 요청 M143 — 릴리스 서명 도구와 사전 점검 스크립트(앱, T3)

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M143 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다.) 이 요청은 앱 저장소 `chanceblog-desktop` 의 것이고, PR 제목 맨 앞이 `[M143]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다. 급하지 않습니다(보통).

## 1. 무엇을 바꾸는지
운영자께서 확인 048 ①로 승인하신 '릴리스 흐름 준비' 중 **서명 도구·릴리스 점검 스크립트와 문서**를 구현했습니다. 진짜 서명 키·태그·릴리스·`.github`·`src/`·`update/`·`vendor/`·스위치·의존성은 0줄입니다(스위치 아홉은 모두 꺼짐, 출하용 서명 키 목록 `SHIPPED_KEYS` 도 그대로).
- **서명 키 쌍 만들기** `scripts/update_keygen.py`: 운영자 PC 에서 오프라인으로 만들고 저장소 밖에만 씁니다(키 값을 화면·기록에 내지 않음).
- **매니페스트 서명** `scripts/update_sign.py`: 키는 환경 변수 `UPDATE_SIGNING_KEY` 로만 받고, 서명하기 전에 앱과 같은 코드로 매니페스트를 검증하고, 서명한 뒤 앱의 검증기와 `openssl` 로 독립 확인합니다.
- **매니페스트 만들기** `scripts/update_manifest.py`: 발행 시각이 허용 범위(2020년에서 2100년, 미래 24시간까지)를 벗어나면 만들지 않습니다.
- **버전 사슬·릴리스 노트 검사** `packaging/release_chain.py`, **올리기 전 사전 점검** `scripts/release_preflight.py`(같은 태그나 초안이 이미 있는지 등을 실패 쪽으로 닫아 확인).
- 바뀐 곳(18개 파일): 코드 5·시험 8(새 여섯 모듈과 도우미·바뀐 기존 시험 하나)·문서 5.

## 2. 왜 필요한지
정식 릴리스를 올릴 때 서명 키를 쓰는 코드가 필요합니다. 키를 다루는 가장 위험한 부분이라 앱 코드와 떼어 두고, 키가 새거나 틀린 서명이 통과하지 않게 규칙과 시험으로 못박았습니다. 릴리스 올리기 워크플로(다음 갈래)가 이 스크립트들을 부릅니다.

## 3. 사용자가 체감하는 변화
**없습니다.** 앱은 한 줄도 바뀌지 않았고, 스크립트들은 릴리스 때 운영자와 워크플로만 씁니다.

## 4. 위험과 알려 둔 한계
- **서명 키는 이 병합에 없습니다.** 키 만들기·보관·시크릿 입력·출하용 서명 키 목록 채우기·태그·릴리스 공개는 운영자만 하는 일(T3)로 남습니다.
- `openssl` 독립 확인은 `PATH` 의 `openssl` 을 믿습니다. 같은 사용자 권한의 악의적 실행 파일은 부모 프로세스의 환경을 직접 읽을 수 있어 환경 걸러내기는 격리가 아닙니다(문서에 사실대로 적음). 앱의 검증기 확인이 따로 서명을 거절하므로 틀린 서명이 통과하지는 않습니다.
- 실제 GitHub `gh` 응답의 모양은 첫 러너 실행에서 확인합니다.
- 재확인이 짚은 시험 보강(자식 환경 허용 목록의 내용 못박기 등)과 정책 둘(릴리스 노트의 보이지 않는 글자 허용 범위 좁히기·발행 시각 미래 여유 시간 줄이기 검토)은 시험 묶음 후속으로 미뤘습니다. 병합을 막는 것은 아닙니다.
- 운영자께 여쭐 것은 없습니다.
