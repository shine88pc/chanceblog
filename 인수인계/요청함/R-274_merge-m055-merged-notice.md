## 이번 묶음이 하는 일 (운영자 요청 — 11-12 오전 채팅)
"병합 완료 알림은 별도로 관리 / P 번호 없이 / `[M###] 병합완료 확인 - 정상 유무`(간단히) / 목적은 내가 진행한 병합이 제대로 되었나를 확인하는 용도"를 구현합니다.
- **새 알림 종류 `merged`**: 폰에는 정상이면 `[M050] 병합완료 확인 - 정상` **한 줄만**(단추 없음), 이상이면 같은 제목 + 사유 한 줄 + `요청 열기` 단추 하나가 갑니다. P 번호·진행 현황·다른 군더더기는 없습니다. 알림 번호는 병합 부탁의 M 번호를 그대로 쓰므로 진행 현황(P)·확인(숫자)·다음 병합 번호 계산에는 영향이 없습니다.
- **틀린 파일이 거짓 '정상'을 보내지 못하게**: 독립 검증이 짚은 문제(모양이 틀린 파일이 옛 모양으로 보내지며 제목이 그대로 폰에 실려, 제목은 '정상'인데 결과는 '이상'인 파일이면 거짓 '정상'이 갈 수 있던 길)를 고쳤습니다. 이제 칸이 틀린 파일은 파일 내용을 한 글자도 싣지 않는 고정 문구 한 통('파일 모양이 틀려 내용을 싣지 않았습니다 — 요청 열기')으로만 갑니다. 폰에 '정상'·'이상' 글자가 가는 길은 검사를 통과한 파일에 코드가 만든 제목뿐입니다.
- **검증·도구**: 같은 M 번호의 병합 부탁 짝이 없거나 같은 M 에 확인이 둘이면 검증기가 오류로 보고하고, 번호 도구는 이 확인의 번호를 새 번호로 세지 않습니다. 파일을 만드는 저의 작업 도구는 기본으로 요청 가지의 코드로 먼저 읽어 보고, 그 코드가 새 종류를 모르면 파일을 만들지 않고 멈춥니다(아래 '병합한 뒤' 순서를 어기는 실수 방지).

## 눈에 보이는 변화

- **공개 글·사이트·글 만들기 자동 실행·기존 알림(진행 현황·병합 부탁·확인 요청)은 그대로입니다** — 독립 검증자가 실제 요청 파일 267개와 무작위 요청 8,400건(푸시 방식까지 합쳐 21,193 케이스)을 옛 코드와 새 코드로 각각 읽어 폰 글·단추·실행 요약·git 호출을 비교해 설명 안 되는 차이 0 을 확인했습니다.
