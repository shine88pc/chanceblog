# 확인 요청 016 — 이슈 #198 검토 (결정은 한 가지)

> 이 글은 **질문**입니다. 텔레그램에서 `016/1/`·`016/2/`·`016/3/` 중 하나로 답하시면 됩니다(의견은 세 번째 칸에). **답이 없으면 1(지금처럼)** 입니다. 이슈의 진행 범위가 '논의·준비까지만'이라 **아무것도 켜지 않았고**, 어느 선택이든 켜는 변경은 따로 한 번 더 부탁드립니다.

## 한눈에
- **결정할 것은 하나**: AI 직접 병합(아래 1번).
- 나머지 둘(감시·알림의 무료 한도, 새 세션 이어받기 안내)은 **보고**입니다 — 승인 없이 진행하고, 문서 변경의 병합은 운영자가 합니다.

## 1. AI 직접 병합 — 결정 필요
**지금 사실**
- 병합은 GitHub 에서 운영자가 누릅니다. AI 쪽에는 병합을 누를 도구(`gh`)가 없습니다.
- 다만 이 PC 에 운영자 계정의 푸시 자격증명이 저장돼 있고 main 에는 보호 규칙이 없어서, AI 가 검사를 통과한 가지를 main 에 밀어 넣으면(빨리감기 푸시) PR 이 자동으로 '병합됨'이 됩니다. 기술적으로 **가능**합니다. 지금까지 하지 않은 것은 안전 규칙 때문입니다(11월 초 main 을 직접 고쳐 실행 파일이 망가졌던 사고).
- 최근 병합 34건(11-09–11-14)을 바뀐 파일로 나누면 **문서만 4건(12%) · 코드 포함 18건(53%) · 운영자 전용 경로(.github·광고 표면·켜는 값·글 등) 12건(35%)** 입니다. 문서만 자동화하면 편해지는 정도가 작고, 코드까지 포함해야 크게 줄지만 그만큼 위험합니다.

**제가 준비해 둔 안전 장치**(검사 전용 도구 — 병합·푸시 기능은 넣지 않았습니다): 가지 이름 규칙·부모 위 한 커밋·빨리감기 가능·제목 번호·변경 등급(문서/시험/코드/운영자 전용)·비밀 모양 낱말·가지 검사 초록·'독립 검증' 기록을 판정합니다. 최근 병합 14건에 돌려 보면 문서 3·코드 7·운영자 전용 4 로 나뉘고, 방금 병합된 M070(문서)은 '문서만' 허용에서 통과, M071(코드·시험)은 '코드까지' 허용에서만 통과합니다.

**선택지**
1. **지금처럼** — AI 는 병합 부탁만 보내고 운영자가 병합합니다. 변화 없음(기본값).
2. **문서만 AI 가 직접 병합(시험 운영)** — 대상은 `인수인계/`·`WORKLOG.md`·`docs/` 의 문서 변경뿐. 조건: 독립 검증 통과 + 가지 검사 초록 + 허용 경로 100% + 비밀 낱말 0. 병합 직후 main 검사·라이브 값을 직접 확인하고 `[M###] 병합완료 확인` 알림을 보내며, 이상이면 즉시 되돌립니다.
3. **문서·시험·코드까지 AI 가 직접 병합** — 위 조건에 더해 **운영자가 승인한 항목 안이거나 자체 개선(T0–T2)일 때만**. 병합 건의 약 65% 가 여기에 듭니다.

**어느 선택이든 계속 운영자만 하는 것**: `.github/` 워크플로·광고 표면(홈·레이아웃·광고 설정)·켜는 값과 레지스트리(`pipeline/*.json`)·공개 글과 고정 페이지·키와 비밀·의존성 파일·발행 정지 해제·제공처 켜기·`workflow_dispatch` 실행. (제 도구도 이 경로가 하나라도 있으면 어떤 정책에서도 '병합 불가'로 판정합니다.)

**위험을 솔직히**: 2·3 에서는 병합 전에 운영자가 한 번 훑어보던 한 겹이 사라지고 AI 끼리의 독립 검증만 남습니다. 3 은 코드가 병합 즉시 main 에 들어가므로(지금은 발행 정지 중이라 새 글에는 영향 없음) 검증이 놓친 결함이 들어갈 수 있습니다 — 대응은 병합 직후 확인과 즉시 되돌림입니다.

**언제든 멈추는 법**(운영자 전용): GitHub 저장소 설정에서 main 의 보호 규칙(병합 전 PR 필수)을 켜면 AI 의 직접 푸시가 즉시 막히고 1 로 돌아갑니다.

**추천: 2 로 두 주 시험 → 이상 없으면 3 을 다시 묻겠습니다.** 이유: 문서 병합은 사이트에 영향이 없고(빌드 제외 파일) 되돌리기 쉬워 메커니즘을 검증하기에 가장 안전하고, 그 사이 병합 건수의 12% 만 줄어도 알림·대기 부담이 조금 줍니다. 더 빨리 줄이고 싶으시면 3 을 고르셔도 됩니다.

## 2. 감시·알림의 무료 한도 — 보고(결정 불필요)
**측정(블로그 저장소, 11-09–11-13 닷새)**: GitHub Actions 실행 782건(하루 약 156건), 실제로 도는 시간 합계는 하루 250분 안팎(여러 작업이 동시에 돌면 청구 분은 이보다 큼). 대부분 푸시 때 도는 검사이고 **정기 예약 실행은 하루 약 21건·8분**뿐입니다.
- **한도**: 공개 저장소의 표준 실행기는 **무료·무제한**입니다(GitHub 공식 문서 확인). 비공개로 바꾸면 무료 계정은 월 약 2,000분이라 지금 사용량(월 7,000분 이상 추정)이 크게 넘습니다 → **저장소를 공개로 두는 한 한도 걱정은 없고, 비공개 전환 계획이 생기면 먼저 알려 주세요.**
- **텔레그램**: 하루 약 32건, 무료. 공식 권고(채팅당 초당 1건 안팎, 그룹 분당 20건)에 한참 못 미칩니다.
- **정기 예약의 현실**: 10분마다 도는 텔레그램 수신 예약은 GitHub 가 부하 때 줄여서 실제로는 하루 4회 안팎입니다 → 이미 승인하신 '7분·37분' 실험(확인 015 의 6번)으로 정리할 예정입니다(구현 전).
- **AI 쪽 감시(이 PC)**: 이슈 감시가 90초마다 GitHub 를 조회해 비인증 한도(시간당 60회, 공용 주소 기준)의 3분의 2 를 쓰고 있었고 실측으로 '변경 없음' 응답도 한도에 세어졌습니다 → 5분 주기·한도 소진 시 쉬기로 고쳤습니다(이 PC 안의 도구라 승인 불필요, 적용 완료). 병합 감시는 `git ls-remote` 만 써서 한도를 쓰지 않습니다.
- **더 줄일 수 있는 것(승인 필요, 아직 안 함)**: 알림 파일 하나만 올려도 **전체 시험(약 6분)이 도는 것을 확인**했습니다 — 요청 가지 최근 푸시 34건에서 시험 33회·약 191분. 알림 전용 푸시는 시험을 건너뛰게 하는 `.github` 한 줄 변경(T3)을 제안할 수 있습니다(필요하시면 다음에 따로 묻겠습니다). 봇이 연 PR 마다 붙는 '승인 대기 만료' 빨간 ✗(범위 검사)는 오류가 아니라 소음입니다.
- **결론**: 지금 방식은 무료 한도 안에서 유지됩니다(공개 저장소 전제) → **전환 불필요**. 비공개 전환·요금제 변경이 생기면 그때 대안(검사 줄이기·예약 줄이기·자체 실행기)을 제안하겠습니다.

## 3. 새 세션 이어받기 안내 — 보고(승인 없이 진행)
- **모의 시험**: 이 저장소 복제본만 가진 별도 AI 에게 '저장소 chanceblog 를 확인하고 이어서 진행해줘' 한 문장만 주고 어디까지 이어 가는지 보았습니다(읽기 전용). 판정은 **일부만 가능** — 상태와 규칙은 거의 재구성했지만 ① 입구 문서마다 읽는 순서가 달라 `작업내용.md` 로 안 가는 곳이 있고 ② 승인 방식 문구가 문서마다 어긋나며(채팅 승인 vs 이슈 답) ③ 병합완료 알림·CI 확인 같은 도구가 이 PC 에만 있고 저장소 사본은 옛 버전이며 ④ '병합·정지 해제·main 직접 푸시 금지' 같은 불변 규칙이 정본 입구 문서에 없고 ⑤ 스냅샷이 낡았는지 바로 알아볼 방법이 없었습니다.
- **고칠 것**: ① 작업내용 맨 위에 **'30초 카드'**(저장소 머리 확인 명령 3줄·열린 PR 읽는 법·승인된 것/안 된 것 표·다음 3단계·푸시 권한이 없을 때 할 일) ② 입구 문서 읽는 순서를 하나로 통일 ③ 승인 채널 문구 정정 ④ 불변 규칙 5개를 입구 문서에 ⑤ 저장소 도구를 최신으로 맞추고 요청 가지 이름 정정 ⑥ 낡은 입구 문서 표시. 문서부터(병합 부탁은 문서만 — 선택 2 가 정해지기 전에는 운영자 병합), 도구는 시험과 함께 따로 올립니다.
- **한 문장 요청 예시**(고친 뒤): '저장소 chanceblog 의 인수인계/작업내용.md 맨 위 30초 카드부터 읽고 이어서 진행해줘.' 푸시 권한이 없는 환경이면 읽기·분석·초안까지 하고 로컬 안내 파일로 멈춥니다.
