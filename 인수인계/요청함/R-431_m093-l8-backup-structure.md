# 병합 요청 M093 — 백업 복원 구조 검사와 올리기 전 새 키·토큰 모양 막기(앱 L8)

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M093 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다.) 이 요청은 앱 저장소 `chanceblog-desktop` 의 것이고, PR 제목 맨 앞이 `[M093]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다. 급하지 않습니다(보통).

## 1. 무엇을 바꾸는지
① **조작된 백업 방어(F074)**: 백업 복원 길 셋(전체 백업 복원·옛 `restore` 명령·주제 엔진 복원)이 보관함 파일을 바꾸기 **전에**, 되돌릴 파일 안에 트리거·뷰·가상 표·모르는 표·색인·숨은 열 같은 개체가 앱이 새 보관함을 만들 때 쓰는 정본에 없는 것이 있는지 봅니다. 있으면 복원 전체를 거절하고(`FULL_BACKUP_INVALID`) 쉬운 이유 한 줄을 보여 줍니다. 같은 복원 길의 구멍도 막았습니다 — 설정의 '연결한 폴더'가 네트워크 경로(NAS 같은 UNC)이거나 주소·제어 문자·1024자 초과이면 거절합니다(조작한 백업이 남의 서버를 가리키면 복원 직후 앱이 그 경로를 열며 윈도 로그인 정보가 새는 길이 있었습니다). ② **새 키·토큰 모양 막기(F069)**: 올리기 직전 모양 검사와 가림 목록에 AWS ASIA·Stripe sk_live_·GitLab glpat-·Slack xapp- 등 열여덟 모양을 더했습니다.

## 2. 왜 필요한지
운영자 방침(세부는 추천안으로 진행하고 알리기만 함)으로 진행하는 안전 묶음(L8)입니다. 백업 복원은 보관함 파일을 통째로 복사하는데 그 앞의 확인이 표의 열 이름만 봐서, 열 이름이 같은 뷰나 트리거가 든 조작된 백업이 복원을 통과하면 이후 저장 때 글이 바뀔 수 있었습니다(공격 탐침으로 재현 — 옛 코드는 트리거대로 글이 바뀌었고 고친 코드는 거절합니다).

## 3. 사용자가 체감하는 변화
정상 백업·복원은 그대로입니다(옛 판 백업도 그대로 복원). 앱이 만든 백업이 아닌 조작된 백업, 앱 밖의 도구로 보관함에 뷰·트리거를 직접 만든 사용자의 백업, 연결한 폴더를 네트워크 경로로 쓰는 사용자의 백업은 복원이 거절되고 이유가 한 줄로 보입니다.

## 4. 위험과 기존 기능에 미치는 영향
- **기존 기능**: 저장 형식·백업 형식·서비스 쓰기·설정 칸은 안 바뀌었습니다. 복원 입구에 **읽기 전용 확인**이 더해지고 가림·올리기 목록이 넓어질 뿐입니다. 제품 코드는 +246줄 −14줄(새 파일 `content/schema_guard.py` 88줄)입니다.
- **알려 둔 한계**: 표 정의의 제약·행 값·보관함 파일 크기 상한은 정하지 않았습니다(행 값이 이상한 백업은 복원 뒤 읽을 때 걸림). 복원이 도중에 실패해 안전 사본으로 되돌릴 때도 같은 검사를 받습니다(지금 파일에 그런 개체가 이미 있었다면 자동으로 되돌리지 못하고 '원래 내용은 안전 사본에 있어요' 라고 알림). 접두어를 모르는 키는 못 막습니다.
- **운영자께 여쭐 것(급하지 않음, 이번 병합과 별개)**: ① 연결한 폴더를 네트워크 경로(NAS)로 쓰는 사용자의 복원 거절은 **유지를 추천**합니다(개인 PC 의 로컬 폴더가 전제이고 조작된 백업이 남의 서버를 가리키면 로그인 정보가 새는 길이 있음) — 그런 사용자를 지원해야 하면 '경고 후 진행' 같은 별도 결정이 필요합니다 ② (선택) 보관함 파일 크기 상한을 정할지 ③ (선택) 블로그 쪽 정본의 키 모양 목록이 넓어졌다면 그 판을 가져온 뒤 겹침 확인.
