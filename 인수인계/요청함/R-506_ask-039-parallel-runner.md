# 확인 요청 039 — 검사 시간 제한을 안 넘기게 (결정은 한 가지)

> 이 글은 **질문**입니다. 이슈 양식 '[답변] AI 확인 요청에 답하기' 에 **대상번호 039**(`39` 처럼 써도 됩니다)와 고른 보기(1·2)를 적어 주세요. **답이 없으면 2(보류)** 입니다. 승인하셔도 이 요청은 **구현을 마무리해 독립 검증을 받고 병합 부탁을 보내는 것**까지이고, 병합은 운영자님만 합니다.

## 쉽게 말해
- 블로그에 변경이 올라올 때마다 도는 자동 검사(guardrails)는 파이썬 3.10 칸과 3.12 칸이 **각각 10분 안에 끝나야** 합니다(그보다 길면 GitHub 가 취소). 지금은 시험을 한 줄로 차례차례 돌려서 시간이 **러너 운에 따라 크게 흔들리고**, 오늘 제한에 걸려 **취소된 검사가 세번**이었습니다. 취소는 '실패' 가 아니라서 main 의 알림이 울리지 않아 조용히 지나갑니다(병합완료 알림에 사유를 적어 알렸습니다).
- 이 요청은 **시험을 하나도 지우거나 건너뛰지 않고** 시험을 여러 프로세스로 나눠 돌려 시간을 줄이는 변경입니다.

## 측정 결과 (운영자님이 승인하신 측정 6회 + 시제품 재측정)
| 칸 | 지금 방식(직렬) — 변경 없는 main 끝, 6회 | 병렬 시제품 — 진짜 검사 5회(모두 초록) |
|---|---|---|
| 파이썬 3.10 칸 단위 테스트 | 304–527초(중앙 347초) | 126–256초(중앙 144초) |
| 파이썬 3.12 칸 단위 테스트 | 253–511초(중앙 437초) | 124–235초(중앙 185초) |
| 10분(600초) 제한까지 남은 여유 | 칸 전체 기준 최소 **51초**(3.10 칸 549초) — 여유 60초 미만인 칸이 20개 중 4개 | 칸 전체 기준 최소 **약 320초** |
- 칸 시간의 중앙 96% 가 단위 테스트이고 설치(3–8초)·검증(4–8초)·actionlint(0–1초)·러너 대기(1–3초)는 합쳐 10–20초입니다. 칸 제한에 걸린 측정은 없었지만 오늘 **실제 변경 검사 세 건이 제한에 걸려 취소**됐습니다([M114] 첫 검사 3.10 칸·[M116] 병합 뒤 main 검사·[M117] 병합 뒤 main 검사 3.10 칸).
- 러너마다 속도가 다른 까닭이 보입니다: 진단 가지가 읽은 러너 CPU 가 **AMD EPYC 7763 이면 3.10 칸 단위 테스트가 약 530초, Intel Xeon 6975P-C 이면 약 340초**였습니다(같은 코드·같은 푸시). 어느 CPU 를 받을지는 GitHub 가 정해서 직렬로는 운에 달렸습니다.

- 시간의 95% 가 **단위 테스트**이고 설치·검증은 합쳐 10–20초입니다. pip 캐시를 켜거나 중복 설치를 없애도 얻는 것은 5초 안쪽이라 **캐시·중복 설치는 이득이 없습니다**(설치 3–9초, 칸마다 한 번만).
- 같은 푸시(11-24 15:30)의 3.10 칸이 한 러너에서 304초, 다른 러너에서 567초가 나올 만큼 **러너마다 속도가 달라서**(약 1.9배) 직렬로는 10분 제한에 늘 아슬아슬합니다.
- 이미 한 것: [M118] 이 시험 코드의 중복 계산을 걷어 약 8–9% 줄였습니다(시험 수·단언 그대로).

## 제안 — 병렬 시험 실행기 (안 A)
한 job 안에서 시험 모듈을 **네 프로세스로 나눠** 돌립니다(러너 CPU 4개). 처음에 모든 시험의 이름을 모아 두었다가 **실제로 돈 시험과 정확히 견주어 하나라도 빠지면 시험이 전부 통과했어도 빨강으로 끝냅니다**(조용히 건너뛰는 일이 없게). 진짜 검사 시제품 결과: 읽은 5번(17:22·19:09·19:35·20:46·21:30) 모두 초록, 3.10 칸 단위 테스트 126–256초(중앙 144)·3.12 칸 124–235초(중앙 185) — 지금 방식 중앙값의 약 40%(3.10)·42%(3.12).

**바뀌는 곳 다섯**(되돌릴 곳도 같은 다섯):
1. `.github/workflows/guardrails.yml` 의 '단위 테스트' 단계 `run:` **한 줄**(`python -m unittest discover -s tests -v` → `python scripts/run_unit_parallel.py --weights tests/unit_test_weights.json`). 권한·시크릿·트리거·`timeout-minutes`·`concurrency`·칸 이름·다른 단계는 그대로.
2. 새 파일 셋: 실행기 `scripts/run_unit_parallel.py`(표준 라이브러리만)·모듈별 예상 초 표 `tests/unit_test_weights.json`·실행기 시험 `tests/test_run_unit_parallel.py`.
3. 기존 시험 둘(강화·허용 항목 추가뿐): `tests/test_guardrails_precheck.py`(단위 테스트 줄을 못박은 단언)·`tests/test_publish_paths.py`(쓰기 길 허용 목록에 실행기 한 항목 — 허용 목록을 넓히는 변경입니다).
4. 문서 몇 줄(`docs/ENGINEERING_GUIDE.md`·`docs/AGENT_RUNBOOK.md`·`docs/PUBLISH_PATHS.md`·결함 대장).
5. 실행기 시험의 `ContractTest`(워크플로 줄이 실행기를 부르는지 단언).

**독립 검증(구현자와 다른 AI 둘) 결과와 반영**: 안전·시험 검증 둘 모두 **'실행기 코드 자체는 안전, 고칠 것 있음'(필수 2씩·권고 합 13)** 이었습니다 — 필수는 코드 결함이 아니라 ① 승인 요청에 쓸 설명 문장(되돌릴 곳이 넷이 아니라 다섯, 시간 이득 예측이 실제와 다름) ② 시험의 구멍 둘(대조 문제만 있고 자식이 모두 통과한 실행의 종료 코드를 지키는 시험이 없음·모으는 범위 기본값을 지키는 시험이 없음)이고 권고에는 모듈 단위 건너뜀이 보고에서 사라지는 틈이 있었습니다. 이 요청의 문장은 그 지적을 반영해 고쳐 썼고, **구현은 지금 새 구현자가 시험을 31개 더해 마무리하는 중이며 끝나면 독립 검증을 다시 받습니다**(승인하셔도 병합 부탁은 그 재검증 뒤입니다)

**위험과 한계**: 실행기가 새 필수 부품이라 버그가 있으면 검사 전체가 빨개집니다(실행기 시험 77개가 같은 검사 안에서 함께 돌고, 실행기가 처음 모은 시험과 실제로 돈 시험을 견주는 장치를 변이 시험으로 확인했습니다). 병렬이라 시험끼리 부딪히는 곳이 있는지는 정적 조사와 전체 실행(이 PC 에서 시험 10,540개 = 10,540)·진짜 검사 다섯번으로 확인했고 실패는 없었습니다. 러너 CPU 가 2개로 줄면 이득이 절반이 됩니다(기본값이 자동으로 줄어듭니다). 새 PC·러너에서 처음 한 번은 로그가 묶음 단위로 나옵니다(맨 끝의 실패 목록에서 찾습니다).

**되돌리기**: 위 다섯 곳을 되돌립니다(워크플로 줄을 옛 줄로 바꾸면 `ContractTest` 가 빨개지므로 그 시험도 함께 되돌려야 합니다).

## 대안 (이 요청에서는 승인받지 않음 — 원하시면 내용 칸에 적어 주세요)
- **칸 제한을 15분으로 늘리기**(워크플로 한 줄): 가장 작은 변경이지만 시간은 그대로이고 느려지는 것이 가려질 수 있습니다.
- **job 을 둘로 나누기**: 효과는 비슷하지만 칸 이름이 바뀌어 알림·문서·시험이 연쇄로 바뀝니다. 병렬 실행기 위에 나중에 얹을 수 있습니다.
- **main 검사가 다음 푸시에 취소되지 않게**(`cancel-in-progress` 한 줄) 등 안전 강화는 별도 묶음으로 따로 여쭙겠습니다.

## 운영자님 몫
병합 한 번(병합 부탁이 나간 뒤). 그 밖의 설정·시크릿은 없습니다.
