# 병합 요청 M124 — 앱 2차 안전 감사 지적 처리 B (앱, T2)

> **병합 방식**: 지금은 AI 병합 기능이 **꺼져 있어** 운영자께서 직접 병합해 주세요. (`M124 승인` 이라고 답하셔도 아직 AI 가 병합하지 않습니다.) 이 요청은 앱 저장소 `chanceblog-desktop` 의 것이고, PR 제목 맨 앞이 `[M124]` 인 것 하나만 병합합니다. 검사는 이미 끝나 초록입니다. 급하지 않습니다(보통).

## 1. 무엇을 바꾸는지
앱 2차 독립 감사(AS-S2)의 권고-2·5·6·7·8 처리입니다. **`.github/` 의 워크플로 파일은 한 글자도 안 바꿨고** `vendor/` 내용·의존성·`capabilities.py` 스위치·`service/external.py` 도 0줄입니다.
① **주제 엔진 백업이 링크·정션을 따라가지 않음(권고-2)**: 가장 낡은 백업 이름 자리에 정션이 놓이면 다음 백업이 그것을 '낡은 백업' 으로 보고 그 목적지(살아 있는 데이터 폴더일 수 있음)의 앱 이름 파일 넷을 지우던 길이 있었습니다(감사 탐침을 시험으로 재현). 이제 백업 목록·정리·만들 때의 임시 이름 자리·읽을 백업 폴더와 파일·복원의 임시 이름 모두 같은 링크 기준(전체 백업이 쓰는 것과 같은 기준)을 씁니다. 링크 판정은 새 잎 모듈 `fslink.py` 한 곳에 있습니다.
② **복원은 구조 검사를 먼저, 한도는 받은 보관함에만(권고-5)**: `topics restore` 가 20만 행 내용 질의를 구조 검사보다 먼저 돌리던 것을 구조 먼저로 바꾸고(감사 탐침: 2.4초 → 0.03초에 '앱이 만들지 않는 구조' 로 거절), 받은 보관함을 읽는 연결에만 시간 상한 60초·길이 한도·읽기 전 크기 상한(보관함 512MiB·목록 1MiB)을 겁니다(새 모듈 `topicdb/limits.py`). 지금 데이터를 점검하는 길에는 걸리지 않습니다.
③ **vendor 총 요약값 고정(권고-6)**: 앱에 들어 있는 검사 규칙 폴더(`vendor/`)를 파일과 목록을 같이 고쳐도 알아채지 못하던 틈을 줄이려고, 폴더 전체의 요약값을 소스(`vendor_pin.py` 의 `PINNED_DIGEST`)에 고정하고 앱 시작·자가 점검(`--selftest` 의 `vendor_core`)·`scripts/sync_core.py --check` 가 같은 값으로 견줍니다. `sync_core.py` 가 vendor 를 새로 가져올 때는 고정값 줄도 같은 길로 다시 씁니다.
④ **시험**: `ci.yml`·`package.yml` 을 승인된 구조와 액션 세 쌍에 글자 그대로 견주는 시험(워크플로 파일 자체는 안 바꿈)·윈도 장치 이름(예약 이름) 표 시험·잎 모듈 못박기 시험·새 시험 모듈 다섯.
⑤ 문서: 결정 D-690–D-696·안전·문제 해결·구조·포장 문서와 CHANGELOG.

## 2. 왜 필요한지
백업 정리가 엉뚱한 폴더의 파일을 지울 수 있는 길은 데이터 보존 원칙의 가장 큰 위험이었고(같은 사용자 권한이 필요한 길이라 지금까지 잃은 데이터는 없습니다), vendor 폴더는 블로그 저장소의 규칙 파일을 글자 하나 바꾸지 않고 가져온 것이어야 하는데 그 일치를 소스가 지키지 못했습니다.

## 3. 사용자가 체감하는 변화
- **설치본은 앱을 열 때 vendor 폴더가 소스에 고정된 값과 다르면 열리지 않고 안내가 뜹니다**(개발 중 소스로 실행할 때는 느슨). vendor 를 새로 가져오는 일(`sync_core.py`)을 한 뒤에는 고정값도 함께 바뀌므로 그 변경이 한 병합에 같이 들어가야 합니다.
- 주제 엔진 백업 폴더 안에 링크·정션이 있으면 '다른 곳을 가리키는 링크' 라는 이유로 백업을 읽지 않고 복원을 멈춥니다. 그 밖의 화면·기능은 그대로입니다.

## 4. 위험과 기존 기능에 미치는 영향
- **알려 둔 한계**: ① 하드 링크로 이어진 백업 파일은 아직 걸러지지 않아 복원이 오래 멈출 수 있습니다(독립 확인이 직접 재현 — 데이터 손실은 없고 같은 사용자 쓰기 권한이 필요) ② 받은 보관함 한도가 '구조는 정상인 거대 백업' 에는 느슨합니다(512MiB 상한) ③ 백업 폴더(`backups/topic_engine`) 자신이 링크이면 조용히 '백업 없음' 으로 다루어 백업이 쌓이고 `restore --latest` 가 틀린 말을 합니다(작은 틈) ④ vendor 총 요약값은 자기참조의 높이를 한 단 올린 것 — vendor/·`VENDOR.json`·`vendor_pin.py` 셋을 모두 고친 변경은 여전히 통과하므로 사람이 검토해야 합니다(완전한 해결은 원본 저장소와 대조하는 검사, 별도 T3) ⑤ 전체 백업의 받은 보관함 연결에는 아직 같은 한도가 없습니다 ⑥ 이 PC 에서 설치 파일 빌드·`--selftest` 열두 항목·ubuntu 칸은 못 돌렸고 앱 검사(CI)가 돌립니다. 위 ①–③ 과 독립 확인이 남긴 시험 보강 권고는 후속 갈래 하나로 묶어 고치고 다시 독립 확인을 받습니다.
- **운영자께 여쭐 것(급하지 않음, 이번 병합과 별개)**: ① CI 에 `VENDOR.json` 의 `ref` 로 원본 저장소 다섯 파일의 해시를 대조하는 단계(새 외부 접속)·CODEOWNERS 로 `.github/`·`vendor/`·`vendor_pin.py`·`capabilities.py`·`requirements*`·`models.lock.json` 의 운영자 검토 필수·의존성 해시 잠금·저장소 설정 점검을 T3 묶음으로 올릴지 — **추천: 지금 묶음 뒤에 한 묶음으로** ② 병합 뒤 새 설치 파일을 만들어 `--selftest` 열두 항목(특히 `vendor_core` 의 새 엄격 검사)과 OneDrive 같은 동기화 폴더에 풀어도 열리는지 운영자 시험지에 넣을지 — **추천: 넣기** ③ 전체 백업의 받은 보관함 연결에도 같은 한도를 걸지 — **추천: 후속에서 같이**.
