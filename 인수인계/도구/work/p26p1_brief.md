## 만들 것 (모두 새 파일, 각 모듈에 시험)
패키지 `src/chanceblog_desktop/topics/`(`__init__.py` 는 설명만). 의존: 표준 라이브러리와 `content.status`(채널 키)·`content.candidates`(검증 헬퍼)·`errors`·`check.claims` 정도만. **`service`·`ui`·`publish`·`render` 를 가져오지 않고, 파일·네트워크·시계·난수·`sqlite3`·`subprocess`·`ctypes` 를 쓰지 않는다**(날짜는 인자, 결정적). 위반을 AST 로 훑는 시험을 둔다.

1. **`channels.py` — 채널 프로필**
   - 채널 이름은 코드의 5키(`github_pages`·`blogger_en`·`blogger_ko`·`naver_a`·`naver_b`)를 **그대로** 쓴다(`PLATFORMS` 에서 가져와 같은지 시험). 전략 문서의 `blogger_a`(한글)·`blogger_b`(영문) 는 **입력 별칭**만(`CHANNEL_ALIAS`, `canonical(name)` — 모르는 이름은 거절). 저장값은 항상 코드 키.
   - `ChannelProfile`(frozen dataclass, 검증): `key`·`display_name`(한국어 표시명)·`language`(`ko`/`en`)·`enabled`·`evergreen_pct`+`realtime_pct`(합 100)·`weights`(6항목 이름 → 정수, 합 100: 채널 적합도 `channel_fit`·작성 가능성 `feasibility`·차별성 `differentiation`·시기 `timing`·근거 `evidence`·수익화 `monetization`)·`top_n`(5)·`cluster_cap`(2)·`subheading_min`(4)·`trend_use`(`primary`/`supporting`/`reference`/`none`)·`dup_cutoffs`(40·60·75 퍼센트)·`topic_clusters`(이 채널이 다루는 주제 묶음 이름들, 영문 소문자-하이픈 식별자)·`expansion_directions`(채널별 확장 방향 낱말들)·`monetization_focus`(태그들). 모르는 칸·합 불일치·범위 밖은 `CONTENT_INVALID` 같은 기존 오류 체계(`errors`) 로 거절하고 쉬운 한국어 안내.
   - **기본값(전략의 값 — 숫자만 데이터로, 설명은 네 말로)**: 가중치 순서 `channel_fit/feasibility/differentiation/timing/evidence/monetization` — `github_pages` 20/15/15/15/25/10 · `blogger_ko` 25/25/20/10/10/10 · `blogger_en` 30/25/20/5/10/10 · `naver_a` 25/15/10/15/10/25 · `naver_b` 25/15/10/20/10/20. 지속형/실시간 — pages 40/60 · blogger_ko 85/15 · blogger_en 90/10 · naver_a 70/30 · naver_b 50/50. `top_n` 5·`cluster_cap` 2·`subheading_min` 4·중복 기준 40/60/75. 활성(`enabled`): **`naver_a`·`naver_b` 만 True**, 나머지 3채널은 False(프로필만 있고 꺼 둠). `trend_use`: `naver_a`·`naver_b` primary · `github_pages` supporting · `blogger_ko` reference · `blogger_en` none. `language`: `blogger_en` 만 en. 표시명: GitHub Pages·Blogger 한글·Blogger 영문·네이버 A·네이버 B(`service/format.py` 의 `PLATFORM_KO` 와 맞춰 보되 import 하지 않는다 — 시험이 둘이 같은지 비교).
   - 공통 상수(채널 무관): 후보 발생 경로 비율 `SOURCE_MIX`(seed 30·follow_up 20·seasonal 20·realtime 15·sponsor 15), Seed 유형별 최초 생성/보관 상한 `PER_SEED`(general 3→2·priority 5→3·seasonal 5→3·realtime 5→3·sponsorable 5→3), 점수 구간 경계 `GRADE_CUTOFFS`(80·65·50), 보류 일수 90, 후속 후보 글당 3, 채널 간 재사용 최대 2. **전략 문서의 해석이 갈리는 곳(예: 협찬 15% 가 네이버 둘에만 적용되는지)은 코드에 넣지 말고 보고서의 '내가 결정할 것'에 적는다.**
   - `default_profiles()`(5개, 불변)·`profiles_from_dict(data)`(엄격: `schema`·정확한 칸·모르는 칸 거절)·`profiles_to_dict`(왕복 시험). 사람이 고치는 JSON 파일을 읽고 쓰는 것은 P3 — 여기서는 dict 변환까지만(`schema=1`).
2. **`model.py` — 엔진 후보(`TopicCandidate`)**: 전략 §29 의 25칸(`candidate_id`(내부 uuid hex)·`display_id`(표시용 `candidate-YYYYMMDD-NNN` 꼴은 **표시 함수**로만 — 접두 선택 규칙과 충돌하므로 저장 id 로 쓰지 않는다)·`source_topic_id`·`seed_id`·`source_type`·`candidate_type`·`channel`·`language`·`topic`·`primary_keyword`·`secondary_keywords`·`search_intent`·`content_type`·`topic_cluster`·`topic_angle`·`target_reader`·`scores`·`trend_status`·`data_status`·`duplicate_status`·`similar_post_ids`·`monetization_tags`·`selection_reasons`·`processing_errors`(선정 이유와 처리 오류를 **분리**)·`status`(작업 흐름: 기존 `Candidate` 의 NEW·REVIEW·SELECTED·HOLD·REJECTED 와 같은 값 집합 — 새로 만들지 말고 `content.candidates` 의 상수를 가져온다)·`grade`(점수에서 파생: recommended·general·hold·excluded — 저장하지 않고 계산하는 속성으로 두거나 저장하면 점수와 일치 검증)·`created_at`·`review_expires_at`)과 `schema=1` 엄격 JSON 왕복(`from_dict` 는 모르는 칸·필수 누락 거절, 한 줄 규칙·마크업·보이지 않는 글자 거절, **결과 약속 표현 금지는 `content.candidates.forbidden_claim` 을 그대로 써서** topic·keyword·sub·reasons 전부에). 열거형 값(`source_type`: seed·follow_up·seasonal·realtime·sponsor / `candidate_type`: evergreen·seasonal·realtime·follow_up·sponsor_prep / `trend_status`: rising·flat·falling·insufficient·unavailable / `data_status`: sufficient·partial·insufficient·unavailable / `duplicate_status`: different_topic·similar_elements·different_angle_needed·duplicate_or_update / `search_intent`·`content_type` 은 전략 예시 값(selection_guide·buying_guide …)을 포함한 **닫힌 목록** — 목록은 네가 정하고 `content_type`→기존 `POST_TYPES` 5종 대응표 `to_post_type()` 을 둔다(예: buying_guide→비교형/제품·서비스 소개형 — 대응은 네 판단이고 보고서에 적는다)).
   - **상대 관심도 전용 칸**: `relative_interest`(값 0~100 정수 또는 None, 기준 기간·비교군 이름·조회일, `trend_status` 와 함께) — 이름·키·라벨 어디에도 `검색량`·`volume`·`demand` 같은 말이 없고 실제 횟수 칸이 **없다**(시험으로 못박는다: 필드 이름·JSON 키·`LABELS` 를 훑음). 기존 `search_demand` 와는 아무 관계도 만들지 않는다.
   - 채널은 후보 한 건에 **하나**(`channel`), 채널 간 재사용은 `similar_post_ids`·같은 `source_topic_id` 로 표현(후보 여러 건) — 최대 2채널 규칙은 P2 이후이니 여기서는 `source_topic_id` 칸까지만.
3. **`score.py` — 6항목 점수와 구간**: `Factors`(6항목 각각 0~100 또는 None = 평가 불가). `score(profile, factors)` → `Score(parts, final, used_weight, missing)`: **없는 항목은 0점이 아니라 빼고 남은 가중치를 100 으로 다시 나눈다**(`suggest_score.combine` 과 같은 규칙 — 같은 함수를 쓰거나 같은 결과를 시험으로 확인), 모두 없으면 `final=None`(구간 `insufficient`). 반올림 규칙(예: 반올림 정수, 경계 79.5→80)은 한 곳에 정하고 문서·시험에 못박는다. `grade(final)`: 80+ recommended·65~79 general·50~64 hold·0~49 excluded·None insufficient. `timing_score(calendar, trend_status)` — 캘린더 상태(`due`·`out_of_range`·`unknown`)와 관심도 상태로 시기 항목 점수를 정하는 **작은 표**(전략 §11.3: 시점 도달+상승 → 높음, 도달+데이터 부족 → 중간(0 아님·`data_status=insufficient` 로 표시), 도달+하락 → 낮음, 범위 밖+급상승 → 실시간 후보 표시, API 사용 불가 → 캘린더만으로) — 구체 점수는 **네가 정한 초기값**이고 보고서에 표로 적는다(운영자가 나중에 조정). `trend_use=none` 인 채널(Blogger 영문)은 관심도를 아예 안 쓴다(시험).
4. **`select.py` — 채널별 우수 후보**: `top_view(candidates, profile)` → `TopView(items, shortfall)`: ① recommended(80+)를 점수 내림차순(동점은 `candidate_id`/생성 순으로 **결정적**)으로 훑으며 같은 `topic_cluster` 가 `cluster_cap`(2)을 넘으면 건너뜀 ② `top_n`(5)에 못 미치면 general(65~79)에서 같은 규칙으로 보충 ③ **hold(50~64)·excluded 로 강제 보충하지 않는다** ④ 그래도 모자라면 `shortfall = 모자란 수`(구조값 — 한국어 안내문은 화면 층에서 만든다) ⑤ `candidates` 가 다른 채널 것이면 거른다(`profile.key`) ⑥ 비활성 채널(`enabled=False`)이면 빈 결과와 이유. 입력은 변경하지 않는다(순수).
5. **시험**(새 모듈 4~5개 `tests/test_topics_*.py`, 빠른 순수 시험 120개 이상, `subprocess`·네트워크·실제 시계 없음): 기본값 못박기(위 숫자 전부 — 문서 값과 코드가 같다는 손으로 쓴 기댓값), 가중치 합 100·비율 합 100, 별칭, 엄격성(모르는 칸·합 불일치), JSON 왕복, 점수 재정규화(항목 하나·둘·전부 없음)·경계(49/50·64/65·79/80)·단조성(점수를 올리면 최종이 안 내려감 — 결정적 반복 루프), 구간, `timing_score` 표 전 경로, 상위 N 선택(묶음 상한·보충·강제 보충 금지·부족 수·동점·빈 입력·다른 채널·비활성), 입력 불변, '금지 import·파일/네트워크/시계/난수 없음' AST 시험, 상대 관심도 칸 이름 시험, 결과 약속 표현 거절, 기존 `Candidate` 로의 투영은 **하지 않는다**(P3).
