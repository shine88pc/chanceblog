운영자(2026-10-28 채팅): "메세지 요청건 말고는 직접 github 접속 해서 알람 뜨는 것들은 무시하도록 할게. 그렇게 앞으로도 작업하는걸로 기록해줘".

**Why:** 비개발자가 공용 PC 에서 일하므로 GitHub 화면의 알림(저장소 첫 화면 'Compare & pull request' 배너, 빨간 Actions 실행·검사, 이슈·메일·앱 알림)을 해석·대응할 여유가 없다. 같은 날 임시 알림 브랜치(`ai/claude/tg-note-58`)의 PR #60 이 의도 없이 만들어진 것처럼 오동작 위험도 있다. 감시·판단은 AI, 사람은 요청 메시지만 처리한다는 분업이다.

**How to apply:** ① 운영자가 해야 하는 일(PR 병합·Actions 실행·설정·시크릿·결정)은 반드시 `인수인계/요청함/R-nnn_*.md` 를 `ai/claude/**` 로 push 해 텔레그램으로 보낸다 — GitHub 화면의 신호가 사용자 행동을 이끌 것이라 기대하지 않는다 ② 요청 메시지는 그 자체로 충분하게(한 줄 요약·단계·버튼 링크) 쓴다 ③ 실패·이상은 AI 가 감시(`scratch/watch_light.py`·`git ls-remote`·공개 웹)해서 처리하고, 운영자 조치가 꼭 필요할 때만 텔레그램으로 요청한다 ④ 임시 브랜치·임시 PR(`tg-note-*`·PR #60)은 운영자 조치를 요구하지 않는다 — 쓴 뒤 AI 가 지운다(병합 안 된 것만; 브랜치를 지우면 그 PR 도 닫힌다) ⑤ 채팅·문서에서 "PR 을 닫아 주세요" 같은 GitHub 화면 조치를 사용자 몫으로 쓰지 않는다(필요하면 요청 메시지로) ⑥ 저장소 기록: `AGENTS.md`(막히면 요청함)·`docs/SESSION_START.md`·`인수인계/작업내용.md` §1 "운영자 대응 방식"·`인수인계/운영자_요청함_사용법.md` 7장 — 묶음 3(PR #57) 병합 전에는 브랜치 `ai/claude/bundle3` 에 있다. **이슈 처리 절차(2026-10-28 첫 실사용 #61·#62·#63 으로 확인)**: 새 소유자 이슈는 감시기가 알리면 공개 웹 페이지(`curl` → `scratch/read_issue_comments.py`)로 본문과 봇 접수 코멘트를 읽는다(AI 는 이슈에 코멘트·닫기를 못 한다). `[답변]`: 번호·답을 읽고 이어서 진행(이슈 #62 `R-005` '했어요' → 사용자가 한 일의 결과를 확인). `[요청]`: 새 일 — 진행 범위가 '논의·준비까지만'이면 조사·선택지만 번호 있는 `decision` 요청(R-nnn)으로 보내고, T3(광고 표면 `index.html`·`_config.yml` 등)는 `[답변]` 승인 뒤에만 만든다. 구현이 끝나면 PR 하나로 묶어(대기 중인 작은 개선 포함) `merge` 요청으로 병합을 부탁한다(운영자가 PR 을 만들 수 있게 `compare/main...<브랜치>?quick_pull=1&title=…&body=…` 링크를 요청 본문에 둔다). 응답 번호는 소문자(`r-002`)로 올 수 있다(D-81 로 PR #66 에 병합돼 지금은 `r-015` 도 접수된다). **운영자 반응 관찰(2026-10-29)**: 새벽(05:33)에도 답하고, 병합 부탁은 **PR 을 만들고 27초 만에 검사를 기다리지 않고 병합**한다 → 병합 전 검증·시험·독립 검증을 푸시 전에 끝내고, 병합 직후 main 의 검사·배포를 AI 가 확인한다.
