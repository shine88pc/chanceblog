내장 브라우저 패널이 `github.com` 을 "조직 정책으로 차단"한다(처음 몇 시간은 열렸고 로그인도 됐었음). 이미 열려 있던 탭의 자바스크립트로 우회하지 않는다. `gh` CLI 는 없고 자격증명 저장소의 토큰을 꺼내 쓰지 않는다. `bind_pr`·워크플로 실행 클릭은 자동 분류기가 막는다. AI 는 `ai/claude/*` 브랜치로 `git push` 만 한다(main 직접 push 금지).

**Why:** 사용자도 이 PC 에서는 패널 로그인을 못 한다(2026-10-27). 그래서 PR 만들기·병합은 운영자가 한다.

**How to apply:** PR 은 **묶음 1개**로 만들어 `WORKLOG.md` 맨 위 항목 충돌을 미리 풀고(`scratchpad/scratch/resolve_worklog_keep_both.py`) 전체 시험을 돌린 뒤 푸시, 제목·본문이 채워진 `compare/main...<브랜치>?quick_pull=1&title=…&body=…` 링크(`scratch/make_batch_guide.py` 방식)를 드린다. 운영자용 단계별 안내는 저장소 `인수인계/PR_병합_방법.md`. 첫 묶음(PR #47, 2026-10-27 13:27 병합)이 이 방식의 첫 사례. 운영자가 구현 브랜치로 PR 을 **먼저** 만들어 두는 일이 잦다(#48~#52, #53/#54, #57 — F1 #56 은 검증 전에 병합됨): 그때는 새 PR 을 만들지 말고 같은 브랜치에 main 을 합친 통합 커밋(충돌 해결·시험 통과)을 **독립 검증이 끝난 뒤에** fast-forward push 한다 — 그 전에는 main 과 충돌 표시가 떠서 운영자가 병합할 수 없는 것이 자연스러운 안전장치다(채팅으로 "병합 가능" 알리기 전엔 병합 말라고 한 줄 안내, 2026-10-27 #57 사례). 병합 감지는 [[merge-check-self]]. **2026-10-28 사례(#57 묶음 3 + G1)**: 독립 검증(D·H 각 2회·G1 2회)·전체 시험(4003개)·충돌 정리를 끝낸 뒤 15:56 에 PR 브랜치로 fast-forward 푸시 → 텔레그램 R-001~R-003 → 16:50 재안내 → 16:58 운영자 병합(squash) → AI 가 공개 웹으로 배포·글 제목·새 워크플로 확인(`scratch/post_merge_check.py`; 이슈 새로 만들기 화면은 로그인이 필요해 못 본다). PR 의 병합 가능 여부는 REST 한 번(`pulls/57` 의 `mergeable_state: clean`)으로 확인했다(공개 PR 화면은 병합 상자를 서버에서 그리지 않는다). 새 기능을 PR 에 넣을 때는 별도 PR 을 만들게 하지 말고 이미 열린 PR 에 합쳐 병합 한 번으로 끝내는 편이 운영자 수고가 적다([[operator-telegram-requests-only]]). **아직 PR 이 없는 브랜치의 병합 부탁(2026-10-28 R-007 사례)**: 운영자는 요청 본문의 'PR 만들기' 링크 대신 저장소 첫 화면의 'Compare & pull request' 배너(가장 최근에 푸시한 브랜치)로 PR 을 만들었고, 그 브랜치가 하필 PR 브랜치가 아니라 **요청 파일만 든 브랜치**(PR #66)였다. 대응: 그 요청 브랜치에 PR 브랜치를 합쳐 푸시해 PR #66 이 모든 변경을 싣게 하고(`git merge --no-ff`), 정정 요청 R-010(`pr: 66`)을 보냈다. **다음부터는 요청 파일 커밋을 PR 브랜치의 마지막 커밋으로 얹어(R-001·bundle3 방식) 한 브랜치만 푸시한다** — 배너로 만든 PR 이 어느 쪽이든 같고 'PR 열기' 버튼도 `pr:` 로 걸 수 있다. 요청 브랜치를 따로 푸시하면 나중에 푸시한 쪽이 배너에 뜬다. **정정 요청도 같은 함정에 걸렸다(R-010, 2026-10-28 22:09)**: 정정을 또 새 브랜치로 푸시했더니 운영자가 그 브랜치로 PR #67 을 만들어 병합했다(요청 파일 한 장뿐, PR #66 은 열린 채 남음). 병합 부탁·정정은 **열려 있는 PR 의 브랜치 맨 위 커밋**으로 얹는다(R-012 가 그렇게 나감: 새 배너 없음, 'PR 열기'=#66). 운영자는 '병합 부탁' 메시지를 받으면 요청 브랜치의 배너·'요청 열기' 화면에서 PR 을 만들어 병합하는 경향이 있다고 보고 설계한다. **광고 표면(`index.html`·`_config.yml` 등) PR 의 squash 함정(D-82, 2026-10-28 PR #66)**: squash 병합은 PR 의 개별 커밋 메시지를 버리고 **PR 제목**만 남기므로 `Ad-Surface-Approved:` 가 사라져 main 푸시의 가드레일(AD-1)이 빨강이 된다(사이트·배포는 정상). 그러니 광고 표면 PR 은 **커밋 한 개**로 올리고 **제목 앞쪽 70자 안**에 `Ad-Surface-Approved: …` 를 넣는다(배너로 만든 PR 의 제목 = 커밋 제목이고, GitHub 은 긴 제목을 70자 근처에서 잘라 나머지를 PR 본문으로 보내며 squash 는 잘린 제목만 쓴다; 커밋이 여러 개면 브랜치 이름이 제목이 되니 한 개로). 2026-10-29 PR #72·#74(제목 66자·광고 표면 아님)가 이 방식으로 배너 PR → 27초 만에 병합됐고 main 검사가 초록이었다. 요청 파일도 같은 커밋에 넣어 푸시는 브랜치 하나만. 임시 빌드 점검 브랜치(`tmp-jekyll-build-check-*`)는 요청 파일이 없는 커밋으로 만들어 요청 알림이 새지 않게 하고, 점검 뒤 지운 다음 실제 브랜치를 마지막에 푸시한다(배너는 가장 최근 푸시가 뜸). 이 PC 의 회사 프록시는 `telegram.org`·`web.telegram.org` 도 "비업무용 사이트"로 막으니(`t.me`·`api.telegram.org` 는 열림) 텔레그램 알림은 휴대폰 기준.
