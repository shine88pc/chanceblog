- 시스템 `core.autocrlf=true`다. **끄지 않는다**(끄면 모든 파일이 수정됨으로 보인다). 작업 사본이 CRLF인 건 정상.
- 커밋 작성자는 저장소 로컬 설정으로만 둔다(강병수 / shine88pc@gmail.com). 전역 설정은 건드리지 않는다.
- 한글 커밋 메시지는 UTF-8 파일로 쓰고 `git commit -F`로 넘긴다(셸 인자로 넘기면 인코딩이 깨질 수 있다).
- push는 GCM(Git Credential Manager)의 브라우저 로그인 자격 증명을 쓴다. 비대화형 push가 인증 오류로 막히면 사용자의 터미널 탭에서 한 번 로그인해야 한다. 이 환경에서는 `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=false`로 대기를 막는다.
- Python 검증: `python scripts/validate_repo.py`, `python -m unittest discover -s tests`(개별 모듈 지정은 `_bootstrap` 임포트 오류가 난다). actionlint·vermin·pyflakes는 scratchpad의 venv에 설치해 쓴다.
- 이 저장소 시작 시 환경 정보가 "git 저장소 아님"으로 나오는 것은 세션 시작 시점의 값이다. 실제로는 `git status`로 확인한다.
- `KCY` 폴더 자체는 git 저장소가 아니다(작업요청서 md 3개, `작업진행확인.txt`, 보고서). `gh` CLI도 없다. 2026-10-25 구현을 시작하면서 `KCY/chanceblog`에 clone을 만들었다(위 항목).
- 작업 clone은 `KCY/chanceblog`(2026-10-25 생성). PR은 `gh`가 없어 브라우저로 만든다: `https://github.com/shine88pc/chanceblog/compare/main...<브랜치>?expand=1` → `read_page`로 제목·본문 textbox ref → `form_input` → "Create pull request". 이 세션의 ccd_pr 도구는 저장소를 바인딩하지 못하므로(체크아웃 origin 불일치) PR·CI 상태는 브라우저의 PR 페이지로 본다. Actions 수동 실행은 뷰포트를 1000x1000으로 에뮬레이션한 뒤 Run workflow 대화상자(브랜치 선택, 입력 로드 대기)로 한다.
- PR 병합(브라우저): PR 페이지를 맨 아래까지 스크롤해야 병합 상자가 로드된다 → 드롭다운에서 "Squash and merge" 선택 → 확인 버튼. 이슈·PR 댓글은 JS로 `#new_comment_field`(PR) 또는 `textarea[placeholder="Use Markdown to format your comment"]`(이슈)에 네이티브 setter로 값을 넣고 input·change·keyup을 보낸 뒤 버튼을 눌러야 활성화된다. 2026-10-25 PR #11을 squash로 병합(ddf0a22), 병합한 브랜치는 지우지 않는다.
- PR 만들기(브라우저) 함정: "Create pull request"를 JS로 누르면 PR이 만들어졌는데도 화면에 "There was an error creating your PullRequest."가 뜨고 주소가 안 바뀔 수 있다. 다시 누르면 같은 오류만 난다 — 먼저 `fetch('/shine88pc/chanceblog/pull/<다음 번호>')`로 이미 만들어졌는지 확인한다(2026-10-26 #31·#32 모두 그랬다). 이슈·PR 댓글·본문 수정은 JS 네이티브 setter로 되고, PR 본문 편집은 첫 `.js-comment-container`의 `summary.timeline-comment-action` → Edit → `textarea[name="pull_request[body]"]` → "Update comment".
- 스쿼시 병합된 PR 위에 쌓아 둔 브랜치(예: #30 위의 #31)는 아래 PR이 스쿼시로 병합되면 원래 커밋과 이력이 달라 `git merge origin/main`에서 여러 파일이 충돌한다. `git diff --stat <아래 PR 끝 커밋> origin/main`이 봇 커밋(글·history.json)만 보이면 main 트리 = 아래 PR 트리이므로 충돌 파일은 `git checkout --ours`로 풀고 `git diff --cached --stat origin/main`이 그 PR의 변경만 보이는지 확인한다. 쌓지 않고 병합을 기다리는 쪽이 더 단순하다.
- 공개 GitHub REST API는 인증 없이 curl로 읽힌다(IP당 시간당 60회, 검증 에이전트와 공유하니 아껴 쓴다). 구현·검증 에이전트는 `scratchpad/`에 각자 clone을 만들고 push는 GCM으로 된다.
- Actions 로그는 GitHub 로그인 없이는 안 보인다. 사용자에게 내장 브라우저에 로그인 화면(`preview_start`의 `url`로 연다. `navigate`는 한 번 막힌 적 있음)을 띄워 주면 사용자가 직접 로그인한다. 로그인 후 읽기: 로그인된 페이지에서 `fetch`로 `/shine88pc/chanceblog/actions/runs/<run>/job/<apiJobId>` HTML의 `jobs/<내부id>/steps` → `steps?change_id=0` JSON의 `log_url`(전체 SHA 필요)을 GET. 요청이 많으면 javascript_tool이 45초에 끊기므로 백그라운드 async로 돌리고 나눠서 읽는다.
- 2026-10-26 추가: ① 자동 모드 분류기가 브라우저 JS로 `Run workflow`(workflow_dispatch)를 누르는 것을 "Production Deploy"로 거부했다 — Actions 수동 실행은 AI가 하지 않고 사용자 몫으로 남긴다(우회 금지). ② Bash 도구는 명령 안의 `\`를 `\`로 한 번 풀어서 넘기는 것 같다 — 정규식·이스케이프가 든 패치 스크립트는 Write 도구로 파일을 만들거나 파이썬에서 `chr(92)`를 쓴다(JS 도구는 `\n`·`\"`가 그대로 간다). ③ 전경 `sleep`은 막혀 있다 — 기다릴 때는 `run_in_background: true`로 `until grep -q ... ; do sleep 3; done` 를 돌린다. `cd A && (cmd) & cd B && ...` 는 `&`가 `cd A && (cmd)` 전체를 백그라운드로 보내 뒤의 `cd B`가 원래 cwd 기준이 된다(목록을 나눠 쓴다). ④ Actions 단계 로그는 로그인된 페이지에서 `/shine88pc/chanceblog/commit/<전체 40자 SHA>/checks/<jobId>/logs/<단계>`를 fetch(짧은 SHA는 500). ⑤ 내 feature 브랜치를 rebase 했을 때는 `git push --force-with-lease=<브랜치>:<옛 SHA>`가 통과한다(main은 force push 금지). ⑥ 스쿼시 병합 위에 쌓은 브랜치는 `git rebase --onto origin/main <옛 쌓은 기반 SHA> <브랜치>`로 옮기고 충돌은 문서뿐이면 양쪽을 합친다. 컴페어 화면에서 PR 제목이 100자에서 잘려 들어오니 제목 입력칸을 직접 채운다.

- 2026-11-03 밤 추가(블로그 문서 변경): 문서·시험만 더하는 변경도 CI 는 전체 시험(`discover -s tests -v`)을 돌린다 — 기존 시험이 문서를 훑는다(예: `test_workflow_names` 의 '접두사 뗀 옛 워크플로 이름을 백틱·따옴표·굵게로 인용하면 실패', `test_agent_docs`·`test_ops_inbox_drafts` 의 문서 표 대조). 푸시 전에 **전체 시험을 한 번** 돌린다: `python -X utf8 S\run_blog_suite.py <작업폴더> 4 <결과폴더>`(약 8~10분, 에이전트가 도는 중이면 더). Write 도구가 만든 새 파일은 **LF**, 기존 작업 사본 파일은 **CRLF**(autocrlf) — 기존 파일을 파이썬으로 고칠 땐 `\r\n` 으로 쪼개서 CRLF 를 유지하고, 새 파일 변이 도구는 `\n` 로 쪼갠다(`grep -c $'\r'` 는 이 PC 에서 CR 을 못 센다 — 파이썬 `bytes.count` 로 확인).
