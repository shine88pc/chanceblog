# 운영자 요청함 사용법 (공용 PC·휴대폰용)

> AI 가 GitHub 화면을 쓸 수 없어 막혔을 때(PR 병합·Actions 실행·설정·시크릿)나 결정이 필요할 때, **텔레그램으로 부탁**하고 운영자가 GitHub 의 **New issue 메뉴**에서 **답하는 방법**입니다. GitHub 에 로그인된 브라우저 하나면 됩니다(휴대폰 브라우저도 됩니다). 마지막 갱신: 2026-10-28, 갱신자: Claude
>
> **한 줄 요약**: 텔레그램 메시지 → **[답하기]** 버튼 → 양식에서 **메시지 맨 위의 `R-번호`** 와 **답**을 고르고 올리기 → 접수 확인(이슈 코멘트 + 텔레그램).
>
> 이 저장소는 **공개**입니다. 이슈에 쓴 글은 누구나 읽을 수 있으니 **비밀번호·토큰·키 값은 절대 쓰지 마세요**(5장).

## 1. 한눈에

| 순서 | 일어나는 일 | 누가 |
|------|------------|------|
| 1 | AI 가 부탁할 일을 요청 파일(`인수인계/요청함/R-001_….md`)로 올립니다 | AI |
| 2 | 휴대폰 텔레그램에 `🔔 AI 요청 R-001 · 병합 부탁` 같은 메시지가 옵니다 | 자동 |
| 3 | 메시지 아래 버튼: **요청 열기**(자세한 설명) · **PR 열기**(있을 때) · **답하기** · **사용법**(이 문서) | 나 |
| 4 | **답하기** → 양식 `AI 요청에 답하기(결정·확인)` → 요청 번호와 답을 고르고 **Submit new issue** | 나 |
| 5 | 잠시 뒤(보통 1~2분, GitHub 가 늦으면 더) 이슈에 `접수했습니다` 코멘트, 텔레그램에 `✅ 답변 접수 R-001 → 승인(이슈 #N)` | 자동 |
| 6 | AI 세션이 이슈를 읽고 이어서 진행하고, 끝나면 텔레그램으로 알립니다. AI 가 꺼져 있으면 다음 세션에서 처리합니다 | AI |

**내가 먼저 AI 에게 일을 맡길 때**는 같은 New issue 메뉴의 `AI 에게 새 일 맡기기(작업 요청)` 양식을 씁니다(3-1 — 접수와 진행 범위만 정하고 T3 승인은 아닙니다).

## 2. 텔레그램 메시지 읽는 법

맨 위 줄이 `🔔 AI 요청 R-001 · 병합 부탁` 모양입니다. **`R-001` 이 요청 번호**(답할 때 씁니다)이고 `·` 뒤가 종류입니다. 급하면 `🚨 급함` 이 붙습니다. 그 아래가 제목, 요약, (있으면) `관련 PR: #번호` 입니다. 자세한 설명과 단계별 방법은 **요청 열기** 버튼으로 엽니다.

| 종류 | 뜻 | 내가 할 일 | 답 |
|------|----|-----------|----|
| 병합 부탁 | PR 을 병합해 달라는 부탁 | **PR 열기** → [`PR_병합_방법.md`](./PR_병합_방법.md) 대로 병합 | `했어요` (문제가 있었으면 `문제` + 메모) |
| 실행 부탁 | Actions 에서 어떤 워크플로를 한 번 눌러 달라는 부탁 | **요청 열기**의 단계대로 실행(4장 C) | `했어요` + 메모에 결과 문구 |
| 확인 부탁 | 화면에서 무언가를 보고 알려 달라는 부탁 | **요청 열기**의 단계대로 확인 | `했어요` 또는 `문제` + 메모에 보이는 문구 |
| 결정 부탁 | 둘 이상 중에서 고르거나 승인·거절해 달라는 부탁 | 요약을 읽고 결정 | `승인`·`거절`·`보류` (선택지가 있으면 선택 칸에 글자) |
| 알림 | 읽기만 하면 되는 소식(예: 처리 결과) | 읽기 | 답하지 않아도 됩니다 |

`결정 부탁`·`확인 부탁` 메시지에는 `답하는 법: 아래 [답하기] → 양식에서 R-001 선택` 한 줄이 붙습니다. 버튼은 최대 4개이고 누르면 GitHub 가 열립니다. 텔레그램 메시지에는 **공개되는 내용**(제목·요약)만 담습니다. 일반 텔레그램 채팅은 종단간 암호화가 아닙니다.

## 3. 답하는 법 (그림 없이 단계만)

1. 텔레그램 메시지에서 맨 위의 **`R-` 번호**를 확인합니다(예: `R-001`).
2. 메시지 아래 **답하기** 버튼을 누릅니다. (버튼이 없으면 저장소 → **Issues** → **New issue**.)
3. 목록에서 **`AI 요청에 답하기(결정·확인)`** 의 **Get started** 를 누릅니다.
4. 칸을 채웁니다.
   - **요청 번호**: `R-001` 처럼 텔레그램의 번호 그대로.
   - **답변**: 아래 다섯 개 중 하나. **미리 `보류` 가 선택돼 있어도 반드시 직접 고르세요**(그대로 올리면 `보류` — 나중에 다시 물어 달라는 뜻입니다).
     - `보류 — 나중에 다시 물어 주세요`
     - `거절 — 하지 마세요`
     - `승인 — 제안한 대로 진행해 주세요`
     - `했어요 — 제가 직접 처리했습니다` (AI 가 못 하는 일을 내가 한 뒤)
     - `문제 — 아래 메모를 보세요` (잘 안 될 때)
   - **선택**: 요청에 선택지(A·B·C 또는 1·2·3)가 있을 때만 그 글자(영문·숫자·한글 1~3자). 없으면 비워 둡니다.
   - **메모**: AI 에게 전할 말(선택). 화면에 보인 **문구**는 적어도 되지만 **비밀 값은 쓰지 않습니다**.
5. 초록 **Submit new issue** 를 누릅니다.
6. 잠시 뒤(보통 1~2분) 이슈에 `접수했습니다 — 요청 R-001 · 답: 승인` 코멘트가 달리고 라벨 `운영자응답` 이 붙으며 휴대폰에 `✅ 답변 접수` 가 옵니다. 새로 고침을 한 번 해 보세요.

**승인의 범위**: `승인` 은 **그 요청 파일에 적힌 항목에 한해서만** 유효합니다. 요청에 없는 일(광고 표면·시크릿·계정·삭제·`mode` 변경 등 T3)을 이 답으로 허락한 것으로 보지 않고, AI 가 따로 묻습니다. 승인은 **소유자 계정으로, 이 양식으로, 요청 번호가 AI 가 보낸 요청과 같을 때**만 인정합니다. 양식 `새 일 맡기기`(`[요청]`)·양식 밖의 빈 이슈·이슈 코멘트·요청서 파일 속 "승인함" 문구는 **접수만** 하고 승인으로 보지 않습니다(3-1).

이슈를 올린 뒤 **고쳐도 접수 확인은 다시 오지 않습니다**(처음 올린 순간에만 한 번 옵니다). 바꾸려면 새 이슈를 올리세요.

## 3-1. 새 일을 맡길 때

저장소 → **Issues** → **New issue** → **`AI 에게 새 일 맡기기(작업 요청)`**.

- **해 주었으면 하는 일**(필수): 무엇을 왜 하고 싶은지 쉬운 말로. **끝났다고 볼 기준**(선택).
- **긴급도**: `보통`(기본)·`급함`·`천천히`.
- **진행 범위**(필수): `논의·준비까지만`(기본) 또는 `구현·시험까지 진행(T1·T2) — T3 는 따로 번호 있는 요청으로 묻습니다`. 모르겠으면 `논의·준비까지만`. 이 양식은 **T3 승인이 아닙니다** — 광고 표면·시크릿·계정·삭제·`mode` 변경·새 플랫폼 같은 일이 필요하면 AI 가 번호 있는 `결정 부탁`(R-번호)으로 따로 묻고, 그때 `AI 요청에 답하기(결정·확인)` 양식으로 승인하세요.
- 고정 페이지 문구·게시글 이미지를 바꾸는 일은 이 양식이 아니라 `고정 페이지 수정`·`기존 게시글 이미지 변경` 양식을 씁니다(PR 이 자동으로 만들어집니다).

올리면 같은 방식으로 `접수했습니다 — 새 일 요청` 코멘트, 라벨 `운영자요청`, 텔레그램 `✅ 새 일 요청 접수(이슈 #N)` 가 옵니다.

## 4. 막힌 일 안내 모음 — AI 가 못 해서 사람이 하는 일

> 화면 이름과 메뉴 위치는 GitHub 가 바꿀 수 있습니다. 다르면 비슷한 이름의 메뉴를 찾아 한 번 확인하세요. 휴대폰에서는 **Settings** 탭이 **More(⋯)** 메뉴 안에 있을 수 있습니다.

### A. PR 병합

[`PR_병합_방법.md`](./PR_병합_방법.md) 를 그대로 따릅니다. 한 줄로: PR 화면 → 아래 검사가 모두 초록 체크 → 초록 **Squash and merge** → **Confirm squash and merge**. 빨간 ✗ 나 `This branch has conflicts` 가 보이면 **병합하지 말고** 답변 `문제` 로 알려 주세요. 병합한 뒤 **Delete branch 는 누르지 않습니다.**

### B. 열려 있는 PR 닫기 (병합하지 말아야 할 PR)

PR 화면 맨 아래 **Close pull request** 를 누릅니다(삭제가 아니라 **닫기**입니다). 브랜치는 그대로 둡니다. 닫은 PR 은 다시 열 수 있습니다.

### C. Actions 에서 `인증 점검만 실행`

Blogger 시크릿을 등록한 직후에 값이 맞는지 확인합니다. 글은 만들지 않고 아무것도 쓰지 않습니다.

1. 저장소 → **Actions** → 왼쪽 목록에서 워크플로를 고릅니다.
   - 영문 블로그: **`[Blogger 영문] 글 자동 작성`**, 한글 블로그: **`[Blogger 한글] 글 자동 작성`**.
   - 두 워크플로로 나뉘기 전(묶음 병합 전)에는 목록에 **`[Blogger] 글 자동 작성(초안함 업로드)`** 하나만 있습니다. 그것을 고르세요.
2. 오른쪽의 **Run workflow** 를 누릅니다. **Use workflow from** 은 **main** 으로 둡니다.
3. 입력 중 **`인증 점검만 실행`**(입력 이름 `auth_check`)을 **체크**합니다. 다른 입력은 건드리지 않습니다. 초록 **Run workflow**.
4. 잠시 뒤 새로 생긴 실행을 열고 **Summary** 의 `결과` 를 읽습니다.
   - **`AUTH_CHECK_OK`**: 토큰 갱신·블로그 조회·블로그 주소 일치가 모두 맞다는 뜻입니다. 끝입니다.
   - **`AUTH_CHECK_FAILED`** + 분류:
     - `auth_expired`(인증 만료): 토큰이 만료·폐기됐습니다. 토큰을 새로 발급해 시크릿을 바꿔야 합니다.
     - `auth_failed`(권한·접근 불가): 블로그 ID·클라이언트 ID·클라이언트 시크릿 값이나 Blogger API 사용 설정·계정 권한이 틀렸습니다.
     - `blog_mismatch`(블로그 주소 불일치): 인증은 됐지만 `…_BLOG_ID` 가 가리키는 블로그가 레지스트리의 블로그와 다릅니다(엉뚱한 블로그에 쓰지 않으려고 멈춘 것).
     - `network`·`bad_response`·`api_error`·`unexpected`: 일시 오류일 수 있습니다. 잠시 뒤 한 번 더 눌러 보세요.
   - **`SECRETS_MISSING`**(시크릿 없음): 게시용 시크릿 4종 중 빠진 이름이 요약에 나옵니다.
   - 요약에 **`시크릿 값에 보이지 않는 문자가 섞여 있어 지우고 썼습니다`** 가 보이면: 이름만 알려 주는 안내입니다. 코드가 지우고 썼으니 지금은 동작하지만, 그 이름의 시크릿을 **원본에서 바로 복사해 다시 등록**하는 것이 안전합니다(E).
5. 결과는 **값이 아니라 화면에 보이는 문구**(예: `AUTH_CHECK_FAILED … auth_failed`)만 답변 `했어요`/`문제` 의 메모에 적습니다.

### D. 저장소 설정 한 줄 바꾸기

예: AI 가 만든 PR 이 자동으로 열리지 않을 때 `Allow GitHub Actions to create and approve pull requests` 를 켭니다.

1. 저장소 → **Settings**(휴대폰은 **More(⋯)** 안) → 왼쪽 **Actions** → **General**.
2. 아래쪽 **Workflow permissions** 에서 **Allow GitHub Actions to create and approve pull requests** 를 체크합니다.
3. **Save**. (읽기 권한을 기본으로 두는 선택은 바꾸지 않습니다.)

### E. 시크릿 등록·교체 (이름은 정확히, 값은 원본에서 바로)

1. 저장소 → **Settings** → **Secrets and variables** → **Actions** → **New repository secret**(이미 있으면 그 이름을 눌러 **Update**).
2. **Name** 칸에 이름을 **글자 그대로** 씁니다. 이름은 AI 가 요청 파일에서 알려 줍니다. 쓰이는 이름은 영문 Blogger `BLOGGER_BLOG_ID`·`BLOGGER_CLIENT_ID`·`BLOGGER_CLIENT_SECRET`·`BLOGGER_REFRESH_TOKEN`, 한글 Blogger `BLOGGER_KO_*` 네 개, 공통 `GEMINI_API_KEY`, 텔레그램 `TELEGRAM_BOT_TOKEN`·`TELEGRAM_CHAT_ID` 입니다.
3. **Secret** 칸에 값을 **원본(발급받은 화면)에서 바로 복사해 붙여넣습니다.** 앞뒤 공백·따옴표를 넣지 않습니다.
4. **Add secret**. 저장한 뒤에는 값을 다시 볼 수 없습니다. 틀렸으면 같은 이름으로 다시 저장하면 됩니다.

> **채팅 앱·메모 앱에서 복사하면 눈에 안 보이는 글자(폭 없는 공백 등)가 섞일 수 있습니다.** 섞이면 인증이 이유를 알려 주지 않고 어긋납니다(이슈 #58). 이제 코드가 그런 글자를 지우고 쓰며 어느 시크릿이었는지 **이름만** `인증 점검만 실행` 요약과 로그로 알려 주지만, **원본에서 바로 복사하는 쪽이 가장 안전**합니다. 값을 채팅·이슈·문서에 쓰지 마세요. AI 에게 값을 입력해 달라고 하지 마세요(AI 는 값을 모릅니다).

## 5. 하지 말 것

- **비밀번호·토큰·키 값을 이슈·메모·채팅·스크린샷에 쓰기.** 썼다면 이미 노출된 것으로 보고 바로 폐기·재발급하세요(보안 문서 [`docs/SECURITY_GUARDRAILS.md`](../docs/SECURITY_GUARDRAILS.md) §4 A).
- **요청 번호 없이 답하기.** 어느 요청에 대한 답인지 알 수 없어 AI 가 승인으로 받지 않습니다. 번호를 모르면 텔레그램 메시지 맨 위를 다시 보세요.
- 다른 사람의 계정으로 답하기. **소유자 계정으로 올린 이슈만** 접수됩니다.
- 양식을 쓰지 않고 빈 이슈로 답하기. 접수 코멘트가 오지 않고, 승인으로 보지 않습니다.
- 내가 올리지 않았는데 텔레그램에 `✅ 답변 접수` 가 오거나 내가 열지 않은 `[답변]`·`[요청]` 이슈가 보이면 **바로 알리세요** — 다른 사람이 내 계정을 쓴 것일 수 있습니다.
- 병합한 브랜치의 **Delete branch** 누르기.

## 6. 안 올 때

| 증상 | 확인할 것 |
|------|----------|
| **텔레그램이 안 온다** | ① 저장소 **Settings** → **Secrets and variables** → **Actions** 에 `TELEGRAM_BOT_TOKEN`·`TELEGRAM_CHAT_ID` 둘 다 있는지 ② Actions → **`[공통] 텔레그램 알림 시험`** → **Run workflow**(main) → 휴대폰에 `✅ 알림 연결 확인` 이 오는지(안 오면 그 실행의 Summary 분류를 보세요, [`.github/editorial/TELEGRAM_SETUP.md`](../.github/editorial/TELEGRAM_SETUP.md) 2-4) ③ AI 가 그 브랜치를 push 했는지: Actions → **`[공통] AI 요청 텔레그램 알림`** 에 실행이 있고 로그에 `AI 요청 알림: R-… 을 알렸습니다` 가 있는지 |
| 요청 파일을 올렸는데 안 온다 | 파일 이름이 `R-001_영문-소문자.md` 모양이고 앞머리(`id`·`kind`·`title`·`summary`)가 맞아야 합니다. 맞지 않으면 그 실행 로그에 이유가 한 줄 남습니다. 브랜치 이름은 `ai/claude/` 로 시작하고 그 뒤는 영문·숫자·`.`·`_`·`-` 조각(`/` 로 이어도 됨)이어야 합니다(한글·`+`·`@`·`#` 이 들어가면 경고만 남기고 보내지 않습니다). 이미 다른 브랜치에도 있는 파일은 다시 알리지 않으며 로그에 `다른 브랜치에도 있어 알리지 않은 요청 파일: R-001` 한 줄이 남습니다 — 같은 요청 커밋을 든 브랜치 둘을 한꺼번에 올리면 아무도 알리지 못할 수 있어 AI 는 하나씩 올립니다 |
| **접수 코멘트가 안 달린다** | ① 이슈를 **소유자 계정**으로 올렸는지 ② 제목이 **`[답변] `** 또는 **`[요청] `** 으로 시작하는지(양식이 자동으로 채웁니다 — 지우지 마세요) ③ Actions → **`[공통] 운영자 응답 접수`** 에 그 이슈 번호의 실행이 있는지. `양식 모양이 달라 처리하지 못했습니다` 코멘트가 달렸다면 안내대로 양식으로 다시 올리세요 |
| **New issue 목록에 두 양식이 안 보인다 / 접수가 전혀 안 돈다** | 이슈 양식과 접수 워크플로는 **`main` 에 병합된 뒤에야** 생깁니다(GitHub 가 기본 브랜치의 것만 씁니다). 병합 전에는 텔레그램의 **요청 열기**로 요청을 읽기만 하세요. 이 기능을 병합해 달라는 `병합 부탁` 이라면 [`PR_병합_방법.md`](./PR_병합_방법.md) 대로 병합한 뒤(양식이 생깁니다) 답하세요 |
| 코멘트는 달렸는데 텔레그램 `✅ 답변 접수` 가 안 온다 | 위 텔레그램 점검과 같습니다. 코멘트가 이미 있으면 같은 이슈를 다시 실행해도 텔레그램은 다시 가지 않습니다 |
| 잘못된 번호로 올렸다 | 새 이슈를 올리세요(번호는 텔레그램 메시지 맨 위의 `R-` 번호). 접수 코멘트의 `요청 번호 R-007 은 AI 가 자기가 보낸 요청과 대조해 처리합니다(…)` 한 줄은 그 요청 파일이 이 저장소 기본 브랜치에 없을 때 붙는 사실 안내입니다 — 요청 파일은 병합 전 브랜치에 있는 것이 보통이라 정상일 수 있고 접수는 됩니다. 번호가 틀렸는지는 AI 가 자기가 보낸 요청과 대조해서 압니다 |

## 7. 알아 둘 것

- 알림은 **보조**입니다. 텔레그램이 멈추거나 GitHub 가 늦으면 늦거나 안 올 수 있고, 원본은 항상 저장소의 요청 파일과 이슈입니다.
- 이 저장소의 이슈·요청 파일은 **모두 공개**입니다. 수익·방문 수치·개인정보는 쓰지 않습니다.
- 받는 사람은 **운영자 본인 한 명**이고 텔레그램으로 **답을 받지는 않습니다**(답은 이슈 양식으로만).
- AI 는 GitHub 이슈에 **쓸 수 없습니다**. 접수 코멘트는 자동 워크플로가 답니다. 이슈를 닫는 일은 운영자의 몫입니다.
