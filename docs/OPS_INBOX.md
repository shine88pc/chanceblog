# 확인 필요 모음 (운영 인박스)

> 대상: 운영자(비개발자)와 이 저장소에서 일하는 AI. 구조는 [`ARCHITECTURE.md`](./ARCHITECTURE.md), 보안은 [`SECURITY_GUARDRAILS.md`](./SECURITY_GUARDRAILS.md), 코드·검증은 [`ENGINEERING_GUIDE.md`](./ENGINEERING_GUIDE.md).

## 1. 한눈에

운영자가 **직접 해야 할 일**과 **확인하면 좋은 일**이 Actions 곳곳(실행 요약, 노란 경고 주석, PR, 워치독 이슈)에 흩어져 있으면, 하나씩 열어 보기 전에는 알 수 없습니다. 예를 들어 Blogger 실행이 초록이어도 게시 시크릿이 없으면 글은 저장소 초안으로만 쌓이는데, 이 사실은 실행 요약을 열어야만 보입니다.

그래서 한곳에 모읍니다.

- **GitHub 이슈 1개** — 제목 `[운영] 확인 필요 모음`, 라벨 `ops-inbox`. 이 이슈 하나만 보면 됩니다.
- **같은 내용의 Actions 실행 요약** — 워크플로 `[공통] 확인 필요 모음`(파일 `ops-inbox.yml`)의 실행 화면 아래쪽.
- **새로 해야 할 일이 생기면 이슈에 코멘트(@멘션)** — 그 코멘트가 휴대폰 알림이 됩니다.
- **초안 현황 구역(2026-10-27)** — 본문 맨 위의 표: 채널(Chance·Blogger 영문·Blogger 한글·티스토리·네이버 …)마다 발행을 기다리는 초안이 몇 건인지, 가장 오래된 것이 며칠째인지, 가장 최근 초안이 무엇인지(링크)를 보여 줍니다. 초안은 라벨 `초안`이 붙은 이슈·PR입니다(§3-1).
- **정리 규칙(2026-11-11)** — 이미 처리된 항목(병합된 PR·병합된 가지의 승인 대기)과 일부러 멈춘 상태(계획된 일시정지·정지 전 초안)는 '지금 해야 할 일'에서 빠지고 참고·확인으로 내려갑니다. 운영자의 결정(유지·폐기 후 닫기 권장·무시)은 정책 파일에서 읽습니다(§10).

2시간 간격으로 예약돼 자동으로 갱신되고(GitHub가 예약 실행을 늦추거나 건너뛰는 일이 잦아 실제로는 보통 3~6시간 간격입니다), 초안 이슈가 열리거나 닫히거나 라벨이 바뀔 때, 초안 PR 이 닫히거나 라벨이 바뀔 때도 곧바로 한 번 더 갱신되며(사람이 한 조작에 한합니다 — §5의 11), 손으로 실행할 수도 있습니다(§2). 해소된 항목은 저절로 사라집니다.

## 2. 운영자가 하는 일

### 처음 한 번

1. 휴대폰에 **GitHub 앱**을 설치하고 로그인해서 알림(푸시)을 켭니다. 앱이 없으면 GitHub 웹의 알림 설정(Settings → Notifications)에서 이메일 알림을 켜도 됩니다. 메뉴 이름은 앱 버전에 따라 다를 수 있으니, "멘션 받았을 때·내가 담당자일 때" 알림이 켜져 있으면 됩니다.
2. 저장소 → **Actions** → 왼쪽 목록의 **[공통] 확인 필요 모음** → **Run workflow**. 첫 실행이면 `연습 실행`을 체크해 결과만 봅니다(이슈를 만들지 않음). 실행 요약이 마음에 들면 한 번 더 `연습 실행`을 체크하지 않고 실행합니다 — 이슈가 생기고, 해야 할 일이 있으면 코멘트로 알림이 옵니다.
3. 이후로는 **이슈 하나만** 보면 됩니다(저장소 → Issues → `[운영] 확인 필요 모음`, 또는 알림을 눌러서).

### 이슈를 읽는 법

본문은 맨 위의 **초안 현황** 표(§3-1)와 세 구역입니다. 항목마다 **▶ 바로 하기** 링크(그 자리로 바로 이동)와 한 줄 안내가 붙어 있습니다.

| 구역 | 뜻 | 알림 |
|------|----|------|
| **지금 해야 할 일** (`action`) | 사람이 손대야 풀립니다: PR 병합·충돌·검사 실패, 실패한 워크플로, 아직 처리되지 않은 승인 대기, 일시정지 해제(의도된 정지가 아닐 때)·재개 승인, 시크릿 등록 | 새로 생기면 코멘트(@멘션)로 알림 |
| **확인하면 좋은 것** (`check`) | 급하지 않거나 사실 확인이 필요한 것: 워치독 경고, 초록 실행의 경고 문구, 오래 열린 PR, 조회 실패, 폐기 후 닫기 권장·철 지난·정지 전 초안(§10) | 알림 없음 |
| **참고** (`info`) | 현황과 진행 중인 것: 블로그별 마지막 글, 검사 진행 중인 PR, 정지된 블로그, 플랫폼 안내성 경고, 계획된 일시정지·유지로 정한 초안(§10) | 알림 없음 |

항목이 있는 구역만 보입니다. '참고' 구역에는 블로그별 마지막 글 현황이 늘 들어 있어서 "지금 확인할 것이 없습니다"라는 문구는 항목이 정말 하나도 없을 때만 나오고 실제로는 거의 보이지 않습니다. 할 일이 없다는 신호는 맨 위 요약의 **지금 해야 할 일 0건**입니다.

### 자주 묻는 일

| 질문 | 답 |
|------|----|
| 이슈를 닫으면? | **닫힌 채로 있습니다.** 닫은 뒤에 *새로 해야 할 일(action)*이 생겼을 때만 코멘트를 쓰고 이슈를 다시 엽니다. 그 밖의 변화(참고·확인 항목)는 닫힌 채로 본문만 고쳐 둡니다(본문 수정은 알림이 없습니다). 계속 조용히 두고 싶으면 닫은 채로 두세요 |
| 이슈를 지우거나 제목을 바꾸면? | 라벨 `ops-inbox`가 붙어 있으면 제목을 바꿔도 같은 이슈로 봅니다. 라벨을 지우고 제목도 바꾸거나 이슈를 지우면 다음 실행이 새로 만듭니다. 지우지 말고 닫아 두는 쪽을 권합니다 |
| 본문을 직접 고치면? | 내용이 바뀌는 다음 갱신 때 덮어씁니다. 내용이 그대로면 건드리지 않습니다 |
| 지금 당장 갱신하려면? | Actions → `[공통] 확인 필요 모음` → Run workflow |
| 끄려면? | Actions → `[공통] 확인 필요 모음` → 오른쪽 위 `⋯` → **Disable workflow**. 이슈는 남으니 닫으면 됩니다 |
| 주기를 바꾸려면? | `.github/workflows/ops-inbox.yml`의 `cron`을 바꾸는 변경(T2)을 AI에게 요청하세요. 현재 값은 2시간 간격 예약(매 짝수 시 40분, UTC)이고 실제 갱신은 보통 3~6시간 간격 |
| 같은 알림이 또 오나요? | 같은 항목은 한 번만 알립니다. 해소됐다가 다시 생기면 새 항목으로 다시 알립니다 |
| 초안을 발행했거나 쓰지 않기로 했으면? | 그 초안 이슈를 **닫으세요**(닫기 = 발행 완료). 쓰지 않을 글은 라벨 `폐기`를 붙이거나 닫으세요. 닫힌 초안과 `폐기` 라벨이 붙은 초안은 초안 현황 표와 해야 할 일에서 빠집니다. 사람이 휴대폰에서 닫거나 라벨을 바꾸면 거의 바로 반영되고(예상: 1~2분 안 — 실제 지연은 병합 뒤 관측 전), 그렇지 않으면 다음 예약 때입니다 |
| 초안만 모아 보려면(휴대폰)? | 초안 현황 구역 맨 아래의 **휴대폰에서 거르기** 링크를 누르세요(대기 초안 전체, 채널별). 직접 하려면 이슈 목록 검색창에 `is:open label:초안 label:"채널:티스토리"`를 넣습니다. Chance 승인 흐름의 PR 초안은 Pull requests 탭의 같은 검색입니다 |
| 초안이 생겼는데 표가 안 바뀌어요 | 자동 초안(티스토리·네이버 패키지, Chance 승인 PR)은 저장소 기본 토큰이 만들어 GitHub 규칙상 이 워크플로를 시작시키지 못합니다(§5의 11). Chance 승인 PR 은 PR 을 연 실행이 이 워크플로를 바로 불러 주므로(R2) 보통 1–2분 안에 반영됩니다(예상 — 병합 뒤 관측 전). 부르기가 실패했거나 티스토리·네이버 초안이면 다음 예약 때 반영됩니다. 급하면 Run workflow |
| Actions 목록에 `이슈 변경(초안만 점검)`·`PR 변경(초안만 점검)` 실행이 자꾸 생겨요 | 모든 이슈·PR의 열림·닫힘·라벨 변경이 이 워크플로를 시작합니다. `초안` 라벨이 없으면 job이 **건너뜀(Skipped)**으로 바로 끝납니다. 정상입니다(러너를 쓰지 않습니다) |

## 3. 무엇을 모으나 (규칙표)

판단은 [`pipeline/inbox.py`](../pipeline/inbox.py)(순수 함수), 읽기·쓰기는 [`scripts/ops_inbox.py`](../scripts/ops_inbox.py)가 합니다. 아래는 현재 기본값이며 근거와 한계를 함께 적습니다.

| 소스 | 조건 | 수준 | 근거·한계 |
|------|------|------|-----------|
| 워치독 이슈 | 열린 `[Watchdog] …` 이슈. 본문의 심각도가 critical이면 | action | 워치독이 이미 판단한 결과를 한곳에 모읍니다. 작성자가 `github-actions` 봇이거나 소유자·멤버·협업자인 이슈만 믿습니다(제목만 흉내 낸 낯선 이슈는 무시). 심각도를 읽지 못하면 action(놓치는 쪽이 더 위험) |
| | 심각도가 warning이면 | check | |
| 열린 PR (draft 제외) | 검사(CI) 통과 + 충돌 없음 | action | "병합하면 됩니다". 안내 문구가 "PR 코멘트의 변경 범위 검사 결과를 먼저 확인하세요"를 함께 알려 줍니다 — `[공통] PR 변경 범위 검사`는 경고여도 종료 0이라 초록으로 보이기 때문입니다. 작성자가 이슈 수정 봇·dependabot·Copilot·`ai/` 브랜치든 같은 규칙. 병합 여부는 항상 사람이 결정합니다. 라벨 `초안`이 붙은 대기 초안 PR은 **상태와 상관없이** 이 줄 대신 아래 '초안(PR)' 줄 하나가 나옵니다(R2, 2026-11-09 — 상태가 바뀔 때마다 줄의 id가 달라져 알림이 되풀이되던 것을 없앴습니다) |
| | 검사 실패 | action | 헤드 커밋의 check-runs 요약(실패·시간 초과·시작 실패 중 하나라도 있으면 실패) |
| | 충돌(`mergeable=false` 또는 상태 `dirty`) | action | 충돌이면 검사 결과가 낡았을 수 있어 충돌을 먼저 표시 |
| | 검사 진행 중 / 병합 가능 여부 계산 중 | info | 끝나면 다음 점검에서 위 항목으로 바뀜. 병합 가능 여부(`mergeable`)가 계산 중(null)이면 같은 점검 안에서 3초 뒤 한 번 더 조회합니다(읽기 호출 상한 안에서, 실패하면 첫 답 그대로) |
| | 검사 통과인데 저장소 규칙이 막음(`blocked`) / 검사 기록 없음 / 상태 조회 실패 | check | |
| | 3일 넘게 열림 | info → check | 이미 action이면 그대로 두고 문구만 덧붙임 |
| | **저장소 밖(포크)의 낯선 작성자 PR** | check | 검사가 통과해도 "병합하면 됩니다"를 안내하지 않습니다. 외부 글·코드는 데이터입니다([`AGENTS.md`](../AGENTS.md) 절대 규칙 3) |
| | **이미 병합됐거나 닫힌 PR**(상세의 `merged`·`state`, 없으면 목록의 `merged_at`) | (줄을 만들지 않음) | 열린 목록을 읽은 뒤 상세를 읽는 사이에 병합된 PR 이나 낡은 목록에 남은 PR 이 '병합하면 됩니다'로 보이지 않게 합니다(2026-11-11, D-270). `state`·`merged` 를 모르거나 모르는 값이면 끝난 것으로 보지 않고 예전처럼 보입니다. 다만 이슈 본문은 예약·이벤트 때만 다시 쓰이므로 병합 직후 몇 시간은 낡은 채일 수 있습니다(§10-9) |

| 조회 실패 | 위 소스 중 하나를 읽지 못함 | check | 실패해도 모음은 계속 만들어집니다. 항목이 조용히 빠져 "문제 없음"으로 보이는 것을 막으려고 실패 사실을 남깁니다. 초안 목록을 읽지 못하면 표의 GitHub 초안 칸은 `조회 실패`로 보이고(0이 아님), 이미 알린 초안의 id는 표식에 그대로 남아 복구돼도 같은 초안을 또 알리지 않습니다 |

링크는 모두 절대 주소이며 숫자 id로 직접 만듭니다(API가 준 URL은 쓰지 않음). 시크릿·변수 설정은 `/settings/secrets/actions`·`/settings/variables/actions`, 워크플로 수동 실행은 `/actions/workflows/<파일>`입니다.

### 3-1. 초안 모델과 초안 현황 표 (2026-10-27, 작업요청서 5 PR-B)

**초안 1건 = GitHub 이슈 1개(티스토리·네이버 초안 패키지) 또는 PR 1개(Chance 승인 흐름)**. 초안을 만드는 쪽과 이 모음이 아래 약속을 같이 씁니다.

| 라벨 | 뜻 | 붙이는 쪽 | 색·설명(고정) |
|------|----|-----------|---------------|
| `초안` | 발행을 기다리는 초안 | 초안을 만드는 쪽 | `c2e0c6` · AI가 만든 초안으로 발행을 기다리는 글 — PR 은 병합하고, 이슈는 직접 발행하면 끝납니다 |
| `채널:<채널 라벨>` | 어느 채널의 글인가 — `채널:Chance`·`채널:Blogger 영문`·`채널:Blogger 한글`·`채널:티스토리`·`채널:네이버`(2026-10-27 한글 Blogger를 등록하면서 `채널:Blogger`를 이 둘로 나눴습니다. 저장소에 이미 만들어진 `채널:Blogger` 라벨이 있으면 쓰지 않는 채로 남습니다 — 지워도 됩니다). 글자는 `pipeline/blogs.json`의 `channel.label`과 같고, 라벨 이름은 레지스트리에서 만듭니다 | 초안을 만드는 쪽 | `bfdadc` · 초안이 속한 채널: <채널 라벨> |
| `폐기` | 쓰지 않기로 한 초안 | 운영자 | `cfd3d7` · 쓰지 않기로 한 초안 — 붙이면 발행 대기 목록에서 빠집니다 |

- **센다**: 열려 있고 · 라벨 `초안`이 있고 · 라벨 `폐기`가 없고 · 작성자가 `github-actions` 봇이거나 저장소 소유자·멤버·협업자인 이슈·PR. **닫으면 안 센다**(닫기 = 발행 완료 또는 폐기). 낯선 사람이 라벨을 흉내 낸 것은 세지 않습니다(워치독 이슈와 같은 원칙).
- **라벨 만들기**: 라벨이 저장소에 없으면 이 스크립트가 **점검 끝에**(이슈를 쓴 뒤) 만듭니다 — 휴대폰에서 라벨을 고르고 초안 목록을 거르려면 라벨이 미리 있어야 합니다. 라벨 목록을 한 번 읽어(100건) 없는 것만 만들고(한 번에 최대 10개), 실패해도 점검 결과·종료 코드에는 영향이 없습니다(로그 한 줄, 다음 점검이 이어서 만듦). 연습 실행(`INBOX_DRY_RUN`)과 토큰 없는 로컬 실행은 만들지 않습니다.
- **라벨 색·설명은 한 곳에서 읽습니다**(R2, 2026-11-09). 라벨을 만드는 코드는 셋(이 모음, Chance 승인 PR `pipeline/drafts.py`, 티스토리·네이버 초안 이슈 `pipeline/publishers/issue_package.py`)이고 예전에는 같은 이름에 서로 다른 색·설명을 가지고 있었지만(`초안`이 `d4c5f9`·`fbca04`·`c2e0c6`), 이제 셋 다 `pipeline/draft_labels.py`의 표 하나(위 표의 값)를 씁니다. 라벨은 **이미 있으면 이름만 보고 색·설명을 바꾸지 않으므로**(이미 있으면 422 로 건너뜀) 저장소에 먼저 만들어진 라벨은 그때의 색·설명을 그대로 가집니다 — 표는 새로 만드는 라벨에만 쓰입니다. 모든 채널 라벨의 색은 같습니다(`bfdadc`). 이미 있는 라벨은 바뀌지 않습니다 — 이 변경 전후로 '출력이 같다'고 말할 때 라벨 색·설명만은 예외이고(새로 만드는 라벨의 색·설명은 세 경로에서 정의상 달라졌습니다), `초안` 라벨의 설명은 이슈 초안(직접 발행하면 끝)과 PR 초안(병합하면 끝)에 모두 맞게 '끝나는 방법'을 나란히 적었습니다(R2 수정 P3).
- **제목 약속**: `[초안][<채널 라벨>] <글 제목>`(초안을 만드는 쪽의 약속). 이 모음은 앞의 `[초안]`·`[채널]` 표지를 떼고 글 제목만 보여 줍니다(표지가 없어도 동작). 제목은 외부(AI) 글이라 §6의 무력화를 거칩니다.
- **채널 라벨이 여럿이면** 글자 순으로 첫 번째만 씁니다. 레지스트리에 없는 채널 라벨의 초안은 `○○ (미등록)` 줄로, 채널 라벨이 없는 초안은 `(채널 표시 없음)` 줄로 보입니다(조용히 사라지지 않게 — 티스토리·네이버를 레지스트리에 등록하기 전에 초안이 생겨도 보입니다).

**표의 칸** — 머리 `채널 | 대기 초안 | 가장 오래된 | 최신 초안`. 줄은 레지스트리 블로그 순서(Chance → Blogger 영문 → Blogger 한글 → …)이고 대기 0이어도 유지합니다(표는 `BOARD_ROWS_MAX`=12줄까지, 넘치는 미등록 채널은 `그 밖의 채널 N개` 한 줄로 합침).

| 대기 초안 칸 | 뜻 |
|--------------|----|
| `N` | 그 채널의 대기 초안(GitHub 이슈·PR) 수. 최신 초안 칸에 번호와 제목이 든 링크(이슈는 `/issues/번호`, PR은 `/pull/번호` 주소) |
| `N+` | 열린 초안 목록이 읽는 상한(100건씩 3쪽 = 300건)에 닿아 **더 있을 수 있음** — GitHub에서 센 칸에 붙고(없으면 `0+`) 표 아래에 그 안내 줄이 붙습니다. 상한 안내(참고 항목)가 본문 길이 제한에 잘려도 표에서 보이게 하려는 것이며, '가장 오래된'도 읽은 범위 안의 값입니다 |
| `0` | 대기 없음 |
| `정지` | 레지스트리 `mode: off`인 채널. 대기 초안이 있으면 `N (정지 전 초안)` — 정지 전에 만든 초안이라 공개를 권하지 않습니다(전체 정지 `PIPELINE_PAUSE` 중에는 초안이 있는 모든 채널의 칸이 같게 보입니다. 이런 칸이 하나라도 있으면 표 아래 설명도 정지용 문구입니다. §10-4) |
| `자동 공개` | Chance(`platform: jekyll-git`)가 승인 흐름이 아닐 때 — 레지스트리 `publish_flow`가 없거나 `direct`(`pr`이면 승인 흐름이라 열린 초안 PR 수를 셉니다 — [`ARCHITECTURE.md`](./ARCHITECTURE.md) §4-4). 초안이 아니라 바로 공개됩니다 |
| `N (대략)` | Blogger 채널(영문·한글 각각): 이력(`state.history` — 영문 `blogger_history.json`·한글 `blogger_ko_history.json`)의 `status: draft_uploaded` 중 최근 14일(`DRAFT_WINDOW_DAYS`) 안의 것을 센 **대략치**. 최신 초안 칸은 마지막 업로드 시각(KST, 링크 없음). **이미 게시했는지는 Blogger 쪽 사실이라 여기서 알 수 없습니다** — 확인·게시는 Blogger 대시보드 → 글 → 초안(블로그 ID가 시크릿이라 링크는 싣지 않습니다). 이 안내 줄은 표 아래에 **정지가 아닌 Blogger 채널이 있을 때만** 붙습니다 |
| `N` (Blogger, `(대략)` 없음) | **게시 확인을 마친 값**(2026-11-02, 이슈 #89): 위 `N (대략)` 과 같은 이력 중 블로그 공개 피드에서 이미 보이는 글(운영자가 게시한 글)을 뺀 수입니다. 표 아래 안내 줄도 "공개 주소(피드)에서 아직 보이지 않는 글만 셉니다"로 바뀝니다. 올린 직후(6시간 안)의 초안도 이 표에는 셉니다(항목 규칙의 6시간 유예는 알림에만 적용) |
| `조회 실패` | 초안 목록(GitHub 채널) 또는 이력 파일(Blogger)을 읽지 못함 — 0이 아닙니다. Blogger 는 **블로그 공개 피드를 읽지 못한 때도** 같습니다. 같은 사실이 "확인하면 좋은 것"에도 있습니다 |

- **가장 오래된**은 대기 초안 중 가장 오래 열린 것의 경과 일수(24시간 단위 내림, 하루 미만은 `1일 미만`)입니다. 점검 시각을 본문에 넣지 않는다는 원칙(§4)의 **유일한 예외**: 이 칸이 하루에 한 번 바뀌므로 대기 초안이 있는 채널마다 하루 한 번 본문이 다시 쓰입니다(알림 없음, 변경이 없으면 쓰지 않는 규칙은 그대로).
- **모바일 필터 링크**는 표 아래 마지막 줄입니다: 대기 초안 전체(이슈)·전체(PR)와, GitHub에 초안이 있는 채널마다 `is:open label:초안 label:"채널:<라벨>"` 검색(주소는 퍼센트 인코딩). PR 초안이 있는 채널은 `○○ PR` 링크가 더 있습니다. 채널 라벨이 평범한 글자(영문·숫자·한글·공백·`_`·`.`·`-`, 40자 이하, 비밀 값 모양 아님)가 아니면 링크를 만들지 않습니다(주소에는 무력화를 쓸 수 없어서). 표의 줄은 남습니다.
- 표는 항목이 아니라 본문의 고정 구역입니다. 길이 제한에서는 항목보다 먼저 자리를 잡고, 표 자체가 남은 길이에 안 들어가면 "초안 현황은 길이 제한으로 줄였습니다" 한 줄로 바뀝니다(실행 요약에는 항상 통째로).

**초안을 만드는 쪽에 부탁하는 것**(작업 C·E): ① 위 라벨 셋을 붙입니다(만들기 전에 라벨을 보장해도 됩니다 — 이미 있으면 422로 끝납니다). ② 이슈·PR을 **저장소 기본 토큰(`GITHUB_TOKEN`)으로 만들면 GitHub 규칙상 이 워크플로가 시작되지 않으므로**, 만든 직후 `workflow_dispatch`로 `ops-inbox.yml`을 불러 주세요(`gh workflow run ops-inbox.yml`, 그 워크플로 권한에 `actions: write` 필요 — 다른 워크플로가 같은 이유로 `pages.yml`·`guardrails.yml`을 부릅니다). 부르지 않으면 표는 다음 예약 때(보통 3–6시간 뒤) 갱신됩니다. **Chance 승인 PR 은 이 호출을 합니다**(R2, 2026-11-09 — `pipeline/draft_flow.py` 가 PR·라벨을 만든 직후 REST 로 부릅니다. 워크플로 파일은 바꾸지 않았습니다). **티스토리·네이버 초안 이슈는 아직 호출하지 않습니다 — 켜기 전에 연결할 일입니다**([`ARCHITECTURE.md`](./ARCHITECTURE.md) §4-2-1). ③ 제목은 `[초안][채널 라벨] 글 제목`.

### Chance 승인 흐름의 초안 PR (현황판이 알아볼 값)

Chance 승인 흐름(레지스트리 `publish_flow: pr`, 지금 켜짐 — [`ARCHITECTURE.md`](./ARCHITECTURE.md) §4-4)이라 봇이 만든 초안 PR 이 열립니다. 확인 필요 모음은 라벨 `초안`(과 작성자)으로 이 PR 을 알아보고, 위 규칙표의 `초안(PR)` 행과 §3-1 의 초안 현황 표로 일반 PR 과 구별해 '내 승인을 기다리는 초안'(`초안 대기 — …` 한 줄 + @멘션 코멘트)으로 보여 줍니다. 아래는 그 PR 이 갖는 값입니다.

| 값 | 모양 |
|---|---|
| 작성자 | `github-actions[bot]` |
| head 브랜치 | `ai/draft/<YYYY-MM-DD>-s<슬롯>`(정기, 슬롯은 9·18) · `ai/draft/<YYYY-MM-DD>-m<HHMMSS>`(수동 실행). 날짜·시각은 KST |
| 제목 | `[초안][Chance] <한국어 제목> / <영어 제목>`(국문 단독이면 `[초안][Chance] <한국어 제목>`, 소독됨, 200자 이하) |
| 라벨 | `초안`, `채널:Chance` |
| 바뀐 파일 | `_posts/…` 하나(국문 단독 — 두 언어 모드면 한국어·영어 두 개)뿐. 이력(`history.json`)은 PR 에 없다 |
| 본문 체크리스트 | `- [ ] 원문과 수치·사실을 대조했다` / `- [ ] 제목·요약에 문제가 없다` / `- [ ] 병합 = 공개(사람 검토 단계)` |
| 이력 항목(`history.json`) | Chance 기존 필드에 `flow: "pr"`, `branch`(위 head 브랜치), `paths`(글 파일 — 둘, 국문 단독이면 하나)가 더해진다. 별도 원장 파일은 없다. `paths`의 글이 main 에 있으면 병합됨, 없으면 승인 대기 또는 닫혀 폐기됨 |

- **검사(CI)는 돌지 않습니다(예상).** `GITHUB_TOKEN`으로 연 PR 은 `pull_request` 워크플로를 시작시키지 않아 헤드 커밋에 check-runs 가 없습니다. 열린 PR 규칙만으로는 이를 알림 없는 `검사 결과 없음`(확인)으로 남기지만, 라벨 `초안`이 붙은 초안 PR 은 위 `초안(PR)` 행 규칙으로 `초안 대기`(해야 할 일) 한 줄과 @멘션 코멘트로 알려지고 그 PR 의 `검사 결과 없음` 줄은 만들어지지 않습니다(검사 기록이 없으면 열린 PR 규칙은 '병합하면 됩니다'로도 올리지 않습니다). 켠 뒤에 관측해야 하는 값입니다.
- 현황판(위 `초안(PR)` 행·§3-1)은 라벨 `초안`(과 작성자)으로 초안 PR 을 알아봅니다. 워치독 `DRAFT_WAITING` 은 head 브랜치 접두 `ai/draft/`(이 저장소의 `ai/draft/…` 브랜치에서 연 열린 PR)로 대기 건수와 가장 오래된 초안이 기다린 시간을 셉니다. 제목 접두 `[초안][Chance]`는 사람이 보는 보조 표지입니다.
- 이력으로 '최근 24시간 글 수'를 세는 '현황' 항목은 초안을 만든 시점에 글이 난 것으로 셉니다(병합 전에도). 승인 흐름을 켜면 이 항목은 공개된 글 수가 아니라 만든 초안 수에 가깝습니다.

## 4. 새 알림이 오는 규칙

- 코멘트는 **새로 생긴 `action` 항목이 있을 때만** 씁니다. 항목마다 안정적인 id가 있고(예: `pr:15:ready`), 본문 맨 끝의 숨은 표식 `ops-inbox:hash=…;items=…`에 "이미 알린 action id"를 적어 둡니다. 다음 점검이 이 표식과 비교합니다.
- PR의 상태가 바뀌면(예: 병합 가능 → 충돌) id가 달라져 새 할 일로 알립니다. 검사가 끝나 `info`가 `action`으로 바뀐 경우도 같습니다.
- 소스 조회가 실패한 점검에서는 그 소스의 이전 id를 표식에 그대로 남깁니다. 조회 실패를 '해소됨'으로 오해했다가 복구 때 같은 항목을 또 알리지 않기 위해서입니다. 초안 목록(`drafts` 소스)은 접두 `draft:`입니다.
- 초안은 새로 열린 이슈·PR마다 `draft:<번호>:wait` action이 하나 생겨 코멘트로 알리고, 열린 지 3일이 넘으면 id가 `draft:<번호>:stale`(check)로 바뀝니다 — action 목록에서 빠질 뿐 새 알림은 없습니다. 닫으면(또는 `폐기`) 목록에서 빠지고, 닫았다가 다시 열면 열린 지 3일 이내일 때만 새 항목으로 다시 알립니다(생성 시각이 그대로라 3일 넘은 초안은 다시 열어도 확인 항목으로만 보입니다).
- 초안 PR은 한 줄만 남깁니다(R2, 2026-11-09). 검사·병합 상태가 무엇이든(`pr:<번호>:ready`·`conflict`·`ci_fail`처럼 열린 PR 규칙이 action으로 올릴 상태까지) 열린 PR 줄(`pr:<번호>:…`)을 빼고 `draft:<번호>:wait`(3일이 넘으면 `draft:<번호>:stale`)가 알립니다. 그래서 검사가 끝나거나 병합 가능 여부가 계산 중으로 돌아와도 id가 바뀌지 않아 **한 번만** 알립니다. PR 목록이나 상세를 읽지 못한 점검에서도 초안 항목은 그대로 알립니다. 충돌·검사 실패는 줄의 설명으로만 알리고 새 알림은 만들지 않습니다(승인을 기다리는 초안이라는 사실은 그대로이기 때문입니다). 초안 목록(`drafts`)만 읽지 못한 점검에서는 초안 PR 이 일반 PR 줄(`pr:<번호>:…`)로 올라오는데, 초안 브랜치(`ai/draft/…`)에서 이 저장소 안으로 연 PR 은 새 알림에서 뺍니다. 브랜치 이름으로 알아보므로 이전 표식에 기대지 않아, 3일이 넘어 확인 수준(`draft:<번호>:stale`, 표식에 id 가 남지 않음)이던 초안도 조회 실패 중에 처음 본 초안도 막습니다(R2 수정 P2 — 예전에는 이전 표식의 `draft:<번호>:wait` 만 보아 3일이 넘은 초안 PR 은 일반 PR 알림이 한 번 더 갔습니다). 표식에는 남아 복구돼도 조용하고, 처음 본 초안은 복구된 점검이 `draft:<번호>:wait` 로 한 번 알립니다. 포크의 PR 은 대상이 아니고, 라벨이 없어 초안 목록에 안 잡히는 PR(라벨 붙이기 실패)은 일반 PR 입니다 — 정리 단계가 라벨을 다시 붙입니다(`ARCHITECTURE.md` §4-4).
- **옛 한계(해소됨, 2026-11-09 R2)**: 예전에는 초안 PR이 이미 `pr:<번호>:ready`로 알려진 뒤 열린 PR 줄이 일시적으로 action에서 빠지는 점검(병합 가능 여부(`mergeable`)가 다시 null로 돌아옴·상세 조회 실패·열린 PR 목록 조회 실패)에서 `draft:<번호>:wait`가 새 id라 한 번 더 알려졌습니다(누락이 아니라 중복). 승인 흐름(`publish_flow: pr`)을 켜기 전에 초안 PR 항목 id를 PR 상태와 무관하게 통일하는 권고를 이렇게 처리했습니다. 남은 것: 초안 PR을 닫았다가 다시 열면(열린 지 3일 이내일 때) 새로 알립니다 — 위 이슈 초안과 같은 규칙입니다.
- 본문은 **보이는 내용(해시)이나 알린 id가 바뀐 때만** 다시 씁니다. 같은 입력이면 본문 글자도 항상 같도록 점검 시각·"N시간 전" 같은 값을 본문에 넣지 않습니다(그래서 몇 시간 전에 열렸는지는 시각으로 표시).
- 코멘트를 먼저 쓰고 그다음 본문을 고칩니다. 코멘트가 실패하면 그 id를 표식에서 빼서 다음 점검이 다시 알립니다(알림을 놓치는 것보다 한 번 더 알리는 쪽이 낫다). 이 경우 실행은 빨강으로 끝납니다.
- **이슈를 처음 만들 때도 같은 순서**입니다: 알린 id 없이 이슈를 만들고, 코멘트가 성공한 뒤에야 본문의 표식에 id를 적습니다. 코멘트가 실패하면 고칠 것이 없고(표식에 id가 없으니 다음 점검이 알림), 코멘트는 성공했는데 id를 적는 쓰기가 실패하면 다음 점검이 한 번 더 알립니다(영영 못 알리는 것보다 낫다).
- 이슈를 만들거나 고치지 못하면(권한 오류, 저장소의 Issues 기능이 꺼져 있음 등) 실행이 빨강으로 끝나 Actions 실패 알림이 갑니다. 반대로 **일부 소스를 읽지 못한 것은 빨강이 아닙니다**(조회 실패 항목으로 남음). 스크립트 자신의 버그(예상 밖 예외)만 그대로 빨강입니다.
- 이슈는 항상 1개만 유지합니다: 라벨 `ops-inbox`가 붙은 이슈를 먼저 찾고(제목을 바꿔도 같은 이슈), 없으면 `github-actions` 봇이 만든 이슈에서 같은 제목을 찾습니다(라벨을 지웠거나 라벨 생성이 실패했던 경우). 작성자가 봇·소유자·멤버·협업자가 아닌 이슈는 무시합니다.
- 담당자는 저장소 소유자(`GITHUB_REPOSITORY_OWNER`)입니다. 담당자 지정이 거부되면(HTTP 422) 담당자 없이 만들고, 알림은 코멘트의 @멘션으로 갑니다.
- **휴대폰(텔레그램) 알림은 코멘트와 짝입니다**(선택, 2026-10-27). 시크릿 `TELEGRAM_BOT_TOKEN`·`TELEGRAM_CHAT_ID`가 둘 다 있으면, 점검이 **코멘트를 쓰려고 할 때마다**(위의 새 action 항목 판정 그대로, 연습 실행 제외) 같은 항목의 제목 줄(`inbox.alert_lines`: 코멘트와 같은 개수 제한·같은 소독, @멘션 없음)을 **평문** 한 통(`📌 확인 필요 모음 — 새로 해야 할 일 N건` + 줄, 버튼 `확인 필요 모음 열기`)으로 보냅니다. 단 **새로 생긴 초안 PR 대기**(`draft:<번호>:wait`, PR)는 이 통에서 빼고 `📝 발행 대기 — 채널: 글 제목` + `→ PR #번호 — 읽고 병합하면 공개, 닫으면 폐기됩니다`(버튼 `열기` = 그 PR)로 **한 건씩 따로** 보냅니다(R2-4, 2026-11-09; 한 번의 점검에서 따로 보내는 것은 3건까지이고 나머지는 이 통의 줄로 갑니다). 그래서 같은 초안이 텔레그램에 두 번 가지 않고, 초안 PR 이 없는 점검의 통은 예전과 글자 하나 다르지 않습니다. 코멘트 성공 여부와 무관하게 보내고(휴대폰 알림은 GitHub 쪽이 막혔을 때를 위한 보조 경로이기도 합니다), 서로 영향을 주지 않습니다 — 텔레그램이 실패하거나 예외를 던져도 코멘트·본문 표식·종료 코드는 그대로이고 로그에 `[참고] 텔레그램 알림을 보내지 못했습니다` 한 줄과 노란 경고만 남습니다. 코멘트가 실패해 다음 점검이 같은 항목을 다시 알릴 때는 휴대폰 알림도 한 번 더 갑니다(위 "한 번 더 알리는 쪽이 낫다"와 같은 원칙). 이미 알린 항목은 표식 때문에 다시 보내지 않습니다. 시크릿이 없으면 이 스크립트의 출력은 예전과 같습니다. 설정·점검: [`TELEGRAM_SETUP.md`](../.github/editorial/TELEGRAM_SETUP.md), 구조: [`ARCHITECTURE.md`](./ARCHITECTURE.md) §4-5.

11. **저장소 기본 토큰(`GITHUB_TOKEN`)이 만들거나 고친 이슈·PR은 이 워크플로를 시작시키지 않습니다**(GitHub가 워크플로가 워크플로를 무한히 부르는 것을 막는 규칙 — `workflow_dispatch`·`repository_dispatch`만 예외). 그래서 이벤트(`issues`·`pull_request`)로 곧바로 도는 것은 **사람이 한 조작**(휴대폰에서 이슈를 닫기·라벨 바꾸기·PR 병합 등)입니다. 자동으로 초안을 만드는 워크플로가 이슈·PR을 만든 직후의 갱신은 만드는 쪽이 이 워크플로를 `workflow_dispatch`로 불러야 하고(§3-1 — Chance 승인 PR 은 `pipeline/draft_flow.py` 가 부릅니다), 그렇지 않으면 다음 예약 때(보통 3–6시간) 반영됩니다. 병합 뒤 실제로 어느 쪽인지 관측해 이 항목을 고칩니다(§8).
12. **모든 이슈·PR 이벤트가 이 워크플로의 실행을 하나씩 만듭니다**(GitHub는 이벤트 종류만 거를 수 있고 라벨은 거를 수 없습니다). `초안` 라벨(또는 방금 뗀 `초안` 라벨)이 없으면 job이 건너뜀으로 끝납니다. Actions 목록의 이 워크플로 실행 중 `이슈 변경(초안만 점검)`·`PR 변경(초안만 점검)`이 건너뜀으로 많이 보이는 것은 정상입니다. 포크에서 온 PR은 라벨이 있어도 건너뜁니다(포크 토큰은 읽기 전용).
13. Blogger 칸은 이력(`draft_uploaded`)을 센 값이고, 블로그 공개 피드로 게시 여부를 확인하면 `(대략)` 없이 게시한 글을 뺀 값입니다(§3-1·한계 6). Blogger가 `mode: off`이거나 이력·공개 피드를 읽지 못하면 숫자 대신 `정지`·`조회 실패`가 보입니다.
14. 라벨 만들기는 있으면 좋은 일이라 이슈를 쓴 뒤에 하고 실패해도 넘어갑니다. 이미 있는 라벨은 **이름만 보고** 색·설명을 바꾸지 않습니다(운영자가 손으로 바꾼 색을 되돌리지 않으려는 것 — 고정 색·설명으로 되돌리려면 그 라벨을 지우고 점검을 한 번 더 돌립니다).
15. 숨은 표식은 알린 action id를 80개(`MARKER_IDS_MAX`)까지만 남깁니다. 열린 action이 80개를 넘으면(초안 약 70건 이상 — 다른 알림도 같은 80개를 나눠 씁니다) 정렬상 뒤의 id가 표식에 남지 못해 점검마다 다시 알려집니다. 초안을 이렇게 쌓아 두지 않는 운영(적체 방지)이 전제입니다.
16. 초안 현황 표를 만들다 예외가 나면(예: 레지스트리 항목의 `key`가 문자열이 아닌 값 — CI의 레지스트리 검증이 막는 오류입니다) 그 점검에서는 표만 빼고 실행 로그에 `[참고] 초안 현황 표를 만들지 못해 이번 점검에서는 뺍니다 …` 한 줄을 남깁니다. 항목·알림·이슈 갱신·종료 코드는 그대로입니다(표는 있으면 좋은 구역이라 모음 전체를 죽이지 않습니다).
17. 병합 직후 몇 시간은 본문이 낡을 수 있고(초안이 아닌 PR 의 병합은 이벤트가 아닙니다), Blogger 초안의 '게시 검토' 신호를 쓰는 쪽이 아직 없으며, 계절 표는 제목의 한국어 낱말만 봅니다 — 2026-11-11 정리의 한계는 §10-9 에 모아 두었습니다.

## 6. 보안

- **쓰기는 이 워크플로의 `GITHUB_TOKEN`만** 씁니다. 권한은 `contents: read`, `actions: read`, `checks: read`, `pull-requests: read`, `issues: write`가 전부이며 체크아웃은 자격 증명을 남기지 않습니다(`persist-credentials: false`). 파일·브랜치·PR은 만들지 않습니다. 쓰는 것은 모음 이슈·코멘트와 초안 모델의 라벨(`issues: write`로 가능)뿐입니다.
- **이벤트 트리거(`issues`·`pull_request`, 2026-10-27, PR 쪽은 2026-11-04 에 줄임)**: ⓪ PR 이벤트의 종류는 `closed`·`labeled`·`unlabeled` 뿐입니다 — `opened`·`reopened` 를 받으면 초안이 아닌 모든 PR(AI 의 병합 PR 포함)을 열 때마다 job 이 '건너뜀' 한 줄로 PR 화면에 생겨 '일부 검사가 안 돈다'로 보였습니다(운영자 요청 2026-11-04). 초안 PR 은 자동화가 기본 토큰으로 만들어 그 이벤트가 오지 않으므로 잃는 것이 없고, 초안 PR 의 닫힘(병합·폐기)·라벨 변경만 곧바로 읽습니다(`issues` 쪽은 열림 포함 그대로). ① job `if`가 `초안` 라벨이 있는 이슈·PR(또는 방금 `초안` 라벨을 뗀 이벤트)만 통과시킵니다. ② `pull_request`는 **이 저장소의 브랜치에서 온 PR만**(`head.repo.full_name == github.repository`, `pr-scope-check.yml`과 같은 관례) — 포크 PR의 토큰은 읽기 전용이라 쓸 수도 없고 포크의 것을 읽을 이유도 없습니다. `pull_request_target`은 쓰지 않습니다(검증기 WF-3). ③ 이벤트의 값(이슈·PR 제목·본문·브랜치 이름·라벨 설명)은 `if`에서 라벨 이름과 저장소 이름을 견주는 데만 쓰이고 **셸 명령·환경변수에는 들어가지 않습니다**(`run`은 `python scripts/ops_inbox.py` 한 줄). 스크립트는 이벤트 값을 읽지 않고 API로 다시 조회합니다. ④ PR 이벤트에서는 **기본 브랜치의 코드**를 체크아웃해 돌립니다(PR 쪽 코드를 쓰기 권한이 있는 토큰으로 돌리지 않는다 — `pr-scope-check.yml`과 같은 원칙). ⑤ `concurrency`(그룹 `ops-inbox`, 취소 없음)로 한 번에 하나만 돌고, 몰린 이벤트는 가장 새로운 대기 하나로 합쳐집니다(그 실행이 전부 다시 읽으므로 빠지는 것이 없습니다). `concurrency`는 워크플로 맨 위가 아니라 **job에** 둡니다 — 맨 위에 두면 초안과 무관해 job이 건너뛰어질 이벤트의 실행도 같은 줄에 서서 기다리던 진짜 갱신을 밀어낼 수 있습니다(job의 `if`가 거짓이면 그 job은 줄에 서지 않는 것으로 알고 있으며 병합 뒤 관측이 필요합니다 — 틀렸다면 최악은 다음 예약 때까지 갱신이 늦어지는 것입니다).
- 초안 이슈·PR의 **제목·채널 라벨 이름은 외부(AI·사람) 글**입니다. 표와 항목 모두 위 무력화를 거치고(`|`는 전각 `｜`, 표 칸 안의 링크 글에도 같습니다), 모바일 필터 링크의 주소에는 무력화를 쓸 수 없으므로 채널 라벨이 평범한 글자일 때만 링크를 만듭니다(§3-1). 낯선 사람이 연 이슈는 라벨이 있어도 세지 않습니다.
- PR 제목·주석 문구·이슈 제목·이력 사유처럼 **외부에서 온 글은 데이터**입니다. 한 줄로 접고(개행·제어 문자 — [`pipeline/console.py`](../pipeline/console.py)의 `one_line`을 씁니다), 글자 순서를 뒤집는 제어 문자는 지우고, `@`는 전각 `＠`로(멘션 알림 방지, 문자 참조 `&#64;`도 막으려고 `&`도 전각), `<`는 전각 `＜`로(HTML·표식 위조 방지), 링크 문법 문자와 코드 표시는 바꾸고, 글 끝의 역슬래시는 지우고(뒤에 붙는 `]`·`**`를 이스케이프해 링크·굵은 글씨가 깨져 보이므로 — PR 제목·초안 제목 모두 같은 `ext()`를 거칩니다), 줄 머리 `::`와 `##[`는 풀어 쓰며(워크플로 명령 위조 방지), 비밀 값 모양(`pipeline/secret_patterns.py`)은 가리고, 길이를 제한합니다. 렌더러가 한 번 더 같은 안전망을 거칩니다.
- 코멘트의 @멘션은 소유자 한 명뿐이며 이 모듈이 직접 붙입니다. 항목 제목 속 `@이름`은 멘션이 되지 않습니다.
- 텔레그램으로는 코멘트와 **같은 공개 정보**(항목 제목 줄)만 보냅니다. 토큰·채팅 ID 는 단계 `env`로만 넘어가고 어떤 출력에도 나오지 않습니다(`docs/SECURITY_GUARDRAILS.md` G-C12).
- 숨은 표식은 본문 맨 끝의 마지막 것만 읽고, 외부 글에서는 `<`가 바뀌어 표식을 흉내 낼 수 없습니다.
- 낯선 사람이 같은 제목의 이슈나 `[Watchdog]` 제목의 이슈를 만들어도 무시합니다(작성자 확인). 포크 PR은 "병합하면 됩니다" 대상에서 뺍니다.

### 10-2. 승인 대기와 가지의 PR 상태 (요구 1·2, D-270·D-271)

- **열린 PR 줄**: `normalize_pull` 이 상세(`GET /pulls/번호`)의 `state`·`merged`(상세에 없으면 목록의 `merged_at`)를 읽고, `pull_items` 는 병합됐거나 닫힌 PR(`merged` 가 참이거나 `state` 가 `closed`·`merged`)의 줄을 만들지 않습니다. 값이 없거나 모르는 값이면 끝난 것으로 보지 않습니다(보이는 쪽이 안전합니다).
- **승인 대기 줄**: [`scripts/ops_inbox.py`](../scripts/ops_inbox.py)의 `fetch_approval_prs` 가 승인 대기 실행의 `head_branch` 마다(중복 없이 최대 10가지, `MAX_APPROVAL_LOOKUPS`) `GET /pulls` 를 `state=all`·`head=<소유자>:<가지>`·`per_page=10` 으로 한 번 읽고, 응답의 PR 을 가지 이름과 저장소(포크가 아님)까지 직접 확인해 가지 상태를 정합니다. 열린 PR 이 하나라도 있으면 `open`, 없고 병합된 PR(`merged_at`)이 있으면 `merged`, 닫힌 PR 만 있으면 `closed` 입니다. `merged`·`closed` 가지의 실행은 `approval_items` 가 싣지 않습니다(5개 제한과 'N건 더' 요약은 남은 것만 셉니다).
- **이 저장소의 그 PR 에 딸린 실행만 뺍니다**(D-281): 가지 상태가 `merged`·`closed` 여도 ① 포크에서 온 PR 의 실행이거나 head 저장소를 알 수 없으면(`event` 가 `pull_request`·`pull_request_target` 인데 `head_repository` 가 이 저장소가 아니거나 비어 있음) ② 실행의 `head_sha` 가 병합됐거나 닫힌 PR 들의 head 커밋(같은 응답의 `head.sha`)에 없으면(병합 뒤 같은 이름의 가지에 새 커밋이 올라온 경우, 또는 그 PR 의 마지막 커밋이 아닌 오래된 커밋의 실행) 싣습니다. 커밋 정보가 없는 호출(`Snapshot.branch_pr_heads` 가 없는 옛 호출·시험)은 가지 이름만 봅니다. 아래 로그 줄의 건수도 이 판정으로 실제로 뺀 실행만 셉니다.
- **모르면 예전처럼 보입니다**: PR 을 못 찾은 가지, 조회가 실패한 가지, 상한을 넘은 가지, 이름 모양이 이상한 가지는 상태를 모르는 것이라 승인 대기를 숨기지 않습니다. 조회가 실패하면 '조회 실패 — 승인 대기 실행의 PR 상태(가지 이름으로 조회)' 확인 항목이 한 건 남고(`approval_prs`, 이전 `approve:` id 는 표식이 이어 갑니다), 그때 처음 보이는 승인 대기는 새 해야 할 일이라 알림이 갑니다(안전한 쪽).
- **호출 수**: 승인 대기가 없으면 0회, 있으면 가지마다 1회입니다. 주석 읽기보다 먼저 하므로 주석은 남는 호출만 씁니다(§5의 5). 가지 상태로 뺀 승인 대기가 있으면 실행 로그의 `[점검]` 줄 바로 뒤에 `[참고] 병합됐거나 닫힌 가지의 오래된 승인 대기 실행 N건은 모음에서 뺐습니다(PR 상태를 알아낸 가지 M개).` 한 줄이 남고, 없으면 로그는 예전과 같습니다.
- 한 가지에 열린 PR 이 하나라도 있으면 그 가지의 승인 대기는 모두 살아 있는 것으로 봅니다. 같은 가지 이름으로 PR 을 다시 열었을 때 오래된 커밋의 실행도 보일 수 있지만, 숨기는 것보다 보이는 쪽이 안전합니다.

### 10-3. 계획된 일시정지 (요구 3, D-272)

| 정책 파일 | 변수 `PIPELINE_PAUSE` | 모음 |
|-----------|----------------------|------|
| 없음·읽지 못함·`planned_pause` 없음·`active: false` | 켜짐 | 예전 그대로: action "자동 발행이 멈춰 있습니다 — 해제 방법"(`pause`) |
| `active: true`(이유·재개 조건·결정 근거·시작일이 모두 있음), `resume_gate_passed: false` | 켜짐 | info "참고: 계획된 일시정지 — 자동 발행 정지를 유지하는 중입니다"(`pause:planned`). 이유·재개 조건 N가지(앞의 셋 요약)·결정 근거·시작일을 보여 주고 링크가 없으며 해제를 권하지 않습니다. 시작일부터 21일(`PLANNED_PAUSE_LONG_DAYS`)을 넘으면 check "계획된 일시정지가 길어졌어요 — 재개 조건을 점검하세요"(`pause:long`)가 더해집니다(경과 일수는 글에 넣지 않습니다) |
| 위와 같고 `resume_gate_passed: true` | 켜짐 | action "재개 승인 필요 — 제한 재개 조건이 모두 통과했습니다"(`pause:resume_approval`). 링크는 변수 화면이지만 문구는 '재개는 운영자가 직접 정합니다 · 이 모음은 변수를 바꾸지 않습니다'입니다 |
| 없음·읽지 못함·`planned_pause` 없음·`active: false` | 꺼짐 | 줄 없음 |
| `active: true`(이유·재개 조건·결정 근거·시작일이 모두 있음) | 꺼짐 | check "정책 파일은 일시정지를 선언했는데 변수 PIPELINE_PAUSE 가 꺼져 있습니다 — 실수로 해제했나요?"(`pause:unset`). 링크가 없고 '일부러 재개한 것이라면 정책 파일의 선언을 끄는 변경을 AI 에게 요청하고, 실수라면 변수를 true 로 다시 켜세요(이 모음은 변수를 바꾸지 않습니다)'만 적습니다 |

`resume_gate_passed` 는 기본값이 false 이고, 켜는 것은 해제 점검표(아래 위치)를 확인한 뒤의 별도 병합(사람이 검토)뿐입니다. 이 모음은 변수를 지우거나 false 로 바꾸지 않고 바꾸라고 '바로 하기'로 권하지도 않습니다(재개 승인 항목만 예외로 변수 화면 링크를 둡니다).

이 모음은 재개 조건이 통과했는지 스스로 알지 못합니다 — '계획된 일시정지' 항목이 알리는 것은 '재개 조건이 모두 통과했다고 정책 파일에 기록되면(AI 가 준비하고 운영자가 병합하는 변경) 재개 승인 항목으로 알립니다'(D-283)입니다.

**해제 점검표의 위치**(재개 승인 항목의 안내가 가리키는 것): ① 정책 파일의 재개 조건 — `planned_pause.resume_conditions`(지금 6가지) ② 코드와 시험으로 보장하는 제한 재개 잠금 — `docs/ARCHITECTURE.md` 4-9절 ③ 운영자가 해제 전에 보는 '16항목 증거 한 장' — `인수인계/작업내용.md` 2장의 12번 항목이 가리키는 것. 해제는 이 셋을 확인한 운영자가 직접 정합니다.

### 10-4. 정지 전에 생성된 초안 (요구 4, D-273)

멈춘 채널(레지스트리 `mode: off`)이거나 전체 정지(`PIPELINE_PAUSE`)인 때 그 채널의 초안(이슈·PR)은 '정지 전에 생성된 초안'입니다. 항목은 `draft:<번호>:paused`(check)이고 "유지·검토·폐기 중에서 고르세요"와 '지금 공개를 권장하지 않습니다'를 적으며 발행·게시·병합을 권하는 문구를 쓰지 않습니다(시험이 낱말을 막습니다). 3일이 넘었어도 한 줄이고 `wait`·`stale` 로 바뀌지 않습니다. 초안 현황 표의 칸은 `N (정지 전 초안)` 이고, 표에 그런 칸이 하나라도 있으면 표 아래 설명이 정지용 문구로 바뀝니다 — 전체 정지이면 '지금은 일시정지 중이라 모두 정지 전에 만든 초안'이라는 설명(Blogger 설명도 같이)이고, 일부 채널만 멈췄으면(`mode: off`) '`(정지 전 초안)` 이 붙은 칸은 멈춰 둔 채널의 정지 전 초안이라 공개를 권장하지 않으며 …'(D-284)입니다. 그런 칸이 없으면(초안이 없으면) 설명은 그대로입니다. Blogger 초안(이력)도 같습니다 — 정지 중이면 check "정지 전에 생성된 초안 N건 — 유지·검토·폐기 중 선택"입니다. 정지가 아닌 채널의 초안은 예전 규칙(`wait`·`stale`)입니다.

### 10-5. Blogger 초안의 '게시 검토' 조건 (요구 5, D-274)

올린 지 6시간이 넘었는데 공개되지 않았다는 사실만으로는 action 이 아닙니다. 아래가 **명시적으로 모두 긍정**일 때만 action "초안 N건 게시 검토"이고, 하나라도 없거나 확인하지 못하면 info "초안 N건 대기(검토 조건 미확인)"입니다(확인하지 못한 조건의 이름을 본문에 적습니다). 초안이 여럿이면 모든 초안이 그래야 합니다.

| 조건 | 읽는 곳 |
|------|---------|
| 채널 활성 | 레지스트리 `mode` 가 `off` 가 아님(`off` 면 '정지 중' 참고 항목만) |
| 파이프라인 정지 아님 | 변수 `PIPELINE_PAUSE` 가 꺼짐(켜짐이면 check '정지 전에 생성된 초안') |
| 품질 Gate 통과 | 이력 항목의 `review_quality` 가 정확히 `pass` |
| 건강·안전 차단 없음 | 이력 항목의 `review_safety` 가 정확히 `clear` |
| 사람 검토 가능 | 블로그 공개 피드로 '아직 공개되지 않음'을 확인했고(§3 Blogger 행의 게시 확인) 모든 초안에 글 번호(`post_id`)가 있음 |

**지금은 이력에 `review_quality`·`review_safety` 를 쓰는 쪽이 없습니다** — 그래서 당분간 Blogger 초안은 모두 '검토 조건 미확인'(참고)이고 action 이 생기지 않습니다. 신호를 쓰는 일은 러너·생성기의 별도 변경입니다(이 정리의 범위 밖). 칸 이름에 `quality_gate` 글자를 쓰지 않은 것은 품질 Gate 연결 격리 시험(`tests/test_generator_quality_gate.py` 의 `ConnectionIsolationTest`)이 그 글자를 생성기·레지스트리 밖의 소스에 쓰지 못하게 막기 때문입니다 — 쓰는 쪽도 이 이름으로 적습니다. 신호 이름은 누가 판정했는가(품질 Gate 인가 사람인가)와 판정 버전을 말하지 않으니, 쓰는 쪽을 만들 때 함께 정합니다(§10-11).

### 10-6. 철 지난 초안 (요구 6, D-275)

### 10-7. 정책 파일 `pipeline/ops_inbox_policy.json` (요구 3·7, D-276·D-277)

운영자 결정을 데이터로 적어 둔 파일입니다. **모음의 분류와 표시만 바꾸고** 읽기 전용이며 **AI 가 자동으로 고치지 않습니다 — 고치는 것은 사람이 검토하는 병합뿐입니다.** 칸:

| 칸 | 뜻 |
|----|----|
| `schema_version` | 정수 1 |
| `_doc` | (선택) 설명, 400자 이하 |
| `planned_pause` | 의도된 일시정지 선언(없거나 null 이면 선언 없음). `active`(참·거짓)가 참이면 `since`(YYYY-MM-DD, 오늘 한국 날짜보다 뒤면 거절)·`reason`(240자 이하)·`decision_ref`(어느 결정에 따른 것인가, 200자 이하)·`resume_conditions`(글 목록 1–12개, 각 160자 이하)가 모두 있어야 하고, `resume_gate_passed`(기본 false)는 재개 Gate 가 모두 통과했을 때만 켭니다 |
| `item_decisions` | 항목 키 → `{decision, date, reason}`, 최대 100개. `decision` 은 `keep`(유지 — 참고로 낮춤)·`discard_close`(폐기 후 닫기 권장 — 확인 항목)·`ignore`(무시 — 싣지 않음), `date` 는 YYYY-MM-DD(오늘 한국 날짜보다 뒤면 거절), `reason` 은 200자 이하 |

항목 키는 항목 id 의 **앞부분**이고 모양은 네 가지뿐이며 다른 모양은 파일 전체를 쓰지 않는 사유입니다(D-287): `approve:<커밋 7자>`(그 커밋의 승인 대기), `draft:<번호>`(`draft:88:wait`·`stale`·`season` 모두), `blogger:<블로그 키>:drafts:<시각 12자리>`(그 시각이 가장 새 대기 초안인 Blogger 초안 항목 — 항목 id 끝의 시각 그대로이고, 새 초안이 오면 시각이 바뀌어 결정이 풀립니다), `pr:<번호>`. 시각을 뺀 `blogger:<블로그 키>:drafts` 나 `approve:more` 같은 넓은 키는 앞으로 올 항목까지 가리므로 받지 않습니다. 워치독·실패한 워크플로·조회 실패 같은 항목은 결정으로 숨길 수 없어 키로 쓸 수 없습니다. 네 모양은 서로 겹치지 않아 어느 키가 이기는지 따질 일이 없습니다(결정 찾기 코드는 가장 긴 키가 이기는 규칙을 그대로 두었지만 파서가 겹치는 키를 만들지 않습니다). 결정은 항목을 **낮추거나 지우기만** 하고 action 을 만들지 않으며, 가리키는 항목이 이미 사라졌으면 아무 일도 없습니다. 이슈·PR 번호나 커밋 하나, 또는 가장 새 초안의 시각에만 맞는 키라서 새 커밋·새 초안은 가려지지 않습니다.

**엄격 검증**: 모르는 칸·잘못된 길이·날짜 모양·결정 종류·키 모양, 같은 칸이 두 번 나오는 것(검토자가 놓치기 쉬운 '마지막 값이 조용히 이김'), 글 안의 물결표·`@`·주소·줄바꿈·제어 문자, 비밀 값 모양, 광고(게시자·앱) 번호·계정·전화번호처럼 보이는 숫자(아홉 자리 이상 숫자·`pub-` 번호·전화 모양 — 날짜와 문서 절 번호는 괜찮습니다), 오늘(한국 날짜)보다 뒤의 시작일·결정일이 하나라도 있으면 파일 전체를 쓰지 않습니다(64KB 를 넘는 파일도, 너무 깊게 중첩돼 파서가 재귀 한도에 닿거나 메모리가 모자란 파일도). **파일이 없으면** 예전 규칙 그대로이고 본문·로그에 새 글자가 없습니다. **있는데 읽지 못하면**(JSON 오류·검증 실패) 예전 규칙으로 표시하고 본문 제목 바로 아래에 인용 한 줄 "참고: 정책 파일(…)을 읽지 못했어요 — 이번 점검은 운영자 결정 없이 예전 규칙으로 표시합니다(사유)"를 더하며 실행 로그에도 한 줄 남깁니다. 어느 쪽이든 읽기 오류·UTF-8 이 아님·재귀 한도·메모리 부족을 포함해 예외로 죽지 않습니다(D-282).

**고치는 법**: 결정을 더하거나 바꾸려면 이 파일을 고치는 변경(모음의 분류만 바뀌는 T2)을 AI 에게 요청하고 사람이 검토해 병합합니다. 재개 Gate 통과를 적는 `resume_gate_passed: true` 는 해제 점검표(§10-3)를 확인한 뒤의 별도 병합입니다(켜면 '재개 승인' 항목이 생길 뿐 변수는 이 모음이 바꾸지 않습니다).

### 10-8. 알림·표식 호환·쓰기 범위

- **새로 action 이 된 항목만** 알립니다(§4 그대로). 이번 정리는 action 을 줄이기만 해서 지금 열려 있는 항목이 한꺼번에 새 항목으로 알려지지 않습니다 — 옛 표식(`approve:…`·`blogger:…:drafts:…`·`pause`·`pr:176:ready`)을 읽어도 깨지지 않고 사라지는 쪽으로만 바뀝니다(시험 `AlertCompatibilityTest`). 새 action 은 `pause:resume_approval`(정책 파일의 Gate 통과 플래그가 켜졌을 때)과 신호가 모두 긍정인 Blogger 초안(`blogger:…:drafts:…`)뿐입니다.
- **쓰기 범위 불변**: 이 워크플로가 쓰는 것은 이 모음의 이슈 본문·코멘트·라벨뿐입니다. `discard_close` 는 '권장'을 표시할 뿐 이슈를 닫거나 라벨 `폐기`를 붙이지 않고, PR·초안·Blogger·변수·파일·브랜치를 바꾸지도 않습니다(시험이 쓰기 호출 목록을 단언합니다). 워크플로 파일·`pipeline/blogs.json`·광고 표면은 바꾸지 않았습니다.

### 10-9. 한계와 켜는 날 필요한 것

- **갱신 주기**: 이슈 본문은 예약(실제로 보통 3–6시간)이나 초안 이벤트 때만 다시 쓰입니다. 초안이 아닌 PR 의 병합은 이벤트가 아니라서 병합 직후 몇 시간은 본문이 낡은 채일 수 있습니다(PR #176 이 병합 뒤에도 '병합하면 됩니다'로 보인 이유). 이번 정리는 다음 갱신 때 바로 사라지게 할 뿐 갱신을 앞당기지 않습니다. 병합(닫힘) 이벤트로 즉시 갱신하려면 `ops-inbox.yml` 의 job 조건이 초안이 아닌 PR 의 닫힘도 통과시켜야 하는데 워크플로 변경이라 운영자 승인(T3)이 필요해 적용하지 않았고 패치 초안만 만들었습니다(이 변경의 보고서, D-279). 병합 뒤 실제 지연은 관측 전입니다(§8). 패치를 켠 뒤 첫 실행에서 닫힘 이벤트의 실행이 승인 대기(`action_required`)로 멈추지 않고 도는지 관측해야 하고, 읽기 전용 토큰으로 도는 PR(의존성 봇 등)의 닫힘은 쓰기 실패로 빨간 실행이 남을 수 있습니다(이 저장소에는 그런 설정이 없습니다 — 패치 초안의 README).
- **'게시 검토' 신호가 아직 없습니다**: 이력에 `review_quality`·`review_safety` 를 쓰는 쪽이 없어 당분간 Blogger 초안은 모두 '검토 조건 미확인'(참고)이고 action 이 생기지 않습니다. 신호 이름은 누가 판정했는가·판정 버전을 말하지 않습니다(§10-11).
- **계절 표의 한계**: 표에 있는 낱말만 봅니다 — 영문 제목과 표에 없는 계절 이야기(개학·졸업·에어컨·패딩 등)는 철 지난 초안으로 가려내지 못합니다(미탐). 반대로 사철 쓰는 말이 계절 낱말로 읽히는 오탐은 일곱 가지를 없앴지만(D-285) 남은 것이 있을 수 있습니다 — 이슈 초안이 철 지난 것으로 잘못 표시되면 확인 항목이 하나 생기고 그 초안의 새 코멘트·텔레그램 알림이 가지 않습니다(PR 초안은 이 판정에서 빠져 알림이 그대로입니다, D-280). 행사 날짜는 해마다 달라 넓은 구간에 유예 14일을 더했고, 본문은 읽지 않고 제목만 봅니다.
- **키가 가리키는 대상**: `draft:<번호>` 는 이슈·PR 번호 하나에, `approve:<7자>` 는 한 커밋에만 맞습니다. 같은 번호의 초안을 닫았다 다시 열면 결정이 그대로 걸립니다. 정책 파일에서 결정을 지우면 다음 점검부터 예전 판정(정지·철·나이)으로 보입니다.
- 승인 대기의 가지 조회가 실패한 점검에서는 승인 대기가 예전처럼 보여 알림이 한 번 더 갈 수 있습니다(숨기지 않는 쪽).

### 10-11. 재개 전에 확인할 것 — 이 모음 쪽 (독립 검증 뒤, D-283·D-288)

재개(운영자가 변수 `PIPELINE_PAUSE` 를 직접 해제)는 해제 점검표를 확인한 뒤의 일입니다(위치는 §10-3). 이 모음의 분류를 믿고 재개하기 전에 아래를 함께 확인합니다 — 정책 파일의 재개 조건 6가지에는 없는 것들입니다.

| 번호 | 확인할 것 | 지금 상태 |
|------|-----------|-----------|
| 1 | **철 지난 초안 규칙의 PR 초안 처리** — 철 판정은 이슈 초안에만 쓰고 Chance 승인 PR 초안은 뺍니다. 재개 뒤 승인 초안 PR 은 제목에 계절 낱말이 있어도 새 초안의 코멘트·텔레그램 알림을 그대로 받습니다 | 고쳤음(D-280). 재개 뒤 첫 승인 초안 PR 에서 알림이 오는지 봅니다 |
| 2 | **Blogger 검토 신호를 이력에 쓰는 쪽** — `review_quality`·`review_safety` 를 쓰는 곳이 없어 재개 뒤에도 Blogger 초안은 action 없이 info 로만 남고, 알림은 러너가 올린 직후 보내는 텔레그램에만 기댑니다 | 열림(러너·생성기의 별도 변경) |
| 3 | **신호 이름이 말하지 않는 것** — 이름이 누가 판정했는가(품질 Gate 인가 사람인가)와 판정 버전을 말하지 않습니다. 쓰는 쪽을 만들 때 판정 주체와 버전을 함께 정하고 §10-5 의 조건 표를 고칩니다 | 열림 |
| 4 | **승인 대기를 가지 이름으로 거르는 규칙** — 병합됐거나 닫힌 PR 의 마지막 커밋의 실행만 뺍니다. 같은 가지의 오래된 커밋의 승인 대기는 보입니다(§10-2) | 고쳤음(D-281) |
| 5 | **정책 파일의 정지 선언 끄기** — 재개하면 정책 파일의 `planned_pause.active` 를 끄는 변경(AI 가 준비하고 운영자가 병합)이 따라와야 '실수로 해제했나요?' 확인 항목이 사라집니다. 정지가 시작일부터 21일을 넘으면 '정지가 길어졌어요' 확인 항목이 생깁니다 | 표시만(D-288) |
| 6 | **정책 파일의 `resume_gate_passed`** — 켜는 것은 해제 점검표를 확인한 뒤의 별도 병합뿐입니다 | 꺼짐 |
