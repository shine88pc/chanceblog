# 확인 필요 모음 (운영 인박스)

> 대상: 운영자(비개발자)와 이 저장소에서 일하는 AI. 구조는 [`ARCHITECTURE.md`](./ARCHITECTURE.md), 보안은 [`SECURITY_GUARDRAILS.md`](./SECURITY_GUARDRAILS.md), 코드·검증은 [`ENGINEERING_GUIDE.md`](./ENGINEERING_GUIDE.md).

## 1. 한눈에

운영자가 **직접 해야 할 일**과 **확인하면 좋은 일**이 Actions 곳곳(실행 요약, 노란 경고 주석, PR, 워치독 이슈)에 흩어져 있으면, 하나씩 열어 보기 전에는 알 수 없습니다. 예를 들어 Blogger 실행이 초록이어도 게시 시크릿이 없으면 글은 저장소 초안으로만 쌓이는데, 이 사실은 실행 요약을 열어야만 보입니다.

그래서 한곳에 모읍니다.

- **GitHub 이슈 1개** — 제목 `[운영] 확인 필요 모음`, 라벨 `ops-inbox`. 이 이슈 하나만 보면 됩니다.
- **같은 내용의 Actions 실행 요약** — 워크플로 `[공통] 확인 필요 모음`(파일 `ops-inbox.yml`)의 실행 화면 아래쪽.
- **새로 해야 할 일이 생기면 이슈에 코멘트(@멘션)** — 그 코멘트가 휴대폰 알림이 됩니다.
- **초안 현황 구역(2026-10-27)** — 본문 맨 위의 표: 채널(Chance·Blogger·티스토리·네이버 …)마다 발행을 기다리는 초안이 몇 건인지, 가장 오래된 것이 며칠째인지, 가장 최근 초안이 무엇인지(링크)를 보여 줍니다. 초안은 라벨 `초안`이 붙은 이슈·PR입니다(§3-1).

2시간 간격으로 예약돼 자동으로 갱신되고(GitHub가 예약 실행을 늦추거나 건너뛰는 일이 잦아 실제로는 보통 3~6시간 간격입니다), 초안 이슈·PR이 열리거나 닫히거나 라벨이 바뀔 때도 곧바로 한 번 더 갱신되며(사람이 한 조작에 한합니다 — §5의 11), 손으로 실행할 수도 있습니다(§2). 해소된 항목은 저절로 사라집니다.

## 2. 운영자가 하는 일

### 처음 한 번

1. 휴대폰에 **GitHub 앱**을 설치하고 로그인해서 알림(푸시)을 켭니다. 앱이 없으면 GitHub 웹의 알림 설정(Settings → Notifications)에서 이메일 알림을 켜도 됩니다. 메뉴 이름은 앱 버전에 따라 다를 수 있으니, "멘션 받았을 때·내가 담당자일 때" 알림이 켜져 있으면 됩니다.
2. 저장소 → **Actions** → 왼쪽 목록의 **[공통] 확인 필요 모음** → **Run workflow**. 첫 실행이면 `연습 실행`을 체크해 결과만 봅니다(이슈를 만들지 않음). 실행 요약이 마음에 들면 한 번 더 `연습 실행`을 체크하지 않고 실행합니다 — 이슈가 생기고, 해야 할 일이 있으면 코멘트로 알림이 옵니다.
3. 이후로는 **이슈 하나만** 보면 됩니다(저장소 → Issues → `[운영] 확인 필요 모음`, 또는 알림을 눌러서).

### 이슈를 읽는 법

본문은 맨 위의 **초안 현황** 표(§3-1)와 세 구역입니다. 항목마다 **▶ 바로 하기** 링크(그 자리로 바로 이동)와 한 줄 안내가 붙어 있습니다.

| 구역 | 뜻 | 알림 |
|------|----|------|
| **지금 해야 할 일** (`action`) | 사람이 손대야 풀립니다: PR 병합·충돌·검사 실패, 실패한 워크플로, 승인 대기, 일시정지 해제, 시크릿 등록 | 새로 생기면 코멘트(@멘션)로 알림 |
| **확인하면 좋은 것** (`check`) | 급하지 않거나 사실 확인이 필요한 것: 워치독 경고, 초록 실행의 경고 문구, 오래 열린 PR, 조회 실패 | 알림 없음 |
| **참고** (`info`) | 현황과 진행 중인 것: 블로그별 마지막 글, 검사 진행 중인 PR, 정지된 블로그, 플랫폼 안내성 경고 | 알림 없음 |

항목이 있는 구역만 보입니다. '참고' 구역에는 블로그별 마지막 글 현황이 늘 들어 있어서 "지금 확인할 것이 없습니다"라는 문구는 항목이 정말 하나도 없을 때만 나오고 실제로는 거의 보이지 않습니다. 할 일이 없다는 신호는 맨 위 요약의 **지금 해야 할 일 0건**입니다.

### 자주 묻는 일

| 질문 | 답 |
|------|----|
| 이슈를 닫으면? | **닫힌 채로 있습니다.** 닫은 뒤에 *새로 해야 할 일(action)*이 생겼을 때만 코멘트를 쓰고 이슈를 다시 엽니다. 그 밖의 변화(참고·확인 항목)는 닫힌 채로 본문만 고쳐 둡니다(본문 수정은 알림이 없습니다). 계속 조용히 두고 싶으면 닫은 채로 두세요 |
| 이슈를 지우거나 제목을 바꾸면? | 라벨 `ops-inbox`가 붙어 있으면 제목을 바꿔도 같은 이슈로 봅니다. 라벨을 지우고 제목도 바꾸거나 이슈를 지우면 다음 실행이 새로 만듭니다. 지우지 말고 닫아 두는 쪽을 권합니다 |
| 본문을 직접 고치면? | 내용이 바뀌는 다음 갱신 때 덮어씁니다. 내용이 그대로면 건드리지 않습니다 |
| 지금 당장 갱신하려면? | Actions → `[공통] 확인 필요 모음` → Run workflow |
| 끄려면? | Actions → `[공통] 확인 필요 모음` → 오른쪽 위 `⋯` → **Disable workflow**. 이슈는 남으니 닫으면 됩니다 |
| 주기를 바꾸려면? | `.github/workflows/ops-inbox.yml`의 `cron`을 바꾸는 변경(T2)을 AI에게 요청하세요. 현재 값은 2시간 간격 예약(매 짝수 시 40분, UTC)이고 실제 갱신은 보통 3~6시간 간격 |
| 같은 알림이 또 오나요? | 같은 항목은 한 번만 알립니다. 해소됐다가 다시 생기면 새 항목으로 다시 알립니다 |
| 초안을 발행했거나 쓰지 않기로 했으면? | 그 초안 이슈를 **닫으세요**(닫기 = 발행 완료). 쓰지 않을 글은 라벨 `폐기`를 붙이거나 닫으세요. 닫힌 초안과 `폐기` 라벨이 붙은 초안은 초안 현황 표와 해야 할 일에서 빠집니다. 사람이 휴대폰에서 닫거나 라벨을 바꾸면 거의 바로 반영되고(예상: 1~2분 안 — 실제 지연은 병합 뒤 관측 전), 그렇지 않으면 다음 예약 때입니다 |
| 초안만 모아 보려면(휴대폰)? | 초안 현황 구역 맨 아래의 **휴대폰에서 거르기** 링크를 누르세요(대기 초안 전체, 채널별). 직접 하려면 이슈 목록 검색창에 `is:open label:초안 label:"채널:티스토리"`를 넣습니다. Chance 승인 흐름의 PR 초안은 Pull requests 탭의 같은 검색입니다 |
| 초안이 생겼는데 표가 안 바뀌어요 | 자동 초안(티스토리·네이버 패키지, Chance 승인 PR)은 저장소 기본 토큰이 만들어 GitHub 규칙상 이 워크플로를 시작시키지 못합니다(§5의 11). 만드는 쪽이 이 워크플로를 직접 불러 주지 않았다면 다음 예약 때 반영됩니다. 급하면 Run workflow |
| Actions 목록에 `이슈 변경(초안만 점검)`·`PR 변경(초안만 점검)` 실행이 자꾸 생겨요 | 모든 이슈·PR의 열림·닫힘·라벨 변경이 이 워크플로를 시작합니다. `초안` 라벨이 없으면 job이 **건너뜀(Skipped)**으로 바로 끝납니다. 정상입니다(러너를 쓰지 않습니다) |

## 3. 무엇을 모으나 (규칙표)

판단은 [`pipeline/inbox.py`](../pipeline/inbox.py)(순수 함수), 읽기·쓰기는 [`scripts/ops_inbox.py`](../scripts/ops_inbox.py)가 합니다. 아래는 현재 기본값이며 근거와 한계를 함께 적습니다.

| 소스 | 조건 | 수준 | 근거·한계 |
|------|------|------|-----------|
| 워치독 이슈 | 열린 `[Watchdog] …` 이슈. 본문의 심각도가 critical이면 | action | 워치독이 이미 판단한 결과를 한곳에 모읍니다. 작성자가 `github-actions` 봇이거나 소유자·멤버·협업자인 이슈만 믿습니다(제목만 흉내 낸 낯선 이슈는 무시). 심각도를 읽지 못하면 action(놓치는 쪽이 더 위험) |
| | 심각도가 warning이면 | check | |
| 열린 PR (draft 제외) | 검사(CI) 통과 + 충돌 없음 | action | "병합하면 됩니다". 안내 문구가 "PR 코멘트의 변경 범위 검사 결과를 먼저 확인하세요"를 함께 알려 줍니다 — `[공통] PR 변경 범위 검사`는 경고여도 종료 0이라 초록으로 보이기 때문입니다. 작성자가 이슈 수정 봇·dependabot·Copilot·`ai/` 브랜치든 같은 규칙. 병합 여부는 항상 사람이 결정합니다. 라벨 `초안`이 붙은 PR은 이 줄이 action이 아니면 아래 '초안(PR)' 줄이 대신합니다 |
| | 검사 실패 | action | 헤드 커밋의 check-runs 요약(실패·시간 초과·시작 실패 중 하나라도 있으면 실패) |
| | 충돌(`mergeable=false` 또는 상태 `dirty`) | action | 충돌이면 검사 결과가 낡았을 수 있어 충돌을 먼저 표시 |
| | 검사 진행 중 / 병합 가능 여부 계산 중 | info | 끝나면 다음 점검에서 위 항목으로 바뀜. 병합 가능 여부(`mergeable`)가 계산 중(null)이면 같은 점검 안에서 3초 뒤 한 번 더 조회합니다(읽기 호출 상한 안에서, 실패하면 첫 답 그대로) |
| | 검사 통과인데 저장소 규칙이 막음(`blocked`) / 검사 기록 없음 / 상태 조회 실패 | check | |
| | 3일 넘게 열림 | info → check | 이미 action이면 그대로 두고 문구만 덧붙임 |
| | **저장소 밖(포크)의 낯선 작성자 PR** | check | 검사가 통과해도 "병합하면 됩니다"를 안내하지 않습니다. 외부 글·코드는 데이터입니다([`AGENTS.md`](../AGENTS.md) 절대 규칙 3) |
| 워크플로 실행 | main 브랜치의 최근 48시간, 파일당 최근 10건. 가장 최근 완료 실행이 failure·timed_out·startup_failure | action | 취소·건너뜀·중립·승인 대기(`action_required`)는 무시합니다(최신 실행이 승인 대기여도 이전 실패는 그대로 보임). 연속 실패 횟수와 시작 시각을 함께 표시. 이 워크플로 자신의 실행은 제외. **포크 PR이 일으킨 실행**(`event`가 `pull_request`·`pull_request_target`이고 `head_repository`가 이 저장소가 아니거나 알 수 없음)은 head 브랜치가 `main`이어도 판단에서 뺍니다(API가 막아 주는지 확인하지 못해 방어적으로). **항목 제목의 워크플로 이름**은 실행의 `name`이 아니라 체크아웃한 워크플로 파일의 최상위 `name`입니다 — 실행의 `name`은 `run-name`이라 실행마다 달라지고 이름을 바꾸기 전의 옛 이름도 이력에 섞여 있어서입니다. 이름을 읽지 못하면 파일 이름(예: `chanceblog.yml`)을 보여 줍니다(API 호출 없음). 이름 맨 앞의 `[구분] ` 접두사(2026-10-27, `[Chance]`·`[공통]` 등)는 대괄호가 링크 문법으로 읽히지 않도록 이슈 본문에서 전각 대괄호(［Chance］)로 바뀌어 보입니다 — Actions 목록의 이름과 같은 글자입니다. 이름 파일은 대괄호로 시작해 `name: "[공통] 확인 필요 모음"`처럼 따옴표로 감싸야 읽힙니다(따옴표 없는 값은 읽지 않고 파일 이름을 보여 줌) |
| | 승인 대기(`action_required`) 실행 | action | "Approve and run". 같은 커밋의 실행은 한 항목으로 묶고 5개까지만 표시(워크플로 이름은 위와 같이 파일의 `name`). 모르는 사람의 코드는 읽어 보기 전에 승인하지 말라고 안내 |
| | 성공한 실행의 주석(annotation) 중 **우리 스크립트가 남긴** warning 수준 문구 | check | 서로 다른 문구 3개까지 한 줄로 접어 나열(같은 문구는 실행마다 되풀이하지 않고 "성공 실행 N회 중 M회"로 합침). 파일마다 최근 성공 실행 3건의 주석만 읽습니다. `::warning::`으로 남긴 건너뜀 사유·시크릿·조회 실패 같은 것이 여기에 잡힙니다. 플랫폼 안내(아래 행)로 판정되지 않는 애매한 warning 은 check 로 둡니다 |
| | GitHub 플랫폼이 붙이는 안내성 주석(warning·notice 수준) | info | 거의 모든 실행에 붙는 소음(2026-10-25 실제 실행 전부: warning "Node.js 20 is deprecated … forced to run on Node.js 24", notice "The ubuntu-latest label will migrate to Ubuntu 26 …")이라 check 가 아니라 **모든 워크플로를 통틀어 info 한 줄**로 합칩니다: "GitHub Actions 플랫폼 경고 N종 — 액션 버전 갱신 필요, 당장은 발행에 영향 없음" + 액션 이름(예: actions/checkout v4)·예시 문구 하나. **어느 워크플로·어느 실행에서 나왔는지는 싣지 않고** 링크는 저장소의 Actions 화면(고정 주소)입니다 — 싣는 순간 다른 워크플로가 돌 때마다 본문이 바뀌어 이슈를 계속 다시 쓰게 되기 때문입니다(같은 문구 집합이면 입력 순서와 상관없이 같은 글자). info 라서 새 알림 대상이 아닙니다. 판정 문구는 `pipeline/inbox.py`의 `PLATFORM_NOISE`(상수 한 곳)이고 `tests/test_ops_inbox.py`의 `PlatformNoticeTest`가 실제 문구 두 개로 고정합니다. `Node.js 20` 처럼 `Node.js`가 붙은 숫자만 소음으로 보며(우리 쪽 `Node 18` 같은 문구는 확인 항목으로 남음), 우리 스크립트의 실제 경고 문구 13개가 소음으로 잘못 분류되지 않는지도 같은 테스트가 확인합니다. 우리 쪽 notice 는 무시합니다 |
| 일시정지 | 저장소 변수 `PIPELINE_PAUSE`가 `1`/`true`/`yes`/`on` | action | "자동 발행이 멈춰 있습니다 — 해제 방법". 일부러 멈춘 것이라면 그대로 둬도 됩니다. 정지 중에는 워치독이 새 알림을 만들지 않으므로 이 항목이 '아직 멈춰 있다'는 유일한 표시입니다 |
| Blogger 게시 설정 | 블로그가 `auto`·`draft`인데, 이력의 **최신 게시 단계 항목**이 `generated_unpublished`이고 사유에 `[SECRETS]`가 있음 | action | 어떤 시크릿 **이름**이 비었는지만 표시(값은 절대 아님) + 저장소 시크릿 설정 페이지 링크. '게시 단계 항목'은 posted·draft·generated_unpublished·publish_failed·draft_uploaded 중 가장 나중 것(게시 단계에 가지 못한 `rejected` 등은 시크릿 상태를 알려 주지 않아 건너뜀). 2026-10-25 현재 레지스트리에서 `blogger_macat`은 `mode: off`라 이 규칙은 쉬고 아래 '정지 중' 참고 항목만 나옵니다 — 시크릿을 등록하고 mode 를 `draft`·`auto`로 켜면 동작합니다 |
| | 이력에 `draft_uploaded`(앞으로 생길 Blogger 초안함 업로드 상태)가 최근 7일 안에 있음 | action | "초안 N건 게시 대기", 링크는 Blogger 관리 화면. 이력으로는 게시했는지 알 수 없어 7일이 지나면 저절로 사라집니다. 새 초안이 올라오면 새 항목으로 다시 알립니다. 초안 현황 표의 Blogger 칸은 창이 다릅니다(14일 대략치, §3-1) |
| | 블로그가 `mode: off` | info | "정지 중". 레지스트리의 `note`(또는 `_note`)가 있으면 이유로 표시 |
| 현황 | 블로그별 마지막 글 시각(KST)·최근 24시간 글 수 | info | 이력 파일에서 읽음(없거나 모양이 달라도 죽지 않음). Chance는 날짜와 게시 슬롯 시각만 기록돼 있어 "09시 슬롯"처럼, 날짜만 있으면 "날짜만 기록됨"으로 표시하고 오늘(KST) 날짜면 24시간 안으로 셉니다. Blogger는 `posted`만 글로 세고 초안·미게시는 따로 셉니다 |
| 초안(이슈) | 라벨 `초안`이 붙은 **열린 이슈**(작성자가 `github-actions` 봇이거나 소유자·멤버·협업자, 라벨 `폐기` 없음)가 열린 지 3일 이하 | action | "초안 대기 — 글 제목" + 채널·이슈 번호. 새로 생기면 코멘트(@멘션)로 알림. id `draft:<번호>:wait`. 안내: 본문을 복사해 발행한 뒤 이슈를 닫기 |
| | 열린 지 3일(`DRAFT_STALE_DAYS`) 넘음 | check | "초안 3일 넘게 대기 — …". 알림 없음. id `draft:<번호>:stale`라서 action에서 옮겨 와도 새 알림이 아닙니다. 닫았다가 다시 열면 **열린 지 3일 이내일 때만** 새 항목으로 다시 알립니다(생성 시각은 그대로라 3일 넘은 초안은 다시 열어도 확인 항목으로만 보입니다) |
| 초안(PR) | 라벨 `초안`이 붙은 **열린 PR**(Chance 승인 흐름의 초안 PR, 작성자·`폐기` 조건은 이슈와 같음)이 열린 지 3일 이하이고, 열린 PR 규칙이 그 PR을 action으로 올리지 않은 상태(검사 기록 없음·검사 진행 중·병합 가능 여부 계산 중·저장소 규칙이 막음·상태 조회 실패, 또는 GitHub의 draft 상태 PR) | action | "초안 대기 — 글 제목" + 채널·PR 번호, 링크는 PR 주소(`/pull/번호`). 새로 생기면 코멘트(@멘션)로 알림. id `draft:<번호>:wait`. 안내: PR을 열어 글을 읽고 병합하면 공개(닫으면 폐기). **그 PR의 열린 PR 줄(`pr:<번호>:…`)은 빼서** 같은 PR이 두 줄이 되지 않게 합니다. 저장소 기본 토큰이 연 PR에는 GitHub 규칙상 검사가 돌지 않아, 열린 PR 규칙만으로는 알림 없는 `검사 결과 없음`(check)으로 남아 승인을 기다리는 초안이 아무 알림 없이 쌓이기 때문입니다 |
| | 열린 PR 규칙이 이미 action으로 올린 상태(병합하면 됩니다·충돌을 풀어야 합니다·검사 실패) | (열린 PR 규칙) | 그 줄이 알리므로 초안 항목을 또 만들지 않습니다(같은 PR이 두 번 알림이 되지 않게). 검사가 끝나 위 초안 항목이 이 줄로 바뀌면 새 id라 한 번 더 알립니다(상태가 바뀌었다는 알림) |
| | 열린 지 3일(`DRAFT_STALE_DAYS`) 넘음(열린 PR 규칙이 action이 아닐 때) | check | "초안 3일 넘게 대기 — …"(PR 번호·병합하거나 `폐기`·닫기 안내). 알림 없음. id `draft:<번호>:stale` |
| 초안 현황 | 레지스트리 블로그의 채널 라벨마다 한 줄, 레지스트리에 없는 채널 라벨의 초안, 채널 라벨 없는 초안 | (표 — 항목이 아님) | 본문 머리 바로 아래. 칸·값·한계는 §3-1 |
| 조회 실패 | 위 소스 중 하나를 읽지 못함 | check | 실패해도 모음은 계속 만들어집니다. 항목이 조용히 빠져 "문제 없음"으로 보이는 것을 막으려고 실패 사실을 남깁니다. 초안 목록을 읽지 못하면 표의 GitHub 초안 칸은 `조회 실패`로 보이고(0이 아님), 이미 알린 초안의 id는 표식에 그대로 남아 복구돼도 같은 초안을 또 알리지 않습니다 |

링크는 모두 절대 주소이며 숫자 id로 직접 만듭니다(API가 준 URL은 쓰지 않음). 시크릿·변수 설정은 `/settings/secrets/actions`·`/settings/variables/actions`, 워크플로 수동 실행은 `/actions/workflows/<파일>`입니다.

### 3-1. 초안 모델과 초안 현황 표 (2026-10-27, 작업요청서 5 PR-B)

**초안 1건 = GitHub 이슈 1개(티스토리·네이버 초안 패키지) 또는 PR 1개(Chance 승인 흐름)**. 초안을 만드는 쪽과 이 모음이 아래 약속을 같이 씁니다.

| 라벨 | 뜻 | 붙이는 쪽 | 색·설명(고정) |
|------|----|-----------|---------------|
| `초안` | 발행을 기다리는 초안 | 초안을 만드는 쪽 | `c2e0c6` · 발행 대기 초안(확인 필요 모음의 초안 현황이 센다) |
| `채널:<채널 라벨>` | 어느 채널의 글인가 — `채널:Chance`·`채널:Blogger`·`채널:티스토리`·`채널:네이버`(한글 Blogger를 등록하면 `채널:Blogger 영문`·`채널:Blogger 한글`). 글자는 `pipeline/blogs.json`의 `channel.label`과 같고, 라벨 이름은 레지스트리에서 만듭니다 | 초안을 만드는 쪽 | `bfdadc` · 초안이 속한 채널: <채널 라벨> |
| `폐기` | 쓰지 않기로 한 초안 | 운영자 | `cfd3d7` · 쓰지 않기로 한 초안(초안 현황에서 빠진다) |

- **센다**: 열려 있고 · 라벨 `초안`이 있고 · 라벨 `폐기`가 없고 · 작성자가 `github-actions` 봇이거나 저장소 소유자·멤버·협업자인 이슈·PR. **닫으면 안 센다**(닫기 = 발행 완료 또는 폐기). 낯선 사람이 라벨을 흉내 낸 것은 세지 않습니다(워치독 이슈와 같은 원칙).
- **라벨 만들기**: 라벨이 저장소에 없으면 이 스크립트가 **점검 끝에**(이슈를 쓴 뒤) 만듭니다 — 휴대폰에서 라벨을 고르고 초안 목록을 거르려면 라벨이 미리 있어야 합니다. 라벨 목록을 한 번 읽어(100건) 없는 것만 만들고(한 번에 최대 10개), 실패해도 점검 결과·종료 코드에는 영향이 없습니다(로그 한 줄, 다음 점검이 이어서 만듦). 연습 실행(`INBOX_DRY_RUN`)과 토큰 없는 로컬 실행은 만들지 않습니다.
- **제목 약속**: `[초안][<채널 라벨>] <글 제목>`(초안을 만드는 쪽의 약속). 이 모음은 앞의 `[초안]`·`[채널]` 표지를 떼고 글 제목만 보여 줍니다(표지가 없어도 동작). 제목은 외부(AI) 글이라 §6의 무력화를 거칩니다.
- **채널 라벨이 여럿이면** 글자 순으로 첫 번째만 씁니다. 레지스트리에 없는 채널 라벨의 초안은 `○○ (미등록)` 줄로, 채널 라벨이 없는 초안은 `(채널 표시 없음)` 줄로 보입니다(조용히 사라지지 않게 — 티스토리·네이버를 레지스트리에 등록하기 전에 초안이 생겨도 보입니다).

**표의 칸** — 머리 `채널 | 대기 초안 | 가장 오래된 | 최신 초안`. 줄은 레지스트리 블로그 순서(Chance → Blogger → …)이고 대기 0이어도 유지합니다(표는 `BOARD_ROWS_MAX`=12줄까지, 넘치는 미등록 채널은 `그 밖의 채널 N개` 한 줄로 합침).

| 대기 초안 칸 | 뜻 |
|--------------|----|
| `N` | 그 채널의 대기 초안(GitHub 이슈·PR) 수. 최신 초안 칸에 번호와 제목이 든 링크(이슈는 `/issues/번호`, PR은 `/pull/번호` 주소) |
| `N+` | 열린 초안 목록이 읽는 상한(100건씩 3쪽 = 300건)에 닿아 **더 있을 수 있음** — GitHub에서 센 칸에 붙고(없으면 `0+`) 표 아래에 그 안내 줄이 붙습니다. 상한 안내(참고 항목)가 본문 길이 제한에 잘려도 표에서 보이게 하려는 것이며, '가장 오래된'도 읽은 범위 안의 값입니다 |
| `0` | 대기 없음 |
| `정지` | 레지스트리 `mode: off`인 채널(대기 초안이 있으면 `N (정지 중)`) |
| `자동 공개` | Chance(`platform: jekyll-git`)가 승인 흐름이 아닐 때 — 레지스트리 `publish_flow`가 없거나 `direct`(작업 E가 정하며 `pr`이면 열린 초안 PR 수를 셉니다). 초안이 아니라 바로 공개됩니다 |
| `N (대략)` | Blogger 채널: 이력(`state.history`)의 `status: draft_uploaded` 중 최근 14일(`DRAFT_WINDOW_DAYS`) 안의 것을 센 **대략치**. 최신 초안 칸은 마지막 업로드 시각(KST, 링크 없음). **이미 게시했는지는 Blogger 쪽 사실이라 여기서 알 수 없습니다** — 확인·게시는 Blogger 대시보드 → 글 → 초안(블로그 ID가 시크릿이라 링크는 싣지 않습니다). 이 안내 줄은 표 아래에 **정지가 아닌 Blogger 채널이 있을 때만** 붙습니다 |
| `조회 실패` | 초안 목록(GitHub 채널) 또는 이력 파일(Blogger)을 읽지 못함 — 0이 아닙니다. 같은 사실이 "확인하면 좋은 것"에도 있습니다 |

- **가장 오래된**은 대기 초안 중 가장 오래 열린 것의 경과 일수(24시간 단위 내림, 하루 미만은 `1일 미만`)입니다. 점검 시각을 본문에 넣지 않는다는 원칙(§4)의 **유일한 예외**: 이 칸이 하루에 한 번 바뀌므로 대기 초안이 있는 채널마다 하루 한 번 본문이 다시 쓰입니다(알림 없음, 변경이 없으면 쓰지 않는 규칙은 그대로).
- **모바일 필터 링크**는 표 아래 마지막 줄입니다: 대기 초안 전체(이슈)·전체(PR)와, GitHub에 초안이 있는 채널마다 `is:open label:초안 label:"채널:<라벨>"` 검색(주소는 퍼센트 인코딩). PR 초안이 있는 채널은 `○○ PR` 링크가 더 있습니다. 채널 라벨이 평범한 글자(영문·숫자·한글·공백·`_`·`.`·`-`, 40자 이하, 비밀 값 모양 아님)가 아니면 링크를 만들지 않습니다(주소에는 무력화를 쓸 수 없어서). 표의 줄은 남습니다.
- 표는 항목이 아니라 본문의 고정 구역입니다. 길이 제한에서는 항목보다 먼저 자리를 잡고, 표 자체가 남은 길이에 안 들어가면 "초안 현황은 길이 제한으로 줄였습니다" 한 줄로 바뀝니다(실행 요약에는 항상 통째로).

**초안을 만드는 쪽에 부탁하는 것**(작업 C·E): ① 위 라벨 셋을 붙입니다(만들기 전에 라벨을 보장해도 됩니다 — 이미 있으면 422로 끝납니다). ② 이슈·PR을 **저장소 기본 토큰(`GITHUB_TOKEN`)으로 만들면 GitHub 규칙상 이 워크플로가 시작되지 않으므로**, 만든 직후 `workflow_dispatch`로 `ops-inbox.yml`을 불러 주세요(`gh workflow run ops-inbox.yml`, 그 워크플로 권한에 `actions: write` 필요 — 다른 워크플로가 같은 이유로 `pages.yml`·`guardrails.yml`을 부릅니다). 부르지 않으면 표는 다음 예약 때(보통 3~6시간 뒤) 갱신됩니다. ③ 제목은 `[초안][채널 라벨] 글 제목`.

### Chance 승인 흐름의 초안 PR (현황판이 알아볼 값)

Chance 승인 흐름(레지스트리 `publish_flow: pr`, 지금 꺼짐 — [`ARCHITECTURE.md`](./ARCHITECTURE.md) §4-4)을 켜면 위 '열린 PR' 규칙에 봇이 만든 초안 PR 이 섞여 들어옵니다. 지금 규칙은 이 PR 을 일반 PR 과 똑같이 다룹니다. 아래는 현황판이 일반 PR 과 구별해 '내 승인을 기다리는 초안'으로 보여 줄 수 있는 표식입니다.

| 값 | 모양 |
|---|---|
| 작성자 | `github-actions[bot]` |
| head 브랜치 | `ai/draft/<YYYY-MM-DD>-s<슬롯>`(정기, 슬롯은 9·18) · `ai/draft/<YYYY-MM-DD>-m<HHMMSS>`(수동 실행). 날짜·시각은 KST |
| 제목 | `[초안][Chance] <한국어 제목> / <영어 제목>`(소독됨, 200자 이하) |
| 라벨 | `초안`, `채널:Chance` |
| 바뀐 파일 | `_posts/…` 두 개(한국어·영어)뿐. 이력(`history.json`)은 PR 에 없다 |
| 본문 체크리스트 | `- [ ] 원문과 수치·사실을 대조했다` / `- [ ] 제목·요약에 문제가 없다` / `- [ ] 병합 = 공개(사람 검토 단계)` |
| 이력 항목(`history.json`) | Chance 기존 필드에 `flow: "pr"`, `branch`(위 head 브랜치), `paths`(글 파일 둘)가 더해진다. 별도 원장 파일은 없다. `paths`의 글이 main 에 있으면 병합됨, 없으면 승인 대기 또는 닫혀 폐기됨 |

- **검사(CI)는 돌지 않습니다(예상).** `GITHUB_TOKEN`으로 연 PR 은 `pull_request` 워크플로를 시작시키지 않아 헤드 커밋에 check-runs 가 없습니다. 지금 규칙은 이를 `검사 결과 없음`(확인)으로 보여 주고(병합 가능 여부가 아직 계산 중이면 '상태 확인 중', 참고), '병합하면 됩니다'(해야 할 일)로 올리지 않습니다. 켠 뒤에 관측해야 하는 값입니다.
- 현황판이 초안을 따로 보이려면 head 브랜치 접두 `ai/draft/`나 라벨 `초안`으로 알아봅니다(제목 접두는 보조). 워치독 `DRAFT_WAITING`도 같은 기준(이 저장소의 `ai/draft/…` 브랜치에서 연 열린 PR)으로 대기 건수와 가장 오래된 초안이 기다린 시간을 셉니다.
- 이력으로 '최근 24시간 글 수'를 세는 '현황' 항목은 초안을 만든 시점에 글이 난 것으로 셉니다(병합 전에도). 승인 흐름을 켜면 이 항목은 공개된 글 수가 아니라 만든 초안 수에 가깝습니다.

## 4. 새 알림이 오는 규칙

- 코멘트는 **새로 생긴 `action` 항목이 있을 때만** 씁니다. 항목마다 안정적인 id가 있고(예: `pr:15:ready`), 본문 맨 끝의 숨은 표식 `ops-inbox:hash=…;items=…`에 "이미 알린 action id"를 적어 둡니다. 다음 점검이 이 표식과 비교합니다.
- PR의 상태가 바뀌면(예: 병합 가능 → 충돌) id가 달라져 새 할 일로 알립니다. 검사가 끝나 `info`가 `action`으로 바뀐 경우도 같습니다.
- 소스 조회가 실패한 점검에서는 그 소스의 이전 id를 표식에 그대로 남깁니다. 조회 실패를 '해소됨'으로 오해했다가 복구 때 같은 항목을 또 알리지 않기 위해서입니다. 초안 목록(`drafts` 소스)은 접두 `draft:`입니다.
- 초안은 새로 열린 이슈·PR마다 `draft:<번호>:wait` action이 하나 생겨 코멘트로 알리고, 열린 지 3일이 넘으면 id가 `draft:<번호>:stale`(check)로 바뀝니다 — action 목록에서 빠질 뿐 새 알림은 없습니다. 닫으면(또는 `폐기`) 목록에서 빠지고, 닫았다가 다시 열면 열린 지 3일 이내일 때만 새 항목으로 다시 알립니다(생성 시각이 그대로라 3일 넘은 초안은 다시 열어도 확인 항목으로만 보입니다).
- 초안 PR은 한 줄만 남깁니다. 열린 PR 규칙이 action으로 올린 상태(`pr:<번호>:ready`·`conflict`·`ci_fail`)이면 그 줄이 알리고 초안 항목은 만들지 않으며, 그 밖의 상태(검사 기록 없음 등)에서는 열린 PR 줄(`pr:<번호>:…`)을 빼고 `draft:<번호>:wait`가 알립니다. 검사가 끝나 `pr:<번호>:ready` 등으로 바뀌면 새 id라 **한 번 더** 알립니다(대기 → 병합 가능으로 상태가 바뀌었으므로). PR 목록이나 상세를 읽지 못한 점검에서도 초안 항목은 그대로 알립니다.
- **한계(초안 PR이 한 번 더 알려지는 경우)**: 초안 PR이 이미 `pr:<번호>:ready`로 알려진 뒤 열린 PR 줄이 일시적으로 action에서 빠지는 점검(병합 가능 여부(`mergeable`)가 다시 null로 돌아옴·상세 조회 실패·열린 PR 목록 조회 실패)에서는 `draft:<번호>:wait`가 새 id라 한 번 더 알립니다(누락이 아니라 중복입니다). 승인 흐름(`publish_flow: pr`)을 켜기 전에 초안 PR 항목 id를 PR 상태와 무관하게 통일하는 것이 권고입니다(후속 작업).
- 본문은 **보이는 내용(해시)이나 알린 id가 바뀐 때만** 다시 씁니다. 같은 입력이면 본문 글자도 항상 같도록 점검 시각·"N시간 전" 같은 값을 본문에 넣지 않습니다(그래서 몇 시간 전에 열렸는지는 시각으로 표시).
- 코멘트를 먼저 쓰고 그다음 본문을 고칩니다. 코멘트가 실패하면 그 id를 표식에서 빼서 다음 점검이 다시 알립니다(알림을 놓치는 것보다 한 번 더 알리는 쪽이 낫다). 이 경우 실행은 빨강으로 끝납니다.
- **이슈를 처음 만들 때도 같은 순서**입니다: 알린 id 없이 이슈를 만들고, 코멘트가 성공한 뒤에야 본문의 표식에 id를 적습니다. 코멘트가 실패하면 고칠 것이 없고(표식에 id가 없으니 다음 점검이 알림), 코멘트는 성공했는데 id를 적는 쓰기가 실패하면 다음 점검이 한 번 더 알립니다(영영 못 알리는 것보다 낫다).
- 이슈를 만들거나 고치지 못하면(권한 오류, 저장소의 Issues 기능이 꺼져 있음 등) 실행이 빨강으로 끝나 Actions 실패 알림이 갑니다. 반대로 **일부 소스를 읽지 못한 것은 빨강이 아닙니다**(조회 실패 항목으로 남음). 스크립트 자신의 버그(예상 밖 예외)만 그대로 빨강입니다.
- 이슈는 항상 1개만 유지합니다: 라벨 `ops-inbox`가 붙은 이슈를 먼저 찾고(제목을 바꿔도 같은 이슈), 없으면 `github-actions` 봇이 만든 이슈에서 같은 제목을 찾습니다(라벨을 지웠거나 라벨 생성이 실패했던 경우). 작성자가 봇·소유자·멤버·협업자가 아닌 이슈는 무시합니다.
- 담당자는 저장소 소유자(`GITHUB_REPOSITORY_OWNER`)입니다. 담당자 지정이 거부되면(HTTP 422) 담당자 없이 만들고, 알림은 코멘트의 @멘션으로 갑니다.
- **휴대폰(텔레그램) 알림은 코멘트와 짝입니다**(선택, 2026-10-27). 시크릿 `TELEGRAM_BOT_TOKEN`·`TELEGRAM_CHAT_ID`가 둘 다 있으면, 점검이 **코멘트를 쓰려고 할 때마다**(위의 새 action 항목 판정 그대로, 연습 실행 제외) 같은 항목의 제목 줄(`inbox.alert_lines`: 코멘트와 같은 개수 제한·같은 소독, @멘션 없음)을 **평문** 한 통(`📌 확인 필요 모음 — 새로 해야 할 일 N건` + 줄, 버튼 `확인 필요 모음 열기`)으로 보냅니다. 코멘트 성공 여부와 무관하게 보내고(휴대폰 알림은 GitHub 쪽이 막혔을 때를 위한 보조 경로이기도 합니다), 서로 영향을 주지 않습니다 — 텔레그램이 실패하거나 예외를 던져도 코멘트·본문 표식·종료 코드는 그대로이고 로그에 `[참고] 텔레그램 알림을 보내지 못했습니다` 한 줄과 노란 경고만 남습니다. 코멘트가 실패해 다음 점검이 같은 항목을 다시 알릴 때는 휴대폰 알림도 한 번 더 갑니다(위 "한 번 더 알리는 쪽이 낫다"와 같은 원칙). 이미 알린 항목은 표식 때문에 다시 보내지 않습니다. 시크릿이 없으면 이 스크립트의 출력은 예전과 같습니다. 설정·점검: [`TELEGRAM_SETUP.md`](../.github/editorial/TELEGRAM_SETUP.md), 구조: [`ARCHITECTURE.md`](./ARCHITECTURE.md) §4-5.

14. 라벨 만들기는 있으면 좋은 일이라 이슈를 쓴 뒤에 하고 실패해도 넘어갑니다. 이미 있는 라벨은 **이름만 보고** 색·설명을 바꾸지 않습니다(운영자가 손으로 바꾼 색을 되돌리지 않으려는 것 — 고정 색·설명으로 되돌리려면 그 라벨을 지우고 점검을 한 번 더 돌립니다).
15. 숨은 표식은 알린 action id를 80개(`MARKER_IDS_MAX`)까지만 남깁니다. 열린 action이 80개를 넘으면(초안 약 70건 이상 — 다른 알림도 같은 80개를 나눠 씁니다) 정렬상 뒤의 id가 표식에 남지 못해 점검마다 다시 알려집니다. 초안을 이렇게 쌓아 두지 않는 운영(적체 방지)이 전제입니다.
16. 초안 현황 표를 만들다 예외가 나면(예: 레지스트리 항목의 `key`가 문자열이 아닌 값 — CI의 레지스트리 검증이 막는 오류입니다) 그 점검에서는 표만 빼고 실행 로그에 `[참고] 초안 현황 표를 만들지 못해 이번 점검에서는 뺍니다 …` 한 줄을 남깁니다. 항목·알림·이슈 갱신·종료 코드는 그대로입니다(표는 있으면 좋은 구역이라 모음 전체를 죽이지 않습니다).

## 6. 보안

- **쓰기는 이 워크플로의 `GITHUB_TOKEN`만** 씁니다. 권한은 `contents: read`, `actions: read`, `checks: read`, `pull-requests: read`, `issues: write`가 전부이며 체크아웃은 자격 증명을 남기지 않습니다(`persist-credentials: false`). 파일·브랜치·PR은 만들지 않습니다. 쓰는 것은 모음 이슈·코멘트와 초안 모델의 라벨(`issues: write`로 가능)뿐입니다.
- **이벤트 트리거(`issues`·`pull_request`, 2026-10-27)**: ① job `if`가 `초안` 라벨이 있는 이슈·PR(또는 방금 `초안` 라벨을 뗀 이벤트)만 통과시킵니다. ② `pull_request`는 **이 저장소의 브랜치에서 온 PR만**(`head.repo.full_name == github.repository`, `pr-scope-check.yml`과 같은 관례) — 포크 PR의 토큰은 읽기 전용이라 쓸 수도 없고 포크의 것을 읽을 이유도 없습니다. `pull_request_target`은 쓰지 않습니다(검증기 WF-3). ③ 이벤트의 값(이슈·PR 제목·본문·브랜치 이름·라벨 설명)은 `if`에서 라벨 이름과 저장소 이름을 견주는 데만 쓰이고 **셸 명령·환경변수에는 들어가지 않습니다**(`run`은 `python scripts/ops_inbox.py` 한 줄). 스크립트는 이벤트 값을 읽지 않고 API로 다시 조회합니다. ④ PR 이벤트에서는 **기본 브랜치의 코드**를 체크아웃해 돌립니다(PR 쪽 코드를 쓰기 권한이 있는 토큰으로 돌리지 않는다 — `pr-scope-check.yml`과 같은 원칙). ⑤ `concurrency`(그룹 `ops-inbox`, 취소 없음)로 한 번에 하나만 돌고, 몰린 이벤트는 가장 새로운 대기 하나로 합쳐집니다(그 실행이 전부 다시 읽으므로 빠지는 것이 없습니다). `concurrency`는 워크플로 맨 위가 아니라 **job에** 둡니다 — 맨 위에 두면 초안과 무관해 job이 건너뛰어질 이벤트의 실행도 같은 줄에 서서 기다리던 진짜 갱신을 밀어낼 수 있습니다(job의 `if`가 거짓이면 그 job은 줄에 서지 않는 것으로 알고 있으며 병합 뒤 관측이 필요합니다 — 틀렸다면 최악은 다음 예약 때까지 갱신이 늦어지는 것입니다).
- 초안 이슈·PR의 **제목·채널 라벨 이름은 외부(AI·사람) 글**입니다. 표와 항목 모두 위 무력화를 거치고(`|`는 전각 `｜`, 표 칸 안의 링크 글에도 같습니다), 모바일 필터 링크의 주소에는 무력화를 쓸 수 없으므로 채널 라벨이 평범한 글자일 때만 링크를 만듭니다(§3-1). 낯선 사람이 연 이슈는 라벨이 있어도 세지 않습니다.
- PR 제목·주석 문구·이슈 제목·이력 사유처럼 **외부에서 온 글은 데이터**입니다. 한 줄로 접고(개행·제어 문자 — [`pipeline/console.py`](../pipeline/console.py)의 `one_line`을 씁니다), 글자 순서를 뒤집는 제어 문자는 지우고, `@`는 전각 `＠`로(멘션 알림 방지, 문자 참조 `&#64;`도 막으려고 `&`도 전각), `<`는 전각 `＜`로(HTML·표식 위조 방지), 링크 문법 문자와 코드 표시는 바꾸고, 글 끝의 역슬래시는 지우고(뒤에 붙는 `]`·`**`를 이스케이프해 링크·굵은 글씨가 깨져 보이므로 — PR 제목·초안 제목 모두 같은 `ext()`를 거칩니다), 줄 머리 `::`와 `##[`는 풀어 쓰며(워크플로 명령 위조 방지), 비밀 값 모양(`pipeline/secret_patterns.py`)은 가리고, 길이를 제한합니다. 렌더러가 한 번 더 같은 안전망을 거칩니다.
- 코멘트의 @멘션은 소유자 한 명뿐이며 이 모듈이 직접 붙입니다. 항목 제목 속 `@이름`은 멘션이 되지 않습니다.
- 텔레그램으로는 코멘트와 **같은 공개 정보**(항목 제목 줄)만 보냅니다. 토큰·채팅 ID 는 단계 `env`로만 넘어가고 어떤 출력에도 나오지 않습니다(`docs/SECURITY_GUARDRAILS.md` G-C12).
- 숨은 표식은 본문 맨 끝의 마지막 것만 읽고, 외부 글에서는 `<`가 바뀌어 표식을 흉내 낼 수 없습니다.
- 낯선 사람이 같은 제목의 이슈나 `[Watchdog]` 제목의 이슈를 만들어도 무시합니다(작성자 확인). 포크 PR은 "병합하면 됩니다" 대상에서 뺍니다.
