# 새 세션 시작·마감 가이드

> 새 AI 세션(Claude Code 등)을 시작할 때와 하루 작업을 마칠 때의 **고정 절차**입니다.
> 사용자는 비개발자이고 회사 PC에서 일하며 **파일을 PC 밖으로 꺼낼 수 없습니다.**(2026-11-04 당시의 값입니다 — 2026-11-15 에 작업 PC 가 다른 공용 PC 로 바뀌었고 운영자가 AI 운영을 개인 PC 로 옮길 수 있습니다. 지금 값은 작업내용 §0-A·§0-3 이고, 이번처럼 PC 를 또 옮길 때는 이 문서 §8 입니다.) 세션을 새로 열면 로컬 PC에 저장소 사본이 없을 수 있으므로, **모든 진실은 GitHub `shine88pc/chanceblog`의 `main`과 열린 PR(`ai/*` 브랜치)에 있습니다.** AI의 개인 기억(메모리)·이전 대화 요약보다 이 저장소의 문서가 우선합니다.

## 2. AI의 첫 30분 (순서 고정)

### 2-1. 작업 환경 만들기 (Windows 회사 PC 기준 — 2026-11-04 값, 새 PC·개인 PC 는 2-4 와 §8)

- clone: `git clone https://github.com/shine88pc/chanceblog.git chanceblog` (공개 저장소라 읽기는 로그인이 필요 없습니다).
- 작성자 설정은 **clone 안에서만**(저장소 로컬 설정), **사람이 만든** 기존 커밋의 작성자와 같게 둡니다 — 최신 커밋이 봇(`🤖 자동 포스팅…`)일 수 있으니 `git log -8 --format="%an <%ae> %s"` 로 사람 커밋을 찾습니다(최근 AI 요청·문서 커밋은 `이름 <메일>` 모양). 전역 git 설정은 건드리지 않습니다.
- 시스템 `core.autocrlf=true`는 **끄지 않습니다.** 작업 사본이 CRLF로 보이는 것은 정상이고, 끄면 모든 파일이 수정된 것으로 보입니다.
- 한글 커밋 메시지는 UTF-8 파일에 써서 `git commit -F 파일`로 넘깁니다(셸 인자로 넘기면 인코딩이 깨질 수 있습니다).
- 파이썬은 `PYTHONUTF8=1`을 붙여 실행합니다(한국어 Windows 콘솔 cp949 문제). 코드는 Python 3.10에서 돌아야 하며 3.12 전용 문법은 금지입니다.
- 검증 도구: `python -m venv .venv` 후 `.venv\Scripts\pip install -r requirements-dev.txt pyflakes vermin`. 기준선 확인: `python scripts/validate_repo.py`(오류 0), `python -m unittest discover -s tests`(전체 통과. 일부만 돌릴 때는 `-s tests -p "test_xxx.py"`).
- push 자격증명: Git Credential Manager가 브라우저 로그인으로 처리합니다. 비대화형 push가 인증 오류로 막히면 사용자에게 터미널 탭에서 한 번 로그인해 달라고 요청합니다(환경변수 `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=false`로 무한 대기를 막습니다). force push는 하지 않습니다.
- `gh` CLI는 없습니다(2026-11-23 이 PC 에서도 없음을 다시 확인 — 새 PC 는 `where gh` 로 본다). 병합 가지(`ai/claude/M###-…`)는 push 하고 검사가 초록이면 `auto-pr.yml` 이 PR 을 자동으로 만들고(병합은 운영자만 — AGENTS §2-1 의 2번·5번), 그 밖의 PR은 웹에서 만듭니다: `https://github.com/shine88pc/chanceblog/compare/main...<브랜치>?expand=1`. 제목·본문은 `.github/pull_request_template.md` 형식을 따릅니다.
- 파이썬 패치 스크립트에 백슬래시·`$`가 들어갈 때 셸 heredoc은 문자를 망가뜨릴 수 있습니다. 파일로 만들어 실행합니다.

### 2-2. 상태 읽기

- 이미 반영된 것: `git log --oneline -20 origin/main`, `WORKLOG.md` 최신 항목, `docs/DEFECT_REGISTER.md`(결함 상태와 하단 관측 체크리스트).
- 열린 PR과 브랜치: `https://github.com/shine88pc/chanceblog/pulls`, `git branch -r`. 병합되지 않은 PR이 있으면 그 PR 본문의 검증 증거와 남은 지적부터 읽습니다.
- 최근 Actions 실행: 공개 API(`curl -s "https://api.github.com/repos/shine88pc/chanceblog/actions/runs?per_page=30"`)로 읽을 수 있습니다(로그인 없이 IP당 시간당 60회 제한이라 아껴 씁니다).
- 로그 원문과 Settings 화면은 로그인이 필요합니다. 필요하면 사용자에게 로그인 화면을 열어 달라고 하고, **로그인은 사용자가 직접** 합니다(AI는 비밀번호·토큰을 입력하지 않습니다).

## 3. 일하는 방식 (이 저장소의 약속)

1. 변경은 **작은 PR**로 합니다. 브랜치 이름 `ai/<AI이름>/<주제>`. T2 이상은 **독립 검증**(다른 세션이 새 clone에서 diff와 직접 실행 결과만 근거로 검증)을 거친 뒤 병합합니다.
2. 구현을 맡기는 하위 에이전트는 작업 폴더 밖의 별도 clone에서 일하고 일반 push만 합니다. 문서·WORKLOG·병합은 총괄 세션이 통합합니다.
3. 서로 같은 문서·워크플로를 건드리는 PR은 **순차**로 병합합니다. 병합 뒤 main에서 확인합니다.
4. 봇이 main에 직접 커밋합니다. 작업 전에 항상 최신 main을 받습니다. main 보호 규칙은 "삭제·force push 차단"만 허용하고, PR 필수·승인 필수·상태 검사 필수는 **켜지 않습니다**(자동 발행이 멈춥니다). 다만 보호 규칙이 없다는 것이 AI 가 main 에 직접 push 해도 된다는 뜻은 **아닙니다** — AI 의 main 직접 push 는 어떤 경우에도 금지입니다(`AGENTS.md` §2-1 의 2번).
5. 병합한 PR의 브랜치는 지우지 않습니다(브랜치 삭제는 T3, 사용자 승인).
6. 결과 보고는 숫자와 실제 출력으로 합니다. 실행하지 않은 검증을 통과했다고 쓰지 않습니다.

운영자가 AI 운영을 개인 PC 로 옮길 수 있습니다(확인 031 의 배경 — `docs/AGENT_RUNBOOK.md` §8). 이 절은 2026-11-15 이관의 핸드셰이크(번들 가지 `ai/claude/NO-MERGE-migration-bundle` 의 `인수인계/이관_번들/README.md`)를 이번 이관에 맞게 요약한 것입니다. **번들 가지는 병합 대상이 아니고 11-15 이관용 임시판입니다** — 도구의 정본은 저장소 `인수인계/도구/` 이고 번들 가지의 `work/` 는 그 이전 판입니다(차이는 도구 README 9-1). **이 절차는 옛 PC·새 PC 를 실제로 오가며 돌려 본 것이 아니라** 11-15 이관의 실제 절차와 도구 코드를 읽고 쓴 것이니, 안 맞는 곳이 있으면 읽은 그대로 따르지 말고 막힌 곳을 번호 있는 요청으로 알립니다.

### 8-1. 옛 PC 에서 (이관을 시작하는 AI)

1. **돌던 갈래를 올립니다**: 진행 중 갈래의 WIP 가지를 `ai/claude/NO-MERGE-<이름>-wip` 이름으로 push 합니다 — 작업 폴더의 WIP 는 그 PC 에만 있어 폴더를 지우면 사라집니다(작업내용 §0-7). 저장소가 공개이니 올리기 전에 비밀·개인 값·윈도 계정 이름이 없는지 훑습니다(변경 파일에서 계정 폴더 경로·메일 모양·토큰 모양 검색). **이 가지는 병합하지 않습니다.** 워크플로(`.github/workflows/`)를 바꾸는 갈래의 가지는 push 하는 순간 `ai/claude/**` push 로 도는 검사(설계된 동작)가 그 가지의 바뀐 파일로 실행될 수 있으니, 올리기 전에 바뀐 워크플로의 `on:` 과 권한을 읽습니다.
2. **감시기·크론을 끕니다**: 세션 안 크론(`CronList` 로 확인해 지움)과 감시기(Monitor)를 멈춥니다. 새 PC 가 켜진 뒤에도 옛 PC 가 알림·크론을 보내면 요청 번호 R·진행 현황 P·병합 M 번호가 겹치고 병합완료 확인이 이중으로 나갑니다(두 PC 동시 가동 금지).
3. **이번 이관용 상태 파일을 올리고 '끝났다'를 표시합니다**: 11-15 규칙을 따릅니다 — 번들 가지 `인수인계/이관_번들/state/OLD_PC_STATUS.json` 의 `state` 를 `PREPARING` → `READY_TO_HAND_OVER`(이전 준비 완료 — 새 PC 가 시작해도 됨) → `HANDED_OVER`(새 PC 가 넘겨받음을 확인 — 옛 PC 는 더 이상 알림·요청을 보내지 않음) → `CLOSED`(옛 PC 정리 끝)로 바꿔 올리고, 요청 가지에 `info` 알림(제목에 `이전 준비 완료`)을 남깁니다. `sequence` 는 갱신마다 1 씩 늘리고 `updated_at` 은 갱신 시각이며, 아직 끝나지 않은 일(`in_flight_on_old_pc`)과 새 PC 가 할 일(`next_for_new_pc`)을 새로 채웁니다. **주의: 2026-11-23 현재 그 파일에 남은 값은 11-15 이관의 마지막 값**(`HANDED_OVER`, `sequence` 4, 11-16 16:19)**이라 이번 이관의 신호가 아닙니다** — 이번 이관의 값은 `sequence` 5 이상이고 `updated_at` 이 이번 이관 시작(`이전 준비 완료` 알림) 이후여야 합니다. 파일 이름·위치를 달리 정하면 그 알림이 알립니다.
4. **도구·기억 사본을 새로 고칩니다**: 이 PC 의 도구(작업 폴더 W 와 `W/scratch/`)와 AI 기억에 저장소 사본보다 새로운 것이 있으면 스테이징 스크립트 `scratch/tools_stage.py`·`scratch/memcopy_stage.py`(읽기만 합니다 — 저장소는 건드리지 않고 개인 정보를 가린 사본을 스테이징 폴더에 만듭니다. 쓰는 법은 도구 README 9-7 — 회사·개인을 알아볼 수 있는 낱말은 환경 변수 `STAGE_FORBID` 로 줍니다)로 사본을 만들고, 저장소(`인수인계/도구/work/`·`인수인계/AI_기억/`)에 반영하는 것은 평소처럼 병합 부탁으로 올립니다.
5. **폴더 삭제·GitHub 로그아웃은 AI 가 하지 않습니다**(운영자 몫 — 작업내용 §3 47번).

### 8-2. 새 PC 에서

1. **옛 PC 가 끝났다는 신호를 확인한 뒤에만 알림·크론을 가동합니다.** 신호는 번들 가지 `OLD_PC_STATUS.json` 의 `state` 가 `READY_TO_HAND_OVER` 이상이고 `sequence`·`updated_at` 이 이번 이관의 값이며 요청 가지에 `이전 준비 완료` 알림이 있는 것입니다(`git ls-remote origin refs/heads/ai/claude/NO-MERGE-migration-bundle` 로 머리를 읽고 `git show origin/ai/claude/NO-MERGE-migration-bundle:인수인계/이관_번들/state/OLD_PC_STATUS.json` 으로 읽습니다). `PREPARING` 이면 1–2분 간격으로 다시 읽으며 기다리고(그 사이 설치·도구 받기 같은 읽기·준비는 해도 됨), 신호를 못 올리고 옛 PC 가 꺼졌을 수도 있으면 요청 가지 머리와 번들 가지 머리를 5분 간격으로 두 번 읽어 움직이지 않는지 봅니다 — 이것은 신호가 없을 때의 임시 점검이고 운영자가 정하면 고칩니다. 그래도 모르면 알림·크론을 켜지 말고 읽기·분석·초안까지만 하며 번호 있는 확인 요청으로 운영자에게 묻습니다.
2. **push 권한을 점검합니다**: 운영자가 이 PC 에서 GitHub 에 로그인(AI 는 비밀번호·토큰을 입력하지 않음)한 뒤 `docs/AGENT_RUNBOOK.md` J1 의 8번 `push --dry-run` 이 종료 코드 0 인지 봅니다. 안 되면 읽기·분석·초안까지만 하고 운영자에게 알립니다.
3. **작업 폴더 W 를 만듭니다**: 블로그 저장소를 clone 하고 `python -X utf8 인수인계/도구/setup_workspace.py <W>`(2-4 의 2번). 도구 안의 `C:/work/ai` 는 옛 PC 의 W 이름이니 다른 경로를 쓰면 도구 README 9-2 의 표를 따릅니다.
4. **옛 PC 가 올린 WIP 가지를 받습니다**: `git -C <W>/wt_r30 worktree add <새 폴더> -b <가지> origin/<가지>` 로 `NO-MERGE-…-wip` 가지를 받아 이어 갑니다(`<W>/wt_r30` 자체는 요청 가지 작업 폴더라 checkout·커밋하지 않습니다).
5. **번호는 늘 `next_notice_no.py`** 가 정합니다(요청 가지의 최댓값 +1 — R·P·M·확인 모두). 문서의 번호는 쓴 시각 기준입니다.
6. **첫 보고와 ACK**: `info` 요청 한 건(제목에 `이관 완료` — 이어받은 상태·옛 PC 와 다른 곳·못 읽은 것·운영자에게 필요한 것)을 보낸 뒤 번들 가지에 `NEW_PC_ACK.json`(`STARTED` → `TOOK_OVER`, 양식 `NEW_PC_ACK.template.json`)을 올립니다. 11-15 의 `TOOK_OVER` 값이 파일에 남아 있으니 `updated_at` 을 새로 씁니다.
7. **그다음에야 크론·감시를 켭니다** — 개인 PC 에서 켤지는 미정입니다(`docs/AGENT_RUNBOOK.md` §8-3, 기본 가정은 '운영자가 켠 동안만'). 새 PC 가 개인 PC 이면 AI 사용량(무료 한도)도 먼저 봅니다.
