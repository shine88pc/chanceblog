## 1. 상태와 한눈에

**상태: 꺼져 있음.** AI 병합을 켜는 변경이 **별도 병합 요청**으로 들어와 **운영자가 직접 병합**하기 전까지 AI 는 아무것도 병합하지 않습니다. 지금까지처럼 병합은 운영자만 합니다.

| 항목 | 내용 |
|---|---|
| 무엇이 켜지나 | 켜지면, 운영자가 `M075 승인` 처럼 병합 번호를 적어 승인한 PR **한 건**만 AI 가 병합합니다 |
| AI 가 독자 판단으로 병합하나 | 아니오 — AI 는 변경을 쉬운 말로 설명하고, 운영자가 번호를 적어 승인해야만 움직입니다 |
| 승인 방식 | 병합 번호와 함께 한 줄(`M075 승인`). `확인했습니다` 같은 말만으로는 승인이 아닙니다 |
| 승인의 유효 범위 | 그 PR 한 건뿐. 다른 PR 이나 이후 변경에 다시 쓸 수 없고, 승인 뒤 새 커밋이 더해지면 무효입니다 |
| AI 가 병합할 수 있는 것 | 일반 프로그램 코드·일반 UI·시험·문서·로컬 저장·조회·오류 수정·접근성·성능 개선 |
| 승인해도 운영자가 직접 병합하는 것 | 12항목(§7) — 워크플로·광고·공개 글·발행 정지와 재개·키와 비밀·의존성·데이터 삭제·외부 비용·main 보호 설정 등. 그리고 안전 장치 파일·새 외부 접속 코드 같은 12항목 밖의 표시(§7-5) |

## 2. 운영자 결정 요지

운영자가 2026-11-15 확인 016 에 `016/3` 으로 답한 내용의 요지입니다. 아래는 **켜졌을 때 적용할 규칙**이고, 지금은 꺼져 있음 — 켜는 변경이 운영자 직접 병합으로 들어오기 전까지 AI 는 병합하지 않습니다.

1. **독자 판단 자동 병합이 아닙니다.** AI 가 변경 내용을 쉬운 말로 설명하고, 운영자가 해당 병합 번호를 명시해 승인하면 AI 가 그 PR 을 병합합니다.
2. 병합 전에 개발자가 아닌 사람도 이해할 수 있게 6가지를 설명합니다 — 전문용어가 아니라 사용자가 체감할 변화 중심으로(§4).
3. 승인은 반드시 병합 번호와 함께 합니다(예: `M075 승인`). 다섯 가지 표현만으로는 승인으로 보지 않습니다(§5).
4. AI 는 승인한 병합 번호와 지금 열려 있는 PR 번호가 일치할 때만 병합합니다. 승인은 그 PR 한 건에만 유효하고 재사용할 수 없습니다. 승인 뒤에도 병합 직전에 8가지 조건을 다시 확인하고, 새 커밋이 더해지거나 변경 범위가 달라지면 기존 승인은 무효라서 새 설명과 새 승인을 받습니다(§5·§6).
5. AI 가 병합할 수 있는 범위는 7가지이고, 12항목은 승인해도 AI 가 직접 병합하지 않고 운영자 직접 병합으로 둡니다(§7).
6. 운영자 PC 의 Git 자격 증명으로 main 에 직접 push 하는 방식은 쓰지 않습니다. 흐름은 정해져 있고 main 직접 push 는 금지입니다(§3·§8).
7. 병합 뒤 main 검사에서 문제가 나오면 추가 변경을 자동 병합하지 않고, 해당 병합을 되돌리기 위한 요청과 쉬운 원인 설명을 먼저 보냅니다(§9).
8. 병합 완료 알림에는 7가지를 담습니다(§9).
9. **이 정책을 먼저 문서화하고 시험합니다.** 실제 AI 병합 기능을 켜는 변경은 별도 병합 요청으로 보내고, 그 변경은 운영자가 직접 병합합니다(§11).
10. 첫 운영은 일반 코드 또는 문서 PR 3건이고, 6가지 조건을 모두 만족해야 계속 쓰며, 한 건이라도 문제가 생기면 AI 병합을 즉시 중지하고 기존 운영자 직접 병합으로 돌아갑니다(§10).

## 3. 흐름 7단계

켜졌을 때의 흐름입니다. 지금은 꺼져 있어서 4·5단계를 운영자가 직접 합니다(표 아래의 굵은 글씨 참고).

AI 가 PR 작성 → 검사와 독립 검증 → 쉬운 병합 설명 발송 → 운영자가 병합 번호를 명시해 승인 → AI 가 승인된 PR 병합 → main 사후 검사 → 병합 완료 알림

| 단계 | 하는 일 | 맡는 코드 |
|---|---|---|
| 1. PR 작성 | AI 가 변경을 PR 로 올립니다. 제목은 `[M075] …` 처럼 병합 번호로 시작합니다 | `pr_title_label` |
| 2. 검사와 독립 검증 | 자동 검사 전체와, 구현한 쪽이 아닌 다른 쪽의 독립 검증을 거칩니다. 이때 변경이 12항목에 걸리는지 분류합니다 | `classify_change` |
| 3. 쉬운 병합 설명 발송 | §4 의 양식으로 설명을 만들어 운영자에게 보냅니다 | `render_explanation`·`explanation_problems` |
| 4. 승인 | 운영자가 `M075 승인` 처럼 번호를 적어 보냅니다 | `parse_approval` |
| 5. 병합 | AI 가 병합 직전 8조건을 다시 확인하고, 모두 통과하면 PR 병합으로 그 한 건만 병합합니다 | `check_preconditions`·`merge_method_allowed` |
| 6. main 사후 검사 | 병합된 main 에서 검사를 다시 돌립니다 | (켜는 변경이 맡음) |
| 7. 완료 알림 | §9 의 7항목을 담아 알립니다 | `completion_notice_problems` |

**지금(꺼져 있음)은 4·5단계 대신 운영자가 PR 화면에서 직접 병합합니다.** 1–3단계의 설명 양식에는 그 사실을 알리는 표지가 붙습니다(§4).

## 4. 쉬운 병합 설명 양식

### 4-1. 6항목

병합 전에 아래 6가지를, 개발자가 아닌 사람도 이해할 수 있는 말로 씁니다. 전문용어만 나열하지 않고 실제 사용자가 체감할 변화 중심으로 씁니다.

| 항목 | 담을 내용 |
|---|---|
| 무엇을 바꾸나요? | 무엇을 바꾸는지 |
| 왜 필요한가요? | 왜 필요한지 |
| 사용할 때 무엇이 달라지나요? | 프로그램을 사용할 때 무엇이 달라지는지 |
| 위험은 무엇인가요? | 기존 기능에 미치는 영향과 위험 |
| 검사 결과 | 검사와 독립 검증 결과 |
| 되돌리기 | 문제가 생겼을 때 되돌리는 방법 |

항목마다 8자 이상의 한글 문장(한글 4자 이상)이어야 하고, 줄 바꿈은 한 줄로 접힙니다(글 속 줄 바꿈으로 양식을 흉내 낼 수 없게).

### 4-2. 표준 양식과 예시

아래 예시는 모듈이 만든 글을 그대로 붙인 것입니다(시험이 같은 글인지 대조합니다). 첫 줄에 병합 번호, 둘째 줄에 대상 PR·머리 커밋이 오고, 이어서 6항목, 변경 파일 목록, 운영자 전용 12항목 점검표, 병합 방식 줄, 승인 안내가 붙습니다. 지금처럼 꺼져 있는 동안은 맨 끝에 승인해도 AI 가 병합하지 않는다는 줄이 한 줄 더 붙습니다.

```text

대상 PR: #198 · 머리 커밋: a1b2c3d
무엇을 바꾸나요? 앱을 닫아도 작성 중인 초안을 다시 열 수 있도록 저장 기능을 추가합니다.
왜 필요한가요? 현재는 앱을 닫으면 초안이 사라집니다.
사용할 때 무엇이 달라지나요? 저장 버튼과 저장된 초안 목록이 추가됩니다.

검사 결과 전체 검사와 독립 검증을 통과했고 기존 복사 기능에는 변화가 없습니다.
되돌리기 문제가 발생하면 M075 병합만 되돌리면 이전 상태로 복구됩니다.
변경 파일 (2개)

- tests/test_drafts_store.py
```

- 점검표의 12항목은 **분류 결과에서 채워집니다**(`classify_change` — 걸린 항목은 `예`, 나머지는 `아니오`). 표준 양식 글을 만드는 `render_explanation` 은 점검표를 글로 받지 않고 넘겨받은 분류 사전에서 채우므로 사람이 점검표 글을 직접 적을 수는 없습니다. 그러나 `render_explanation` 은 그 분류 사전의 모양, 분류의 경로가 지금 변경 파일 목록과 같은지, 분류 안에 모순(`ai_ok` 인데 걸린 항목이 있거나 그 반대)이 없는지만 확인하고 `classify_change` 로 계산했는지는 모릅니다 — 워크플로 경로인데 `ai_ok`·걸린 항목 없음으로 일관되게 지어낸 분류 사전을 넘기면 점검표가 전부 `아니오` 인 글이 만들어지고 `explanation_problems` 도 문제를 찾지 못합니다. 병합 직전 재확인(§6)은 경로·바뀐 줄 규칙으로 분류를 다시 계산하므로 그 규칙에 걸리는 변경은 지어낸 분류로 병합이 통과하지 못하지만(사람이 하는 선언 6항목은 다시 계산하지 못합니다 — §7-3), 운영자가 읽는 설명 글의 점검표는 거짓일 수 있습니다. 12항목 밖의 표시(안전 장치 파일 등)가 걸리면 점검표 아래에 `12항목 밖의 표시: …` 줄이 붙습니다. **다만 손으로 쓴 설명 글을 `explanation_problems` 로 점검하는 경로에서는** 점검표가 모두 `아니오` 이고 모양이 맞으면 통과하며, 그 `아니오` 가 실제 분류와 같은지는 코드가 모릅니다(§7-7). 그 경로의 마지막 방어선은 독립 검증자입니다.
- **12항목이 전부 `아니오` 이고 그 줄이 없어야** AI 병합 대상입니다. 하나라도 `예` 이거나 빠지거나, 같은 항목이 두 번 나오거나, 점검표 밖(빈 줄 뒤 등)에 점검표 항목처럼 보이는 줄이 있거나, 알 수 없는 줄이 있으면 AI 병합 대상이 아니고 운영자가 직접 병합합니다.
- 병합 방식 줄은 정해진 두 문장 중 하나와 **글자 그대로 같아야** 합니다. 지금은 `지금은 AI 병합 기능이 꺼져 있어 운영자께서 직접 병합해 주세요.` 이고, 켜진 뒤에는 `승인하시면 AI 가 이 PR 한 건만 PR 병합으로 병합합니다. main 에 직접 push 하지 않습니다.` 로 바뀝니다. 다른 말이 덧붙으면 문제이고, main 직접 push 나 운영자 PC 자격 증명 이야기가 들어 있으면 따로 알립니다.
- 꺼져 있는 동안은 `승인 예` 줄 바로 다음에 `지금은 꺼져 있어 이 승인 글을 보내도 AI 는 병합하지 않습니다.` 줄이 붙습니다. 켜진 뒤의 설명에는 이 줄이 없습니다.
- 첫 줄의 번호·`승인 예` 의 번호·PR 제목의 `[M###]` 는 모두 같아야 합니다. 글 속에 다른 번호의 `M### 승인` 문구가 들어 있으면 문제로 봅니다.
- 보이지 않는 글자(방향을 바꾸는 글자·너비 없는 글자)가 있으면 문제로 봅니다 — 운영자가 눈으로 읽는 글을 속이는 데 쓰이기 때문입니다.
- 설명이 정말 쉬운지는 코드가 알 수 없습니다. 길이와 한글 여부만 점검하고, 쉬운 말인지는 독립 검증자가 읽고 확인합니다.

## 5. 승인 방식

이 절은 켜진 뒤의 동작이며 지금은 꺼져 있어 승인 글을 보내도 AI 는 병합하지 않습니다.

### 5-1. 허용하는 정확한 형태

글 **전체**가 `M###` 한 개 + 공백 + `승인` 일 때만 승인입니다. 예: `M075 승인`

- 앞뒤 공백과 줄 바꿈, 끝의 마침표 하나는 허용합니다. `m075 승인` 처럼 M 이 소문자여도 `M075` 로 읽습니다. 번호와 `승인` 사이는 공백(칸) 또는 탭 하나 이상입니다.
- 번호는 M + 숫자 세 자리(M001–M999) 또는 네 자리(M1000–M9999)입니다. 알림 번호의 표준 규칙(`pipeline/notify.py` 의 `NOTICE_NO_RE`)과 같은 값이며, 앞에 0 을 더 붙인 `M0075`·`M000` 은 번호가 아닙니다.
- 승인을 읽는 코드는 `parse_approval`(번호 또는 없음)과 `check_approval_text`(이유와 다시 보낼 안내까지)입니다.

### 5-2. 불허 문구 5개

아래 표현만으로는 병합 승인으로 판단하지 않습니다.

- 확인했습니다
- 진행하세요
- 좋아 보입니다
- 기본값대로
- 다음 단계 진행

### 5-3. 모호하면 거절하고 정확한 형태를 다시 안내합니다

승인이 아닌 글에는 이유와 함께 `병합 승인은 병합 번호와 함께 한 줄로 M075 승인 처럼 보내 주세요.` 라는 안내를 돌려줍니다. 아래는 모두 승인이 아닙니다.

| 글 | 승인이 아닌 이유 |
|---|---|
| `확인했습니다` 등 불허 문구만 있는 글 | 번호가 없고 승인 문구가 아님 |
| `승인`·`승인합니다` | 번호가 없음 |
| `M075 M076 승인` | 번호가 둘 이상이라 어느 병합인지 모름 |
| `M075 승인하되 이름은 바꿔 주세요` | 번호와 승인 뒤에 다른 말이 붙음 |
| `오늘 M075 승인` | 다른 문장 속에 섞인 번호 |
| `M75 승인`·`M0075 승인`·`M000 승인` | 표준 번호가 아님 |
| `승인 M075`·`M075승인`·`M075: 승인` | 순서가 다르거나 칸이 없거나 기호가 낌 |
| 줄이 나뉜 글 | 한 줄이어야 함 |
| 전각 글자·보이지 않는 글자가 섞인 글 | 겉모습이 같아도 다른 글자 |

### 5-4. 승인은 그 PR 한 건에만 유효합니다

- AI 는 승인한 병합 번호와 지금 열려 있는 PR 의 번호(제목의 `[M075]`)가 같을 때만 병합합니다(`approval_matches`).
- 같은 승인으로 다른 PR 을 병합하거나, 같은 PR 을 두 번째 승인으로 다시 병합하려는 시도는 거절합니다(`ApprovalLedger`). 거절해도 기록은 바뀌지 않습니다.
- 승인 뒤에 새 커밋이 더해지거나 변경 파일 목록이 달라지거나 번호가 맞지 않으면 기존 승인은 **무효**이고, 새 설명과 새 승인을 받아야 합니다(`approval_still_valid`).
- **승인 때의 머리 커밋(`approved_head_sha`)은 쉬운 병합 설명을 보냈을 때의 머리 커밋**입니다. 승인 글이 도착했을 때 PR 의 머리 커밋이 설명을 보냈을 때와 다르면, 운영자는 지금 내용이 아니라 옛 설명을 승인한 셈이라 그 승인은 **무효**입니다. 두 값을 함께 담는 기록이 `ApprovalRecord` 입니다(`explained_head_sha` 와 `head_sha_at_approval` 이 다르면 무효). 재확인 조건 2 도 설명 때·승인 글이 도착했을 때·지금 세 머리 커밋이 모두 같아야 통과합니다.
- 승인 글·병합 번호·머리 커밋·병합 방식은 일반 글자(`str`)만 받습니다. 비교를 바꿔치는 글자 하위 형식은 거절합니다.

## 6. 병합 직전 재확인 8조건

이 절은 켜진 뒤의 동작이며 지금은 꺼져 있습니다.

승인을 받은 뒤에도 병합하기 직전에 아래 8가지를 다시 확인합니다. **모든 값이 있어야 하며 빠진 값은 실패입니다**(없다고 통과로 보지 않습니다). 하나라도 실패하면 병합하지 않고, 실패한 조건과 쉬운 말 이유를 알립니다(`check_preconditions`).

| 번호 | 조건 | 어떻게 확인하나 |
|---|---|---|
| 1 | 승인된 병합 번호와 PR 일치 | 승인 번호와 PR 제목의 번호가 같고, 승인할 때 설명한 PR 번호와 지금 PR 번호가 같고, 이미 쓴 승인이 아님. PR 이 열려 있고(`open`) 초안(draft)이 아님 |
| 2 | 승인 이후 Commit 추가 없음 | 쉬운 설명을 보냈을 때·승인 글이 도착했을 때·지금의 머리 커밋(40자 해시) 셋이 모두 같음 |
| 3 | 검사 전체 통과 | 검사 결과가 하나 이상이고 모두 `success` — 건너뜀·중립·취소는 통과가 아님. 반드시 통과해야 하는 검사(필수 검사)의 이름 목록이 비어 있지 않고 모두 결과에 있으며 `success`. 직전 병합의 main 검사가 `success` 이거나 첫 병합(`none`) |
| 4 | 독립 검증 통과 | 검증 기록의 결과가 `pass`, 검증자가 구현자와 다름, 남은 필수 지적 0건, 검증한 내용(트리 — 변경 내용 전체의 지문)이 지금 내용과 같음 |
| 5 | 충돌 없음 | 충돌 여부가 정확히 거짓(모르면 실패) |
| 6 | 변경 범위가 승인 설명과 일치 | 승인 설명의 파일 목록과 지금 변경 파일이 같고, 변경 분류가 지금 파일 목록으로 계산되었고 운영자 전용 항목에 안 걸림. 넘겨받은 분류를 믿지 않고 지금 변경 파일과 바뀐 줄로 분류를 다시 계산해도 걸리지 않음 |
| 7 | 비밀정보 노출 없음 | 비밀 모양 검사의 발견 수가 0(결과가 없으면 실패) |
| 8 | 원복 방법 확인 | 되돌리는 방법이 10자 이상의 구체적인 문장(없음·미정·해당 사항이 없습니다 같은 말은 안 됨) |

확인에 쓰는 값(`FACT_KEYS`)은 아래 23개입니다. 켜는 변경이 이 값들을 채워 넘깁니다. 이 함수가 스스로 다시 계산하는 것은 변경 분류와 머리 커밋 일치뿐이고 나머지 값은 모양만 확인합니다 — 그래서 값은 GitHub 에서 직접 읽는 신뢰할 수 있는 워크플로가 만든 것이어야 합니다(§11-3).

| 값 | 뜻 | 쓰는 조건 |
|---|---|---|
| `approved_number` | 승인된 병합 번호(`M075`) | 1 |
| `approved_pr_number` | 승인할 때 설명한 PR 번호 | 1 |
| `pr_number` | 지금 병합하려는 PR 번호 | 1 |
| `pr_title_label` | PR 제목의 병합 번호 | 1 |
| `consumed_numbers` | 이미 쓴 승인 번호 목록 | 1 |
| `approved_head_sha` | 쉬운 병합 설명을 보냈을 때의 머리 커밋 | 2 |
| `current_head_sha` | 지금의 머리 커밋 | 2 |
| `current_tree` | 지금 머리 커밋의 트리 해시 | 4 |
| `approved_paths` | 승인 설명의 변경 파일 목록 | 6 |
| `current_paths` | 지금 변경 파일 목록 | 6 |
| `checks` | 검사 결과 목록(이름과 결과) | 3 |
| `independent_verification` | 독립 검증 기록 | 4 |
| `has_conflict` | 충돌 여부 | 5 |

| `repo_kind` | 저장소 종류(`blog`·`desktop`) | 6 |
| `changed_text` | 바뀐 줄 — 추가된 줄과 지운 줄 — 의 글 | 6 |
| `head_sha_at_approval` | 승인 글이 도착했을 때의 머리 커밋 | 2 |
| `required_checks` | 반드시 통과해야 하는 검사의 이름 목록 | 3 |

독립 검증 기록(`independent_verification`)의 값은 `verdict`·`verifier`·`implementer`·`verified_tree`·`open_required_findings` 5개입니다. 검증은 커밋이 아니라 **내용(트리 해시)** 에 묶습니다 — 병합 가지를 검증 뒤에 한 커밋으로 새로 만들어도 내용이 같으면 검증이 유효합니다.

### 7-1. AI 가 병합할 수 있는 범위 7가지

- 일반 UI

| 12 | Main Branch 보호 설정 | 사람의 선언(워크플로 파일은 1번에서 걸림) |

경로 이름은 대소문자를 가리지 않고 비교하고(§7-8 의 내부 항목 목록과 §7-6 의 `tests/` 면제만 대소문자까지 같아야 합니다), `normalize_repo_path` 가 경로를 `/` 로 통일합니다(줄 끝의 줄 바꿈만 떼고 경로 자체는 다듬지 않습니다). 이름 바꾸기는 옛 경로와 새 경로를 모두, 삭제도 변경 파일에 넣어 분류합니다. `..` 구간이 든 경로·절대 경로·**어느 구간이든 앞뒤에 공백(유니코드 공백 포함)이 있는 경로**·제어 문자(DEL·C1 포함)가 든 경로·글자가 아닌 입력·사전을 경로 목록으로 넘긴 입력은 확인할 수 없는 입력이라 운영자 전용입니다. 맨 앞의 공백 한 칸이 `docs` 같은 내부 폴더 이름처럼 보이게 하던 우회를 이렇게 막습니다.

**바뀐 줄의 글(`changed_text`)은 추가된 줄과 지운 줄을 둘 다** 넣습니다. 지운 줄에 광고 코드나 `PIPELINE_PAUSE` 가 있어도 운영자 전용입니다(예전 이름 `added_text` 도 받지만 두 이름을 함께 쓰면 입력 오류입니다). 경로마다 나눠 넘기는 사전은 **키가 모두 변경 파일 목록에 있어야 하고 변경 파일마다 키가 있어야** 합니다. 어긋나면 입력 오류입니다(시험·문서 면제를 흉내 내거나 코드 파일의 바뀐 줄을 숨길 수 없게). **빈 글은 바뀐 줄이 정말 없는 파일(이름만 바뀐 파일·빈 파일 등)에만** 넣습니다. **바뀐 줄을 읽지 못한 파일**(diff 가 너무 커서 GitHub 가 내용을 주지 않는 파일·바이너리 파일 등)의 글은 빈 글이 아니라 **`None` 으로** 넘기고, `None` 이나 키가 없는 것은 입력 오류라 운영자 전용입니다. 읽지 못한 코드 파일을 빈 글로 넘기면 그 파일의 내용 규칙(키·광고 코드·외부 접속 따위)을 통째로 건너뛰므로, 코드는 빈 글을 '읽어 보니 바뀐 줄이 없다' 는 결과로만 믿습니다(읽지 못한 파일을 빈 글로 속이지 않는 것은 호출하는 쪽의 약속입니다 — §11-3). 코드가 입력 오류로 돌려주는 이유 문구도 같은 뜻으로 적혀 있습니다(`바뀐 줄이 정말 없는 파일은 빈 글, 읽지 못한 파일은 None 으로 넘기면 운영자 전용이 됩니다`). 함수 설명(독스트링)의 '글이 없는 파일은 빈 글' 은 바뀐 줄이 정말 없는 파일을 뜻합니다.

### 7-3. 사람이 정해야 하는 항목은 점검표로 선언합니다

데이터 삭제·Migration, 외부 비용 발생 기능, 자동 게시 활성화, Provider 활성화, 발행 모드와 발행 재개, Main Branch 보호 설정 6가지는 파일 이름이나 줄만으로는 알 수 없습니다. 그래서 **PR 설명의 점검표로 선언**하고, 독립 검증자가 그 선언이 맞는지 확인합니다.

- **하나라도 참이거나 미응답이면 운영자 전용**입니다(보수적). 값이 없거나, 참·거짓이 아닌 값이어도 미응답으로 봅니다.
- 경로·내용 규칙에 걸린 항목은 선언이 거짓이어도 운영자 전용입니다 — 선언이 규칙을 이기지 못합니다.
- 12항목 모두에 대해 선언이 참이면(규칙이 못 찾은 경우까지) 그 항목으로 운영자 전용이 됩니다. 알 수 없는 항목 이름이 선언에 있으면 확인할 수 없는 입력으로 봅니다.
- 선언은 사람이 정하는 값이라 병합 직전 재확인(§6)도 다시 계산하지 못합니다. 재확인은 경로·바뀐 줄 규칙만 다시 계산하고 선언은 넘겨받은 분류를 따릅니다.

### 7-4. 데스크톱 앱 저장소의 규칙

앱 저장소(`desktop`)는 `.github/`·`requirements*.txt`·`vendor/`·`VERSION`·패키징 설정·비밀 모양을 운영자 전용으로 봅니다. 위 12항목 중 워크플로(`.github/`)·의존성(`requirements*.txt`·`vendor/`)·키와 비밀(비밀 모양)은 같은 항목으로 걸립니다. 바뀐 줄의 내용 규칙(광고 코드 낱말·`PIPELINE_PAUSE`·비밀 모양·삭제 명령)은 두 저장소에 똑같이 적용되고, 광고·공개 글·발행 설정 파일의 경로 규칙과 §7-8 의 기본 거부는 블로그 저장소에만 적용됩니다.

### 7-5. 12항목 밖에서 보수적으로 더한 표시

운영자 결정 원문의 12항목은 줄이거나 넓히지 않았습니다. 그와 별개로, 아래 5가지는 결과의 `extra_flags` 에 따로 표시하고 운영자 전용으로 둡니다. 운영자가 바꾸라고 하면 따릅니다.

| 표시 | 뜻 | 왜 보수적으로 두었나 |
|---|---|---|
| `policy_self` | 이 정책의 문서·모듈·시험 자체를 바꾸는 변경 | AI 가 스스로 규칙을 느슨하게 만든 뒤 그 규칙으로 병합하는 길을 막기 위해(§12) |
| `safety_guard` | 안전 장치 파일(§7-6) | 총괄(AI)의 보수적 판단 D-347 — 운영자 확인 대기. 검사·보안 장치와 AI 가 읽는 규칙 문서를 AI 가 스스로 약하게 만든 뒤 그 장치로 병합하는 길을 막기 위해 |
| `external_connection` | 새 외부 접속 코드(§7-6) | 총괄(AI)의 보수적 판단 D-347 — 운영자 확인 대기. 외부 비용 발생 기능·API Key 항목으로 이어지는 입구라 코드의 바뀐 줄에서 따로 잡습니다 |

### 7-6. 안전 장치 파일과 새 외부 접속 코드 (총괄(AI)의 보수적 판단 D-347 — 운영자 확인 대기)

위 두 표시(`safety_guard`·`external_connection`)는 12항목 목록을 넓힌 것이 아니라 **12항목 밖의 표시**입니다. 오탐을 줄이려고 시험·문서 안의 주소와 예시는 걸리지 않게 했고, 의심스러우면 운영자 전용 쪽으로 봅니다. 이 절의 규칙은 총괄(AI)의 판단이고 운영자의 확인을 기다립니다.

**안전 장치 파일(`safety_guard`)** — 승인해도 운영자가 직접 병합합니다.

- 낱말로 알아내는 파일: 문서가 아닌 파일은 경로의 어느 구간에든 `validate_repo`·`guardrail`·`guard`·`security`·`secret`·`egress`·`policy`·`safety`·`sandbox`·`ai_flow` 가 있으면 해당합니다. 예: `scripts/validate_repo.py`·`pipeline/egress.py`·`pipeline/secret_patterns.py`·`pipeline/source_policy.py`·`pipeline/ai_guard.py`·`tests/test_guardrails.py`·`tests/test_security_settings.py`·`tests/test_egress.py`.
- 이름으로 적은 파일(낱말로는 알 수 없는 발행 잠금·품질 Gate·인증 확인·발행기·생성기·토큰 발급·감시 도구·발행 실행기·접수 판정과 사이트 정리 시험): `pipeline/publish_lock.py`·`pipeline/quality_gate.py`·`pipeline/gates.py`·`pipeline/auth_check.py`·`pipeline/registry.py`·`pipeline/source_registry.py`·`pipeline/health.py`·`pipeline/draft_flow.py`·`pipeline/edits/runner.py`·`generator.py`·`blogger_generator.py`·`scripts/get_blogger_token.py`·`scripts/watchdog.py`·`tests/test_site_cleanup.py`·`pipeline/run.py`·`pipeline/operator_loop.py`·`pipeline/telegram_inbox.py`, 그리고 폴더 `pipeline/publishers` 의 모든 파일. 이름이 정확히 같을 때만 해당하고 대소문자는 가리지 않습니다.
- **이 목록은 저장소가 바뀔 때마다 유지가 필요하다.** 새 안전 장치가 생기거나 파일 이름이 바뀌면 이 목록과 시험을 한 묶음으로 고쳐야 하고(운영자가 직접 병합하는 변경), 시험이 목록의 파일이 실제로 있는지 지킵니다. 목록에 없는 파일은 걸리지 않습니다(§7-7). 위 두 목록은 처음 정할 때 실제 저장소에 없는 이름(`pipeline/generator.py`·`pipeline/blogger_generator.py`)을 빼고 실제 생성기 파일(`generator.py`·`blogger_generator.py`)로 바꿔 적었습니다.
- AI 가 읽고 따르는 규칙 문서 18개도 운영자 전용입니다: `AGENTS.md`·`CLAUDE.md`·`GEMINI.md`·`AI_COLLAB.md`·`HANDLER.md`·`docs/CHARTER.md`·`docs/SECURITY_GUARDRAILS.md`·`docs/ACTIONS_GUIDE.md`·`docs/AGENT_RUNBOOK.md`·`docs/SESSION_START.md`·`docs/ENGINEERING_GUIDE.md`·`docs/AGENT_DELEGATION.md`·`docs/COPILOT_GUIDE.md`·`docs/AI_FLOW.md`·`docs/AI_MODEL_GUIDE.md`·`docs/SOURCE_POLICY.md`·`docs/QUALITY_GATE.md`·`docs/REQUEST_BRIEFING.md`. 이 문서를 AI 가 스스로 고쳐 자기 규칙을 바꾸는 길을 막기 위해서입니다. 용어 사전(`docs/GLOSSARY.md`)은 규칙이 아니라 사전이라 넣지 않았습니다(§7-7). 이 정책의 문서·모듈·시험 4개는 `policy_self` 로만 표시합니다. 그 밖의 문서(`.md`·`.rst`·`.txt`·`.adoc`)는 이 규칙에 걸리지 않습니다.
- **시험 폴더도 면제하지 않습니다.** 안전 장치를 지키는 시험을 고쳐 장치를 약하게 만드는 길을 막으려는 것이지만, **낱말·이름 목록에 걸린 시험만 막습니다.** 파일 이름에 안전 낱말이 들어 있는 시험(예: `tests/test_guardrails.py`)이나 이름 목록에 있는 시험(`tests/test_site_cleanup.py`)이 그 경우입니다. 목록의 장치를 지키는 전용 시험이라도 이름에 낱말이 없고 목록에도 없으면 걸리지 않습니다(§7-7).

**문서 파일의 낱말 규칙(총괄(AI)의 판단 — 운영자 확인 대기)** — 문서 파일(`.md`·`.rst`·`.txt`·`.adoc`)의 바뀐 줄에는 낱말 규칙(키·토큰·비밀번호 낱말·`secrets.` 참조·`Authorization` 헤더·`PIPELINE_PAUSE`·삭제 명령과 마이그레이션 낱말·접속 낱말)을 적용하지 않습니다. 문서가 그 낱말을 설명하는 것은 그 항목을 바꾸는 것이 아니기 때문입니다. 운영자 원문은 AI 병합 범위에 '문서'를 명시했고 첫 운영도 '일반 코드 또는 문서 PR 3건'이라고 했는데, 작업 기록 한 줄에 `PIPELINE_PAUSE` 나 토큰 이야기가 들어갔다고 운영자 전용이 되면 원문과 부딪히기 때문입니다. 아래는 문서에서도 그대로 적용합니다.

- **강한 비밀 모양**(실제 키·토큰 모양·개인 키 블록·Stripe 형식 키·긴 Bearer 값·긴 값을 넣는 키 할당)과 광고 코드 낱말(`adsbygoogle`·`ca-pub-`)

- 글자 하나로 받은 글은 바뀐 파일이 모두 문서일 때만 면제이고, 경로를 아는 글(사전)은 그 문서 파일의 글만 면제입니다. 문서인지는 파일 이름의 확장자만 봅니다.

### 7-7. 이 규칙이 모르는 것

이 규칙은 모양만 보는 거친 장치입니다. 아래는 코드가 알 수 없거나 일부러 풀어 둔 곳이고, 독립 검증의 점검표가 마지막 방어선입니다. 규칙을 넓힐지는 운영자가 정합니다(총괄(AI)의 판단 — 운영자 확인 대기).

- **AI 병합 가능 7종은 목록이 아니라 '12항목과 표시에 안 걸리면' 이라는 거절 목록으로 구현했습니다.** 걸리지 않은 것은 7종 중 어느 것인지 확인하지 않고 통과합니다.
- 코드는 글의 **모양**만 봅니다. 설명이 정말 쉬운지·변경 내용이 설명과 맞는지·되돌리는 방법이 정말 구체적인지·이상 유무가 사실인지는 사람(독립 검증자)이 읽고 확인합니다. 되돌리는 방법 칸에 열 자가 넘는 아무 말이나 적어도 코드는 통과시키고, 완료 알림에 `-` 같은 값이 있거나 main 검사 결과가 실패인데 이상 없음이라고 적은 모순도 알아내지 못합니다.
- 이름에 안전 낱말이 없고 §7-6 의 이름 목록에도 없는 검사·정화 코드는 걸리지 않습니다(예: 콘텐츠 안전 프로필 `pipeline/profiles/`). 목록에 넣을지는 운영자가 정합니다.

- **전각 글자로 쓴 이름은 글자 규칙과 '어디서도 쓰이지 않는다' 검사를 비켜 갑니다.** 파이썬은 코드의 이름(변수·함수·모듈 이름)을 모양만 다른 같은 글자로 접어서 읽습니다(NFKC). 그래서 `requests` 의 첫 글자만 전각 글자 `ｒ` 로 쓴 `import ｒequests` 도 똑같이 실행되는데, 글자 규칙은 글자를 접지 않고 찾아서 모릅니다. 외부 접속 모듈 이름·삭제 명령(`os.remove` 꼴)·동적 실행(`exec`·`__import__`)·키와 토큰 낱말·`PIPELINE_PAUSE` 를 이렇게 쓴 사례를 확인했고 모두 `ai_ok` 가 됩니다. 정책 모듈을 `from pipeline import ｍerge_policy` 꼴로 불러와도 `NotWiredTest` 의 일반 글자 검색은 못 봅니다(구문 트리 점검을 받는 예외 한 파일에서는 파이썬이 접은 이름으로 읽어 잡습니다). 지금은 꺼져 있어 영향이 없고, 켜기 전에 풀어야 할 항목입니다(§11-3 의 '켜기 전 필수 결정').

### 7-8. 블로그 저장소의 기본 거부

블로그 저장소는 **사이트로 내보내지 않는 맨 위 항목 21개**만 내부 항목으로 봅니다(저장소 `_config.yml` 의 exclude 와 같습니다): `AGENTS.md`·`AI_COLLAB.md`·`CLAUDE.md`·`GEMINI.md`·`HANDLER.md`·`WORKLOG.md`·`docs`·`인수인계`·`generator.py`·`blogger_generator.py`·`pipeline`·`scripts`·`tests`·`history.json`·`blogger_history.json`·`blogger_ko_history.json`·`naver_history.json`·`pages.json`·`requirements-dev.txt`·`requirements-edits.txt`·`requirements-pipeline.txt`. 이 목록 밖의 모든 맨 위 파일·폴더는, 다른 규칙이 아무것도 걸지 않았더라도, **공개 파일로 보고 운영자 전용**(공개 게시물과 고정 페이지 항목)으로 둡니다. 새 고정 페이지·정적 파일·`README.md`·`CNAME`·`.nojekyll`·`_data`·`_sass`·`_plugins` 가 AI 병합으로 새지 않게 하는 기본 거부입니다.

- 이름은 대소문자까지 같아야 내부 항목입니다(GitHub Pages 는 대소문자를 가려 `Docs/x.html` 은 내보내는데 `docs` 만 뺍니다).
- 맨 위 항목만 봅니다. 내부 폴더 안쪽의 이름(예: `docs/README.md`)은 보지 않습니다.
- 목록은 실제 `_config.yml` 과 사이트 정리 시험의 상수와 시험(`SiteConfigMatchTest`)이 맞춰 봅니다. 사이트가 새 항목을 빼면(exclude 에 더하면) 이 목록도 한 묶음으로 고쳐야 합니다(운영자가 직접 병합하는 정책 변경).
- 앱 저장소(`desktop`)에는 적용하지 않습니다.

## 8. 병합 방식 제한

이 절은 켜진 뒤의 동작이며 지금은 꺼져 있습니다. 다만 main 에 직접 push 하지 않는다는 원칙은 꺼져 있는 지금도 그대로입니다.

- **main 직접 push 금지.** AI 가 운영자 PC 의 Git 자격 증명을 이용해 main 에 직접 push 하는 방식은 쓰지 않습니다.
- 강제 push 도 금지입니다.
- 병합은 **GitHub 의 PR 병합**으로만 합니다(`pr_merge`). 아래 값은 모두 거절입니다(`merge_method_allowed`).

| 값 | 결과 |
|---|---|
| `pr_merge` | 허용 |
| `push_main`·`direct_push`·`force_push` | 거절 |
| 그 밖의 값(`squash`·`merge`·`PR_MERGE`·빈 글·글자가 아닌 값 등) | 거절 — 모르는 값은 거절입니다 |

## 9. 사후 처리

이 절은 켜진 뒤의 동작이며 지금은 꺼져 있습니다.

1. 병합된 main 에서 검사를 다시 돌립니다(main 사후 검사).
2. **병합 완료 알림**에 아래 7가지를 반드시 담습니다. 알림 글은 `render_completion_notice` 가 만들고 `completion_notice_problems` 가 빠진 곳을 찾습니다. 항목은 `이름: 값` 한 줄씩입니다.

   - 병합 번호
   - PR 번호
   - 병합된 Commit
   - 실제 반영된 변화
   - main 검사 결과
   - 이상 유무
   - 원복 Commit 또는 원복 방법

3. 알림 예시(모듈이 만든 글을 그대로 붙인 것입니다).

```text
병합 완료 알림
병합 번호: M075
PR 번호: #198
병합된 Commit: e4f5a6b8c9d0
실제 반영된 변화: 저장 버튼과 저장된 초안 목록이 앱에 반영되었습니다.
main 검사 결과: 전체 통과
이상 유무: 이상 없음
원복 Commit 또는 원복 방법: 병합 커밋 한 개를 되돌리는 PR 을 만들어 운영자께 보냅니다.
```

4. **main 검사에서 문제가 나오면** 추가 변경을 자동 병합하지 않습니다. 해당 병합을 되돌리기 위한 요청과 쉬운 원인 설명을 **먼저** 운영자에게 보냅니다. 되돌리는 PR 도 운영자가 병합합니다.
5. 다음 병합을 해도 되는지는 직전 병합의 main 검사 결과로 정합니다(`evaluate_post_merge`, 결과는 `PostMergeDecision`). 같은 값이 재확인 조건 3 에도 들어갑니다(`previous_merge_main_check`).

| 직전 병합의 main 검사 | 다음 병합 | AI 가 할 수 있는 일 |
|---|---|---|
| `success` | 가능(다른 조건은 따로 모두 통과해야 함) | 제한 없음 |
| `none`(아직 병합한 적 없음) | 가능(첫 병합) | 제한 없음 |
| `pending` | 불가 | 없음 — 결과가 나올 때까지 기다림 |
| `failure` | 불가 | 되돌리기 요청과 쉬운 원인 설명 보내기 둘뿐 |
| 그 밖의 값 | 불가 | 없음 — 운영자의 확인을 기다림 |

## 10. 첫 운영 3건 시험과 즉시 중지

이 절은 켜진 뒤의 동작이며 지금은 꺼져 있습니다.

첫 운영은 **일반 코드 또는 문서 PR 3건**으로 시험합니다. 3건 모두 아래 6가지를 만족하면 승인형 AI 병합을 계속 사용합니다.

- 승인받은 PR만 병합
- 승인 후 변경 없음
- main 검사 전체 통과
- 원복 발생 0건
- 다른 PR 오병합 0건
- 운영자 전용 경로 변경 0건

**즉시 중지 규칙:** 문제가 한 건이라도 발생하면 AI 병합을 **즉시 중지**하고 기존 운영자 직접 병합 방식으로 돌아갑니다. 기록이 3건 미만이어도 마찬가지입니다.

`evaluate_trial` 은 병합 기록을 읽어 세 가지 중 하나를 돌려줍니다(위반한 곳의 이유까지 보려면 `trial_report`).

| 결과 | 뜻 |
|---|---|
| `continue` | 서로 다른 번호의 기록이 3건 이상이고 모두 6가지를 충족 — 계속 사용 |
| `pending` | 위반은 없지만 3건 미만이거나, main 검사 결과를 아직 모름 — 더 지켜봄 |
| `stop_immediately` | 한 건이라도 위반 — 즉시 중지 |

기록의 값은 6가지 각각 '충족했는가'입니다. 값이 없거나 참·거짓이 아니거나, 번호가 표준이 아니거나, 같은 번호가 두 번 나오면(승인 재사용 의심) 위반으로 봅니다. 아직 모르는 것은 main 검사 결과뿐이고, 그것도 '모름'일 때는 계속으로 치지 않고 `pending` 입니다.

## 11. 켜는 방법

### 11-1. 원칙

AI 병합을 실제로 켜는 변경은 **별도 병합 요청**으로 보내고, 그 변경은 **운영자가 직접 병합**합니다. 켜는 변경은 워크플로 파일(`.github/`)을 건드리므로 어차피 12항목의 첫 번째 항목입니다. 그 변경이 들어오기 전까지 이 정책은 꺼져 있습니다.

### 11-2. 설계 메모 — Actions 워크플로 방식과 제약

켜는 변경을 만들 때 아래를 입력으로 씁니다. 지금은 구현하지 않았고, 확인하지 못한 것은 확인 필요로 적었습니다.

1. **AI 세션은 병합 자격 증명을 갖지 않습니다.** 병합은 Actions 워크플로가 자기 `GITHUB_TOKEN` 으로 PR 병합을 호출해서 합니다. 운영자 PC 의 Git 자격 증명이나 개인 토큰은 쓰지 않습니다(§8).
2. **병합 호출에 승인 시점의 머리 SHA 를 지정합니다.** 승인 시점의 머리 SHA 는 쉬운 병합 설명을 보냈을 때의 머리 SHA 이고 승인 글이 도착했을 때와 같아야 합니다(§5-4 `ApprovalRecord`). 승인한 뒤 커밋이 더해졌다면 GitHub 가 병합을 거절하므로 '승인 후 커밋 없음'을 GitHub 가 보장합니다. 그래도 호출 전에 §6 의 8조건을 코드로 다시 확인합니다.
3. **`GITHUB_TOKEN` 으로 한 병합은 `push` 로 도는 후속 워크플로(사이트 자동 배포·저장소 규칙 검사)를 깨우지 못합니다.** 그래서 병합한 뒤 `workflow_dispatch` 로 따로 호출해야 합니다(두 워크플로 모두 이미 `workflow_dispatch` 를 지원합니다). 호출에는 `actions: write` 권한이 필요합니다.
4. **승인은 소유자 계정의 글에서만 읽습니다.** 소유자(`shine88pc`)의 이슈·댓글, 또는 텔레그램 답으로 만든 이슈에서 `M### 승인` 한 줄을 읽습니다. 이슈·댓글 본문은 믿을 수 없는 입력이라 명령에 끼워 넣지 않고 환경 변수로만 읽습니다.
5. **판정 코드는 기본 가지의 것만 실행하고 PR 쪽 파일은 읽기만 합니다**(`[공통] PR 변경 범위 검사` 와 같은 방식). 그래서 PR 이 판정 규칙을 고쳐서 자기 자신을 통과시킬 수 없습니다(§12 의 `policy_self` 와 함께 막습니다).
6. **승인 기록·시험 3건 기록·즉시 중지는 저장소 밖에 따로 두지 않고 병합된 PR 이력(제목의 `[M###]`)에서 다시 계산합니다.** main 에 직접 쓸 수 없으니 이 방식이 규칙(§8)과 맞습니다. 위반이 한 번 나오면 이력에서 계속 위반으로 계산되어 스스로 멈추고, 재개는 운영자가 정합니다.
7. **독립 검증 기록은 커밋이 아니라 트리 해시에 묶습니다**(§6). 병합 가지를 검증 뒤에 새 커밋 하나로 다시 만들어도 내용이 같으면 검증이 유효합니다.
8. **필요한 권한이 저장소의 가드레일과 부딪힙니다.** 병합 호출은 쓰기 권한이 필요한데, 저장소 검증기는 워크플로의 권한과 트리거를 허용 목록으로 지킵니다. 켜는 변경이 그 허용 목록도 함께 고쳐야 하고, 그것도 운영자가 직접 병합하는 변경입니다.
9. **확인 필요:** 저장소 설정(필수 검사·리뷰 요구)과 `GITHUB_TOKEN` 병합의 상호작용은 AI 가 설정 화면을 볼 수 없어 확인하지 못했습니다. 텔레그램 한도(3,800자)를 넘는 큰 PR 의 파일 목록을 어떻게 나눠 보낼지, 알림 전송이 실패했을 때 다시 보내는 방식도 정해야 합니다.

### 11-3. 켜기 전에 갖춰야 할 것

- 켜는 변경이 §6 의 23개 값을 모두 채워 `check_preconditions` 에 넘기는지(빠진 값이 있으면 병합하지 않음). 특히 아래는 빠뜨리기 쉽습니다.
  - 변경 파일 목록에는 **이름을 바꾼 파일의 옛 경로와 새 경로를 모두**, **지운 파일**까지 넣습니다. **변경 파일 목록은 모든 페이지를 읽어 PR 의 변경 파일 수와 같을 때만 씁니다.** GitHub 의 PR 파일 목록은 페이지 단위로 나뉘고 한 PR 이 돌려주는 파일 수에 상한이 있는 것으로 알려져 있어(확인 필요 — AI 가 GitHub 에 직접 접속해 확인하지 못했습니다), 일부만 읽은 목록으로 분류하면 읽지 못한 파일이 숨습니다. 파일 수가 맞지 않거나 상한을 넘으면 운영자 전용으로 둡니다.
  - 바뀐 줄(`changed_text`)에는 **추가된 줄과 지운 줄을 둘 다** 넣습니다(지운 줄에 광고 코드나 `PIPELINE_PAUSE` 가 있을 수 있어서). 경로마다 나눠 넘기는 사전은 키가 모두 변경 파일 목록에 있어야 하고 변경 파일마다 키가 있어야 합니다. **읽지 못한 파일(너무 큰 diff·바이너리라 GitHub 가 내용을 주지 않는 파일 등)의 글은 `None` 으로 넘깁니다** — 입력 오류라 운영자 전용이 됩니다. **빈 글(`""`)은 바뀐 줄이 정말 없을 때만** 넣습니다.
  - **필수 검사의 이름 집합**(`required_checks`)을 저장소 설정과 맞춰 넣습니다. 이 집합을 모르면 시작도 하지 않은 검사가 결과에 보이지 않아 통과로 읽힙니다.
  - 승인 때의 머리 SHA 는 **쉬운 설명을 보냈을 때의 것**(`approved_head_sha`)과 **승인 글이 도착했을 때의 것**(`head_sha_at_approval`)을 각각 넣습니다(`ApprovalRecord`). 둘이 다르면 승인은 무효입니다.
- 12항목 분류 결과가 지금 변경 파일 목록으로 계산되는지(분류는 병합 직전에 이 함수가 다시 계산합니다)
- **값의 출처**(켜기 전의 필수 조건): `repo_kind`·`changed_text`·`checks`·`required_checks`·`independent_verification`·`has_conflict`·`secret_findings`·`pr_state`·`pr_draft`·`previous_merge_main_check` 는 GitHub 에서 직접 읽는 신뢰할 수 있는 워크플로가 만든 값이어야 합니다. PR 작성자나 PR 쪽 파일이 채울 수 있으면 안 됩니다 — 이 함수는 이 값들의 모양만 확인하고 진짜인지는 알 수 없습니다. 특히 `secret_findings` 는 문서 파일을 포함한 모든 바뀐 파일에서 센 값이어야 합니다 — 이 함수는 넘겨받은 수가 0 인지만 확인하고 어디서 셌는지는 모르며, 분류 규칙은 강한 비밀 모양을 문서 파일에서도 운영자 전용으로 보기 때문입니다(§7-6).
- 병합 설명을 보내기 전에 `explanation_problems` 로 점검하는지. 쉬운 설명 글에서 번호·머리 커밋·점검표를 되읽는 `parse_explanation` 은 **지금 만들지 않았습니다**. 켜는 변경이 설명 글을 구조화된 값으로 되읽어야 하면 그때 정하고, 설명과 실제 변경이 같은 값에서 나오게 하는 쪽을 먼저 봅니다.
- **독립 검증 기록의 출처와 위조 방지**(켜기 전의 필수 조건): `independent_verification` 은 코드가 값의 모양만 봅니다. 그 기록이 정말 구현자와 다른 검증자가 남긴 것인지는 코드가 알 수 없으므로, 켜기 전에 기록을 쓸 수 있는 주체를 제한하고(소유자 계정의 이슈·댓글처럼 신뢰할 수 있는 곳에서만 읽고, 같은 PR 의 작성자나 PR 쪽 파일이 기록을 만들 수 없게 합니다) 기록이 어느 트리 해시에 대한 것인지 함께 남겨야 합니다.
- 병합 직후 `workflow_dispatch` 로 후속 검사와 배포를 호출하고, 결과를 기다려 완료 알림을 보내는지
- **병합을 호출하기 직전마다** 병합 이력 전체로 `evaluate_trial` 을 돌려(한 건이라도 위반이면 중지) 통과하고, 직전 병합의 main 검사 결과(`evaluate_post_merge`)도 통과인지 — 둘 다 통과해야 병합합니다
- 첫 운영 3건의 기록을 이력에서 만들어 `evaluate_trial` 로 판단하는지
- **켜기 전 필수 결정**(운영자와 정할 것 — 정하기 전에는 켜지 않습니다):
  - **첫 운영 3건의 범위**: 첫 3건은 경로가 모두 `.py`·`.md`·`tests/` 인 변경으로 한정하는 것으로 읽었고 운영자 확인을 받습니다(바뀐 파일이 전부 `.py` 파일·`.md` 파일·`tests/` 폴더 안의 파일 중 하나인 변경 — 운영자 결정 016 의 "일반 코드 또는 문서 PR"). `ai_ok` 는 '12항목·표시에 안 걸림' 이라는 뜻이라 코드도 문서도 아닌 파일(예: `pipeline/profiles/` 의 설정 파일)도 통과할 수 있고, 시험 기록(`evaluate_trial`)에도 PR 종류 칸이 없습니다. 이 한정은 코드가 확인하지 않으므로 켜는 변경이 지켜야 합니다.
  - **안전 장치 목록의 확장**: §7-7 에 적은 빈틈 — 가져오는 순간 실행되는 파일(`pipeline/__init__.py`·`tests/_bootstrap.py`·하위 폴더의 `conftest.py`·`sitecustomize.py`·`usercustomize.py`), 하위 폴더의 `AGENTS.md`·`CLAUDE.md`·`GEMINI.md`, 목록의 장치를 지키는 전용 시험 — 을 안전 장치 목록에 넣을지, 그리고 `pipeline/drafts.py`·`pipeline/shadow_run.py` 의 기본값을 운영자 전용으로 둘지(검증자 P 의 권고는 운영자 전용)를 **켜는 변경 전에 운영자와 정합니다**. 정하지 않았으므로 지금은 §7-7 에 적은 대로 걸리지 않습니다.
  - **전각 글자 같은 모양만 다른 이름**: 파이썬이 이름을 모양만 다른 같은 글자로 접어서(NFKC) 읽는데 글자 규칙과 '어디서도 쓰이지 않는다' 검사는 접지 않아 비켜 갑니다(§7-7). 켜기 전에 둘 중 하나를 정합니다. (가) 글을 NFKC 로 접은 뒤에 규칙을 적용합니다 — 정책 모듈이 가져오는 것을 `re`·`dataclasses` 로 못박은 순수성 시험을 고쳐 `unicodedata` 를 허용해야 하고, `NotWiredTest` 의 글자 검색도 접은 글에서 찾아야 합니다. (나) 전각 영숫자(U+FF10–FF19·U+FF21–FF3A·U+FF41–FF5A)와 수학 영숫자(U+1D400–U+1D7FF)가 코드 파일의 바뀐 줄에 있으면 `invalid_input` 으로 보아 운영자 전용으로 둡니다. 정하지 않았으므로 지금은 §7-7 에 적은 대로 걸리지 않습니다(꺼져 있어 영향은 없습니다).
  - **켜는 변경의 지시서는 이 목록을 그대로 넣습니다.** 이 세 항목(첫 3건의 범위·안전 장치 목록의 확장·전각 글자 같은 모양만 다른 이름)마다 운영자가 정한 결과를 지시서에 적고, 정하지 못한 항목이 있으면 켜지 않습니다.

## 12. 이 문서를 바꾸는 법

이 문서와 `pipeline/merge_policy.py`, 시험 두 개(`tests/test_merge_policy.py`·`tests/test_merge_policy_docs.py`)는 **운영자 결정으로만** 바꿉니다.

- 이 네 파일을 바꾸는 변경은 AI 병합 대상이 아닙니다(`policy_self`). 새 운영자 결정(채팅·이슈 답)을 근거로 별도 병합 요청을 보내고, 운영자가 직접 병합합니다.
- 운영자 전용 12항목·재확인 8조건·불허 문구 5개·완료 알림 7항목·시험 기준 6가지·AI 병합 가능 7종은 운영자 결정 원문의 목록입니다. 줄이거나 넓히지 않습니다. 운영자가 새로 정하면 이 문서·모듈 상수·시험을 **한 묶음으로** 같이 고칩니다.
- 모호한 곳은 더 보수적으로 읽습니다 — 승인 인정은 좁게, 운영자 전용은 넓게.
