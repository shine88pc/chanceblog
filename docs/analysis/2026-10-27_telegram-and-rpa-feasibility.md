# 텔레그램 알림·붙여넣기 발행과 오토마우스(RPA) 자동 발행 — 적용 가능성 조사 (2026-10-27)

> 사용자 질문(2026-10-27 채팅): "텔레그램 봇으로 초안 알림을 받아 붙여넣기 방식으로 발행하려 한다. 별도 프로그램(오토마우스)으로 사람이 초안을 확인하고 발행을 누르는 동작을 자동으로 돌리는 것이 적용 가능한지, 다른 방법은 없는지."
> 방법: 읽기 전용 조사(영역별 에이전트 6명 + 비판 검토 1명, 웹 문서·약관·공식 저장소 읽기만; 로그인·가입·발송 없음). **교차 검증(독립 재조사) 단계는 세션이 끊겨 끝내지 못했다** — 아래 '확인 못 한 것'을 함께 읽는다. 법률 판단이 아니라 "공식 문구가 이렇게 적혀 있다"까지만 적었다.

## 0. 결론

| 방식 | 판정 | 한 줄 이유 |
|------|------|-----------|
| 텔레그램으로 알림 + 링크 버튼 | **가능·권장** | 서버 없이 GitHub Actions 에서 `api.telegram.org` 호출만으로 된다. 구현은 작업 TG(`pipeline/notify.py`) |
| 텔레그램에서 본문을 복사해 붙여넣기 | **가능, 단 제한** | 복사 버튼은 256자, 메시지 한 통은 4,096자. 본문은 1~3통으로 나누거나 GitHub 이슈 링크로 둔다. 서식·이미지는 따로 확인 필요 |
| 텔레그램 버튼 한 번으로 "승인 → 자동 발행" | 가능하지만 **서버가 필요, 비권장(선택)** | 버튼 응답을 받으려면 공개 수신기(Cloudflare Worker 등)와 GitHub 호출용 토큰이 새로 필요하고, 텔레그램 안에는 검토 화면이 없어 형식적 승인이 되기 쉽다 |
| 오토마우스(RPA)로 "확인·발행 클릭" 자동화 | **비권장** | 좁은 조건에서만 돌고, 사람 검토를 기계 클릭으로 바꾸면 검토가 사라지며, 네이버 약관·로그인 보호와 부딪힌다 |

한 줄 권고: **알림은 텔레그램, 검토와 승인은 검토 화면이 있는 곳(GitHub 모바일의 PR, Blogger 초안 미리보기, 티스토리·네이버 편집기), 발행 클릭은 사람.**

## 1. 텔레그램 알림 + 복사 붙여넣기

확정에 가까운 것(공식 문서 원문은 읽지 못했고 라이브러리 문서·공식 채널·공식 소스로 확인 — 신뢰도 표시):
- 메시지 본문 1~4,096자(엔티티 파싱 후), 캡션 1,024자, 봇 파일 업로드 50MB (high). 한글은 어느 단위로 세어도 1글자=1단위(medium).
- `parse_mode=HTML` 은 `b·i·u·s·a·code·pre·blockquote` 등만 받고 `p·br·ul·table·img` 는 400 오류 → 블로그 HTML 원문은 평문(또는 `pre` 엔티티)으로 보내야 한다 (medium).
- 인라인 버튼: `url`(수신 서버 불필요), `callback_data`(64바이트, 응답 서버 필요), **`copy_text`**(Bot API 7.11, 2024-10-31 도입, 1~256자, 클라이언트가 직접 복사) (high). iOS·Desktop 소스에 처리 코드가 있으나 Android·최소 앱 버전은 미확인.
- 봇은 사용자가 먼저 `/start` 해야 메시지를 보낼 수 있다(403 `can't initiate conversation`), 같은 채팅 초당 약 1통, 429 `retry_after`.
- 토큰이 URL 경로(`/bot<토큰>/sendMessage`)에 들어가므로 **예외·로그에 URL 이 찍히면 토큰이 샌다**(requests 계열 예외 문자열이 요청 URL 을 포함하는 것으로 알려짐, 실제 CVE 사례 있음). 공개 저장소는 Actions 로그도 공개다. 그래서 우리 구현은 `requests`·`print(예외)` 를 쓰지 않는다.
- 일반(클라우드) 채팅은 종단간 암호화가 아니다 → 이미 공개될 글 제목·주소만 보낸다.
- **이 PC 의 네트워크는 `telegram.org`·`core.telegram.org`·`web.telegram.org` 를 "비업무용 사이트"로 막는다**(`t.me`·`api.telegram.org` 는 열림, 2026-10-27 확인). 그래서 공식 문서를 이 PC 에서 읽지 못했고, **알림은 휴대폰에서 받는 것을 기준**으로 한다. GitHub Actions 에서 호출하는 것은 GitHub 서버가 하므로 이 차단과 무관하다.

채널별 실용성: 티스토리(HTML 모드에 붙여넣기)는 실용적, 네이버는 편집기가 붙여넣은 HTML 의 일부 서식을 무시한다는 보고가 있어(low) 사용자가 표본 글 1건으로 먼저 확인해야 하고, Blogger(초안함 API)·Chance(초안 PR)는 붙여넣기가 필요 없어 "발행 화면으로 가는 링크 버튼"이 가장 낫다.

## 2. 승인 버튼(콜백)을 서버 없이 받는 방법 (참고)

| 구조 | 판정 | 핵심 |
|------|------|------|
| GitHub Actions 예약 실행이 `getUpdates` 로 버튼 누름을 읽음 | 부분 | 이 저장소의 예약 실행은 10~60분 이상 늦게 돈다 → 반응이 수십 분~수 시간. 웹훅과 동시 사용 불가 |
| Cloudflare Worker 웹훅 → `workflow_dispatch` | 가능(비개발자에게 약 15단계) | PAT 는 이 저장소 1개·Actions:write 만(Contents:write·PR 병합 권한 금지), 비밀 헤더·소유자 ID 검증, 제3자에 토큰 보관 |
| Google Apps Script 웹앱을 웹훅으로 | 비권장 | POST 에 302 응답으로 텔레그램이 실패로 보고 재시도해 중복, 헤더 검증 불가 |
| 사용자 PC·집 서버 리스너 | 부적합 | 항상 켜져 있어야 하고 업무용 PC 는 정책·절전 문제 |
| **텔레그램은 알림만, 승인은 GitHub 모바일(PR 병합·환경 승인·`workflow_dispatch`)·Blogger 화면** | **가능·권장** | 승인 화면이 곧 검토 화면(PR 의 변경 파일·검사 결과). 추가 서비스·토큰·지연 없음. GitHub 모바일의 `workflow_dispatch` 입력·딥링크 동작은 미확인 |

## 3. 오토마우스(RPA)

- **기술**: 좌표·이미지 방식은 해상도·배율(DPI)·창 위치·팝업·UI 개편에 깨지고, PyAutoGUI 는 한글을 **조용히 무시**한다(소스 확인, 클립보드 붙여넣기로 우회해야 함). 이미지 찾기는 1~2초, 주 모니터만. 화면 잠금·UAC·관리자 권한 창에는 일반 권한 매크로의 입력이 가지 않고, 작업 스케줄러로 화면을 누르려면 로그온한 대화형 세션이 필요하다. 로그인 캡차·2단계 인증·새 기기 확인은 사람이 해야 한다. DOM 방식(Playwright 등)은 안정적이지만 로그인 상태 파일 보관·헤드리스 탐지가 따른다.
- **업무용 PC**: 자동 잠금, 앱 실행 제어, 보안 솔루션, 겸업·업무시간 규정, 개인 계정 세션 저장 문제가 겹친다. 규정을 모르는 상태에서 설치·실행하지 않는 것이 안전하다(사용자가 확인할 항목).
- **정책**: 구글 게시자 정책 페이지의 Tips 에 "수동 검토·큐레이션 없는 자동 생성 콘텐츠에 광고를 두지 말라"는 예시가 있다(정책 본문이 아니고 '수동 검토'의 정의는 없음, high). **RPA 가 누르는 클릭은 '검토'가 아니다** — 위반을 직접 만들지는 않지만 마지막 사람 판단을 없애 위험을 키운다(추정). 이 저장소의 원칙("의심스러우면 게시하지 않는다", 로그인·세션·쿠키 자동화와 CAPTCHA 우회를 만들지 않는다)과도 충돌한다.
- **네이버**: 블로그 "API 를 이용한 글쓰기"는 2020-05-06 종료됐다(이유: 반복적·기계적 대량 발행이 약관·운영정책 위반, 언론 인용 — medium~high). 약관은 사전 허락 없는 자동화 수단 이용을 금지한다고 전해진다(2차 자료, **조항 번호·원문 미확인**). 자동 로그인에는 '자동입력 방지'·해외 로그인 본인 확인이 걸린다는 보고가 있다. 허용으로 읽을 근거는 없고 제재로 읽을 근거는 있다.
- **티스토리**: Open API 는 2024-02 종료(공지 2664, official high). 약관·운영정책에 글 발행 자동화를 직접 금지하는 조항은 찾지 못했다(요약 모델 경유라 '단어 없음' 판정은 원문 대조 전). 포괄 조항(서비스 운영 방해·허용하지 않은 방법)과 카카오 로그인 보호(새 환경 추가 인증·로봇 확인)가 자동 로그인을 구조적으로 막고, 댓글 자동화는 명시적 제재(2025-09-29 시행)가 있다. 공지 2705(2026-10-12)는 AI 글을 거의 그대로 발행해 경험·생각이 안 드러나는 경우를 크리에이터 선정에서 아쉬운 점으로 든다(제재 문구 없음).
- **대안 스펙트럼**(권장 순): ① 알림 + 수동 발행에 '복사 편의' ② 공식 API 가 있는 곳(Blogger, GitHub Pages PR)은 API·병합으로 자동화하되 **사람 승인 게이트** ③ (선택, 개인 PC 한정) 사용자 본인 브라우저의 사용자 스크립트·북마클릿이 편집기를 **채우기만** 하고 발행은 사람이 누름 ④ 모바일 자동화(Tasker·MacroDroid)·Actions 러너 RPA·완전 무인 RPA 는 비권장.

## 5. 확인 못 한 것·사용자가 확인할 것

- 텔레그램 공식 문서·FAQ·약관 원문(이 PC 의 네트워크 차단), 네이버 약관·운영정책·고객센터 원문(조사 도구가 접근 거부 — AI 크롤러를 막는 사이트라 우회하지 않았다), 티스토리·카카오 약관은 요약 모델을 거쳐 읽었다.
- Android 에서 `copy_text`·`pre` 탭 복사 동작, 러너에서 `api.telegram.org` 호출(작업 TG 의 `[공통] 텔레그램 알림 시험` 으로 확인), 네이버·티스토리 편집기의 붙여넣기 서식, GitHub 모바일의 `workflow_dispatch`·딥링크, Blogger `publishDate` 형식·과거 날짜 동작은 **실제로 해 보기 전에는 미확인**.
- 사용자가 확인할 것: ① 알림을 받을 기기(휴대폰?)와 붙여넣을 기기가 같은지 ② 업무용 PC·사내망에서 텔레그램·블로그 편집기·GitHub 에 접속되는지, 개인 계정 로그인·붙여넣기를 감시하는 정책이 있는지 ③ "오토마우스"가 완전 무인 발행인지, 사람이 읽고 승인한 뒤 붙여넣기·클릭만 대신하는 것인지(후자라도 위 이유로 비권장) ④ 하루 발행 편수와 글당 이미지 수(사람 시간 추정에 필요).
