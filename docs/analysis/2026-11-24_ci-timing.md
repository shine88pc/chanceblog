## 3. 읽는 법과 발견
### 3-1. 시간은 어디에 쓰이나
칸 시간 = 러너 시작 지연(1–3초) + 체크아웃 + setup-python(0–6초) + 의존성 설치(3–9초) + 저장소 가드레일 검증(4–8초) + **단위 테스트(250–570초)** + actionlint(3.12 칸 0–1초). 단위 테스트가 칸 시간의 95% 안팎이다.

### 3-2. 러너 편차 — 같은 코드인데 최대 1.7–2.0배
변경 없는 가지의 3.10 칸 단위 테스트는 11-24 15:30 에 304초, 21:30 에 527초였다(같은 코드 기준 1.7배, 3.12 칸은 253초와 511초로 2.0배). 같은 15:30 의 진단 가지는 567초였지만 시간 재는 시험이 더해진 가지라 편차 계산에서는 뺐다. 저녁 슬롯에서 러너 CPU 가 읽혔다 — **AMD EPYC 7763 이면 약 530초, Intel Xeon 6975P-C 이면 약 340초**(같은 3.10 칸·같은 코드, 슬롯 5 대 6의 진단 가지). 같은 파이썬·같은 단계로 본 직렬 값의 범위는 3.10 칸 304–527초(변경 없음 6회, 진단 가지 포함 304–567초), 3.12 칸 253–511초 다. 제한 600초에 가장 가까웠던 칸은 3.10 칸 단위 테스트 567초(여유 10초)였다.

### 3-3. 제한과 취소
- 오늘 시간 제한(10분)으로 **취소된 검사**: [M114] 첫 검사 3.10 칸, [M116] main 검사, [M117] main 검사(3.10 칸, 단위 테스트 단계 취소) 등. 취소된 칸은 '실패' 가 아니라 '취소' 라 main 의 알림 job(`failure` 일 때만 보냄)이 울리지 않는다 — 병합완료 알림 사유에 적어 알렸다.
- main 에서는 새 push 가 오면 앞선 main 실행을 취소한다(`concurrency … cancel-in-progress: true`)는 점도 같은 종류의 조용한 취소다(제안: main 만 취소하지 않게 — 별도 T3).

### 3-4. 캐시·중복 설치는 이득이 작다
- pip 캐시 설정이 없어 설치는 매번 새로 받는다(미스) — 그래도 설치는 3–9초다. 캐시를 켜도 얻는 것은 5초 안쪽이다. 같은 칸에서 같은 요구 파일을 두 번 설치하는 곳은 없다(칸당 한 번). actionlint 는 3.12 칸에서만.
- 파이썬은 러너 도구 캐시에 있어 3.12 는 0초, 3.10 은 4–6초(내려받았을 수 있음).

## 5. 권고
**안 A(병렬 시험 실행기)를 별도 T3 변경안으로 올린다**(확인 039, 22시 전후 발송). 이유: ① 시험을 지우거나 건너뛰지 않고 ② 직렬 대비 중앙값 약 2.4배 빠르고 가장 느린 러너에서도 여유가 크며(직렬 최소 여유 51초 → 병렬 약 320초) ③ 워크플로는 `run:` 한 줄만 바뀐다. 위험(새 필수 부품·병렬로 드러나는 시험끼리의 부딪힘)은 독립 검증 둘이 지적한 시험 구멍과 설명 문장을 고치는 재작업과 재검증으로 줄이고, 시험 id 를 처음 모은 것과 실제 돈 것을 정확히 견주는 장치(변이로 확인)가 빠짐을 막는다.
- 별도로 묶어 여쭐 작은 T3: main 검사가 다음 push 에 취소되지 않게(`cancel-in-progress` 한 줄)·시간 제한 취소가 알림 job 에서 조용한 문제의 보강. 칸 제한 15분으로 늘리기와 job 분리는 안 A 가 승인되지 않을 때의 대안이다.
- 이미 병합된 [M118](시험 코드 중복 계산 제거, 약 8–9%)은 안 A 와 함께 쓸 수 있다. 다음 단계의 제품 쪽 메모(`fact_topics.blocked_in` — T2 후보)는 병렬 뒤에 필요가 줄어든다.
