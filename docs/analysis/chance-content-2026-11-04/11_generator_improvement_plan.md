### ① 출처 없는 사실을 생성하지 않는가

- **빈 곳(증거)**:
  1. 지침을 어겨도 코드가 모릅니다. 공개 글(10-27 DG Energy, 한글)에 원문에 없는 원화 환산이 남아 있고(진단 담당 출처 대조로 확인), 시뮬레이션 S4 가 이 글을 정확히 잡습니다. D-77 은 지침만 고쳤고 '모델이 어길 수 있어 눈으로 확인'으로 남겼습니다(`docs/ARCHITECTURE.md` §4-1 공통 작성 지침).
  2. 근거 입력이 구조적으로 얇습니다. 오늘 12:03 피드 표본: NASA 항목 10건 — 모델이 받는 글자 합 2,851자 vs 같은 피드 항목의 전체 본문 42,576자(7%), 본문 속 숫자 170개 중 9개(5%)·고유명사형 낱말 331개 중 41개(12%). NASA 는 `description`(중앙 366자)과 `content:encoded`(중앙 4,342자, 최대 11,021자)를 둘 다 주는데 `text_of`(1237~1247줄)가 문서 순서상 먼저 나오는 `description` 만 읽습니다. EU 디지털 전략은 `description` 중앙 1,682자를 300자로 자릅니다.   4. 한·영 두 글은 같은 근거에서 나오는데 서로 대조하지 않습니다. 10-27(CEF) 글은 한글에만 4조·2천억 같은 환산 수치가 있고, 10-30(통계청) 글은 한글이 '2%포인트'(71−69 계산값), 영문이 'nearly 70%'(반올림)를 더했습니다(§5 S5, 손으로 확인).

### ⑦ 이미지 출처와 사용 조건을 확인하는가
운영자가 지시한 기준(#118 보충 전달)을 그대로 적용합니다: **'주제가 비슷하다'는 이유만으로 쓰지 말고, 실제 설명과 일치하는지·제작 주체·상업 블로그에서 쓸 수 있는 조건·캡션·alt 를 실제 내용 기준으로 확인한다.**
- **지금 막는 것(U3 포함, 코드 근거)**: 사진은 Unsplash 검색(`content_filter=high`·가로형, `search_unsplash` 358~399줄)으로 받고, 주소가 `images.unsplash.com/photo-…` 모양이며 사용 알림 주소가 `api.unsplash.com` 인 사진만 씁니다(`_record_photo` 308~355줄, `pipeline/unsplash_credit.py`). **작가 출처를 모르는 사진은 새 글에 쓰지 않고**(`pick_images` 464~466줄, 마지막 방어선 2277~2280줄), 이미 쓴 사진·이력의 사진은 피하고, 접근(HEAD)이 되는 것만 고르고, 고른 사진은 사용 알림을 보내며(`trigger_download` 402~411줄), 글에는 작가·Unsplash 출처 한 줄(utm 링크)을 이미지 바로 아래에 넣습니다. API 키는 리다이렉트를 따라가지 않는 머리글로만 보냅니다(`_api_request`).
- **못 막는 것(증거)**:
  1. **사진이 글의 실제 대상인지**: 선택은 모델이 만든 영어 검색어 3개에 대한 '주제 비슷한 첫 결과'입니다(프롬프트 1543~1545줄). 예: 같은 우주 사진이 우주날씨 한·영 글과 일본 MMX 영문 글, 세 편에 재사용됨(공개). 허블 글의 사진도 허블 사진인지 확인된 바 없음(표준 글 담당).
  2. **인물·상표·로고·건물**: 검색어에서 피하라고만 요청, 코드는 안 봄. 스톡 사진 라이선스는 사람·재산 사용 허락(릴리스)을 보장하지 않는다고 알려져 있어 상업 블로그에서는 별도 권리 문제가 될 수 있음(법률 판단 아님 — 운영자·전문가 확인 필요, 내가 라이선스 원문을 이번에 다시 읽지는 않음).
  3. **제작 주체의 진위**: 이름은 API 응답 그대로이고 이스케이프·길이 제한만 함(평문이면 어떤 이름도 통과 — `docs/ARCHITECTURE.md` §4-8 이 이미 인정).
  4. **사용 조건 기록**: 라이선스 안내 주소·확인일·사진 응답의 광고(스폰서)·유료 표시 필드를 이력에 남기지 않음. 응답에 그런 필드가 있는지는 이 저장소 코드가 읽지 않아 내가 확인하지 못함.
  5. **alt·캡션**: 본문 사진의 alt 는 항상 'Thumbnail'(`validate_post_data` 1950~1955줄) — 공개 글의 본문 사진 28개가 모두 이 값입니다(맞춤 alt 는 비공개 글 1개뿐). 캡션 없음. 홈 카드는 글 제목을 alt 로 쓰지만(`index.html` 220줄) 글 모달 표지는 'Cover'(312줄)입니다(광고 표면, T3).
  6. **기존 글**: 52편 모두 front matter `image` 가 있고 그중 12편(공개 10·비공개 2)은 본문에 사진 줄이 없으며(홈 카드·미리보기에만 쓰임), 작가 출처 줄·`ixid` 는 U3 이전 글 52편 모두 없음. 핫링크라 Unsplash 에서 사진이 내려가면 깨지는데 확인은 생성 시점 1회뿐입니다.
- **제안**
  - P7-a **선택 기준 분리**: 사진을 `subject`(글의 실제 대상을 보여 줌 — 사람이 지정하거나 1차 기관 사진) 와 `illustration`(분위기·이해를 돕는 사진)으로 나누고 **기본값은 illustration**. illustration 에는 코드가 고정 캡션 한 줄('이해를 돕기 위한 사진이며 실제 ○○의 사진이 아닙니다' 꼴)을 붙입니다. 사진이 대상인지는 코드가 판정할 수 없으므로 subject 지정은 사람 몫입니다. [캡션 문구는 정책·톤 → T3]
  - P7-b **alt**: 글 제목·핵심어 기반 한 문장 alt 를 요청하고 코드가 형식을 검사('Thumbnail'·'image'·파일명·제목과 똑같은 글자 금지, 10~125자).
  - P7-c **기록 확장**: 이력에 사진 ID·작가·프로필·검색어·선택 일시·라이선스 안내 주소·응답이 주는 설명(`alt_description` 등, 있다면)을 남깁니다.
  - P7-d **건너뛰기 규칙 검토**: 응답 설명·태그에 사람·브랜드·로고 낱말이 있으면 그 사진을 건너뛰는 규칙(응답 필드 확인 뒤 결정).

  - P7-f **비 Unsplash 이미지**(예: NASA 공개 사진)는 자동 경로가 받아들이지 않습니다(`pipeline/edits/checks.py` 의 허용 주소는 `images.unsplash.com` 만). 사용할 때는 제작 주체·사용 조건 페이지를 직접 열어 확인하고 크레딧 문구를 그대로 표기한 뒤 PR 로 반영(운영자 승인).

### 3-A-2 분야 판정 단계(신규) — 무엇을 어디에서 하나
1. **두 층 구조**: 공통 층(범용 가이드의 사실성·출처·귀속·재료·권리·중복 검사 — 모든 글에 같게)과 분야 층(주제별 가이드가 분야마다 요구하는 출처 종류·검증 규칙·피해야 할 방식). 공통 층은 3-A-1, 분야 층은 3-A-4.
2. **판정은 코드가 합니다(결정적)**: 모델이 분야·규칙을 고르게 하지 않습니다(G-L1). 입력은 **소스(이름·도메인)·편집 축(lane)·피드의 분류 태그·제목 핵심어** 네 가지이고 출력은 `주 분야`·`보조 분야`·`판정 근거`입니다. 소스 가족의 기본값(3-A-3)에서 시작해 제목·태그에 분야를 바꾸는 말이 있으면 보조 분야를 더합니다.
3. **여러 분야에 걸친 글**(주제별 가이드 §10): 독자의 핵심 질문에 가까운 분야 하나를 주 분야로, 나머지는 보조 분야로 두고, 규칙은 **합집합**을 쓰며 충돌하면 **더 엄격한 사실 검증·안전·권리 기준**을 따릅니다. 판정 근거가 약하면(소스 기본값과 키워드가 충돌) '분야 판정 신뢰도 낮음'을 기록하고 가장 엄격한 규칙 합집합을 쓰며 사람 확인 표시를 남깁니다.
4. **위치**: `fetch_news_items` 가 후보를 만든 뒤 `generate_blog_posts` 의 후보 루프(2199줄 근처)에서 후보마다 `classify_field(item, lane)`(`pipeline/quality_checks.py`, 순수 함수)를 부르고 결과를 `item["field"]` 에 둡니다. 쓰는 곳: (a) `build_post_prompt` 가 분야 지시 한두 줄을 소스별 `prompt_rule` 처럼 더함 (b) 사전 게이트(근거 기준) (c) 사후 검사(분야 규칙) (d) 실행 요약·이력에 분야 기록.
5. **새 분야는 별도 승인**: 지금 글감 소스는 과학·기술·정책·경제·통계(+건강 통계)뿐입니다. 생활정보·IT·여행·리뷰·교육·취미 가이드의 규칙 세트는 문서로 준비하되 코드에는 `enabled: false` 로 두고, 켜는 것은 소스·약관·톤 변경이라 **T3** 입니다.
6. **단계**: shadow(판정과 규칙 결과를 기록만) → 판정 정확도를 사람이 표본 확인 → 분야 지시를 프롬프트에 반영(T1/T3) → 분야 규칙의 결정적 부분만 hold 로 승격(T3).

범용 §10 은 '자동 품질 검사만으로 보장된다고 보지 않는다'고 했으므로, 위 후보는 **보류에만** 쓰고 '통과'를 증명하는 데 쓰지 않습니다(통과해도 사람 표본 점검은 계속).

### 3-A-6 범용 §8·§7 에서 설계에 더해진 것
- **내부 링크 주소 검증**(§8-1 '실제 게시글 URL 또는 공식적인 동적 URL 기능으로 검증'): Jekyll 의 `post_url` 태그는 빌드 때 글의 존재를 확인해 주는 공식 기능이지만, **없는 글을 가리키면 사이트 빌드 전체가 실패**합니다. 게시되는 문서 속 Liquid 가 빌드를 깨뜨린 전례(D-24, ENGINEERING_GUIDE R14)가 있으므로 **본문에는 `post_url` 을 쓰지 않고** 일반 주소를 쓰되, 생성기가 후보 목록(실제 글 파일과 permalink 규칙으로 계산, `posts.json` 과 대조)에 있는 주소만 허용하고 배포 뒤 확인 단계(`pages.yml verify`)에서 열리는지 보게 하는 쪽을 제안합니다(후자는 워크플로 변경이라 T2·별도 승인).
- **이미지는 설명 기능이 우선**(§7): 지금 생성기는 대표 이미지 2장을 못 구하면 글을 저장하지 않고 예외로 끝냅니다(2254~2256줄). 설명 기능이 없는 사진을 억지로 붙이는 것보다 '사진 없이 발행'(홈 카드는 `index.html` 의 `post.image` 조건이 있으나 JS 렌더 쪽 동작은 미확인)이나 **표·도식·그래프**가 낫다는 가이드와 어긋납니다. 이미지를 선택 사항으로 두는 정책은 레이아웃·홈 카드 영향이 있어 **운영자 결정(T3)** 항목이고, 기본값은 현행 유지입니다.
- **생성 이미지 표시**(§7): 지금은 AI 생성 이미지를 쓰지 않으므로 해당 없음. 쓰게 되면 '생성 이미지' 캡션을 코드가 붙이는 규칙을 같은 변경에 넣습니다.

## 4. 'auto 유지'와 양립하는 보류 설계

**원칙**: 자동 실행(정기 예약·슬롯·`mode: auto`·`direct`)은 한 글자도 바꾸지 않습니다. 바뀌는 것은 '후보 검증 칸에서 검사가 더 늘고, 그 검사에 걸린 후보는 지금의 본문 검증 탈락과 똑같이 취급된다'는 것뿐입니다.

### 4-1 흐름(지금 + 새로 얹는 것)
```
정기 실행(매시 17분·47분 UTC) → 그 슬롯에 글이 이미 있으면 정상 건너뜀(지금과 같음)
→ 후보 수집(약관 허용 소스·신뢰 도메인·72시간·제외 규칙)
→ [새·사전, 모델 호출 0] 같은 원문 주소 재사용(DUP_URL) · 근거량 부족(THIN_INPUT, 승인 시)
→ 후보 최대 3개, 후보마다 모델 호출 1회 → 응답 읽기 → 제목 유사도 → 본문 검증(분량·원문 링크·머리말)
→ [새·사후] 품질 검사: shadow 는 기록만, hold 는 그 후보를 탈락시킴
→ 통과한 첫 후보로 이미지 고르기 → 저장·이력·커밋·배포(지금과 같음)
→ 후보 전부 탈락 → ALL_REJECTED: 정기 실행은 글 없이 경고(초록)로 끝나고, 30분 뒤 다음 실행이 다시 시도
```
이 마지막 줄은 지금 코드가 이미 하는 일입니다(`generate_blog_posts` 2240~2245줄, `finish_run` 2419~2440줄, 시험 `test_candidates_all_rejected_is_all_rejected_in_schedule_mode`·`test_all_rejected_is_a_warning_not_a_failure`). 수동 실행은 지금처럼 예외(빨강)로 끝납니다. 이미지 2장을 못 구하는 경우의 예외(2254~2256줄)는 보류가 아니라 지금처럼 빨강입니다.

### 4-2 재시도 비용 — 이 설계의 가장 큰 숨은 위험(G-L5)
- 지금은 탈락한 후보를 어디에도 기억하지 않아, 슬롯이 열려 있는 동안 매 정기 실행이 같은 상위 후보로 모델을 다시 부릅니다. 정기 실행은 하루 약 30번(9~17시 18번 + 18~23시 12번, `docs/ARCHITECTURE.md` §4-8 이 같은 계산을 적음)이고 한 실행에 후보 최대 3개이므로, **탈락이 계속되면 하루 최대 약 90번의 Gemini 호출**이 될 수 있습니다(정상일 때 슬롯당 1~2번). 보호 장치는 `MAX_ATTEMPTS = 3`(55줄)뿐입니다.
- 지금은 탈락 원인이 드물어 문제가 안 보이지만, 품질 검사를 보류로 올릴수록 이 호출이 늘 수 있습니다. 운영 문서 G-L5 는 **'사용량이 늘면 T3'** 이므로 이 부분이 승인 항목입니다(WORKLOG U3 라운드도 같은 한계를 '재시도 간격을 늘릴지: 운영자 결정'으로 남겼습니다).
- 줄이는 층(앞의 것일수록 안전):
  1. **사전 게이트 먼저(모델 호출 0)**: `DUP_URL`·`THIN_INPUT` 은 모델을 부르기 전에 후보를 버립니다.
  2. **보류 모드의 실행당 후보 수를 2로**: 호출이 줄어드는 방향이라 안전합니다(`MAX_ATTEMPTS` 이하).
  3. **탈락 후보 기억**: 같은 원문 주소가 품질 검사로 K번 탈락하면 N시간 제외. 기억을 어디에 둘지는 아래 표 — 기본 추천은 '처음엔 기억 없이 1~2번만 적용하고, 첫 1주의 호출 수를 보고 결정'.
  4. **시간 기반 후퇴(상태 없음)**: 슬롯이 열린 지 몇 시간이 지나면 47분 틱은 새 후보를 시도하지 않음(호출 감소 방향, 슬롯 판정 변경이라 T2).

| 기억 방법 | 장점 | 위험·비용 | 판단 |
|---|---|---|---|
| (a) 기억 없음 + 1·2번 | 구현 최소, 소비자 영향 없음 | 최악 호출이 실행당 2개 × 30 = 하루 60번 | **시작은 이것** |
| (b) 별도 작은 파일(후보 주소·횟수·마지막 시각, 읽는 코드 없음) | 이력 소비자와 안 섞임 | 보류만 한 실행도 커밋·푸시 → `Pages 배포 실행`(`chanceblog.yml` 100~108줄)이 불필요하게 돌므로 워크플로 보정(T2) 필요 | 호출이 많을 때 |
| (c) `history.json` 에 `status: "held"` 항목 | 한 곳에 기록 | **회귀 위험 큼**: `health.py`(`REAL_POST_STATUSES` 21줄·`REJECT_STREAK` 156줄), `slot_state`(2067줄), `note_manual_over_cap`(2462줄), 확인 필요 모음의 글 수가 이력 항목을 글로 셈 | 비추천 |
| (d) Actions 캐시 | 커밋 없음 | 워크플로 변경(T2), 캐시 만료·실패 시 기억 사라짐 | (b) 대안 |

실제 호출 수는 이미 실행 요약에 나옵니다(`Gemini 호출: N회(실패 K회)`, `render_run_summary` 2392~2394줄) — 별도 측정 장치는 필요 없고, 보류 승격 뒤 첫 1주의 하루 합계를 운영자가 정한 기준(예: 하루 12회, 정상의 6배)과 비교하면 됩니다.

### 4-3 기록(G-L4 '사유를 이력에 남김')
운영 문서 G-L4 는 탈락 사유를 이력에 남기라고 하지만 Chance 는 로그·실행 요약(탈락 사유 3건까지, 2399~2401줄)에만 남깁니다. 제안: 그림자 단계는 **요약·로그에만**(소비자 영향 0). 이력 기록이 필요해지면 `history.json` 이 아니라 별도 파일(위 b)에 쓰고, 내용은 날짜·슬롯·후보 원문 주소·검사 번호·모드뿐입니다(값·본문 발췌·방문/수익 수치는 쓰지 않음 — R9·G-O7).

### 4-4 워치독 기준(36시간)
`pipeline/blogs.json` chance 의 `health.max_gap_hours: 36`(44줄)이라 마지막 글로부터 36시간이 지나면 `health.py` 가 STALE(심각)을 냅니다(144~148줄 근처). 어제 글이 0건이면 `NO_POSTS_DAY` 경고, 이틀 연속이면 심각입니다. 보류로 게시 빈도가 낮아지면 정상적인 보류가 심각 경고로 보입니다. 제안: 운영자가 목표 빈도(A1 권고: 주 2~3편 이하)를 정한 뒤 `max_gap_hours` 를 목표 간격의 약 1.5배(예: 72)로 조정. 값 하나 바꾸는 일이라 등급은 T1 이지만 '무엇을 정상으로 볼지'는 정책이므로 운영자 확인을 받습니다. (참고: 마지막 글 11-03 15:57 KST 기준 36시간은 11-05 03:57 KST 입니다.) 알림이 소란스러워지지 않게 보류 때마다 알리지 않고, 알림은 주 1회 요약이 낫습니다(별도 변경, G-C12 의 '공개 정보만' 준수).

### 4-5 사람 검토와의 관계(G-C11)와 '승인 흐름'
보류 게이트는 자동 검사이며 사람 검토를 대신하지 않습니다. 승인 흐름(`publish_flow: pr`)은 구현돼 있으나 꺼져 있고 실제 GitHub 에서 한 번도 돌려 보지 못했습니다(`docs/ARCHITECTURE.md` §4-4). 운영자는 'auto 유지'를 요구했으므로 이 개선안은 `pr` 없이 가능한 방어까지 설계하고, `pr` 병행은 별도 T3 선택지로 남깁니다. 켜게 되면 shadow 결과를 PR 본문의 '자동 점검 결과' 칸(`pipeline/drafts.py` 354~359줄 자리)에 넣어 사람이 보게 할 수 있습니다. 최소한의 사람 검토로는 운영 문서가 권하는 월 1회 5건 샘플 점검(SECURITY_GUARDRAILS '정책 위험에 대한 솔직한 평가' (4))에 `12_quality_checklist.md` 를 쓰면 됩니다.

### 4-6 되돌리는 법
검사별 `hold → shadow → off` 설정 한 줄(`pipeline/blogs.json`)로 즉시 되돌리고, 전체를 멈추려면 저장소 Variables 의 `PIPELINE_PAUSE=true`(G-O1), 코드는 `git revert`. 각 단계의 되돌리기는 §6 표와 `14_test_and_change_plan.md` 의 변경 이력 틀에 칸으로 있습니다.


### 4-7 범용 §12 '3단계 판정' ↔ 자동 처리 매핑(제안)
범용 가이드의 판정은 **통과 · 수정 후 통과 · 발행 보류** 세 가지입니다. 'auto 유지'에서는 사람이 중간에 끼는 칸이 없으므로 자동 실행에서는 아래처럼 풀어 씁니다. **세 판정 모두 자동 실행·슬롯·모드를 바꾸지 않습니다.** 발행하는 것은 '통과' 하나뿐이고 나머지 둘은 지금의 '후보 탈락'과 같은 길(그 후보를 버리고 다음 후보 → 전부 탈락이면 무게시·다음 실행 재시도)을 갑니다.
| 판정 | 자동으로 가르는 조건(제안) | 'auto 유지'에서의 처리 | '승인 흐름(pr) 병행'(선택)에서의 처리 | 기록 |
|---|---|---|---|---|
| **통과** | 결정적 검사를 모두 통과 | **지금처럼 발행** | 초안 PR(병합 = 공개) | 실행 요약에 `[QUALITY] verdict=PASS`. 경향 신호가 겹쳤으면 '사람 확인 우선' 표시만 붙임(판정은 안 바뀜) |
| **수정 후 통과** | '사람이 고치면 통과하는' 결정적 실패: 본문 안 원문 링크 없음(S1), 진짜 본문 분량 미달(S3), 출처 줄 형식·alt 형식 미달, 한·영 숫자 불일치(S5 — 어느 쪽이 맞는지 사람이 봐야 함) | **자동 발행하지 않음**: 그 후보를 버리고 다음 후보/다음 실행에서 다른 후보 시도. (사람 대기열이 없으므로) 같은 원문이 반복해서 이 판정을 받으면 운영자 요청 파일·주간 요약에 후보로 보고(별도 변경) | 초안 PR 에 '수정 후 통과' 표시와 사유를 올려 사람이 고쳐 병합 | `verdict=FIXABLE code=S1` |
| **발행 보류** | 중대 실패: 근거 부족(`THIN_INPUT`), 핵심 사실 불일치(S4 환산·G1 근거에 없는 숫자·분야 규칙의 결정 조건), 과도한 중복(`DUP_URL`), 주제 이탈(`TOPIC_DRIFT` — 근거 텍스트가 필요해 이번에 시뮬레이션하지 못했으므로 shadow 로 오탐을 본 뒤에만 승격 후보), 이미지 권리 미확인(기록 누락) — 범용 §10 의 보류 사유 5가지 | **자동 발행하지 않음 + 기록**. 같은 원문 주소는 일정 시간 다시 시도하지 않음(재시도 호출 감소, §4-2 의 기억 방법 선택에 따름) | PR 을 열지 않음(이미 열렸다면 닫기 권고) + 기록 | `verdict=HOLD code=S4` |
**경향 신호(숫자 부족·가정형·일반론·인과 단정 등)는 판정을 바꾸지 않습니다.** 신호를 판정에 넣으면 후반 14쌍 중 9~12쌍이 발행되지 않아(§5) 사실상 게시 중단이 되기 때문입니다. 신호는 '통과' 안에서 사람이 먼저 볼 순서를 정하는 태그로만 씁니다.
**시뮬레이션(후반 14쌍, 위 규칙을 52편에 소급해 적용)**: 통과 11쌍(그중 신호 2개 이상으로 '사람 확인 우선'이 붙는 쌍 7), 수정 후 통과 2쌍(10-26 Pew 한글 진짜 분량 미달, 10-30 통계청 분량 + 한·영 숫자 불일치), 발행 보류 1쌍(10-27 원화 환산). 즉 새 규칙이 있었다면 3쌍(21%)이 그 슬롯에서 발행되지 않았을 것입니다.
**사람 검토와의 관계**: 이 세 판정은 자동 점검이며 사람 검토를 대신하지 않습니다(범용 §10, 저장소 G-C11). 'auto 유지'만으로는 '통과' 글도 사람이 읽지 않으므로 월 1회 5편 표본 점검(체크리스트)을 같이 둡니다.
