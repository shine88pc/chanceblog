# 용어·관계 사전 (GLOSSARY)

> 대상: 운영자(비개발자)와 이 저장소에서 일하는 모든 AI. 목적은 하나입니다 — **같은 낱말을 모두가 같은 뜻으로 쓰게 하는 것.**
> 이 문서는 **규칙을 새로 정하지 않습니다.** 규칙의 정본은 각 문서(`AGENTS.md`·`docs/CHARTER.md`·`docs/SECURITY_GUARDRAILS.md`·`docs/ARCHITECTURE.md` …)이고, 이 문서가 코드·레지스트리(`pipeline/blogs.json`)와 어긋나면 **코드·레지스트리가 맞고** 이 문서를 고칩니다.
> GitHub 화면의 용어(워크플로·잡·PR·병합·라벨 …)는 `docs/ACTIONS_GUIDE.md` §8 '용어 풀이'가, 역할(모자)과 변경 등급의 정의는 `docs/CHARTER.md` §4·§5 가 정본입니다. 여기서는 **이 프로그램 안의 낱말, 그리고 같은 낱말이 곳마다 다른 뜻으로 쓰이는 경우**만 다룹니다.
> 배경: 운영자 요청(2026-11-03) — '업무 관계를 자연어 규칙 문서로 적어 두고 사람이 승인한다'는 방식을 이 프로그램에도 적용합니다. 그래프 데이터베이스·온톨로지 도구는 쓰지 않고, 이 문서 한 장과 그것을 지키는 시험 하나로 시작합니다.

## 1. 쓰는 법

1. 모르는 낱말·헷갈리는 낱말은 §3(개념 사전)과 §4(같은 낱말, 다른 뜻)에서 먼저 찾습니다.
2. **운영자에게 말하거나 요청 파일을 쓸 때**, §4 에 있는 낱말은 어느 뜻인지 붙여 씁니다. 예: "요청" 하나만 쓰지 않고 "요청 파일 r089"·"작업요청서"·"`[요청]` 양식"으로, "번호" 하나만 쓰지 않고 "요청 r089"·"PR #107"로 씁니다. (운영자에게 보이는 요청 번호는 소문자 r + 숫자 세 자리이고, 저장소의 파일 이름·앞머리 `id`·기록은 `R-089` 그대로입니다.)
3. 새 낱말이 생기거나 뜻이 바뀌면 **같은 변경에서** 이 문서를 고칩니다(§7).
4. 이 문서의 코드 이름(모드·채널 라벨·플랫폼·파일 경로 등)이 실제와 맞는지는 시험(`tests/test_glossary_docs.py`)이 지킵니다. 시험이 지키지 못하는 설명 문장은 사람이 고칩니다.

## 2. 관계 — 그림 대신 문장으로

한 줄이 한 관계입니다.

1. 블로그 하나는 레지스트리 항목 하나이고 `key`(영문 이름)로 구분합니다.
2. 블로그 하나는 **채널 하나·플랫폼 하나·모드 하나**를 가집니다. 채널 라벨은 그 블로그를 실행하는 워크플로 이름 맨 앞의 `[라벨]` 과 같은 글자입니다.
3. **플랫폼**이 '어디에 어떻게 올리는지'(어댑터)와 필요한 시크릿 역할을 정하고, **모드**가 '공개되는지'를 정합니다. `off`·`draft`·`package` 는 공개되지 않는 쪽이고 `auto` 만 자동으로 공개합니다. Chance 는 게시 방식(`publish_flow`)이 `pr` 이면 운영자가 PR 을 병합해야 공개됩니다.
4. 글 하나가 만들어지는 길: 주제 선정 → 생성(LLM) → **게이트** → (게시 · Blogger 초안함 · 초안 이슈 · 저장소 초안) → 이력 기록. 게이트가 하나라도 실패하면 게시하지 않습니다.
5. 게이트는 그 블로그의 **프로필**(콘텐츠 정책 파일) 기준으로 검사합니다.
6. **이력**은 중복·쿨다운·슬롯 판단에 읽는 기록 파일입니다. 직접 고치지 않습니다.
7. 광고는 두 층입니다 — **광고 선언**(`ads`)은 의도를 적고, **광고 표면**(보호 경로)은 T3 라서 운영자 승인 없이 바꾸지 않습니다. 실제 광고는 각 플랫폼 화면에서 운영자가 켭니다.
8. 사람에게 가는 길은 둘입니다. 운영 문제는 확인 필요 모음(GitHub 이슈 1개)과 워치독 이슈로, 새 글·초안 대기·AI 의 요청과 진행 현황은 **텔레그램**으로 갑니다.
9. AI 가 운영자에게 부탁할 일은 **요청 파일(R-nnn)** 로 보내고, 운영자는 PR 병합 또는 `[답변]` 양식으로 응답합니다. 운영자가 AI 에게 새 일을 맡길 때는 `[요청]` 양식이나 채팅입니다. **승인(T3)은 채팅(또는 소유자 응답 이슈)에서만 생깁니다** — 요청 파일을 쓰거나 병합 부탁을 보냈다고 승인이 생기지 않습니다.
10. T2 이상 변경은 구현자와 검증자가 **다른 세션**이어야 하고(독립 검증), 병합은 운영자가 합니다. 검증자의 '병합 가능'은 판정이지 병합이 아닙니다.
11. 데스크톱 프로그램은 이 저장소와 **별개 저장소**(chanceblog-desktop)에서 만들며, 같은 블로그들에 글을 올리는 Windows 프로그램입니다. 낱말 대응은 §5 입니다.

## 3. 개념 사전

### 3-1. 블로그와 발행

| 낱말 | 뜻 | 정본 |
|------|----|------|
| 블로그 | 레지스트리(`pipeline/blogs.json`) 항목 하나. 이름·주소·역할·플랫폼·모드·스케줄·상한·시크릿 이름을 가진다 | `docs/ARCHITECTURE.md` §3, `pipeline/registry.py` |
| `key` | 블로그를 구분하는 영문 이름(예 `chance`·`blogger_kcyoon`). 첫 글자는 영문 소문자이고 모두 2~31자의 영문 소문자·숫자·밑줄 | `pipeline/registry.py` |
| 채널·채널 라벨 | 운영자 화면에서 블로그를 묶어 부르는 이름. 레지스트리 `channel`(`key`·`label`)에 적고 라벨은 `Chance`·`Blogger 영문`·`Blogger 한글`·`티스토리`·`네이버` 다섯 중 하나다. 워크플로 이름 맨 앞 `[라벨]`·초안 이슈 라벨(`채널:<라벨>`)·현황판이 같은 글자를 쓴다. 블로그에 속하지 않는 워크플로는 `[공통]`·`[내부]` | `pipeline/registry.py`, `docs/ACTIONS_GUIDE.md` §2 |
| 플랫폼 | 올리는 방식. `jekyll-git`(저장소에 커밋 → GitHub Pages) · `blogger`(Blogger API) · `naver`·`tistory`(초안 패키지만 — 공식 자동 게시 수단이 없다) | `pipeline/registry.py`, `pipeline/publishers/` |
| 모드(`mode`) | 블로그마다 하나. `off` 정지 · `draft` 초안(공개 안 함 — Blogger 는 초안함에 올리고, 게시용 시크릿이 없으면 저장소 파일에만 저장) · `package` 초안 패키지(`naver`·`tistory` 전용) · `auto` 자동 게시. 정지한 이유는 `note` 에 적는다 | `pipeline/registry.py` |
| 게시 방식(`publish_flow`) | Chance 전용. `direct` 만들자마자 main 에 올려 공개(기본) · `pr` 초안 브랜치와 PR 로 올리고 운영자가 병합하면 공개(지금 꺼짐). `pr` 로 바꾸는 것은 T3 | `pipeline/registry.py`, `pipeline/drafts.py` |
| 광고 선언(`ads`) | 그 블로그의 광고 **의도**. `off` 없음(새 블로그의 시작값) · `pending_gate` 품질 게이트를 통과하면 켜려는 곳 · `on` 광고 코드가 사이트에 들어 있음(코드를 우리가 관리하는 `jekyll-git` 에서만). 올리는 편집은 T3 | `pipeline/registry.py`, `docs/SECURITY_GUARDRAILS.md` G-C10 |
| 광고 표면 | 광고 심사·광고 코드에 영향을 주는 파일(`index.html`·`privacy.md`·`about.md`·`contact.md`·`_includes/`·`_layouts/`·`_config.yml`·`robots.txt`·사이트 인증 파일 등). 전체 목록은 레지스트리의 `protected_paths`. 승인 없이 바꾸지 않는다 | `AGENTS.md` §2, `docs/CHARTER.md` §6.2 |
| 슬롯 | 글을 만드는 시각 칸. 레지스트리 `schedule.slots_kst` 에 한국 시각(시) 목록으로 적는다(Chance 는 9시·18시). 예약 실행(`cron`)의 시각은 UTC 다 | `pipeline/blogs.json`, `docs/ACTIONS_GUIDE.md` §8 |
| 이력(history) | 만든·올린 글의 기록 파일. 블로그의 `state.history` 가 가리킨다(`history.json`·`blogger_history.json`·`blogger_ko_history.json`·`naver_history.json`). 중복·쿨다운·슬롯 판단에 읽으므로 **직접 고치지 않는다** — 손상되면 `STATE_CORRUPT`, AI 에게 복구를 요청한다 | `pipeline/state.py`, `docs/ACTIONS_GUIDE.md` §6 |
| 콘텐츠 폴더(`content_dir`) | 글(또는 초안) 파일이 놓이는 폴더. Chance `_posts/`, Blogger 영문 `_blogger_drafts/`, Blogger 한글 `_blogger_ko_drafts/`, 네이버 `_naver_drafts/` | `pipeline/blogs.json` |
| 프로필(콘텐츠 프로필) | 한 블로그의 콘텐츠 정책·검증 기준 파일(길이·제목·구조·금지 표현·시드 주제 등). 레지스트리 `profile` 이 이름을 가리킨다 | `pipeline/profiles/`, `pipeline/registry.py` |
| 게이트 | 게시 전 자동 검사(파싱 → HTML 정화 → 정책·중복). 하나라도 실패하면 게시하지 않는다(fail closed) | `pipeline/gates.py`, `AGENTS.md` §2 |
| 어댑터(publisher) | 플랫폼별 게시 구현 | `pipeline/publishers/` |
| 킬 스위치 | 전체 정지는 저장소 Variables `PIPELINE_PAUSE=true`, 한 블로그만 정지는 그 블로그의 `mode: off` | `docs/SECURITY_GUARDRAILS.md` G-O1 |
| 제한 재개 잠금(`resume_lock`) | 레지스트리 최상위 스위치(기본 꺼짐). 켜면 사람 승인 없는 공개 경로(Chance 직접 게시·Blogger 자동·수동 즉시 게시·기존 글 이미지 직접 커밋)가 코드로 막히고 하루 최대 1편·굴러가는 7일에 최대 2편(주간 상한)·열린 초안 상한이 강제된다. 켜고 끄는 것은 T3. 발행 정지(`PIPELINE_PAUSE`)와 다른 스위치다 — 정지는 모든 실행을 멈추고, 잠금은 실행은 하되 승인 없는 공개만 막는다 | `docs/PUBLISH_PATHS.md`, `pipeline/publish_lock.py` |
| 초안 패키지 | `package` 모드의 결과. 글을 GitHub 이슈 1개(= 초안 1건)로 보여 주고 운영자가 복사해 직접 발행한다. 계정 정보는 저장·처리하지 않는다 | `pipeline/publishers/issue_package.py` |
| 워치독 | 발행 중단·반복 실패를 감시해 문제일 때만 이슈 `[Watchdog] …` 를 여는 작업. 판단 규칙은 `pipeline/health.py` | `scripts/watchdog.py` |
| 확인 필요 모음(운영 인박스) | 운영자가 직접 해야 할 일·확인하면 좋은 일을 한곳에 모은 GitHub 이슈 1개(`[운영] 확인 필요 모음`)와 같은 내용의 실행 요약 | `docs/OPS_INBOX.md`, `pipeline/inbox.py` |

### 3-3. 요청과 알림

| 낱말 | 뜻 | 정본 |
|------|----|------|
| 요청 파일(R-nnn) | AI → 운영자. `인수인계/요청함/` 아래 `R-<세 자리 번호>_<슬러그>.md`. 종류(`kind`)는 `merge` 병합 부탁 · `run` 실행 부탁 · `confirm` 확인 부탁 · `decision` 결정 부탁 · `info` 알림. 번호는 모든 원격 브랜치에서 겹치지 않아야 한다. 운영자가 읽는 글(텔레그램·접수 코멘트·양식)에는 같은 번호가 `r090` 꼴(소문자 r + 세 자리, 하이픈 없음)로 보인다 | `인수인계/요청함/README.md`, `pipeline/notify.py` |
| 병합 부탁 | `kind: merge` 요청. 운영자가 PR 하나를 병합해 달라는 부탁이다. 요청에 병합할 PR 제목을 적는다 | `인수인계/요청함/README.md`, `docs/AGENT_RUNBOOK.md` J4 |
| 알림 번호 | 폰 알림 맨 위의 번호(2026-11-06 표준, 계획 R-165): 진행 현황 `P001`(`info`)·병합 요청 `M001`(`merge`)·사용자 확인 요청은 숫자만 `001`(`decision`·`confirm`·`run`). 유형마다 번호가 따로 늘고 확인 번호는 다시 쓰지 않는다. 요청 파일 앞머리 `no` 에 적는다. 작업 식별자(요청 번호 `R-nnn`)와 별개다 | `인수인계/요청함/README.md`, `docs/ARCHITECTURE.md` §4-6-2 |

## 4. 같은 낱말, 다른 뜻

한 낱말이 곳마다 다르게 쓰이면 엉뚱한 것을 고르거나 지웁니다. 아래 낱말은 **종류를 붙여** 씁니다.

| 낱말 | 뜻 | 쓸 때 |
|------|----|-------|
| 키 | ① 블로그 `key`(`chance` 등) ② 시크릿의 **역할 이름**(`llm_api_key`·`unsplash_key`) → 그것이 가리키는 시크릿 **이름**(`GEMINI_API_KEY`) → 그 이름의 **값**(API 키, 비밀) ③ '핵심 키워드' | "블로그 key"·"시크릿 이름"·"키 값" 중 하나를 붙인다. 값은 저장소·로그·채팅·이슈 어디에도 쓰지 않는다(`AGENTS.md` §2) |
| 번호 | ① 요청 번호(요청 파일의 정본은 `R-nnn`, 운영자가 읽는 글에서는 `rnnn`) ② 이슈·PR 번호(`#107`) ③ Actions 실행 번호 ④ 점검 ID(`G-O1`·`WF-12`·`REG-1` 같은 규칙·검사 이름) ⑤ 절차 번호 `J3` ⑥ 등급 `T2` ⑦ **알림 번호**(폰에 보이는 번호 — 진행 현황 `P001`·병합 요청 `M001`·확인 요청은 숫자만 `001`, 유형마다 따로 늘고 요청 번호 R 과 별개) | 번호만 쓰지 않고 종류를 붙인다("요청 r089", "PR #107"). `R-nnn`·`rnnn` 은 PR·이슈 번호와 무관하다 |
| 요청 | ① 요청 파일(AI → 운영자, R-nnn) ② `[요청]` 양식(운영자 → AI, 번호 없음, T3 아님) ③ 작업요청서(운영자 → 저장소를 볼 수 있는 AI) ④ 이슈 수정 요청(이슈 양식 → 자동 PR) | 위 이름 그대로 부른다. "요청을 승인했다"처럼 '요청' 하나로 두지 않는다 |

| 게시·공개·업로드 | ① 게시 = `auto` 모드가 만들자마자 공개하는 것 ② 업로드 = Blogger 초안함에 올림(공개 아님) ③ 초안 이슈로 보여 줌 = `package`(공개 아님) ④ 공개 = ①이거나, 운영자가 직접 발행했거나, `pr` 흐름에서 PR 을 병합한 뒤 | '올렸다'와 '공개됐다'를 구분한다. ②·③ 은 공개가 아니다 |

## 5. 이름 대응표 (클라우드 ↔ 데스크톱)

이 저장소(클라우드 파이프라인)와 데스크톱 프로그램은 같은 블로그를 **다른 이름**으로 부릅니다. 한쪽 이름을 다른 쪽에 그대로 쓰지 않습니다.

| 블로그 `key`(레지스트리) | 채널 `key` · 라벨 | 플랫폼 | 데스크톱 구분 | 비고 |
|--------------------------|-------------------|--------|---------------|------|
| `chance` | `chance` · `Chance` | `jekyll-git` | `github_pages` | 같은 사이트(GitHub Pages) |
| `blogger_macat` | `blogger_en` · `Blogger 영문` | `blogger` | `blogger_en` | 영문 Blogger. 채널 key 와 데스크톱 구분이 같은 글자지만 **블로그 key 와는 다르다** |
| `blogger_kcyoon` | `blogger_ko` · `Blogger 한글` | `blogger` | `blogger_ko` | 한글 Blogger |
| `naver_life_tips` | `naver` · `네이버` | `naver` | `naver_a` · `naver_b` 중 어느 쪽인지 **미정** | 잠정 중단(`mode: off`). 데스크톱은 네이버 블로그를 둘(A·B)로 나누는데 이쪽 블로그가 어느 쪽과 같은지는 운영자가 정한다(이관 단계 입력) |

- 티스토리는 레지스트리에 블로그가 없습니다. 플랫폼 `tistory`·라벨 `티스토리`·워크플로 `tistory.yml` 만 남아 있고 2026-11-03 에 최종 중단했습니다(정기 실행 없음). 데스크톱에는 대응하는 구분이 없습니다.
- 이력 파일(`history.json` 등)과 콘텐츠 폴더는 클라우드의 기록입니다. 데스크톱의 '보관함'과 **같은 것이 아닙니다.** 어느 기록이 어느 쪽 항목에 대응하는지는 이관 단계에서 따로 정합니다(이관 매핑표 — 아직 없음).
- 데스크톱 쪽 이름의 정본은 chanceblog-desktop 저장소 문서입니다. 이 표의 '데스크톱 구분' 열은 시험이 지키지 못하므로(저장소가 다르다), 데스크톱 쪽 이름이 바뀌는 변경에서는 이 표도 함께 고치는 병합 부탁을 따로 보냅니다.

## 6. '모름'과 '0' — 읽지 못한 것은 0 이 아닙니다

1. **읽지 못한 것**(오류·권한·로그인 필요·시간 초과)과 **읽었더니 0 인 것**은 다릅니다. 읽지 못했으면 '0건'·'정상'·'없음'이라 쓰지 않고 **'읽지 못함'** 이라 쓰고 이유를 한 줄 덧붙입니다. 도구가 없는 환경에서는 읽은 것과 읽지 못한 것을 구분해 적습니다(`docs/AGENT_RUNBOOK.md`). 의심스러우면 게시하지 않는다는 규칙(`AGENTS.md` §2)도 같은 뿌리입니다.
2. **아직 모르는 숫자**(예: Gemini 한도)는 추정해 적지 않고 '아직 모릅니다'라고 쓰고 확인할 곳을 붙입니다(`docs/ACTIONS_GUIDE.md`).
3. 조사 보고서의 근거 표시 `[확인됨]`·`[부분 확인]`·`[확인 못 함]` 에서 '확인 못 함'은 '없음'이 아닙니다(`docs/analysis/2026-11-02_free-ai-code-editing.md`).
4. 이력 파일이 손상돼 읽지 못하면 `STATE_CORRUPT` 이지 '글 0건'이 아닙니다.
5. 방문자·수익 대시보드를 만들게 되면(`docs/ANALYTICS_PLAN.md` 제안) 값이 없는 칸은 0 이 아니라 '데이터 없음'으로 표시하고, 합계·평균에서도 0 으로 세지 않습니다.

## 7. 이 문서를 바꿔야 하는 때

- 코드에 새 모드·플랫폼·채널 라벨·광고 선언·게시 방식·요청 종류가 생기면 **같은 변경에서** §3 에 한 줄을 더합니다. 시험이 빠진 낱말을 찾아냅니다.
