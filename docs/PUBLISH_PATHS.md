# 공개 경로 전수조사와 제한 재개 잠금

> 2026-11-09 운영자 결정(일정·제한 재개): 발행 정지(`PIPELINE_PAUSE`)를 풀기 전에 **Chance 는 승인 흐름(`publish_flow: pr`), Blogger 는 초안 전용, 자동·직접 게시는 꺼짐, 하루 최대 1편(재개 뒤 일주일에 1–2편 — 확인 요청 007 답, 2026-11-09 20:33), 사람 승인 없는 공개 경로 0개**가 성립해야 하고,
> 이것을 코드와 시험으로 보장하지 못하면 정지를 유지한다. 이 문서는 ① 모든 공개 경로를 조사한 표 ② 레지스트리의 **제한 재개 잠금**(`resume_lock`)이 각 경로를 어떻게 막는지 ③ 켤 때 바꿀 값 ④ 남은 위험을 적는다.
> 코드 `pipeline/publish_lock.py` · 시험 `tests/test_publish_lock.py`·`tests/test_publish_paths.py` · 변경 등급 T2(워크플로 둘은 T3 성격이라 이유를 모두 적었다).

## 쉬운 설명 — 제한 재개 잠금이란

**잠금**은 레지스트리(`pipeline/blogs.json`) 맨 위의 스위치 한 줄(`"resume_lock": true`)입니다. 이 줄이 **없거나 `false`** 이면 아무것도 달라지지 않습니다(지금 상태 — 이전과 똑같이 동작).
이 줄을 **켜면** 사람이 글을 읽고 승인(PR 병합 또는 Blogger 화면에서 직접 게시)하지 않은 글이 공개 화면에 나갈 수 있는 길이 코드로 막힙니다. 규칙을 어기는 값이 하나라도 있으면 **글을 만들지 않고 빨간 실행으로 멈춥니다**(조용히 넘어가지 않습니다):

| 켜면 | 그래서 |
|------|--------|
| Chance 는 초안 PR 로만 올라간다(`publish_flow: pr`) | 병합(= 공개)은 사람이 한다. 닫으면 폐기 |
| Blogger 두 곳은 초안함·파일로만 간다(`auto` 금지, 수동 `publish`(즉시 게시) 입력도 거절) | 공개는 Blogger 화면에서 운영자가 직접 |
| 기존 글 이미지 교체(`[Chance] 기존 글 이미지 교체(수동)`)의 실제 교체는 멈춘다(연습 실행은 저장하지 않으므로 그대로 된다) | 이미지 변경은 이슈 수정 요청(수정안 PR)으로 |
| 하루에 만드는 글은 최대 1편(정기 실행·수동 실행 모두) | 지금은 정기 실행이 슬롯 2개로 하루 2편이고 수동 실행은 상한을 따지지 않는다 |
| 일주일(오늘을 포함한 굴러가는 7일)에 만드는 글은 최대 2편(정기·수동 모두 — 승인 대기·닫은 초안·병합된 글도 센다) | 지금은 정기 실행만으로 일주일에 14편이고 수동 실행은 상한이 없다. 운영자 조건 '재개 시 주 1–2편'을 코드로 못박는다 |
| 승인을 기다리는 초안이 3개에 닿으면 새 초안을 만들지 않는다 | 검토가 밀리면 더 쌓지 않는다 |
| 워치독(`watchdog.yml`)은 Chance 만 **주 단위 기준**으로 본다 — 마지막 글 허용 시간이 설정값 36시간에 7일을 더한 204시간이 되고 '어제 새 글이 없음'(`NO_POSTS_DAY`)은 알리지 않는다 | 주 1–2편 운영에서는 글이 며칠 없는 것이 정상이라, 이전 기준(36시간)이면 켠 직후부터 거짓 경보가 쌓인다. 잠금이 꺼져 있으면 이전 기준 그대로(§7-22) |
| 레지스트리의 잠금 줄을 잘못 적으면(`resume_lok` 같은 오타, 대소문자·하이픈·뒤 공백, 맨 위가 아니라 `defaults`·블로그 항목 안이나 그 안의 `limits` 같은 더 깊은 곳) | 줄이 없는 것과 달리 '켠 줄 알았는데 꺼져 있는' 일이 없도록 **그것도 오류로 멈춥니다** — 단 줄 이름이 `resume_lock` 과 거의 같을 때(글자 한두 개 차이)만 글 만들기를 멈추고, 이름이 전혀 다른 모르는 줄은 병합 전 검사만 거절합니다(§1 끝·§7-16) |

켜는 값 목록은 §6, 켜는 변경은 **별도 T3 병합**입니다(이 일은 레지스트리 값을 바꾸지 않았습니다).

**잠금 키 검사가 잡는 범위(과장 방지 — 독립 재검증 D3)**: 잠금 줄을 잘못 적은 것 중 코드가 잡는 것은 ① 값 오타(L0) ② 이름이 `resumelock` 을 품거나 편집 거리 2 이내인 최상위 키 오타(K1)와, 같은 모양의 키를 최상위 밖 어느 깊이(상한 16)에 둔 것(K2)이다. 이름이 전혀 다른 모르는 최상위 키(예: 두 낱말이 모두 망가진 `rsmlck`)는 병합 전 검사(검증기 REG-1)만 거절하고 실행 시에는 막지 않는다(§7-16). 켠 뒤에는 잠금 줄을 지우거나 옮겨 놓은 변경을 표지판 시험(§9)이 막는다.

## 2. 정의와 판정 기준

- **공개 경로**: 새 글·글 수정이 **사람 승인 없이 공개 화면**(GitHub Pages 사이트, Blogger 공개 글)에 나타나는 길. **사람 승인** = 사람이 글을 읽고 하는 동작 — Chance 는 초안 PR 의 병합, Blogger 는 초안함의 글을 Blogger 화면에서 직접 게시.
- **기록 파일·초안 폴더 커밋은 공개가 아니다 — 단, Jekyll 이 공개하는 경로로 들어가면 공개다.** 판정 규칙: 공개 사이트 파일이 되는 것은 ① `_posts/` 아래 글 ② 점(.)·밑줄(_)로 시작하는 구간이 없고 `_config.yml` 의 `exclude` 에 없는 파일. 밑줄 폴더(`_blogger_drafts`·`_blogger_ko_drafts`·`_naver_drafts`)와 점 폴더(`.github`)는 Jekyll 이 처리하지 않고, 이력 파일(`history.json`·`blogger_history.json`·`blogger_ko_history.json`·`naver_history.json`)과 `pages.json` 은 `exclude` 에 있다.
  시험(`RecordFilesAreNotPublicTest`)이 레지스트리의 모든 `state` 경로와 워크플로가 커밋하는 파일이 공개 경로가 아님을 같은 규칙으로 확인한다(대조군: `_posts/` 아래와 `about.md` 는 공개로 판정된다).
- 저장소는 공개라서 초안 브랜치·초안 PR·초안 이슈는 **GitHub 화면에서는** 누구나 읽을 수 있다. 블로그 사이트(공개 화면)는 아니다 — 이것은 승인된 설계다(`SECURITY_GUARDRAILS.md` G-L9 ⑧).

`contents: write` 를 가진 워크플로는 정확히 아홉 개(`blogger-en.yml`·`blogger-ko.yml`·`blogger.yml`·`chance-fix-images.yml`·`chanceblog.yml`·`issue-edit.yml`·`naver.yml`·`sync-issue-form.yml`·`tistory.yml`)이고, 글 전체를 커밋하는 `git add -A` 는 P1·P2 의 두 파일에만 있으며,
`gh pr merge` 는 어디에도 없다(사람의 병합이 곧 승인이다). 세 가지 모두 시험이 고정한다.

### 파이썬 쪽 쓰기 길(워크플로 글자에 안 보이는 것)
- `pipeline/draft_flow.py` `deliver`: 초안 두 파일을 초안 브랜치로 push 하고 `history.json` 한 파일만 main 에 커밋한다(`history.json` 은 공개 경로가 아니다 — 시험 확인). PR 은 `pull-requests: write` 로 연다.
- `pipeline/run.py`: Blogger API 로 초안 업로드 또는 공개 게시. 공개 게시(`draft=False`)는 mode `auto` 이거나 수동 `publish` 입력일 때뿐이다(P3·P4).
- `blogger_generator.py`: `pipeline.run.main` 을 부르는 호환용 얇은 래퍼다(워크플로가 부르지 않는다). 잠금은 러너 안에 있으므로 어떻게 시작하든 같은 규칙이 적용된다.
- 모든 새 파이썬 진입점은 `ALLOWED` 표에 올라 있어야 한다(새 명령이 더해지면 시험이 빨강).

## 4. 잠금 설계 — 켜면 코드가 강제하는 것

### 4-1. 레지스트리 규칙 (검증기: `python -m pipeline.registry`·`pipeline.plan`·`pipeline.run`·`validate_repo` REG-1)

**L0–L8 은 잠금이 켜져 있을 때만** 적용된다(꺼져 있으면 값 모양 검사 두 가지뿐 — L5·L8 의 둘째 줄). 모르는 값은 켜진 것으로 읽는다(fail closed). **K1·K2 는 잠금과 무관하게 항상** 적용된다 — 잠금 키가 아예 없는 지금의 레지스트리는 그대로 통과한다.

| 규칙 | 내용 | 막는 길 |
|------|------|---------|
| **L0** | `resume_lock` 의 **값**은 `true` 또는 `false` — 그 밖의 값(문자열 `"true"`·숫자·null)은 켜진 것으로 읽고 이 오류를 낸다. **L0 은 값 오타만 막는다**(키 이름 오타·위치 오류는 아래 K1·K2 가 막는다) | 값 오타로 잠금이 꺼지는 것 |
| **L1** | `chance.publish_flow` 는 `pr` — 적지 않으면 `direct` 로 읽히므로 `pr` 을 직접 적어야 한다 | P1 |
| **L2** | Chance 밖의 모든 블로그의 `mode` 는 `off`·`draft`·`package` 중 하나(`auto` 금지, 기본값 상속도 실제 값으로 판정) | P3 |
| **L3** | `chance.mode` 가 `auto` 이면 `publish_flow: pr` 가 함께 적혀 있어야 한다(자동 생성은 PR 로만) | P1 |
| **L4** | `chance.limits.max_posts_per_day` 는 1 | 하루 상한 |
| **L5** | `chance.limits.max_open_drafts`(열린 초안 PR 상한)가 있고 1 이상 3 이하 정수. 잠금이 꺼져 있어도 값이 적혀 있으면 1 이상 정수여야 한다(잘못 적은 값이 조용히 '규칙 없음'이 되지 않게) | 초안 적체 |
| **L6** | `chance.languages` 가 있으면 `ko` 를 포함하고 `ko`·`en` 만 겹침 없이(`["ko"]` 또는 `["ko", "en"]`) — 국문 우선 방향 | 번역 복제 |
| **L7** | Chance 밖의 모든 블로그의 `limits.max_posts_per_day` 도 1 (이 일이 더한 확장 규칙 — 운영자 조건 '하루 최대 1편'을 모든 블로그로 넓힘. 지금 값은 이미 1) | 하루 상한 |
| **L8** | `chance.limits.max_posts_per_week`(주간 상한 — 굴러가는 7일에 만드는 글 수)가 **있어야** 하고(없으면 오류 — fail closed) 1 이상 2 이하 정수(`MAX_POSTS_PER_WEEK` = 2, 불리언 아님). `defaults.limits` 에서 물려받은 값도 같다. 잠금이 꺼져 있어도 값이 적혀 있으면 1 이상 정수여야 한다(L5 와 같은 방식 — 잘못 적은 값이 조용히 '주간 상한 없음'이 되지 않게). **Chance 밖의 블로그(Blogger·네이버 초안 패키지)에는 주간 상한을 강제하지 않는다**: 그것들은 운영자가 직접 게시하는 초안 흐름이고 하루 1편 상한(L7)이 그대로 있다. 세는 방법은 §4-4(운영자 조건 '재개 시 편수 제한 주 1–2편', 확인 요청 007 답) | 주간 상한 |
| **K1** | 레지스트리 **최상위에는 알려진 키만** 둔다: `_doc`·`schema_version`·`shared_secrets`·`defaults`·`blogs`·`resume_lock`(`pipeline/publish_lock.py` 의 `KNOWN_TOP_LEVEL_KEYS` — 새 키는 이 목록과 시험(`KeyTypoTest`)을 함께 고쳐 의도적으로 더한다). 모르는 키는 오류('알 수 없는 최상위 키')이고, 줄인 이름(전각·호환 글자를 보통 글자로 풀고 소문자로 바꾼 뒤 `_`·`-`·공백을 뺀 것 — 전각으로 쓴 이름도 같다)이 `resumelock` 을 품거나 `resumelock` 과 **편집 거리 2 이내**(글자 하나의 삽입·삭제·바꿈을 1 로 센다)이면 'resume_lock 오타로 보입니다' 라고 알려 준다(`resume_lok`·`Resume_Lock`·`resume-lock`·`resume_lock `(뒤 공백)·`resumlok`·`resume_lock_v2` 등 — `block`·`clock`·`unlock`·`locked`·`resumed`·`blocklist`·`resume_after` 같은 평범한 모르는 키는 오타로 보지 않는다. 독립 재검증 D2) | 키 이름 오타로 잠금이 꺼진 채 통과하는 것 |
| **K2** | `resume_lock`(과 K1 이 오타로 보는 이름)은 **최상위에만** 둔다 — 최상위 밖 **어느 깊이든**(`defaults`·블로그 항목과 그 안의 `limits`·`schedule`·`state`·`health` 같은 사전, 목록 안의 사전까지) 있으면 오류('최상위에 두어야 한다'). 레지스트리 전체를 반복문으로 사전·목록마다 한 번씩만 훑고(순환·같은 하위 구조도 한 번), 깊이 상한은 `MAX_KEY_SCAN_DEPTH`(16 — 정상 레지스트리는 4)이며 그보다 깊으면 '구조가 너무 깊다' 오류로 멈춘다(fail closed). 예전에는 직속 키만 봐서 `chance.limits` 안의 `resume_lock` 이 통과했다(독립 재검증 D1) | 잘못된 위치로 잠금이 꺼진 채 통과하는 것 |

K1·K2 는 잠금 키가 없는 지금의 레지스트리에서 아무 오류도 내지 않는다(최상위 키가 모두 알려진 것이다). **실행 시에도 멈춘다**: 오타로 보이는 최상위 키(K1)와 잘못된 위치(K2)를 '잠금 키 문제'라 부르고, 가드·`chance_flow`·Blogger 러너·`check`·`check-direct` 가 이것을 만나면 글을 만들지 않고 멈춘다 — 오타가 '꺼짐'으로 읽혀 P2·P4·하루 1편 상한이 열리는 것을 막는다(독립 검증 지적 1). 잠금과 관계없는 모르는 키(위 오타 모양이 아닌 것)는 검증기만 거절하고 실행 시에는 새 실패 방식을 만들지 않는다. 오류 문장은 앞 `MAX_KEY_MESSAGES`(20)개만 내고 나머지는 '… 외 N개' 한 줄로 줄인다 — 모르는 키가 수천 개여도 검증기·가드의 출력이 커지지 않는다(예전에는 2만 개에서 4MB — 독립 재검증 D4, GitHub 실행 요약 한도는 1MiB).

### 4-2. 실행 시 가드 — 레지스트리 검증을 안 거친 길까지

| 길 | 어디서 | 잠금이 켜져 있으면 |
|----|--------|--------------------|
| 생성기(정기·수동) | `generator.py` `main()` 정지 검사 직후 한 줄 `publish_lock.guard_start(...)` | 규칙 위반이면 글을 만들지 않고 `::error::` + 종료 1. 하루 상한(1편)에 닿았으면 건너뜀(종료 0, 수동 실행이면 `::notice::`). 열린 초안 브랜치가 상한에 닿았거나 확인하지 못하면 건너뜀. 굴러가는 7일의 글 수가 주간 상한(L8, 1–2편)에 닿았으면 건너뜀(종료 0, 코드 `LOCK_WEEKLY_CAP`, 수동 실행이면 `::notice::` — §4-4). 이력 파일이 깨졌거나 이력 항목의 날짜를 믿을 수 없으면 세지 못해 멈춤 |
| 기존 글 이미지 교체 | 같은 가드 + 워크플로 첫 단계 | 실제 실행은 종료 1(연습 실행은 쓰는 것이 없어 가드는 통과하지만 워크플로 첫 단계가 어떤 실행이든 멈춘다) |
| Chance 발행 흐름 읽기 | `drafts.chance_flow()` — '발행 흐름 확인' 단계·`draft_flow deliver`·생성기가 쓰는 한 곳 | 규칙 위반이면 `direct` 로도 `pr` 로도 답하지 않고 멈춘다 → 그 단계가 실패하면 뒤 단계(직접 커밋·배포 요청·초안 올리기)는 하나도 돌지 않는다 |
| Blogger 러너 | `pipeline/run.py` — 레지스트리를 읽자마자 규칙 검사, 전달 방식이 정해진 직후 즉시 게시 검사 | 규칙 위반이면 어떤 글도 만들지 않고 `::error::` + 종료 2. `publish`(수동 입력·`--publish on`) 은 어떤 표기로도 거절. 초안함 업로드(`draft`)·파일 저장(`off`)은 그대로 된다 |
| Blogger 대상 계산 | `pipeline.plan`(워크플로 plan 잡) | 레지스트리 검증이 먼저라 규칙 위반이면 글 생성 잡이 시작되지 않는다 |
| 직접 커밋 워크플로 | `python -m pipeline.publish_lock check-direct`(`chance-fix-images.yml` 첫 단계) | 켜져 있거나 레지스트리를 읽지 못하면 종료 1 |

- **꺼짐 = 이전과 같다**: 잠금이 꺼져 있고 `max_open_drafts` 값도 없으면 가드는 레지스트리를 읽는 것 말고 아무것도 하지 않는다(이력·원격·출력 없음 — 시험 `GuardOffTest`가 부르면 실패하는 대역으로 확인). `main()` 수준의 같음은 `GeneratorMainTest` 의 `…guard_changes_nothing…` 시험이 지킨다(같은 하루를 가드를 거쳐 돌린 실행과 가드를 건너뛴 실행의 반환값·출력·요약·모델에 보낸 글·이력이 같다). `chance_flow`·러너는 기존 시험(`test_drafts`·`test_run`·`test_blogger_split` 등)이 그대로 통과한다. `generator.main` 을 돌리는 기존 시험은 흐름만 보도록 가드를 `guard_off()`(tests/lock_helpers.py)로 건너뛴다 — 켜는 변경이 레지스트리 값을 바꿔도 그 시험들이 임시 폴더에서 열린 초안을 세려다 멈추지 않게 하려는 것이고, 이유는 §9 에 있다.
- **읽기 전용 실행은 상한을 세지 않는다**: 연습 실행(`DRY_RUN`)과 그림자 실행(`SHADOW_RUN`)은 글을 올리지 않으므로 하루 상한·열린 초안 상한·주간 상한을 세지 않는다. 다만 규칙 위반(과 잠금 키 문제)은 가드에 닿은 실행이면 연습이든 그림자든 멈춘다(우회 없음).
- **합친 뒤의 순서(A)**: `generator.py` `main()` 에서 **정지 검사 → 그림자 분기(GATE 묶음, `SHADOW_RUN`) → 잠금 가드** 순서로 확정했다(코드 주석에도 적었다). 그림자 분기는 읽기 전용으로 처리하고 끝나므로 그림자 실행은 가드에 닿지 않는다 — 그래서 '그림자도 규칙 위반이면 멈춘다'는 순서 B(가드가 먼저)에서만 참이고 A 에서는 아니다(그림자는 쓰는 길이 없어 위험하지 않다). 가드 안의 `SHADOW_RUN` 예외(상한을 세지 않음)는 평소에는 닿지 않는 **방어선**이다: 그림자 분기를 지나쳐 가드에 온 경우를 위한 것이다. GATE 병합 전의 main 에는 그림자 분기가 없어 생성기가 `SHADOW_RUN` 을 모르므로 이 예외가 오히려 상한을 건너뛰는 틈이 된다 — 그래서 `chance-shadow.yml` 은 첫 단계에서 그림자 실행 코드(`pipeline/shadow_run.py`)가 없으면 실패하고, 잠금을 **켜는 변경은 GATE 병합 뒤에만** 한다(§5-7·§6).
- **`SHADOW_RUN` 값 집합(이 문서가 한 곳)**: 켜짐 `1`·`true`·`yes`·`on`·`enabled`, 꺼짐 비움·`0`·`false`·`no`·`off`·`disabled`(대소문자·앞뒤 공백은 무시). 그 밖의 값은 **잠금이 켜져 있을 때** 가드가 실행을 거절한다(종료 2, 로그 `[SKIP] code=LOCK_BLOCKED reason=SHADOW_RUN_VALUE`, `::error::` 는 고정 문장). 잠금이 꺼져 있으면 가드는 값을 보지 않는다(출력이 이전과 같다). GATE 의 `generator.py` 판정과 같은 집합이어야 하고, 병합 뒤에는 `ShadowValueTest` 가 둘을 견준다(GATE 는 2026-11-10 에 병합됐고(M037) 이 견줌은 건너뛰지 않고 돈다 — 시험이 GATE 코드의 값 집합과 이 문서의 값 집합이 같은지 본다).
- **상태 줄(검증 지적 1②)**: 잠금이 **켜져 있으면** 가드가 로그에 `[잠금] 제한 재개 잠금: 켜짐` 한 줄을 남긴다. **꺼져 있으면(키가 없든 `false` 든) 아무것도 남기지 않는다** — 꺼진 상태의 출력이 이전과 바이트까지 같아야 하므로 '항상' 이 아니라 '켜져 있을 때만'을 골랐다. 기준선(origin/main)과 시나리오 56개를 견주니 '키가 있을 때만'(꺼짐 줄 포함)은 `resume_lock: false` 인 시나리오 둘이 한 줄 달라졌고 '켜져 있을 때만'은 꺼진 모든 시나리오가 같았다. 꺼짐은 `check` 로 본다. 키 이름 오타·위치 오류는 K1·K2 로 멈추므로 '조용히 꺼진 채'가 되지 않는다. `check`·`check-direct`(워크플로 단계의 명령)는 늘 상태를 로그에, `GITHUB_STEP_SUMMARY` 가 있으면 실행 요약에도 남긴다.
- **열린 초안 수 세기의 한계**: 생성기 프로세스에는 저장소 쓰기 토큰을 주지 않는다(`test_the_generator_step_does_not_get_the_github_token`). GitHub API 로 '열린 PR 수'를 세려면 토큰이 필요하므로 git 으로 원격의 초안 브랜치(`ai/draft/…`)를 읽고, 글이 이미 main 에 있는(병합된) 초안은 빼서 센다. **닫은 초안도 브랜치가 정리되기까지(7일) 열린 것으로 센다** — 실제 열린 PR 수보다 크거나 같아 상한을 넘기는 쪽으로는 틀리지 않는다(승인을 연달아 닫으면 최대 7일 새 초안이 쉬는 것이 비용이다).
- **하루 상한의 단위**: 이력(`history.json`)의 `date`(한국 날짜)가 오늘인 항목 수다. 승인 대기·닫힘·병합 모두 이력에 남으므로 닫은 뒤에도 같은 날 다시 만들지 않는다.
- **실제 git 으로 확인한 이야기**: `tests/test_publish_lock_git.py`(`RealGitLockStoryTest`)가 임시 bare origin 과 실제 생성기로 하루하루를 따라간다 — 잠금이 켜진 승인 흐름에서 main 에는 이력 한 파일만 올라가고 글은 초안 브랜치에만 있다, 같은 날 두 번째 슬롯은 원격을 그대로 두고 건너뛴다, 열린 초안 수는 **실제 `git ls-remote`** 로 세며 병합한 초안은 빼고 이력에 없는 브랜치는 센다, 규칙을 어긴 레지스트리는 아무것도 올리지 않는다.

### 4-4. 주간 상한 — 굴러가는 7일에 최대 2편 (규칙 L8, 운영자 조건 '재개 시 편수 제한 주 1–2편')

운영자가 확인 요청 007 에 답했다(2026-11-09 20:33): 재개 시 **편수 제한(주 1–2편)** 과 사람 승인 필수. 하루 상한(1편)만으로는 주 7편까지 열려 있으므로, 잠금이 켜져 있으면 Chance 가 **굴러가는 7일**(오늘을 포함해 오늘과 그 6일 전까지, 한국 날짜)에 `chance.limits.max_posts_per_week`(1 또는 2)편까지만 만들게 한다. 한 줄로: **일주일 안에 글이 둘이면 셋째는 첫 글이 7일 창을 떠난 뒤에**. 센 값이 상한에 닿으면 정기·수동 실행 모두 코드 `LOCK_WEEKLY_CAP`(로그 줄 `[SKIP] code=LOCK_WEEKLY_CAP since=… until=… week=… cap=…`)로 정상 건너뜀(초록)한다. 사람 승인(초안 PR 을 직접 병합)은 그대로이고, 이 상한은 **시스템이 초안 PR 을 일주일에 상한보다 많이 만들지 않게** 한다 — 병합을 미룬 주에도 새 초안이 쌓이지 않는다.

세는 방법은 이 작업에서 가장 어려운 부분이라 선택을 표로 못박았다(시험 `tests/test_publish_lock_weekly.py` 가 행마다 확인한다):

| 항목 | 선택 | 이유·근거 |
|------|------|-----------|
| 세는 단위 | 이력 항목 하나(두 언어 모드면 한국어·영어 **한 쌍**, 국문 단독이면 글 하나) 또는 이력에 없는 초안 브랜치 하나 | 하루 상한과 같은 단위다(§7-14). 글 파일 수가 아니다 |
| 세는 것 | 창 안의 **(이력 항목) + (이력에 아직 없는 원격 초안 브랜치)** | 이력(`history.json`)은 공개된 글·승인 대기·닫은 초안·병합된 글을 모두 담는다 — `draft_flow.deliver` 가 생성 때 이력 항목을 글과 따로 main 에 올리기 때문에(PR 에는 글 파일뿐 — 둘, 국문 단독이면 하나) 병합을 미룬 초안도 이력에 있다. 그래도 이력 push 와 롤백이 모두 실패한 드문 경우에는 원격에 초안 브랜치가 있는데 이력에는 없으므로 그런 브랜치는 따로 센다 |
| 중복 제거 열쇠 | **초안 브랜치 이름**(`ai/draft/YYYY-MM-DD-sN` 정기, `ai/draft/YYYY-MM-DD-mHHMMSS` 수동) | 이력 항목의 `branch` 와 원격 브랜치 이름이 같다(`drafts.unmerged_draft_branches` 가 쓰는 열쇠와 같다). 이력 항목이 `flow=pr` 이고 `branch` 가 글자일 때만 잇고, 이어진 브랜치는 이력 항목으로만 센다(날짜는 이력의 `date`). 잇지 못하면(`flow` 가 `pr` 이 아니거나 `branch` 가 글자가 아님 — 이 코드가 만들지 않는 모양) 두 번 센다: 상한을 넘기는 쪽으로는 틀리지 않는 쪽이다 |
| 창 경계 | 오늘(KST)과 그 6일 전까지 **양끝 포함**. 7일 전은 창 밖. 시험: 오늘·6일 전·7일 전·월·연·윤년 경계·자정 직후(UTC 로는 아직 전날) | 하루 상한과 같은 '한국 날짜' 기준이고, 굴러가는 창은 달력 주(월–일)보다 엄격하다(§7-17) |
| 날짜(이력 항목) | `date` 가 정확히 `YYYY-MM-DD`(아스키 숫자, 실제 달력에 있는 날)인 글 | 시각·시각대 표기(`2026-11-09T09:00:00+09:00`)·앞뒤 공백·줄바꿈·전각 숫자·달력에 없는 날은 읽지 않는다 — 시각대를 바꿔 풀면 날짜가 하루 어긋날 수 있다 |
| 날짜를 믿을 수 없을 때 | **멈춘다**(종료 1, `[SKIP] code=LOCK_BLOCKED reason=…`, `::error::` 는 고정 문장): 사전 항목의 `date` 가 없거나 위 모양이 아님 `HISTORY_DATE_UNREADABLE` · 오늘보다 뒤 날짜 `HISTORY_DATE_FUTURE` · 이력에 없는 브랜치의 이름 날짜가 오늘보다 뒤 `DRAFT_BRANCH_DATE_FUTURE` | 하루 상한의 원칙(`read_history_strict`) 그대로 — 알 수 없으면 멈추고 **읽을 수 있는 것만 세고 지나가지 않는다**. 오래된 항목이라도 날짜를 못 읽으면 창 안인지 알 수 없다. 로그에는 항목 수만 적는다(항목마다 한 줄을 내지 않는다 — 출력 상한) |
| 사전이 아닌 항목 | 세지도 멈추지도 않는다 | 실제 `history.json` 의 맨 앞 5개는 옛 형식의 제목 문자열이다(날짜 없음). 이것을 '읽을 수 없음'으로 멈추면 켜는 순간 영영 못 돈다. 슬롯 판정·하루 상한도 사전 항목만 읽는다. 시험이 실제 이력 파일을 읽어 확인한다 |
| 이 흐름이 만들지 않는 브랜치 이름 | 세지 않는다(`ai/draft/odd`·달력에 없는 날짜·슬롯 24 이상) | 열린 초안 상한과 같은 규칙이다 |
| 초안 목록을 모를 때 | **멈춘다**: 코드 `OPEN_DRAFTS_UNKNOWN`(종료 0, `::warning::` 고정 문장) — 열린 초안 상한이 쓰는 같은 목록을 한 번만 읽는다 | fail closed. 이력만으로 이미 상한이라는 것을 알 수 있어도 목록을 못 읽으면 같은 코드로 건너뛴다(둘 다 새 글이 없다). 일시 장애에 다음 정기 실행이 다시 시도하도록 초록으로 둔다(§7-12) |
| 닫은 초안 | 창 안에서는 **센다** | GitHub API 로 닫힘과 대기를 가르려면 토큰이 필요한데 생성기에는 쓰기 토큰을 주지 않는다. 이력에 남아 있으므로 원격 브랜치가 정리돼도 센다. 하루 상한도 같다 — 닫은 뒤에 같은 날 다시 만들지 않는다 |
| 병합된 글 | 센다 | 공개된 글도 그 주의 편수다. 열린 초안 상한은 병합된 초안을 빼지만 주간 상한은 빼지 않는다 |
| 수동 실행 | 정기 실행과 **같은 규칙**: 슬롯 없는(`slot: null`) 항목도 한 건, 같은 날 여러 번 해도 브랜치 이름(`-mHHMMSS`)이 달라 건마다 센다. 상한에 닿으면 건너뛰고 `::notice::` 한 줄 | 정기·수동 모두 하루 상한을 받는 것과 같다 |
| 연습·그림자·이미지 교체 연습 | 세지도 막지도 않는다 | 이력·브랜치를 남기지 않는다. 규칙 위반(L8 포함)과 잠금 키 문제는 가드에 닿은 실행이면 멈춘다 |
| 상한을 보는 순서 | 하루 → (원격 목록을 못 읽으면 멈춤) → 열린 초안 → 주간. 둘 다 걸리면 앞의 코드가 나온다 | 코드가 안정되고(같은 입력은 같은 코드), 주간 상한이 생기기 전에 있던 결과는 바뀌지 않으며 새 코드는 그동안 통과하던 경우에만 나온다 |
| 상한값 | 레지스트리 `chance.limits.max_posts_per_week`(1 또는 2). 코드 상수 `MAX_POSTS_PER_WEEK`(2)는 L8 의 천장이다 | `max_open_drafts`(값)와 `MAX_OPEN_DRAFTS`(천장)의 관계와 같다 |
| 잠금이 꺼져 있을 때 | 세지 않는다 — 값이 적혀 있어도 모양(1 이상 정수)만 본다. 값이 없으면(지금의 레지스트리) 이전과 같다 | 꺼진 상태의 출력은 이전과 바이트까지 같아야 한다 |
| Chance 밖의 블로그 | 강제하지 않는다(L8 도 읽지 않는다) | Blogger·네이버 초안 패키지는 운영자가 직접 게시하는 초안 흐름이라 공개 경로가 아니고, 하루 1편 상한(L7)이 그대로 있다. 레지스트리의 `limits.max_posts_per_week` 는 그 블로그들에도 1–14 정수 검사(`registry.py`)만 받는다 |

| 이력과 원격의 모습 | 결과 |
|---------------------|------|
| 11-05 글 1건 | 통과 — 한 주 안의 둘째 글을 만든다 |
| 11-03·11-05 글 2건 | `LOCK_WEEKLY_CAP since=2026-11-03 until=2026-11-09 week=2 cap=2` 로 건너뜀 |

## 5. 그림자 실행 워크플로(`chance-shadow.yml`)가 어떤 쓰기도 못 하는 이유

목적: 발행 정지를 유지한 채 최소 품질 Gate 가 붙은 생성기가 만드는 초안을 읽기 전용으로 평가한다. 생성기의 `SHADOW_RUN=1`·`SHADOW_OUT`·`SHADOW_COUNT` 인터페이스를 부르고(출력 형식은 `docs/QUALITY_GATE.md`), 두 번째 단계에서 **별도 프로세스**로 측정 도구를 돌려 실행 요약(숫자만)과 아티팩트(보관 14일)로 낸다.

1. 트리거는 `workflow_dispatch` 하나 — 정기 실행·push·PR·이슈 이벤트가 없다.
2. 권한은 `contents: read` 뿐 — push 도 PR·이슈·배포 요청(`actions: write`)도 할 수 없다. 체크아웃은 `persist-credentials: false` 라 토큰이 git 설정에 남지 않는다. job 이 권한을 올리지도 않는다.
3. 단계에 `git`·`gh`·`curl` 이 없고 `GITHUB_TOKEN` 을 어느 단계에도 넘기지 않는다. 비밀(Gemini·Unsplash 키)은 생성기 단계의 `env` 로만 간다.
4. 정지 변수 `PIPELINE_PAUSE` 는 값을 그대로 넘길 뿐 바꾸지 않는다(정지가 켜져 있어도 건너뛰는 것은 생성기의 그림자 모드 코드다).
5. 생성기는 측정 도구를 부르지 않는다. 측정 단계는 도구(`pipeline/quality_shadow.py`)가 저장소에 있을 때만 돌고 없으면 건너뛴다. 실행 요약에는 숫자와 고정 문장만 쓴다.
6. 이 모든 것을 `ShadowWorkflowCannotWriteTest` 가 파일에서 직접 확인한다. 이 워크플로를 어떤 다른 워크플로도 부르지 않는다.
7. **병합 순서 의존(정직하게)**: 위 1–6 은 워크플로가 하는 약속이고, '읽기 전용으로 돈다·정지 중에도 돈다'는 말은 **그림자 실행 코드(GATE 묶음 — `pipeline/shadow_run.py` 와 `generator.py` 의 `SHADOW_RUN` 분기)가 먼저 병합된 뒤에만** 참이다. 그 코드가 없는 저장소의 생성기는 `SHADOW_RUN` 을 모르기 때문에 일반 실행으로 돌아 글을 만들고 Gemini 무료 한도를 쓴다. 그래서 체크아웃 바로 뒤 첫 단계가 `pipeline/shadow_run.py` 가 없으면 '이 저장소에는 그림자 실행 코드가 없어 중단합니다' 로 실패한다(없는 채로 도는 것을 구조로 막는다. 시험: `ShadowWorkflowCannotWriteTest` 의 단계·파일 존재 검사). **실제 병합 순서는 계획과 달라졌다**: 이 잠금(M034)은 그림자 실행 코드(GATE)보다 **먼저** 병합됐다(처음 계획은 GATE 가 맨 앞이었다. 2026-11-09 에는 main 에 SHADOW(M030)·R2(M031)·FACT(M032)가 먼저 들어 있었고, GATE 는 2026-11-10 에 병합됐다(M037) — SRC(허용 목록)는 아직 병합 전이다). 그래서 GATE 병합 전의 main 은 잠금이 꺼진 채라서 안전했고(이 워크플로는 첫 단계가 GATE 없이 도는 것을 막는다), **켜는 변경은 GATE 병합 뒤에만** 한다(§6) — 그 조건은 이제 충족됐다. 출력 형식 문서 `docs/QUALITY_GATE.md` 는 GATE 병합(M037) 뒤 저장소에 있다.

## 6. 켜는 방법 — 레지스트리에서 바꿀 값 (별도 T3 병합)

**켜기 전 조건: Gate 병합 뒤에만 켠다** — 그림자 실행 코드(GATE 묶음의 `pipeline/shadow_run.py` 와 `generator.py` 의 `SHADOW_RUN` 분기)가 main 에 들어오기 전에 켜면 가드의 그림자 값 예외가 하루 상한을 건너뛰는 틈이 된다(켠 사본에서 `SHADOW_RUN=1` 이고 오늘 이미 1건이어도 글이 둘째로 만들어졌다 — §4-2·§5-7, 독립 재검증 D6).

잠금을 켜려면 **한 번의 변경**으로 다음 **다섯 값**을 함께 고친다(하나라도 빠지면 검증이 빨강이라 병합 전에 걸린다 — 주간 상한 `max_posts_per_week` 도 값이 없으면 L8 이 거절한다):

| 위치 | 켜기 전 | 켤 때 | 규칙 |
|------|------|-------|------|
| 최상위 `resume_lock` | 없음 | `true` | L0 |
| `chance.publish_flow` | `direct` | `pr` | L1·L3 |
| `chance.limits.max_posts_per_day` | `2` | `1` | L4 |
| `chance.limits.max_open_drafts` | 없음 | `3` | L5 |
| `chance.limits.max_posts_per_week` | 없음 | `2` | L8 |
| `chance.mode` | `auto` | 그대로(`pr` 은 `auto` 일 때만 허용) | L3 |
| `blogger_macat.mode`·`blogger_kcyoon.mode` | `draft` | 그대로 | L2 |
| `naver_life_tips.mode` | `off` | 그대로(`package` 도 허용) | L2 |
| `chance.languages` | `["ko", "en"]` | 그대로(국문만 시작하려면 `["ko"]`) | L6 |
| Blogger·네이버 `limits.max_posts_per_day` | `1` | 그대로 | L7 |
| `PIPELINE_PAUSE`(저장소 변수) | 켜짐 | **이 일은 건드리지 않는다** — 잠금·최소 품질 Gate·그림자 검증이 끝난 뒤 운영자가 해제 | — |

같은 변경에서 함께 고쳐야 하는 시험의 고정값(켜는 변경이 일부러 깨뜨리는 표지판): 이 문서 §9 의 목록.
**잠금을 끄는 것**(`resume_lock` 을 지우거나 `false`)과 규칙을 줄이는 것도 T3 다 — 승인 없는 공개 경로를 다시 여는 변경이다(`SECURITY_GUARDRAILS.md` §3).

## 7. 한계와 남은 위험

1. **P5(워크플로 밖 main 직접 push)는 막지 못한다.** main 룰셋은 삭제·강제 푸시만 막고 PR 필수 규칙은 켜지 않았다(운영자 결정 2026-10-25 — 봇이 main 에 직접 push 해야 한다). 잠금이 켜지면 봇이 main 에 직접 올리는 것은 기록 파일(공개 아님)뿐이므로 PR 필수 규칙(봇 우회 허용 필요 — 미검증)을 켜는 것이 다음 단계 후보이고, 켜는 것은 운영자 설정이다.
2. 닫은 초안도 최대 7일 열린 것으로 센다(§4-2) — 새 초안이 쉬는 쪽의 오차다. 열린 PR 을 API 로 정확히 세려면 토큰이 필요한 별도 단계가 필요하고 시험이 막아 둔 '생성기에 토큰 금지' 원칙과 부딪힌다(운영자 결정 대기).
3. 이력 파일(`history.json`)이 깨지면 생성기의 `read_history` 는(잠금과 무관하게) 빈 기록으로 계속하는 기존 약점이 있다. 잠금 가드는 이 경우 하루 상한을 셀 수 없어 **멈춘다**(fail closed). 잠금이 꺼져 있을 때의 기존 동작은 바꾸지 않았다.
4. 하루 상한은 이력에 기록된 글 수로 센다. 같은 날 두 번째 슬롯·수동 실행을 막지만, 이력 커밋(`deliver` 가 main 에 올린다)이 실패해 롤백된 초안은 기록이 없어 세지 않는다(그 초안도 브랜치째 지워진다).
5. 레지스트리를 아예 읽지 못하면 글을 만드는 길은 `chance_flow()` 가 멈추지만 가드 자체는 새 실패 방식을 만들지 않는다(기존 동작 유지). 레지스트리를 읽지 않던 이미지 교체 길만 읽지 못하면 멈춘다.
6. `chance.mode: off` 는 Chance 생성기가 읽지 않는다(Chance 의 정지는 `PIPELINE_PAUSE` 뿐이다 — 기존 사실). 그래서 L1·L4–L6 은 Chance 의 `mode` 와 무관하게 적용한다.
7. 그림자 실행의 아티팩트는 공개 저장소의 공개 산출물이다(초안 PR 과 같은 취급). 비밀·수익 수치는 싣지 않는다.
8. 시험을 지우거나 약하게 만드는 변경은 시험이 지키지 못한다 — 사람 검토(독립 검증·`CODEOWNERS`)가 막는다.
9. `pages.yml` 의 수동 배포는 사람이 누르는 것이고 글을 만들지 않는다. 가지 배포를 환경 규칙이 막는지는 이 일에서 확인하지 못했다(미검증).
10. 잠금이 켜져 있으면 `chance.mode` 는 `auto` 로 고정된다(`publish_flow: pr` 은 `auto` 일 때만 허용되는 기존 규칙). Chance 만 따로 멈추려면 `mode: off` 가 아니라 전체 정지(`PIPELINE_PAUSE`)나 잠금을 끄는 T3 변경을 쓴다.
11. 그림자 실행 워크플로의 정지 우회(`SHADOW_RUN` 이 켜짐일 때만 정지 검사를 건너뜀)와 쓰기 차단은 생성기 쪽 코드(GATE 묶음)가 맡는다 — 이 문서와 시험은 워크플로가 읽기 전용이라는 것과 그 인터페이스(`SHADOW_RUN`·`SHADOW_OUT`·`SHADOW_COUNT`)만 증명한다. **'그림자 실행은 정지 중에도 돌고 읽기 전용이다'는 GATE 가 먼저 병합된 뒤에만 참이다**(§5-7). 합친 뒤의 `main()` 순서는 정지 검사 → 그림자 분기 → 잠금 가드(A)이므로 그림자 실행은 잠금 가드에 닿지 않는다 — '그림자도 규칙 위반이면 멈춘다'는 순서 B 에서만 참이다(§4-2). 병합한 뒤 실제 실행으로 확인한다(미관측).
12. **원격 초안 목록을 못 읽으면 조용히 건너뛴다**: `git ls-remote` 가 실패하면 가드는 종료 0(초록)으로 건너뛴다(`OPEN_DRAFTS_UNKNOWN`, `::warning::` 한 줄). 그 상태가 계속되면 글이 조용히 나오지 않고, 드러나는 곳은 워치독의 '마지막 글 36시간 격차' 알림뿐이다(빨강이 아니다). 일시 장애에 다음 정기 실행이 다시 시도하게 하려고 일부러 초록으로 두었다. 주간 상한(§4-4)도 같은 목록을 쓰므로 목록을 못 읽은 실행은 주간 상한을 세지 않고 같은 코드로 건너뛴다.
13. **닫은 초안은 7일간 열린 것으로 센다**(§4-2): 초안 PR 을 닫아도 브랜치가 정리되는 7일까지(`RETENTION_DAYS`) 상한에 들어가므로, 3개를 닫아도 새 초안이 며칠 쉴 수 있다.
14. **하루 '1편'은 한 번의 생성이다**(두 언어 모드면 한국어·영어 한 쌍, 국문 단독이면 글 하나): 한 번의 생성이 글 파일을 만들고(두 언어 모드면 둘 `KR`·`EN`) 이력에는 항목 하나가 남는다. 하루 상한 1 은 이 '한 번의 생성'을 센다(글 파일 수가 아니다).
15. **L6 은 GATE 의 `languages` 검증과 판정이 다르다(독립 검증의 비교표, 2026-11-09)**: L6 은 키가 없거나 `null` 이면 규칙을 적용하지 않고(그 경우는 기존 검증기와 GATE 의 검증이 따로 거절한다), 값이 목록이면 `ko` 를 포함하고 `ko`·`en` 만 겹침 없이 담았는지만 본다(순서 무관 — 허용 언어는 정확히 `{ko, en}` 이고 시험이 못박는다). GATE 묶음의 검증은 잠금과 무관하게 항상 켜져 있고, 비교한 시점의 GATE 는 순서(`["en", "ko"]`)·키 없음·`null` 도 거절해 L6 보다 엄격했다. GATE 가 순서를 가리지 않는 쪽(L6 과 같은 집합)으로 맞추는 중이라 병합 때 차이가 키 없음·`null` 로 줄 수 있다 — 병합 때 이 문장을 다시 확인한다. 어느 쪽이든 GATE 병합 뒤에는 두 검증을 모두 통과해야 레지스트리가 통과하므로 더 엄격한 쪽이 이긴다(서로 모순되지 않는다).
16. **실행 시 멈춤은 오타로 '보이는' 키만 본다**: 가드·`chance_flow`·Blogger 러너·`check` 가 멈추는 잠금 키 문제는 이름이 `resumelock` 을 품거나 `resumelock` 과 편집 거리 2 이내인 최상위 키(K1)와, 같은 모양의 키가 최상위 밖 어느 깊이(상한 16)에 있는 위치 오류(K2)뿐이다. 모양이 다른 모르는 최상위 키(두 낱말이 모두 망가진 오타 포함)는 병합 전 검사(검증기 REG-1)가 거절하지만 실행 시에는 막지 않는다 — 그 키는 잠금과 무관하게 무시된다. 그런 오타가 조용히 '꺼짐'으로 남는 것을 알아채는 길은 `check` 의 `꺼짐` 표시와, 켠 뒤의 표지판 시험(§9)과, 켜진 잠금이 로그에 남기는 상태 줄(`[잠금] 제한 재개 잠금: 켜짐`)이 안 보이는 것이다.
17. **굴러가는 7일은 달력 주와 다르다**: 주간 상한은 '오늘을 포함한 최근 7일'을 매일 새로 센다(월–일 한 주가 아니다). 어느 7일 구간에서도 상한을 넘지 않으므로 달력 주 한 주에도 넘지 않지만, 상한이 2 일 때 토·일에 두 편을 만들면 월요일이 와도 다음 토요일까지 새 글이 없다(달력 주 기준이면 월요일에 다시 열릴 것이다). 일주일 편수가 상한보다 적게 나가는 쪽의 오차다.
18. **창 안에서 닫은 초안도 센다**: 운영자가 초안 PR 을 닫아도(거절) 그 글은 이력에 남아 창을 떠날 때까지 건수에 든다 — 닫아서 새 초안을 곧바로 얻을 수는 없다. GitHub API 로 닫힘과 대기를 가르려면 토큰이 필요하고 시험이 '생성기에 토큰 금지'를 고정하고 있다(운영자 결정 대기). 초안 브랜치가 지워져도 이력으로 센다. 반대로 병합된 글도 센다.
19. **세는 값은 이력과 원격 브랜치 목록의 정확도만큼만 정확하다**: 이력은 마지막 200개 항목만 남기지만(`generator.write_history`) 창은 7일이라 문제가 없다. 이력을 손으로 지우거나 고쳐 항목이 사라지면 그 글은 세지 않는다(원격에 브랜치가 남아 있으면 이름으로 센다). 이력 항목의 날짜를 잘못 고치면(없음·모양 오류·미래) 가드가 멈춘다(종료 1 — 빨강) — 고쳐질 때까지 새 글이 없다. 사전이 아닌 항목(옛 형식의 제목 문자열)은 날짜를 읽지 않는다.
20. **Chance 밖의 블로그에는 주간 상한이 없다**: Blogger 두 곳·네이버 초안 패키지는 하루 1편(L7)만 코드로 강제한다 — 운영자가 직접 게시하므로 공개 경로가 아니라는 판단이다. 주간 편수 약속이 이 블로그들에도 필요해지면 따로 결정한다(T3).
21. **꺼진 잠금의 레지스트리에 값을 적어도 세지 않는다**: `max_posts_per_week` 는 잠금이 켜져 있을 때만 가드가 센다(꺼져 있으면 모양만 본다). 값을 미리 적어 두는 것은 안전하지만 상한은 켠 뒤에야 효력이 있다.
22. **켠 직후 일주일은 켜기 전의 글도 센다, 그리고 워치독은 주 단위 기준으로 바뀐다**(결함 D-169 해소, D-220–D-224): 켜기 전에 직접 게시한 최근 7일의 글도 이력에 있으므로 건수에 든다 — 켜기 전 마지막 글로부터 7일이 지나기 전에 켜면 그만큼 새 글이 늦게 나온다. 워치독(`pipeline/health.py`)의 '글이 안 나옴' 알림(`STALE` — Chance `max_gap_hours` 36 — 과 `NO_POSTS_DAY`)은 하루 한 편에 가깝던 때의 기준이라, 주 1–2편 운영에서는 글이 며칠 없는 정상인 날에도 울려 켠 직후부터 거짓 경보가 쌓인다. 그래서 `evaluate` 에 선택 키워드 `weekly_cap`(기본 `None` = 이전과 같음, 키워드 전용)을 더했고, `scripts/watchdog.py` 의 `chance_weekly_cap` 이 **제한 재개 잠금이 켜져 있고 잠금 키가 잘못 적혀 있지 않고 규칙을 어기지 않고 `chance.limits.max_posts_per_week` 가 1 이상 정수일 때만, Chance 에만** 그 값을 넘긴다(읽는 함수는 잠금 가드의 `lock_active`·`lock_key_problems`·`lock_errors`·`weekly_posts_limit` 를 그대로 가져다 쓴다). 주 단위 모드에서는 ① `STALE` 허용 시간이 설정값에 `WEEK_WINDOW_DAYS`(7일) × 24시간을 더한 값이 된다(Chance 36 → 204시간. 상한 1 이면 글 사이가 정확히 7일까지 정상이고, 하루 한 번 도는 실행·재작성 실패·후보 탈락의 여유가 더 든다. 문구에 '주 단위 기준(상한 N편)' 을 밝힌다) ② `NO_POSTS_DAY` 는 울리지 않는다(글이 없는 날이 정상 운영이다 — 살아 있음은 `STALE`·`FAIL_STREAK`·`RUN_FAIL_STREAK`·`REJECT_STREAK`·`UNPUBLISHED`·`PAGES_*` 가 그대로 본다) ③ 승인 흐름의 `DRAFT_WAITING` 변환(열린 초안 PR 이 있으면 `STALE` 을 가림, 72시간 이상 방치되면 `STALE` 경고도 함께)은 그대로이고 새 허용 시간 기준으로 `STALE` 이 울릴 때만 일어난다 — 그래서 `NO_POSTS_DAY` 에서 나오던 `DRAFT_WAITING` 도 없다(승인 대기 알림은 확인 필요 모음이 맡는다). 주간 상한에 닿아 쉬는 동안 새 알림(정보 이슈)은 만들지 않는다. 잠금이 꺼져 있거나 상한이 없거나 잠금 키가 잘못 적혀 있거나 규칙을 어기거나 레지스트리를 읽지 못하거나 Chance 가 아닌 블로그는 키워드를 넘기지 않아 출력이 지금과 바이트까지 같다(경보가 더 울리는 쪽 — 안전한 쪽). `pipeline/blogs.json`(`health.max_gap_hours` 포함)과 `.github/` 워크플로는 바꾸지 않았다(설정 변경은 T3 — 켜는 변경과 따로).
    - 이 방식을 고른 이유: 코드가 잠금·상한에서 스스로 파생하므로 켜는 변경 하나로 끝나고(고칠 설정값이 따로 없다) 잠금을 끄면 저절로 이전 기준으로 돌아가 두 곳이 어긋날 일이 없다. 모르는 상태(키 오타·규칙 위반·읽지 못함)는 모두 경보가 더 울리는 쪽이고, 꺼진 상태는 지금과 바이트까지 같아 되돌리기 쉽다.
    - 고르지 않은 대안 (가) 설정값 `max_gap_hours` 만 204 로 올림: 켜는 변경과 한 묶음이어야 하는 설정 변경(T3)이고 잠금을 끄면 다시 되돌려야 해서 두 곳이 어긋나기 쉽다. 하루 단위 `NO_POSTS_DAY` 는 그대로 울린다.
    - 고르지 않은 대안 (나) 경보를 그대로 두고 운영자가 무시: 정상 운영 중에도 거짓 경보(확인 요청 수준 알림)가 쌓여 진짜 경보를 못 알아본다.
    - 한계: 주 단위 모드의 `STALE` 은 마지막 활동 뒤 204시간(8.5일)에야 울린다 — 그 사이에 글 만들기가 빨갛게 실패하거나 탈락이 이어지면 `FAIL_STREAK`·`REJECT_STREAK`·`RUN_FAIL_STREAK` 이 먼저 울리지만, 초록으로 조용히 건너뛰는 중단은 이전 기준(36시간)보다 7일 늦게 드러난다. 승인이 평소보다 밀려 마지막 병합 뒤 204시간을 넘기면 `DRAFT_WAITING`(경고)이 울리고 열린 초안이 3일(72시간) 이상 기다리면 `STALE` 경고도 함께 남는다 — 의도한 승인 대기 신호이고, 켠 직후 첫 주에 켜기 전 글이 늦게 병합되면 한 번 울릴 수 있다(평소 늘 같은 만큼 늦게 승인하면 병합 사이가 7일이라 조용하다 — `WeeklySimulationTest`). 켠 뒤 실제 Actions 에서의 동작은 미관측이다. '마지막 활동'은 글·초안 기록과 글 커밋뿐이고 워크플로 실행 기록은 세지 않는다 — 그래서 실행이 아예 돌지 않거나(예약 실행이 꺼짐) 초록으로 건너뛰기만 해도 204시간(8.5일, 점검 간격까지 최대 약 9일)에야 `STALE` 이 울린다. 켠 뒤 첫 두 주는 4-1 의 매일 1분 점검에서 '마지막 글'과 열린 초안 수를 눈으로 확인한다.

## 9. 켜는 변경이 일부러 깨뜨리는 시험 고정값

켜는 변경(§6)은 별도 T3 병합이고, 그 변경은 **같은 변경에서** 진짜 레지스트리 값을 못박은 '표지판' 시험을 의도적으로 고친다(레지스트리만 슬쩍 바뀌면 이 시험들이 빨강이 되게 하려는 것이다).
이 목록은 켜는 값을 레지스트리 파일에 글자 그대로 넣은 복사본에 전체 시험(당시 98개 모듈)을 돌려 얻은 것이고, 아래 고침을 더한 복사본은 그때 전체가 초록이었다. GATE 병합(M037) 뒤의 main 에서 다시 돌리면 같은 이유로 `test_shadow_run` 한 건이 더 빨개진다(`DefaultUnchangedTest` 의 '정기 실행은 이전처럼 글을 쓴다' 시험 — 켜는 변경이 같은 변경에서 `setUpModule()` 로 `guard_off()` 를 단다, 아래 표 다음 문단과 같은 종류의 고침).

**다른 가지의 새 시험 12개(켜는 변경이 같은 변경에서 고친다 — 독립 재검증 D7)**: 두 묶음(GATE 는 2026-11-10 에 병합돼 그 시험 1개는 이미 main 에 있고, 다른 묶음은 병합 전)의 새 시험이 진짜 레지스트리로 `generator.main()`·`run_cli()` 를 돌려서, 켠 뒤에는 켜진 가드가 열린 초안 확인(`git ls-remote`)·하루 상한에 걸려 `SystemExit(0)`·`[잠금] … 켜짐` 줄·글 0개로 끝나 기대와 달라진다. 꺼진 상태에서는 모두 통과하므로 병합을 막지 않고, 켜는 변경이 합쳐질 때 같이 고친다.

| 묶음 | 모듈 | 깨지는 시험 | 개수 |
|------|------|-------------|------|
| SRC | `tests/test_generator_source_policy.py` | `AllowlistNoCallTest`(6)·`AllowlistFetchTest`(1)·`LegacyByteTest` 의 하위 시험(4) | 11 |
| GATE | `tests/test_shadow_run.py` | `DefaultUnchangedTest.test_a_normal_scheduled_run_writes_the_post_as_before_and_never_touches_the_shadow_path` | 1 |

고치는 법: 두 모듈에 모듈 수준 `setUpModule()` 을 두어 `guard_off()`(`tests/lock_helpers.py`)를 시작하고 `tearDownModule()` 에서 멈춘다 — 독립 재검증이 켠 합성의 스크래치 사본에서 두 모듈이 모두 통과함(35개·78개)을 확인했다. 주간 상한(L8)을 더한 뒤 같은 합성(이 변경 + GATE 가지 + SRC 가지 + 켜는 값 다섯, 2026-11-10 시점의 가지 머리)에서 다시 확인했다: 깨지는 시험은 그대로 12개(위 표 — 클래스별 개수는 이때 센 것)이고 모듈 수준 `guard_off()` 를 달면 두 모듈이 모두 통과한다(36개·82개) — 주간 상한 때문에 목록이 늘거나 바뀌지 않았다(주간 상한은 열린 초안 목록을 읽은 뒤에야 세므로 임시 폴더의 `git ls-remote` 실패나 하루 상한에서 이미 끝난다). 이후 가지에 같은 모양의 시험(진짜 레지스트리로 `generator.main()` 을 돌리는 시험)이 생기면 같은 방식으로 고친다. 켜는 변경은 GATE 와 SRC 가 든 합성에 켠 값을 적용해 전체 시험을 먼저 돌려 본다.

**이 일이 미리 보강해 둔 것**(켜는 변경이 건드리지 않아도 된다):
- `generator.main` 을 임시 폴더에서 돌리는 기존 시험(`test_generator_drafts` 의 `run_tick`·`test_generator_slots` `MainPolicyTest`·`test_manual_run_defaults` 둘·`test_gemini_call_log` 하나)은 잠금 가드를 `guard_off()`(`tests/lock_helpers.py`)로 건너뛰고 흐름만 본다. 가드가 임시 폴더(저장소가 아님)에서 열린 초안 수를 `git ls-remote` 로 세려다 멈추기 때문이다. `draft_flow_on` 을 시험 쪽에서 고정해 온 것과 같은 방식이다. 가드를 거치는 같음은 `GeneratorMainTest` 가 따로 지킨다. 새 시험이 `generator.main` 을 돌리면 같은 방식을 쓰고, 잠금 자체를 보는 시험만 `run_tick(..., guarded=True)` 로 돌린다.
- 실제 레지스트리를 복사해 Blogger 를 `auto` 로 두는 임시 저장소·사본(`test_run.make_root`·`test_plan_and_watchdog.registry_all_auto`·`test_drafts.real_registry`)은 `resume_lock` 키를 뺀다 — 그 시험들은 잠금이 꺼진 설정의 흐름을 보고, 잠금 규칙은 `test_publish_lock` 이 본다.
- 수동 실행의 하루 상한 경고 시험(`test_manual_run_defaults.ManualOverCapTest`)은 상한 2 를 읽는 '잠금 꺼짐' 레지스트리 사본으로 고정한다.
- 이 일의 시험은 '꺼짐' 기준에 진짜 레지스트리 대신 `today_registry()`(진짜 값을 오늘의 값으로 맞춘 사본)를 쓴다. 진짜 값에 묶인 것은 위 표의 `test_publish_lock` 한 시험뿐이다.

**표지판 시험은 고치되 지우지 않는다**: `LockStateTest.test_the_real_registry_has_the_lock_off_today` 는 켠 뒤 `resume_lock is True` 이고 `reg == lock_ready()` 인지 확인하는 시험으로 **바뀐다**(위 `flip.patch` 가 그렇게 고친다). 이 시험을 지우면 레지스트리의 잠금 줄을 지우는 변경(키가 없으면 꺼짐)을 아무도 못 잡는다 — K1·K2 는 오타와 잘못된 위치를 잡지만 줄을 통째로 지운 것은 이 시험만 잡는다.
**워치독의 '글이 안 나옴' 알림(결함 D-169 — 해결)**: 이 묶음이 워치독을 주 단위 기준으로 맞췄다(§7-22, D-220–D-224). 켜는 변경이 따로 할 일은 없다 — 레지스트리 값 다섯을 적으면 코드가 잠금·상한에서 스스로 파생해 Chance 의 `STALE` 은 마지막 글 204시간 뒤에 울리고 `NO_POSTS_DAY` 는 울리지 않는다(`health.max_gap_hours` 값은 그대로).
**켠 뒤에 달라지는 동작**: 18시 슬롯의 정기 실행은 하루 상한(1편)에 닿아 만들지 않고 정상 건너뜀(`[SKIP] code=LOCK_DAILY_CAP`, 초록)으로 끝난다. 수동 실행도 같은 날 두 번째부터는 같다. 승인을 기다리는 초안이 3개에 닿으면 새 초안을 만들지 않는다. 굴러가는 7일(오늘 포함)에 이미 두 편이 있으면(승인 대기·닫은 초안·병합된 글 모두) 세 번째는 `[SKIP] code=LOCK_WEEKLY_CAP`(초록)으로 건너뛴다 — 첫 글이 창을 떠나는 7일째에 다시 만든다(§4-4).
**켠 뒤 틀리는 문구**(워크플로 파일은 이 가지에서 바꾸지 않았다 — 켜는 변경(T3)에서 같이 고친다): `chanceblog.yml` 수동 입력 `dry_run` 의 설명 '(수동 게시는 게시 시각·하루 상한을 따지지 않습니다)' 는 잠금 아래에서 틀린다(수동 게시도 하루 1편과 굴러가는 7일에 2편을 따진다). 같은 취지의 문서: `docs/ACTIONS_GUIDE.md` 3-1 과 3-13 의 '수동 게시는 … 하루 상한(2편)도 따지지 않습니다'·'막지는 않고 노란 경고와 요약 줄로 알립니다'.
**같은 변경에서 고칠 문서**(시험이 일치를 확인하지는 않는다): 이 문서의 맨 위 설명과 §1 표의 `지금(꺼짐)` 열·§6 의 `지금` 열, `docs/ARCHITECTURE.md` §4-9 의 스위치 문단('이 일은 레지스트리 값을 바꾸지 않았다' 문장), `docs/ACTIONS_GUIDE.md` 3-22 의 `지금(꺼짐)` 열과 '켜졌는지 보는 법'. 그리고 허용 목록을 켜는 변경에서는 `docs/SOURCE_POLICY.md`(197·206행)와 `docs/ACTIONS_GUIDE.md` 6-1 의 `SOURCE_POLICY_NO_ACTIVE_PROVIDER` 행에 적힌 '36시간 뒤 STALE' 이 제한 재개 잠금이 켜진 Chance 에서는 204시간이라는 점도 맞춘다('36시간'·'STALE' 낱말은 `tests/test_source_policy_docs.py` 가 못박으므로 지우지 않고 덧붙인다).

**S2BFIX 로 달라진 것(`docs/FACT_PATH.md` D-308·D-309)**: 위 표와 12개 시험의 고침은 켜는 값 가운데 잠금·Gate·상한만 본 목록이다 — 값 전체(콘텐츠 출처 facts·허용 목록 모드·국문 단독·승인 흐름·NOAA 켜기)를 저장소 밖 임시 사본에 적용해 외부 접속을 막고 전체를 돌리면 시험 25모듈 약 670건이 빨개졌다. 병합 가지(S2BFIX)가 켜기 전·후 어느 상태에서도 초록인 수정을 먼저 담았다: 켜기 전 경로를 시험하던 클래스는 `lock_helpers.pre_flip` 으로 켜기 전 고정 표본(`tests/fixtures/registry_states/pre_flip_blogs.json`)을 읽는다 — 고정 표본은 잠금이 꺼져 있어 위 12개 시험도 잠금 가드에 걸리지 않으므로 켜는 PR 은 `guard_off()` 모듈 수준 고침을 더하지 않아도 된다. 켜는 PR 이 하는 일은 진짜 값 적기, 진짜 값을 못박은 소수 시험(`test_registry`·`test_publish_lock` 등)의 갱신, `tests/registry_states.py` 의 `EXPECTED_STATE` 를 한 칸 옮기는 한 줄이다(알려진 상태 가드 `tests/test_registry_state.py` 가 어긋남을 막는다).
