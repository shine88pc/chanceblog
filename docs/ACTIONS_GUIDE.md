## 먼저 읽기

1. **초록 ✓는 "프로그램이 오류 없이 끝났다"는 뜻입니다. "글이 올라갔다"는 뜻이 아닙니다.** 글이 올라갔는지는 실행 화면의 **Summary** "결과" 줄로 확인합니다(6장 '정상일 때').
   - 2026-10-25 진단에서 Chance는 글을 만들 시각이 된 정기 실행 13회 중 11회가 글 없이 초록이었고, Blogger는 게시용 시크릿 없이 초안만 만든 채 초록이었습니다.
   - 지금은 글이 없는 실행에 이유(`[SKIP] code=…`)가 남고, 이상 신호는 빨강입니다. 그래도 초록이 곧 "글이 올라감"은 아닙니다.
2. 시간은 모두 **한국시간(KST)** 입니다. 설정 파일의 시각은 UTC라서 9시간을 더합니다. GitHub는 예약 실행을 제때 시작하지 않고 자주 건너뜁니다(이 저장소에서 매시 예약 워크플로가 48시간에 48회 중 12회 실행된 관측이 있습니다, 2장 시간표).
3. **미확인**은 코드·기록으로 확인하지 못했다는 뜻이고, **예정**은 아직 반영되지 않은 계획이라 지금 동작이 아닙니다.
4. 이 문서는 **공개 사이트에 게시**됩니다. 비밀 값·개인정보·수익·방문자 수치는 적지 마세요. 시크릿은 **이름**만 적습니다.
5. GitHub 메뉴 이름과 누르는 순서는 외부 지식이라 이 저장소에서 시험하지 못했습니다. **화면 구성은 GitHub 업데이트로 달라질 수 있으니**, 다르면 비슷한 이름의 메뉴를 찾아 한 번 확인하세요.
6. 공통 이동: 저장소 → **Actions** → 왼쪽 목록의 워크플로 이름(맨 앞의 `[Chance]`·`[Blogger]`·`[공통]` 같은 `[구분]`이 어느 채널인지 알려 줍니다, 2장) → **Run workflow**(수동 실행). "Use workflow from"은 **main**으로 둡니다. 입력 칸에는 이름(`dry_run`) 대신 설명 문장이 보일 수 있어, 이 문서는 설명의 첫머리(예: `연습 실행`)로 입력을 가리키고 괄호에 입력 이름을 적습니다. 휴대폰에서는 Settings 탭이 "More"(⋯) 메뉴 안에 숨어 있을 수 있습니다.

## 1. 먼저 보는 곳

**가장 먼저 `[운영] 확인 필요 모음` 이슈 하나를 봅니다.** 아래 알림들에서 사람이 할 일을 한곳에 모아 둔 이슈입니다(라벨 `ops-inbox`, 담당자는 저장소 소유자). 현재 이슈 #22이고 Issues 목록 맨 위에 고정돼 있습니다. 2시간 간격으로 예약돼 자동 갱신되지만 GitHub가 예약을 늦추거나 건너뛰어 실제로는 보통 3~6시간 간격일 것입니다(예상: 정기 실행의 실제 간격은 아직 관측 전).

- 본문은 세 구역입니다. **지금 해야 할 일**(사람이 손대야 풀림: PR 병합·충돌·검사 실패, 실패한 워크플로, 승인 대기, 일시정지 해제, 시크릿 등록), **확인하면 좋은 것**(워치독 경고, 초록 실행의 경고, 오래 열린 PR), **참고**(현황·정지된 블로그). 항목마다 "바로 하기" 링크가 있습니다. 맨 위 한 줄 요약(`지금 해야 할 일 N건 · 확인하면 좋은 것 N건 · 참고 N건`)에서 **"지금 해야 할 일 0건"이면 급한 일이 없다는 뜻**입니다.
- 새로 해야 할 일이 생기면 이슈에 @멘션 코멘트가 달려 알림이 갑니다. 같은 항목은 한 번만 알립니다.
- 하지 않아도 되는 일: 이슈를 지우거나 제목 바꾸기(지우지 말고 닫아 두기 — 닫아 두면 새 "해야 할 일"이 생길 때만 다시 열립니다), 본문 직접 고치기(다음 갱신 때 덮어씀). 이슈가 안 보이거나 닫혔거나 지워졌을 때는 3-14를 봅니다.
- 이슈가 이미 있으면(현재 #22) 만드는 단계는 필요 없습니다. 이슈가 없을 때(지워졌을 때 등)는 정기 실행이나 수동 실행(`연습 실행` 해제) 때 새로 만들어집니다. 먼저 Actions → `[공통] 확인 필요 모음` → Run workflow에서 `연습 실행`을 체크해 요약만 확인한 뒤, 체크 없이 한 번 더 실행해도 됩니다. 자세한 내용은 6-10과 [`OPS_INBOX.md`](./OPS_INBOX.md)에 있습니다.

## 3. 이럴 땐 이렇게

### 3-1. 글을 지금 한 편 올리고 싶다

- **가능 여부**: Chance만 가능합니다(주제는 고를 수 없음). Blogger는 정지라 눌러도 "대상 0개"로 끝납니다(3-12).
- **할 일**
  1. 저장소 → **Actions** → `[Chance] 글 자동 작성·게시` → **Run workflow**.
  2. `연습 실행`(`dry_run`)의 **체크를 풀고**(기본은 체크) → **Run workflow**. 체크를 둔 채 누르면 연습이라 파일·커밋·게시가 없고 가짜 AI 응답을 써서 Gemini 한도도 쓰지 않습니다.
  3. 끝나면 그 실행의 Summary에서 "결과" 줄을 봅니다. `PUBLISHED`면 한·영 글이 만들어져 main에 커밋된 것이고, 곧 `[공통] 사이트 자동 배포`가 자동으로 뜹니다. 그것이 끝나면 사이트(https://shine88pc.github.io/chanceblog/)에서 글을 확인합니다. (승인 흐름을 켠 뒤에는 결과가 `DRAFT_CREATED`이고 글은 초안 PR 로 올라갑니다 — 병합해야 공개됩니다, 3-17.)
  4. 다른 결과는 6-1의 결과 코드 표에서 뜻을 찾습니다.
- **알아 둘 것**
  - Gemini·Unsplash를 실제로 부릅니다(무료 한도를 씁니다, 3-13).
  - 수동 게시는 슬롯 기록이 남지 않고(정기 실행의 슬롯 규칙은 3-2) 하루 상한(2편)도 따지지 않습니다. 오늘 이미 2편 이상이면 노란 경고와 요약 줄로 알려 주지만 막지는 않습니다.
  - 같은 시간대의 정기 실행이 글을 **한 편 더** 만들 수 있어서, 하루 2편을 넘겨 3편 이상이 될 수 있습니다.
  - 기사가 하나도 없으면 빨강(`ALL_LANES_EMPTY`)이고, 후보가 전부 탈락해도 수동 실행은 빨강입니다.
- **하지 말 것**: 시험 삼아 연타(글이 추가되고 한도를 씁니다). `[Blogger] 글 자동 작성(초안함 업로드)`을 눌러 글을 기대하기. `BLOGGER_*` 시크릿 등록.

### 3-2. 오늘 글이 안 올라왔다

- **증상**: 사이트에 오늘 새 글이 없는데 Actions는 초록이거나, 실행이 아예 안 보입니다.
- **먼저 알아 둘 규칙**: Chance는 하루 두 번 글을 만들 시각(슬롯)이 있습니다. 한국시간 **9~17시**에 정기 실행이 한 번이라도 돌아야 9시 슬롯 글이, **18~23시**에 돌아야 18시 슬롯 글이 만들어집니다. 0~8시의 정기 실행은 항상 "첫 게시 시각 전"(`OUT_OF_WINDOW`)으로 끝나는 것이 정상입니다. 슬롯 시간대 안에서는 글이 생길 때까지 매시 정기 실행이 다시 시도하고, 시간대가 지나면 그 슬롯은 포기합니다(과거 슬롯을 몰아서 만들지 않음).
- **원인 후보와 확인**

| 확인 | 어디서 | 뜻 |
|---|---|---|
| 그 시간대에 `정기` 실행이 있었나 | Actions → `[Chance] 글 자동 작성·게시` 목록의 제목 `… · 정기` | 없으면 GitHub가 예약 실행을 건너뛴 것입니다(자주 있음). 시간대가 끝나기 전에 다음 정기 실행이 보충하고, 끝났으면 그 슬롯은 건너뜁니다 |
| 결과 코드 | 실행의 Summary "결과" 줄 | `ALREADY_PUBLISHED`(이미 글 있음)·`OUT_OF_WINDOW`·`PAUSED`는 정상 건너뜀(승인 흐름을 켠 뒤에는 `DRAFT_PENDING` — 그 슬롯의 초안이 내 승인을 기다리는 중이거나 닫혀 폐기됨 — 도 정상 건너뜀, 3-17). `ALL_DUPLICATES`·`NO_CANDIDATES`·`ALL_REJECTED`는 초록+노란 경고(후보 없음·탈락, 다음 정기 실행이 다시 시도). `ALL_LANES_EMPTY`·`SOURCES_UNREACHABLE`은 빨강 |
| 글은 만들어졌는데 사이트에 없음 | 저장소 Commits의 "🤖 자동 포스팅/이미지 수정", `[공통] 사이트 자동 배포` 실행. 승인 흐름을 켰다면 Pull requests 의 `[초안][Chance]` PR | 3-7의 `[공통] 사이트 자동 배포`. 승인 흐름이면 PR 이 병합을 기다리는 것일 수 있습니다(3-17) |

- **할 일**: Summary의 결과 코드(또는 로그의 `[SKIP] code=` 한 줄)를 6-1 표에서 찾습니다. 어제 새 글이 없으면 워치독이 `NO_POSTS_DAY` 경고를, 그제도 없으면 심각으로 알립니다. 다만 Chance는 마지막 글이 36시간을 넘으면 `STALE`(심각)이 대신 알리고 `NO_POSTS_DAY`는 자동으로 닫힙니다(6-5). 승인 흐름을 켠 뒤에는 열린 초안 PR 이 있는 동안 이 둘 대신 `DRAFT_WAITING`(경고)이 올라오며, 뜻은 "멈춘 게 아니라 내 승인을 기다리는 초안이 있다"입니다(3-17). 급하면 3-1.
- **하지 말 것**: 원인을 모른 채 Run workflow 연타.

### 3-3. 기존 글의 이미지를 바꾸고 싶다

| 상황 | 길 | 결과 |
|---|---|---|
| 글 하나, 원하는 장면이 있음 | 이슈 양식 `기존 게시글 이미지 변경` | PR이 만들어짐 → 확인 후 병합 |
| 깨진·없는·중복 이미지를 여러 글에서 한꺼번에 | Actions의 `[Chance] 기존 글 이미지 교체(수동)` | **PR 없이 main에 바로 커밋**(잘못 바뀌면 AI에게 되돌려 달라고 요청) |

**길 1. 이슈 양식**
1. 저장소 → **Issues** → **New issue** → **기존 게시글 이미지 변경**.
2. "게시글 주소 또는 제목"에 글의 공개 주소(주소창의 URL)를 붙여 넣습니다(정확한 제목도 가능). "원하는 이미지 설명"에 장면을 구체적으로 씁니다.
3. **Submit new issue**. 이슈가 열리면 `[Chance] 이슈 수정 요청 처리(수정안 PR 만들기)`가 자동으로 돕니다.
4. 이슈에 "✅ 수정안을 PR 로 만들었습니다" 코멘트와 PR 링크가 달리면 PR을 열어 3-11을 확인한 뒤 **Merge pull request**. 병합하면 `[공통] 사이트 자동 배포`가 자동으로 돕니다. 사이트에서 이미지를 확인합니다.
- "⚠️ 수정하지 않았습니다"가 오면 사유대로 고쳐 **새 이슈**를 만듭니다(이미 만든 이슈는 고쳐도 다시 처리되지 않음).
- 이미지는 Unsplash에서 찾고 새 주소는 `https://images.unsplash.com/photo-…` 형식만 받습니다. "조건에 맞는 새 이미지를 찾지 못했습니다"가 오면 설명을 더 구체적으로 적어 새 이슈로 올립니다(첫 후보가 다른 형식이면 재시도 없이 거부되는 한계가 있습니다. 7장).

**길 2. 여러 글 한꺼번에**
1. Actions → `[Chance] 기존 글 이미지 교체(수동)` → Run workflow. `연습 실행`은 **체크한 채** 실행합니다.
2. Summary의 "이미지 점검: 완료: …" 줄(대상·교체·건너뜀 건수, 연습이면 "DRY_RUN: 실제 변경 없음")과 로그의 "문제(duplicate)" 같은 줄(종류: `missing`·`local-path`·`duplicate`·`broken`)로 대상을 봅니다.
3. 맞으면 `연습 실행` 체크를 풀고 다시 실행합니다. main에 바로 커밋("🤖 자동 포스팅/이미지 수정")되고 사이트 배포가 요청됩니다. 한 번에 최대 20건만 처리하고 나머지는 다음 실행으로 넘깁니다(요약에 표시).
4. 잘못 바뀌었다면 AI에게 해당 커밋을 되돌려 달라고 요청합니다(저장소 Commits에서 "🤖 자동 포스팅/이미지 수정" 중 그 시각의 커밋을 알려 줍니다).
- 연습 실행은 기본이 가짜 AI 검색어라 Gemini 한도를 쓰지 않지만, **Unsplash 검색은 연습에서도 실제로 부릅니다.** 입력 `연습 실행에서도 실제 Gemini를 호출`(`real_ai`, 기본 꺼짐)을 체크하면 글마다 Gemini 호출도 합니다(3-13).

**하지 말 것**: 연타하거나 정기 실행이 도는 매시 17분·47분 전후에 누르기 — 두 Chance 워크플로가 같은 대기열(`chanceblog`)을 써서 대기 중이던 실행이 취소될 수 있습니다. 연습을 건너뛰고 실제 교체부터 하기.

### 3-4. 고정 페이지의 문구·제목·링크를 바꾸고 싶다

- **가능 여부**: 가능합니다. 대상은 소개(`about`)·카테고리(`categories`)·문의(`contact`)·개인정보처리방침(`privacy`).
- **할 일**
  1. 저장소 → **Issues** → **New issue** → **고정 페이지 수정**.
  2. **대상 페이지**와 **수정 항목**을 고르고 아래 표대로 칸을 채웁니다.
  3. **Submit new issue** → PR 링크가 달리면 3-11을 확인한 뒤 **Merge pull request**.

| 하고 싶은 일 | 수정 항목 | 쓰는 법 |
|---|---|---|
| 문구 바꾸기 | 문구 수정 | 변경 전 = 파일 원문 그대로, 변경 후 = 새 문장(변경 전을 비우면 AI가 최소 수정안을 만듦) |
| 링크 바꾸기 | 링크 변경 | 변경 전 = 현재 주소, 변경 후 = 새 주소 |
| 제목·설명(SEO) | SEO 메타 수정 | 변경 후 = `title: 새 제목` 또는 `description: 새 설명` 줄 |
| 문단·구조 바꾸기 | 섹션/레이아웃 변경 | 원하는 결과를 구체적으로(AI가 그 파일 안에서만 수정) |

- "변경 전"은 화면에 보이는 글이 아니라 **파일 원문**(마크다운)과 글자까지 같아야 찾습니다.
- 소개·문의·개인정보처리방침은 광고 심사 대상이라 **소유자 요청만** 처리합니다. PR 본문에 "병합이 곧 승인" 경고가 붙습니다.
- 첫 화면(`index.html`)·레이아웃·워크플로·코드는 어떤 요청으로도 못 고칩니다. 한 요청은 한 파일만, 바뀐 줄은 80줄 이하입니다.
- **개인정보·비밀을 쓰지 않습니다.** AI 수정은 페이지 원문 전체를 Gemini로 보내고 이슈·PR은 공개입니다.
- **하지 말 것**: 이미 만든 이슈를 고쳐 쓰고 다시 처리되기를 기다리기(새 이슈로 올립니다). 광고 표면 페이지의 PR을 3-11 확인 없이 병합하기.

**실패 사례**: 이슈에 달리는 코멘트로 읽습니다(코멘트 종류는 6-6).

| 증상 | 원인 | 할 일 |
|---|---|---|
| ⚠️ "항목 제목이 중복되었습니다" | 본문 안에 양식 제목과 같은 줄(`### 대상 페이지` 등)이 있음 | 그 줄을 빼고 새 이슈 |
| ⚠️ "'변경 전' 문구를 페이지에서 찾지 못했습니다" | 파일 원문과 글자가 다름 | GitHub에서 파일을 열어 원문을 복사해 새 이슈 |
| ⚠️ "AI·이미지 검색으로 보내지 않았습니다" | 요청·변경 전·페이지 원문에 키·주민등록번호·카드번호 모양이 있음 | 키라면 이슈가 공개라 이미 노출된 것 → 폐기·재발급(4-2). 실제 번호라면 이슈를 삭제(아래 설명)하고 카드사 등에 알림. 숫자 표·일련번호 오탐이면 그 부분을 줄이거나 문장으로 바꿔 **새 이슈**. 값은 코멘트에 적지 않습니다 |
| ℹ️ "이미 처리한 이슈입니다" | 같은 이슈는 한 번만 처리 | 코멘트의 브랜치·PR 확인. 더 고칠 것은 새 이슈 |
| Run workflow가 첫 단계에서 실패 | 수동 실행의 `issue_number`가 1~999999999의 숫자가 아님(앞자리 0 불가) | 올바른 번호로 다시 |
| ❌ "처리 중 오류가 발생했습니다" | 처리 중 오류. 코멘트에는 종류만 있음 | Actions 로그의 `원인(로그 전용)` 줄을 AI·저장소 관리자에게 전달. 첫 처리가 실패해 브랜치·라벨이 없으므로 고친 뒤 같은 번호로 Run workflow 하면 다시 처리됨 |

- **이슈를 삭제해야 할 때**(실제 카드·주민등록번호가 노출된 경우): 이슈 화면 오른쪽 열의 Notifications 아래 "Delete issue"를 누르고 확인창의 "Delete this issue"를 누릅니다(개인 저장소는 소유자만 가능하며 화면 구성은 GitHub 업데이트로 달라질 수 있습니다). **삭제는 되돌릴 수 없고 운영자 승인 사항이라** AI에게 시키지 말고 운영자가 직접 하거나 채팅으로 승인한 뒤 맡깁니다. 지워도 이미 공개된 값은 노출된 것으로 봅니다.

### 3-5. 새 페이지가 수정 대상 목록에 없다

- **가능 여부**: 저장소 맨 위 폴더(루트)의 `.md`·`.html` 파일만 됩니다. 하위 폴더 페이지는 수정 대상이 될 수 없습니다.
- **할 일**
  1. 새 페이지 파일 맨 위 `---` 줄 사이(front matter)에 `editable: true` 한 줄을 넣고 main에 저장(commit)합니다. 직접 하기 어려우면 AI에게 맡기되, AI가 고칠 수 있는 페이지를 넓히는 일이라 운영자의 채팅 승인이 필요합니다(T3 = 운영자 승인이 필요한 등급. `docs/CHARTER.md`의 "자동 수정 범위 확대").
  2. `[공통] 이슈 양식 페이지 목록 갱신`이 자동으로 돕니다. 새 페이지면 "chore: pages.json·이슈 양식 자동 동기화" 봇 커밋이 생깁니다.
  3. 이후 양식의 대상 페이지 목록에 나타납니다.
- **안 될 때**: 자동 실행이 안 보이면 Actions → `[공통] 이슈 양식 페이지 목록 갱신` → Run workflow. 로그가 "변경 없음"이면 `editable: true`의 철자와 위치(front matter 안)를 확인합니다. 파일 이름이 영문·숫자·`_`·`-`(40자 이하)가 아니면 front matter에 `edit_id: faq`처럼 id를 적습니다. 기존 페이지 4개는 명세에 고정돼 있어 건드릴 필요가 없습니다.
- **하지 말 것**: 개인정보·비밀이 들어갈 페이지를 `editable: true`로 열기(그 페이지 원문이 AI 수정 때 외부로 나갑니다).

### 3-6. 이슈를 만들었는데 아무 일도 없다 / PR 대신 링크만 왔다

1. Actions에 `[Chance] 이슈 #번호 수정 요청 처리 · 자동(이슈 등록 시)` 실행이 새로 생겼는지 봅니다. 실행이 없거나, 있어도 작업(job) 칸이 회색(건너뜀)이면 작성자가 소유자·멤버·협업자가 아니거나 양식을 쓰지 않은 이슈입니다(제목이 `[페이지 수정]`·`[이미지 변경]`으로 시작하지 않고 라벨 `blog-control`도 없음). 양식으로 새 이슈를 만드세요.
2. 이슈를 **나중에 고쳤거나 다시 열었다면** 처리되지 않습니다(새로 열릴 때 한 번만 돕니다). 새 이슈를 만드세요.
3. 실행이 있고 코멘트가 달렸다면 6-6의 코멘트 종류로 읽습니다.
4. "수정 브랜치를 만들었습니다" 코멘트와 링크만 왔으면 링크의 **Create pull request**를 누릅니다. 설정 "Allow GitHub Actions to create and approve pull requests"(Settings → Actions → General)가 꺼졌을 수 있습니다. 2026-10-25 시험에서는 PR이 자동으로 만들어졌으니 보통은 켜진 상태입니다.
5. 실행은 있는데 코멘트가 없으면 실행을 열어 빨간 단계의 로그를 봅니다(3-7). 그 밖의 증상은 [`ISSUE_EDITS.md`](./ISSUE_EDITS.md)의 문제 해결표(§6)를 봅니다.

**하지 말 것**: 이슈를 고쳐 쓰거나 다시 열어 처리되기를 기다리기. 같은 요청의 이슈를 여러 개 올리기(PR이 여러 개 생깁니다).

### 3-7. 빨간 ✗가 떴다

- **공통 순서**
  1. Actions 목록에서 빨간 ✗ 실행을 엽니다. 실행 화면 위쪽 주석(`::error::` 문장)과 **Summary**의 "결과" 줄을 읽습니다.
  2. 빨갛게 표시된 단계를 눌러 로그 끝의 `::error::`·`[SKIP] code=`·`ERROR` 줄을 읽습니다.
  3. 아래 표에서 워크플로를 찾습니다. 원인을 모르겠으면 그 줄들을 AI에게 보여 주세요(비밀 값이 섞였는지 먼저 확인).

| 워크플로 | 빨강의 뜻 | 먼저 할 일 |
|---|---|---|
| `[공통] 발행 중단 감시·알림` | **문제를 찾았다는 신호**입니다. 이번 점검에서 새로 생긴 심각 건이 있을 때만 빨강이 되며(로그 `::error::새로 생긴 심각 건: …`) 고장이 아닙니다. 이미 알린 건이 이어지는 동안은 초록입니다. 스크립트 오류일 때도 빨강(드묾) | Issues(라벨 `watchdog`)의 이슈를 읽고 코드대로 3-2·이 표를 따릅니다 |
| `[공통] 사이트 자동 배포` | 어느 잡이 빨강인지 봅니다(표 아래 목록) | 빌드: "Jekyll 사이트 빌드" 단계 로그를 AI에게. 반영 확인: 요약의 "해석" 줄과 6-4. 몇 분 뒤 새 글 주소를 직접 열어 봅니다 |
| `[공통] 저장소 규칙·테스트 자동 검사` | 규칙 위반·테스트 실패·`actionlint` 지적. 경고(WARN)는 통과입니다 | PR이면 **병합하지 말고**, main이면 이미 병합된 변경이 규칙을 어긴 것입니다. "저장소 가드레일 검증" 단계의 `ERROR [검사ID] 파일:줄`을 AI에게 |
| `[Chance] 글 자동 작성·게시` | 아래 목록 | 아래 목록 |
| `[Blogger] 글 자동 작성(초안함 업로드)` | 게시용 시크릿 누락·AI 실패·`blog` 입력 오타 | 6-3의 코드 표 |
| `[Chance] 이슈 수정 요청 처리(수정안 PR 만들기)` | 처리 중 오류 | 이슈 코멘트와 로그(3-6) |
| `[공통] PR 변경 범위 검사` | ❌ 범위 밖 판정(설계된 빨강) | 병합하지 않기(3-11) |
| `[공통] 이슈 양식 페이지 목록 갱신` | 페이지 id 중복·push 3회 실패 | 로그의 `[오류]` 줄(3-5) |

`[공통] 사이트 자동 배포`의 빨간 잡
- `사이트 빌드`: Jekyll 오류(지난 사례는 문서 속 Liquid 문법). 직전 성공본이 계속 공개되지만 새 글은 반영되지 않습니다.
- `사이트 게시`: GitHub Pages 배포 오류.
- `사이트 반영 확인`: 배포는 됐는데 새 글 주소가 12분 동안 열리지 않았습니다.

**Chance가 빨강일 때**: 같은 빨강이 하루에 여러 번 보일 수 있습니다. 정기 실행은 그 시간대 글이 생길 때까지 계속 다시 시도합니다.
1. `ALL_LANES_EMPTY`: 6개 분야 모두 검증을 통과한 기사가 없었습니다. 운영자가 할 일은 없습니다. 며칠 계속되면 Summary 표의 탈락 사유를 AI에게 전달하세요.
2. `SOURCES_UNREACHABLE`: 시도한 뉴스 소스에 모두 접속하지 못했습니다(네트워크·소스 장애). 보통 다음 실행에서 풀립니다.
3. 로그에 "GEMINI_API_KEY 환경 변수가 없습니다"·"모든 Gemini 모델 호출 실패": 키·한도 문제입니다(4-2, 3-13).
4. 로그에 "대표 이미지를 2개 확보하지 못했습니다": Unsplash 검색이 실패한 데다 예비 이미지 32장도 다 쓰였거나 열리지 않을 때 나옵니다. 키만 고쳐서는 안 풀릴 수 있으니 `UNSPLASH_ACCESS_KEY`와 한도를 확인하면서 로그를 AI에게 전달합니다.
5. 커밋 단계의 push 거부: 재시도가 없고, 다음 정기 실행이 다시 시도합니다.
6. **수동 실행**은 후보가 전부 탈락해도 빨강입니다. 정기 실행에서는 초록 + 노란 경고입니다(6-1 표).
7. (승인 흐름을 켠 뒤에만) 빨간 단계가 `초안 올리기와 승인 PR 열기 (승인 흐름일 때만)`이면: 요약의 `DRAFT_BRANCH_ONLY`는 "초안 브랜치는 올라갔는데 PR 을 못 열었다"는 뜻이고 글은 잃지 않았습니다. 3-17의 '빨강일 때'를 봅니다. 다른 이유(브랜치·이력 push 실패)는 로그의 `작업 실패` 줄을 읽고 다음 정기 실행이 다시 시도하는지 지켜봅니다.

오래된 빨강(예: 문서 속 Liquid 문법 사고)은 해결된 지난 일입니다. 최근 실행부터 봅니다.

**하지 말 것**: 빨강이라고 Re-run이나 Run workflow를 반복하기(정기 실행은 다음 정기 실행이 알아서 다시 시도하고, 수동 글은 추가 글이 됩니다). 비밀이 섞인 로그를 채팅·이슈에 그대로 붙이기.

### 3-8. 글이나 이미지가 중복됐다

1. **더 만들지 않게 먼저 멈춥니다**(3-9). 고치려고 워크플로를 다시 누르지 마세요.
2. 원인을 봅니다. 그 시간대 Chance 실행의 제목이 `· 수동`인지 확인합니다. 수동 글은 슬롯 기록이 없어 같은 시간대의 정기 실행이 한 편 더 만들 수 있습니다. `history.json`에서 `slot` 값이 비어 있는(`null`) 항목이 수동 글입니다.
3. **글이 중복**이면 자동화는 글을 지우지 않습니다. 삭제는 운영자 승인 사항(T3)이라, AI에게 채팅으로 "이 글(한·영 2개)을 삭제해 줘"라고 요청합니다. `history.json`은 중복 방지 기록이라 그대로 둡니다.
4. **이미지만 중복**이면 먼저 **일시정지를 풀고**(3-9 되돌리기) 고칩니다. 일시정지 중에는 `[Chance] 기존 글 이미지 교체(수동)`가 아무 일 없이 초록으로 끝나고, `[Chance] 이슈 수정 요청 처리(수정안 PR 만들기)`도 "일시정지 중"으로 멈추기 때문입니다. 글 하나는 3-3 길 1, 여러 글이면 길 2(연습 먼저)를 씁니다.
5. 정리가 끝나면 **일시정지 변수를 삭제합니다**(3-9 되돌리기). 변수가 남아 있으면 자동 발행이 계속 멈춰 있습니다.

새 글은 이미 쓴 이미지를 피해 고르고, 기존 글과 제목이 비슷하면 후보에서 버립니다(코드 확인). 그래도 겹치는 경로는 미확인입니다.

**하지 말 것**: 원인을 모른 채 글 파일을 직접 지우거나 `history.json`을 고치기(중복 방지 기록이 무너집니다).

### 3-9. 자동 발행을 잠시 멈추고 싶다

- **가장 안전한 방법**: 저장소 변수 `PIPELINE_PAUSE`. Chance·Blogger·이슈 수정을 함께 멈추고 수동 실행도 멈춥니다.
- **할 일**
  1. 저장소 → **Settings**(휴대폰은 More(⋯) 메뉴 안) → **Secrets and variables** → **Actions** → **Variables** 탭 → **New repository variable**.
  2. Name에 `PIPELINE_PAUSE`, Value에 `true`(또는 `1`·`yes`·`on`) → **Add variable**.
  3. 확인: Actions → `[Chance] 글 자동 작성·게시` → Run workflow(`연습 실행` 체크 유지). Summary에 "일시정지"가 나오면 멈춘 것입니다(로그 `[SKIP] code=PAUSED var=PIPELINE_PAUSE`).
  4. **되돌리기**: 같은 화면에서 변수를 삭제합니다.

| 구분 | 워크플로 |
|---|---|
| 멈춤 | `[Chance] 글 자동 작성·게시`, `[Chance] 기존 글 이미지 교체(수동)`, `[Blogger] 글 자동 작성(초안함 업로드)`(정기·수동 모두), `[Chance] 이슈 수정 요청 처리(수정안 PR 만들기)`(이슈에 "일시정지 중" 코멘트만 남김), `[공통] 발행 중단 감시·알림`(새 알림만 안 만듦) |
| 안 멈춤 | `[공통] 사이트 자동 배포`, `[공통] 저장소 규칙·테스트 자동 검사`, `[공통] PR 변경 범위 검사`, `[공통] 이슈 양식 페이지 목록 갱신`, `[공통] 확인 필요 모음`(멈춰 있다는 사실을 "지금 해야 할 일"로 알려 줌) |

- **알아 둘 점**
  - 멈춘 동안에도 실행은 시작되고 초록으로 끝납니다(글·커밋만 없음). 실행 화면 위쪽에 파란 안내(`::notice::`)가 남습니다.
  - 멈춘 동안 올라온 수정 요청 이슈 가운데 형식이 맞는 새 요청에는 "일시정지 중" 코멘트만 달립니다(AI·이미지 검색을 부르지 않고 파일·PR도 만들지 않음; 형식·권한이 틀린 요청은 평소처럼 거부·무시, 이미 처리한 이슈는 "이미 처리한 이슈입니다"). 변수를 지운 뒤 같은 이슈 번호로 Actions → `[Chance] 이슈 수정 요청 처리(수정안 PR 만들기)` → Run workflow(`issue_number`, `연습 실행`은 풀고)를 하면 처리됩니다.
  - 승인 흐름(3-17)을 켠 뒤라면: 멈춘 동안 새 초안도 만들지 않고 PR 을 열거나 브랜치를 지우는 정리도 멈춥니다. 이미 열린 초안 PR 은 그대로 남고 병합·닫기는 내가 합니다.
  - 워치독은 멈춘 동안 새 알림을 만들지 않고, 이미 열린 알림도 그대로 둡니다. 재개한 직후에는 마지막 글이 오래돼 `STALE`이 열릴 수 있고, 새 글이 나오면 자동으로 닫힙니다.
  - 한 블로그만 멈추려면 레지스트리의 `mode: off`(코드 변경이라 AI에게 요청. 멈추는 방향이라 승인 등급은 낮음)를 씁니다.
  - 워크플로 하나만 멈추려면 Actions → 해당 워크플로 → "⋯" → **Disable workflow**, 되돌리기는 Enable workflow입니다(모바일 앱 메뉴는 미확인).
  - 외부 지식: 공개 저장소는 60일간 활동이 없으면 예약 실행이 자동으로 꺼질 수 있습니다(이 저장소에서 확인하지 못함). 오래 멈췄다면 재개 뒤 예약 실행이 다시 생기는지 확인하세요.
- **하지 말 것**: 변수를 켜 두고 잊기(실행 화면의 파란 안내와 `[공통] 확인 필요 모음`의 일시정지 항목으로 드러나고, 워치독은 멈춘 동안 침묵합니다). 코드가 고장 나 빨강이 계속될 때 `PIPELINE_PAUSE`만 믿기 — 그때는 Disable workflow를 씁니다.

### 3-10. 이슈 수정을 '연습 실행'으로 점검하고 싶다

중요: **새 요청 이슈를 만드는 순간 자동으로 실제 처리됩니다**(브랜치·PR·코멘트가 생김). 연습 실행은 **이미 만든 이슈**를 파일·PR·코멘트 없이 다시 점검할 때 씁니다.

1. 저장소 → **Actions** → `[Chance] 이슈 수정 요청 처리(수정안 PR 만들기)` → **Run workflow**.
2. `issue_number`에 이슈 번호를 적고 `연습 실행`은 **체크 유지**(기본) → **Run workflow**. 실행 제목은 `[Chance] 이슈 #번호 수정 요청 처리 · 수동(연습: PR·코멘트 안 만듦)`입니다.
3. 실행을 열어 마지막 단계 "DRY_RUN 결과 출력"을 봅니다. `status`는 `ok`(수정안 있음)·`rejected`(범위·형식 위반, 사유 표시)·`ignored`(처리 대상 아님)·`error`(처리 중 오류)·`paused`(`PIPELINE_PAUSE`가 켜져 있어 처리하지 않음, 3-9) 중 하나입니다. `duplicate`(이미 처리한 이슈)는 연습에서는 나오지 않고 실제 실행에서만 나옵니다.

- 연습이어도 키가 있으면 AI·이미지 검색을 부를 수 있고(문자 그대로 교체·링크·SEO는 AI 없음), 요청 내용이 로그에 보입니다(워크플로 명령으로 해석되지 않게 감싸서 출력). 공개 저장소의 로그는 누구나 볼 수 있다고 보고, 요청문에 비밀·개인정보를 쓰지 마세요.
- 이미 처리한 이슈에도 연습은 반복할 수 있습니다(참고 문장만 남음). 실제 처리를 시험하려면 같은 이슈를 다시 돌리지 말고 **새 시험 이슈**를 씁니다.
- **처음 시험(권장)**: 광고 표면이 아닌 `categories`에 "SEO 메타 수정"으로 `title: 카테고리 (시험)`을 요청합니다. PR이 생기면 **병합하지 말고 닫습니다**(Close pull request). 확인할 항목은 [`DEFECT_REGISTER.md`](./DEFECT_REGISTER.md) 하단의 관측 체크리스트에 있습니다.
- **하지 말 것**: 이미 처리한 이슈를 연습 없이 다시 돌리기(코멘트만 달립니다). 시험 PR 병합하기. 요청문에 비밀·개인정보 쓰기.

### 3-11. PR을 병합하기 전에 볼 것

PR → **Files changed**와 하단 **Checks**에서 봅니다. 병합을 막아 주는 규칙(PR 필수·승인 필수·상태 검사 필수)은 봇의 자동 발행을 막지 않으려고 일부러 켜지 않았습니다(5장). 그래서 **눈으로 막아야** 합니다. 아래 표는 **이슈 수정이 만든 PR** 기준입니다.

| 확인 | 어디서 | 정상 |
|---|---|---|
| 변경 파일 수 | Files changed | 1개(이슈 수정은 한 파일만) |
| 바뀐 줄 수 | PR 본문 "바뀐 줄: N줄" | 문구 교체는 보통 1~3줄(규칙상 80줄 이하) |
| 광고 표면·금지 경로 파일 | Files changed의 파일 이름 | 요청과 무관하면 병합 금지 |
| 검사 결과 | Checks, `[공통] PR 변경 범위 검사` 코멘트 | ✅ 통과 / ⚠️ 직접 읽기 / ❌ 병합 금지 |
| `Fixes #번호` | PR 본문 맨 끝 | 있어야 이슈가 닫히고 범위 검사가 동작 |
| 파일 전체가 바뀐 것처럼 보임 | Files changed | 줄 끝(LF/CRLF) 변경일 수 있음 → 병합하지 않기 |

- PR 본문 아래의 "리뷰 체크리스트"(요청한 항목만 바뀌었다 · 사실·수치·링크가 맞다 · 광고 코드·레이아웃은 그대로다)를 눈으로 확인합니다.
- 광고 표면: `index.html`·`privacy.md`·`about.md`·`contact.md`·`robots.txt`·`ads.txt`·`_config.yml`·`_includes/`·`_layouts/`·사이트 인증 html 2개. 금지 경로(일부): `.github/`·`pipeline/`·`scripts/`와 `.py`·`.yml`·`.json` 파일.
- 요청한 광고 표면 페이지(about·contact·privacy)면 PR 본문에 "⚠️ 광고 표면 페이지… 병합이 곧 승인" 인용 상자가 있어야 정상입니다.
- ❌가 나오면 PR에 "요청한 부분만 바꾸고 나머지는 되돌려 주세요"라고 답글을 답니다.
- **`[초안][Chance]` PR**(승인 흐름이 올린 글 초안, 브랜치 `ai/draft/…`)은 위 표와 다릅니다: 바뀐 파일은 `_posts/`의 글 두 개이고 `Fixes #번호`가 없으며, 봇이 만든 PR이라 검사(CI)·`[공통] PR 변경 범위 검사`가 돌지 않습니다. 병합하면 곧 공개되므로 3-17의 체크리스트대로 글을 읽고 병합합니다.
- **`ai/…` 브랜치의 PR**(AI가 올린 작업 PR)은 위 표의 "변경 파일 1개"와 맞지 않을 수 있습니다. **AI가 채팅으로 "검증 끝, 병합해도 됨"이라고 알린 것만 병합합니다.** 확인 필요 모음이 "병합하면 됩니다"라고 안내해도 그것은 검사(CI) 통과와 충돌 없음만 뜻합니다. 그 안내에 붙는 "PR 코멘트의 변경 범위 검사 결과를 먼저 확인하세요"는, `[공통] PR 변경 범위 검사`가 경고(⚠️)여도 초록으로 보이기 때문입니다.
- **봇이 만든 수정 PR**에는 `[공통] PR 변경 범위 검사`가 자동으로 안 돌 수 있습니다(봇이 `GITHUB_TOKEN`으로 만든 PR은 다른 워크플로를 시작시키지 않으며, 만들기 전에 같은 검사를 이미 통과합니다). 코멘트를 보고 싶으면 Actions → `[공통] PR 변경 범위 검사` → Run workflow → `pr_number`. 그 브랜치의 `[공통] 저장소 규칙·테스트 자동 검사`는 봇이 수동 실행 형태로 따로 돌립니다.
- `[공통] PR 변경 범위 검사`는 `Fixes #번호`가 없으면 검사 없이 초록(코멘트 없음)입니다. Copilot PR은 하단의 **Approve and run workflows**를 눌러야 검사가 돕니다(미관측). 결과가 안 보이면 병합하지 않습니다.
- 제목만 바꾸는 PR(SEO 메타 `title:`)은 `[공통] 저장소 규칙·테스트 자동 검사`가 초록이어야 합니다. 병합 뒤 `[공통] 이슈 양식 페이지 목록 갱신`이 `pages.json`·`page-edit.yml`을 새 제목으로 고칩니다(그 사이 양식에는 옛 제목이 보임).
- 병합: **Merge pull request** → 확인. 병합하면 `[공통] 사이트 자동 배포`가 자동으로 돕니다.
- **하지 말 것**: 검사 결과가 없거나 ❌인데 병합하기. 광고 표면·금지 경로 파일이 섞인 PR 병합하기.

### 3-12. Blogger를 다시 켜려면

- **상황**: `blogger_macat`은 정지 중입니다. 켜는 순서가 중요하고, **지금은 시크릿을 등록하지 않습니다**: 2차 보강(D-64 ⑦)과 `mode: draft` 승인(T3)이 아직이고, 시크릿이 있으면 수동 실행에서 `publish`로 공개 게시를 고르는 것만으로 검토 없이 공개 게시될 수 있습니다.
- **순서**

| # | 할 일 | 누가 | 메모 |
|---|---|---|---|
| 1 | 영문 프로필·프롬프트 준비 — **병합 완료(PR #40·#43)**, 2차 보강(D-64 ⑦)은 AI가 진행 중 | AI | 프로필·언어·톤 변경은 운영자 채팅 승인(T3) |

| 7 | 며칠 초안 모드로 운영 | 운영자 | `rejected`·실패 이슈가 없는지 봄. 문제가 없으면 `auto` 전환(T3, 운영자 승인) |

1. Actions → `[Blogger] 글 자동 작성(초안함 업로드)` → Run workflow에서 `인증 점검만 실행`(`auth_check`)을 체크하고 실행합니다.
2. 글을 만들지 않고(Gemini 호출 0회, 저장소 변경 없음) 토큰 갱신 → 블로그 조회 → 돌려준 블로그 주소가 `pipeline/blogs.json`의 `url`과 같은지만 확인합니다.
3. 정지(`mode: off`) 중에도, `연습 실행`이 체크돼 있어도 실제로 점검합니다.
4. 통과하면 실행 요약에 `AUTH_CHECK_OK`(확인한 시크릿 이름만, 값은 없음)가 나옵니다. **`AUTH_CHECK_OK`가 없으면 통과가 아닙니다.** `PIPELINE_PAUSE`가 켜져 있으면 점검하지 않고 `PAUSED`(초록, 종료 0)로 끝납니다(3-9).
5. 실패하면 6-3의 분류표를 봅니다.

**6번의 초안은 Blogger 초안함에 올라갑니다.**
- `mode: draft`이고 시크릿 4종이 모두 있으면 글이 Blogger **초안함**에 업로드됩니다(공개되지 않음). 운영자가 Blogger 화면에서 눈으로 확인한 뒤 **직접 게시**합니다.
- 시크릿이 하나도 없으면 저장소 파일에만 저장합니다(오류 아님). **일부만** 있으면 빨강(종료 2)이므로 4종을 한꺼번에 등록합니다.
- 수동 실행의 `publish`는 `off`(저장소 파일에만)·`draft`(기본, 초안함 업로드)·`publish`(즉시 공개 게시) 중에서 고릅니다.
- 이 연동의 실제 구글 호출은 아직 한 번도 한 적이 없어 첫 실행에서 처음 검증됩니다. 로그에 `Blogger 초안함에 업로드했습니다`가 보이고 Blogger 글 목록에 초안이 있는지 확인합니다.
- 시크릿 등록 뒤 최소 8일은 `draft`로 두고 인증 실패가 없는지 봅니다(토큰 7일 만료 경계).
- 자세한 절차와 동작 표는 [`BLOGGER_API_SETUP.md`](../.github/editorial/BLOGGER_API_SETUP.md)의 동작 방식 절을 봅니다.

- **알아 둘 것**
  - `mode`는 항상 블로그 항목에 직접 적고, AI에게도 `draft`라고 값을 못 박아 요청합니다. 줄이 없으면 검증기(REG-1)가 오류로 막습니다. 새 블로그를 추가할 때도 같습니다.
  - 정지 중의 수동 실행은 "대상 0개"로 끝나므로(`인증 점검만 실행`만 정지 중에도 점검하는 예외), 시험은 `mode`를 켠 뒤에 합니다. 정지 중에는 워치독도 이 블로그를 감시하지 않습니다.
  - 재개 직후에는 마지막 활동이 오래돼 워치독 `STALE`(50시간)이 바로 열릴 수 있고, 글이 나오면 자동으로 닫힙니다.
  - 공개 게시가 아닌 초안 시험도 그날 하루 상한(1건)을 씁니다. 한국시간 11시 정기 실행 전에 시험하면 정기 실행이 `DAILY_CAP`으로 건너뜁니다. 정기 실행 뒤에 하거나 `topic`을 입력합니다(상한을 건너뜀).
  - 값을 만드는 `scripts/get_blogger_token.py`는 값을 화면에 출력합니다. **본인 터미널에서만** 실행하고 AI 도구나 로그를 모으는 환경에서는 실행하지 않습니다. 작업 PC에서 파일을 꺼낼 수 없으면 다른 PC가 필요합니다([`HANDLER.md`](../HANDLER.md) §10).
  - [`BLOGGER_API_SETUP.md`](../.github/editorial/BLOGGER_API_SETUP.md)가 이 가이드와 다르면 이 가이드와 HANDLER §3 P1을 따릅니다.
- **하지 말 것**: 2차 보강·`mode: draft` 승인 전에 시크릿 등록하기. 시크릿 값을 채팅·저장소·메일에 쓰기. 공개 게시를 시험 삼아 고르기. `auto`를 승인 없이 켜기.

### 3-13. Gemini 무료 한도가 걱정된다

- **알아 둘 사실**
  - 무료 한도는 **프로젝트 단위**라 Chance·Blogger·이슈 수정이 같은 키(`GEMINI_API_KEY`)로 **한 통을 나눠 씁니다**. 수동 실행도 같은 통을 씁니다.
  - 한도 숫자(분당·하루 요청 수)는 이 저장소에서 알 수 없고 **아직 모릅니다**. 운영자가 Google AI Studio의 한도·사용량 화면(주소 예: `aistudio.google.com/rate-limit`)에서만 볼 수 있습니다. 화면 구성은 구글 업데이트로 달라질 수 있습니다.
  - 실행 요약에 `Gemini 호출: N회(실패 K회)` 줄이 있으면 그 실행이 쓴 요청 수입니다(Chance·Blogger·이슈 수정 모두 같은 형식이고, 호출이 없었던 실행도 `0회`라고 적힙니다 — 이 줄이 없으면 호출 기록이 생기기 전의 옛 실행입니다). 로그에는 요청마다 `[GEMINI] label=… purpose=… model=… result=… sec=… served=… tokens=…` 줄이 남습니다.
  - 이 기록은 **측정 전용**이라 호출·재시도 동작을 바꾸지 않습니다. 기록한 수가 서버가 세는 요청 수와 같다는 보장은 없으니 AI Studio 화면과 대조합니다. 하루 단위 장부와 예비 한도는 후속 작업입니다.
- **수동 연습 실행은 한도를 쓰지 않는 것이 기본입니다**
  - `[Chance] 글 자동 작성·게시`와 `[Chance] 기존 글 이미지 교체(수동)`의 `연습 실행`(기본 켜짐)은 **가짜 AI 응답**을 쓰고 Gemini 키를 넘기지 않아 호출이 0회입니다. 실제 호출로 시험하려면 `연습 실행에서도 실제 Gemini를 호출`(`real_ai`, 기본 꺼짐)을 체크합니다. 그러면 실행 제목에 "실제 AI 호출"이 붙고 요약에 `AI 응답` 줄이 남습니다.
  - 이미지 교체 연습은 Gemini 한도는 쓰지 않아도 **Unsplash 검색은 실제로 부릅니다.**
  - `[Blogger] 글 자동 작성(초안함 업로드)`의 `연습 실행`(`dry_run`)도 기본이 켜짐이고 가짜 AI 응답을 씁니다. 체크를 풀어야 실제 Gemini로 초안을 만들어 저장소에 커밋하고 그날 하루 상한을 씁니다.
  - 정기 실행과, 연습을 풀고 실제로 게시·교체하는 수동 실행은 항상 실제 Gemini를 부릅니다.
  - `[Chance] 기존 글 이미지 교체(수동)`의 실제 교체는 한 번에 최대 20건만 처리하고 나머지는 다음 실행으로 넘깁니다(요약에 표시).
  - Chance 수동 게시를 할 때 오늘 이미 게시된 글이 하루 상한(2편) 이상이면 막지는 않고 노란 경고와 요약 줄로 알립니다.
- **누가 한도를 쓰나**

| 실행 | Gemini 사용 |
|---|---|
| 정기 실행(Chance·Blogger), `연습 실행`을 풀고 한 수동 실행 | 항상 부름. Chance는 정상이면 1회, 후보 탈락·모델 실패가 겹치면 최대 9회(후보 3건 × 모델 3개). Blogger는 글 한 번에 보통 1회(게이트 탈락 시 재작성 최대 3번, 시드 주제가 바닥나면 주제 확장 호출 추가)이고, 한도 오류(429)에는 같은 모델을 재시도해 한 번의 호출이 최대 12건까지 늘 수 있음 |
| `연습 실행`(Chance·이미지 교체·Blogger) | 기본은 가짜 AI 응답이라 **0회**. `real_ai`를 체크한 Chance·이미지 교체 연습만 실제로 부릅니다 |
| `[Chance] 이슈 수정 요청 처리(수정안 PR 만들기)` | AI가 쓰는 경우(문구 수정에서 `변경 전`을 비운 때·섹션/레이아웃 변경·이미지 변경)만. 문자 그대로 교체·링크·SEO는 0회. 연습 실행도 같습니다(3-10) |
| `[Chance] 기존 글 이미지 교체(수동)`의 실제 교체 | 문제가 있는 글마다 검색어 호출(한 번에 최대 20건) |

- **증상**: 빨강 + 로그의 "모든 Gemini 모델 호출 실패"(429·한도 문구).
- **할 일**: AI Studio에서 사용량을 확인합니다 → 수동 실행을 줄입니다 → 한도를 늘리거나 유료로 바꾸는 것은 비용 증가라 운영자 승인 사항(T3)입니다. 한도 숫자를 확인하면 이 가이드에 적도록 알려 주세요.
- **하지 말 것**: 한도를 확인하려고 실행을 연타하기. 키를 여러 개 추가해 우회하기(한도는 키가 아니라 프로젝트 단위).

### 3-14. 알림이 안 오거나 `[운영] 확인 필요 모음` 이슈가 안 보인다

- **휴대폰·메일 알림이 안 온다**: 5-2 D를 순서대로 확인합니다. 알림이 실제로 닿는지는 아직 확인하지 못했습니다(미확인).
- **이슈가 목록 맨 위에 없다**: 현재 #22이고 맨 위에 고정돼 있습니다. Issues에서 닫힌 이슈(Closed)까지 찾아 봅니다. 닫았다면 그대로 두어도 됩니다. 새로 해야 할 일이 생길 때만 다시 열리고 코멘트가 달립니다.
- **이슈가 지워졌다**: 다음 실행(정기 또는 수동, `연습 실행` 해제)이 새로 만듭니다. 급하면 Actions → `[공통] 확인 필요 모음` → Run workflow에서 `연습 실행`을 풀고 실행합니다. 새 이슈는 번호가 바뀝니다.
- **이슈가 갱신되지 않는 것 같다**: Actions에서 `[공통] 확인 필요 모음`의 마지막 실행 시각을 봅니다. 정기 실행은 3~6시간 늦을 수 있습니다(예상). 급하면 수동으로 실행합니다.
- **하지 말 것**: 이슈를 지워서 정리하기(닫아 두기), 본문 직접 고치기(다음 갱신 때 덮어씀).

### 3-15. PR이 "충돌"이거나 "검사 진행 중"이다

- 확인 필요 모음은 충돌을 "지금 해야 할 일"로 표시합니다. **충돌이 있는 PR은 병합하지 않습니다.** 직접 풀지 말고 AI에게 풀어 달라고 요청합니다.
- "검사 진행 중"이나 "병합 가능 여부 계산 중"은 기다리면 됩니다. 끝나면 다음 점검에서 "병합하면 됩니다"나 "검사(CI) 실패"로 바뀝니다. 급하면 `[공통] 확인 필요 모음`을 수동으로 실행합니다.
- "검사(CI) 실패"는 PR 하단 Checks의 빨간 항목을 열어 3-7로 읽습니다. 병합하지 않습니다.
- 병합 전에 볼 것은 3-11입니다.

### 3-16. 이미 올라간 글에 사실 오류가 있다

1. 먼저 자동 발행을 멈춥니다(3-9).
2. AI에게 그 글(한·영 2개의 주소)을 알립니다. 글을 비공개로 돌리거나 삭제하는 일은 운영자 승인(채팅)이 필요합니다.
3. 이슈 양식으로는 고정 페이지의 문구와 글의 이미지만 바꿀 수 있습니다. 글 본문 수정은 AI에게 요청합니다.
4. 어떤 검사가 놓쳤는지 AI가 확인해 규칙을 보강합니다([`SECURITY_GUARDRAILS.md`](./SECURITY_GUARDRAILS.md) §4-B).
5. 끝나면 일시정지 변수를 삭제합니다(3-9 되돌리기).

### 3-17. Chance 글을 내가 승인한 뒤에 공개하고 싶다

- **지금 상태**: **꺼져 있습니다**(레지스트리 `publish_flow: direct`). 코드와 시험은 있고 실제 GitHub 에서는 한 번도 돌려 보지 않았습니다(미확인). 켜기 전에는 3-1·6-1이 그대로 맞습니다. 켜는 것은 운영자 채팅 승인(T3)이 필요합니다.
- **켜면 달라지는 것**: 정기 실행이 한·영 글 한 쌍을 만드는 방식은 같은데, 글을 main 에 바로 올리지 않고 **초안 PR**로 올립니다. 제목은 `[초안][Chance] 한국어 제목 / English title`, 라벨은 `초안`·`채널:Chance`입니다. 휴대폰 GitHub 앱에서 PR 을 열어 읽고 **Merge pull request 를 누르면 공개**(곧 `[공통] 사이트 자동 배포`가 자동으로 돕니다), **Close pull request 를 누르면 폐기**입니다. 닫은 슬롯은 같은 날 다시 만들지 않고 그 브랜치는 7일 뒤 자동으로 지워집니다. 이유는 구글 게시자 정책이 사람의 검토 없이 자동 생성한 콘텐츠에 광고를 두지 말라고 안내하기 때문입니다.
- **켜기 전 준비(운영자)**
  1. 저장소 → Settings(휴대폰은 More(⋯) 메뉴 안) → **Actions** → **General** → "Workflow permissions"의 **Allow GitHub Actions to create and approve pull requests**가 켜져 있는지 화면에서 확인합니다(5-1에는 켜짐으로 적혀 있지만 이 흐름을 켜기 직전에 다시 봅니다). 꺼져 있으면 초안 브랜치는 올라가지만 PR 이 안 열려 실행이 빨강(`DRAFT_BRANCH_ONLY`)이 됩니다.
  2. 휴대폰에서 PR 알림이 오는지 확인합니다(5-2 D). 알림이 없어도 `[운영] 확인 필요 모음`에 열린 PR 이 올라옵니다(검사가 돌지 않아 '검사 결과 없음'으로 보임).
  3. 승인할 시간이 있는지 생각합니다. 하루 최대 2편이라 하루 PR 이 2개 쌓입니다. 며칠 두면 글감(기사)이 낡고 워치독이 `DRAFT_WAITING`(경고)으로 알립니다.
  4. 알아 둘 것: 병합했거나 닫은 초안 브랜치는 7일 뒤 자동으로 지워집니다(봇이 만든 임시 브랜치 `ai/draft/…`만, 열린 PR 이 있으면 지우지 않음). 브랜치 삭제는 CHARTER의 T3 범위에 닿으므로 켜는 승인에 이것도 포함됩니다.
- **켜는 법**: 채팅으로 AI 에게 "Chance 승인 흐름을 켜 줘"라고 승인합니다(T3). AI 가 `pipeline/blogs.json`의 chance 항목 `"publish_flow": "direct"`를 `"pr"`로 바꾸는 PR 을 올리고(`mode`·시크릿·광고 표면은 그대로. 이 값을 지금 값으로 못 박아 둔 표지판 시험의 기준 한 줄 `tests/draft_helpers.py`의 `REAL_PUBLISH_FLOW`도 함께 바꾼다 — 레지스트리만 바뀌면 시험이 빨강이 되어 슬쩍 켜지지 못합니다), 병합한 뒤 아래 순서로 확인합니다.
  1. Actions → `[Chance] 글 자동 작성·게시` → Run workflow, `연습 실행`은 **체크 유지**. 실행 요약에 `발행 흐름` 블록("승인 흐름(pr): 글은 초안 브랜치와 PR 로 올라가고…" 줄)이 있으면 스위치를 제대로 읽은 것입니다(파일·브랜치·PR 이 만들어지지 않습니다).
  2. 같은 화면에서 `연습 실행`의 **체크를 풀고** 한 번 실행합니다(수동 실제 실행: 슬롯·하루 상한을 따지지 않고 글 한 쌍을 만듭니다). 요약의 결과가 `DRAFT_CREATED`이고 마지막 단계 `초안 올리기와 승인 PR 열기`의 요약에 `DRAFT_OPENED`와 PR 링크가 있으면 성공입니다. Pull requests 탭에 `[초안][Chance]` PR 이 보여야 합니다.
  3. PR 을 읽고(아래) 병합합니다. 곧 `[공통] 사이트 자동 배포`가 자동으로 돌고 `사이트 반영 확인`이 초록이면 사이트에서 글이 열립니다.
- **초안 PR 에서 볼 것**: 본문 맨 위에 "승인 대기 초안입니다. 병합하면 공개…" 안내와 내 이름 멘션이 있고, 요약(분야·출처·원문 링크·슬롯), 한·영 제목, 첫 문단 발췌, 자동 점검 결과(분량·원문 인용·출처 목록·고지문·제목 유사도 — 사람의 확인을 대신하지 않음), 승인 체크리스트 세 줄이 이어집니다. **Files changed**에는 `_posts/`의 글 두 개만 있어야 합니다. 원문 링크를 눌러 수치·사실을 대조하고, 마음에 들지 않으면 **병합하지 말고 닫습니다**. 글을 조금 고치고 싶으면 PR 의 브랜치에서 파일을 직접 고친 뒤 병합합니다(고친 내용은 그대로 공개되고 다시 검사되지 않습니다).
- **평소 운영**: 슬롯(9시·18시)마다 PR 이 하나씩 생깁니다. 읽지 않고 쌓아 두지 않습니다. 같은 슬롯의 PR 을 닫아도 그날 그 슬롯의 글은 다시 만들지 않습니다(다른 슬롯은 따로). 수동 실행으로 만든 초안(브랜치 이름이 `m`+시각)은 슬롯과 무관한 추가 글입니다.
- **빨강일 때**(마지막 단계 `초안 올리기와 승인 PR 열기`)

| 요약·로그 | 뜻 | 할 일 |
|---|---|---|
| `DRAFT_BRANCH_ONLY` | 초안 브랜치와 이력은 올라갔는데 **PR 을 열지 못함**(대개 5-1의 설정이 꺼져 있어서 — 로그의 HTTP 403). 글은 잃지 않았고 같은 슬롯을 다시 만들지도 않습니다 | 설정을 켜면 다음 정기 실행(보통 30분 안, GitHub 지연 가능)이 PR 을 다시 엽니다(3일 안, 그 실행은 초록). 급하면 GitHub 의 브랜치 화면에서 `ai/draft/…` 브랜치의 **Compare & pull request** |
| 로그 `작업 실패` | 브랜치 또는 이력을 올리지 못함 | 다음 정기 실행이 처음부터 다시 만듭니다. 계속되면 로그를 AI 에게 |

- **되돌리기**: 급하면 `PIPELINE_PAUSE`(3-9)로 멈춥니다. 직접 게시로 돌리려면 AI 에게 채팅으로 승인하고 `publish_flow`를 `direct`로 되돌리는 변경을 요청합니다(게시 방식 변경이라 T3). 그 전에 열린 초안 PR 은 병합하거나 닫고, 남은 `ai/draft/…` 브랜치는 브랜치 화면에서 직접 지웁니다(자동 정리는 승인 흐름에서만 돕니다).
- **켠 뒤 처음 확인할 것**(실제 GitHub 에서 한 번도 확인하지 못했습니다, 미관측)
  - [ ] 연습 실행의 요약에 `발행 흐름` 블록("승인 흐름(pr): 글은 초안 브랜치와 PR 로 올라가고…" 줄)이 나온다
  - [ ] 수동 실제 실행으로 PR 이 열리고 라벨 `초안`·`채널:Chance`가 붙는다(라벨이 없던 저장소라 새로 만들어짐)
  - [ ] PR 본문이 읽기 좋고(멘션·링크·체크리스트) 이상한 자동 링크가 없다
  - [ ] 봇이 연 PR 에는 `[공통] 저장소 규칙·테스트 자동 검사`·`[공통] PR 변경 범위 검사`가 돌지 않는다(예상 — 돌면 알려 주세요)
  - [ ] 병합하면 `[공통] 사이트 자동 배포`가 자동 실행되고 `사이트 반영 확인`이 초록이다
  - [ ] 정기 슬롯의 둘째 틱이 `DRAFT_PENDING`으로 건너뛴다(같은 슬롯이 두 번 만들어지지 않음)
  - [ ] PR 을 닫은 뒤에도 같은 슬롯이 다시 만들어지지 않고 7일 뒤 브랜치가 지워진다
  - [ ] 열린 초안 PR 이 있는 동안 워치독이 `STALE` 대신 `DRAFT_WAITING`으로 알린다
  - [ ] `[공통] 확인 필요 모음`에 초안 PR 이 '검사 결과 없음'(확인) 항목으로 보인다
- **하지 말 것**: 글을 읽지 않고 병합하기(병합 = 공개). 5-1의 설정을 확인하지 않고 켜기(PR 이 안 열림). 초안 브랜치를 직접 지우기(이력이 남아 있어 그 슬롯은 다시 만들어지지 않고 글만 사라집니다). 같은 슬롯 글을 다시 받으려고 수동 실행 연타하기(수동 글은 슬롯과 무관한 추가 글입니다). main 에 "상태 검사 필수"·"PR 필수" 보호 규칙 켜기(5장 경고 — 봇이 연 초안 PR 은 검사가 돌지 않아 병합이 막히고 이력 push 도 거부됩니다).

### 3-19. 티스토리·네이버 초안 이슈를 읽고 직접 발행하려면

> 티스토리·네이버에는 자동으로 올리는 공식 방법이 없어서([`ARCHITECTURE.md`](./ARCHITECTURE.md) §7-B-2) **글을 GitHub 이슈 한 개(초안 패키지)로 만들어 보여 드리고, 운영자가 복사해 직접 발행**합니다. **지금은 두 블로그가 등록되기 전이라 이슈가 만들어지지 않습니다**(블로그 주소·주제를 받으면 시작합니다. 받은 뒤 할 일은 같은 문서 §7-B-2의 체크리스트).

1. **초안 이슈 찾기**: 저장소 → **Issues** → 제목이 `[초안][티스토리] …`·`[초안][네이버] …`인 것(라벨 `초안`과 `채널:티스토리`·`채널:네이버`). 새 이슈가 알림으로 오는지는 GitHub 계정 알림 설정에 달려 있고 실제 도착은 **미확인**입니다. 초안 현황을 `[운영] 확인 필요 모음`에 모아 보는 기능은 별도 작업입니다.
2. **이슈 본문을 위에서부터** 따라 합니다. 상자 오른쪽 위의 복사 버튼을 씁니다(휴대폰 GitHub 앱도 같습니다 — 미확인).
   - **복사용 제목** → 블로그 제목 칸에 붙여넣기.
   - **본문** — 티스토리: **PC 웹** 글쓰기 화면에서 편집기 모드를 **HTML**로 바꾼 뒤 `html` 상자를 복사해 붙여넣고 미리보기로 서식을 확인합니다(모바일 앱 편집기에는 HTML 모드가 없고, 모드를 바꾸면 서식이 달라질 수 있습니다). 네이버: '서식 있는 글' 구역의 두 가로줄 사이를 끝까지 선택해 복사한 뒤 스마트에디터에 붙여넣습니다. 서식이 깨지면 '평문' 상자를 붙여넣고 소제목·목록은 직접 꾸밉니다(붙여넣을 때 서식이 보존되는지는 **미확인**이라 첫 글은 비공개로 시험합니다).
   - **해시태그** → 쉼표로 구분되어 있고 `#`은 없습니다. 태그 입력 칸이 쉼표를 어떻게 받는지는 **미확인**이라 시험 글로 확인합니다.
   - **이미지** → 자동으로 고른 이미지는 아직 없습니다. 대표 이미지는 직접 올립니다(티스토리는 외부 링크 이미지가 본문에는 보여도 목록 썸네일에 안 나옵니다). 이미지를 쓰면 출처·라이선스·AI로 만든 이미지인지를 표 모양대로 적어 두고, Unsplash 이미지는 작가·Unsplash 링크 표기 문구를 글 아래에 넣습니다.
   - **근거 출처·게이트 점검 결과** → 읽어 봅니다. **게이트는 사실 확인을 하지 않습니다**(길이·표현·주제·중복만 봅니다). 사실·수치·고유명사는 직접 확인합니다.
3. **직접 겪은 일·판단을 한 문단 이상 더한 뒤 올립니다.** 티스토리 공지 2705(2026-10-12)는 AI가 쓴 글을 거의 그대로 발행해 경험·생각이 드러나지 않는 글을 아쉬운 사례로 듭니다(적용 2027-01-02, 발행 자체에는 영향이 없다고 밝힘). 광고·협찬 표기가 필요한지도 봅니다. 신규 채널은 품질 게이트를 통과하기 전까지 **플랫폼 화면에서도 광고를 켜지 않습니다**([`SECURITY_GUARDRAILS.md`](./SECURITY_GUARDRAILS.md) G-C10).
4. **발행하면** 이슈의 체크리스트를 채우고 발행 주소를 코멘트로 남긴 뒤 **이슈를 닫습니다**(닫으면 발행 완료). 쓰지 않을 초안은 라벨 `폐기`를 붙이거나 닫습니다.
5. **열린 초안(라벨 `폐기`가 붙은 것은 제외)이 3건 이상 쌓이면 새 초안을 만들지 않습니다**(`PACKAGE_BACKLOG`, 실행은 초록 + 파란 안내). 이슈를 닫거나 `폐기`를 붙이면 다음 실행부터 다시 만들어집니다.

알아 둘 것: 이슈 본문의 `@이름`·`#숫자` 뒤에 눈에 안 보이는 글자(영폭 공백)가 들어 있는 것은 의도한 소독입니다(알림·자동 링크가 안 가게 풀어 둔 것, 복사한 글에도 따라가지만 보이지 않습니다. 이메일·주소 안의 것은 그대로입니다). 이슈에 사람이 단 코멘트는 자료일 뿐 봇이 읽어 실행하지 않습니다. 이슈를 직접 고쳐도 되고, 고친 뒤에도 같은 초안은 다시 만들어지지 않습니다(숨은 표지 `draft-id`를 지우지 마세요).

## 4. 점검 루틴과 키 교체

### 4-1. 점검 루틴

알림이 오면 1장 순서로 봅니다. 그 밖에 보험으로 아래를 권합니다. `[운영] 확인 필요 모음` 이슈를 읽으면 "매주" 줄의 이슈·PR·변수 확인을 대신할 수 있습니다.

| 언제 | 어디서 무엇을 | 정상 | 이상이면 |
|---|---|---|---|
| (선택) 매일 1분 | Actions 맨 위 목록 | 최근 24시간이 초록·회색 | 3-7 |
| (선택) 매일 1분 | 사이트 최신 글 | 마지막 글이 36시간 이내 | 3-2 |
| 매주 5분 | Issues → 라벨 `watchdog` | 열린 이슈 0건 | 이슈 본문, 6-5 |
| 매주 5분 | Pull requests | 처리하지 않은 수정 PR 없음. (승인 흐름을 켠 뒤) 라벨 `초안`의 열린 PR 이 2일 넘게 방치되지 않음 | 3-11 후 병합·닫기, 초안은 3-17 |
| 매주 5분 | Settings → Secrets 이름 | 두 이름(`GEMINI_API_KEY`·`UNSPLASH_ACCESS_KEY`)만 있음 | 모르는 이름이면 확인 |
| 매주 5분 | Settings → Variables | 비어 있음(멈춘 중이면 `PIPELINE_PAUSE`만) | 모르는 변수면 확인 |
| 매월 | 5장 점검표, AI Studio의 사용량·키 설정 | 체크 완료 | 5장 |

- **정상 신호**: Chance 결과가 9시·18시 시간대마다 `PUBLISHED`(하루 최대 2번)이고 나머지 실행은 `OUT_OF_WINDOW`·`ALREADY_PUBLISHED`입니다(승인 흐름을 켠 뒤에는 `DRAFT_CREATED`+초안 PR 이고 나머지는 `DRAFT_PENDING`·`ALREADY_PUBLISHED`). Blogger는 "대상 0개"(정지 중). 워치독은 "이상 없음".
- **이상 신호**: 빨강, 며칠째 같은 노란 경고, 워치독 이슈, 마지막 글이 36시간을 넘음.
- 글이 올라왔는지 빨리 보려면 저장소 → **Commits**에서 "🤖 자동 포스팅/이미지 수정"을 찾습니다.

### 4-2. 키·토큰 교체

공통 규칙
1. 값은 이 문서·이슈·PR·채팅·로그에 쓰지 않습니다. 새 값은 발급 화면에서 복사해 곧바로 GitHub 입력칸에만 붙입니다.
2. 순서는 **새 키 발급 → Secrets 교체 → 옛 키 폐기**입니다. 정기 교체는 새 키가 동작하는 것을 확인한 뒤 옛 키를 폐기하고, **유출이 의심되면 확인을 기다리지 않고 바로 폐기**합니다(공개된 값은 지워도 유출로 봅니다).
3. 저장소 이력을 고쳐 쓰는 것(force push)은 하지 않습니다. 효과가 제한적이고 T3이며, 핵심은 키 교체입니다. 사고 대응은 [`SECURITY_GUARDRAILS.md`](./SECURITY_GUARDRAILS.md) §4-A에 있습니다.
4. 입력 경로: Settings(휴대폰은 More(⋯) 메뉴 안) → **Secrets and variables** → **Actions** → **Secrets** 탭 → 이름 옆 연필 → 값 붙여넣기 → **Update secret**.

| 값 | 증상 | 갱신 |
|---|---|---|
| `GEMINI_API_KEY` | Chance 빨강, 이슈 수정 오류 | AI Studio에서 새 키 → Secrets 교체 → 옛 키 폐기 |
| `UNSPLASH_ACCESS_KEY` | 조용함(새 글은 예비 이미지, 이미지 변경 거부) | 개발자 화면에서 재발급 → Secrets 교체 |
| `BLOGGER_*` 4종 | 미등록. 지금 등록하지 않음 | 3-12 |
| `GITHUB_TOKEN` | 해당 없음 | 실행마다 자동 발급. 교체 불필요 |

`GEMINI_API_KEY` 교체 순서
1. Google AI Studio에서 새 키를 만듭니다. 옛 키는 아직 지우지 않습니다.
2. 위 입력 경로로 `GEMINI_API_KEY`를 새 값으로 바꿉니다.
3. Actions → `[Chance] 글 자동 작성·게시` → Run workflow에서 `연습 실행`은 체크한 채 **`연습 실행에서도 실제 Gemini를 호출`(`real_ai`)도 체크**합니다. 연습 실행은 기본이 가짜 AI 응답이라 `real_ai`를 체크하지 않으면 새 키를 시험하지 못합니다(3-13). 로그에 "Gemini 모델 호출 성공"이 보이면 새 키가 동작하는 것입니다. 그 줄이 안 보이면(후보 기사 없음 등) 확인이 안 된 것이니 다음 정기 실행의 결과를 봅니다.
4. 동작을 확인한 뒤 옛 키를 삭제합니다.

`UNSPLASH_ACCESS_KEY`가 만료·오류면 새 글이 예비 이미지로 대체되고(로그 "[경고] 검색 결과 없음, 폴백 풀 이미지 사용") 이미지 변경 이슈는 "찾지 못했습니다"로 거부됩니다. 예비 이미지도 없으면 글 저장이 실패(빨강)합니다.

`BLOGGER_*`를 등록·교체한 직후에는 `인증 점검만 실행`을 1회 합니다(3-12). 요약에 `AUTH_CHECK_OK`가 없으면 통과가 아닙니다. 토큰 만료(`auth_expired`)면 동의 화면이 "프로덕션"인지 확인하고 토큰을 새로 받아 `BLOGGER_REFRESH_TOKEN`을 교체합니다.

## 5. 보안 설정 점검표

> **참고(AI·관리자용)**: 설정은 한 번 해 두고 매월 점검표(5-1)만 봅니다. 평소에는 읽지 않아도 됩니다.

코드로 못 바꾸고 운영자만 GitHub 설정에서 할 수 있는 항목입니다. 상태 칸은 운영자가 2026-10-25에 화면을 읽어 둔 **2차 기록**(캡처 없음)이거나 이 저장소에서 확인한 사실입니다. 바꾸기 직전에 같은 화면을 다시 확인하세요. **클릭 순서는 외부 지식이라 이 저장소에서 시험하지 못했고, 화면 구성은 GitHub 업데이트로 달라질 수 있습니다.**

> **경고: main 브랜치 보호 규칙을 함부로 켜지 마세요.**
> 자동 발행 4종(`[Chance] 글 자동 작성·게시`·`[Chance] 기존 글 이미지 교체(수동)`·`[Blogger] 글 자동 작성(초안함 업로드)`·`[공통] 이슈 양식 페이지 목록 갱신`)은 `GITHUB_TOKEN`으로 **main에 직접 push**합니다.
> 아래를 main에 켜면 이 push가 거부되어 **자동 발행이 멈출 수 있습니다**: "Require a pull request before merging"(PR 필수) · 승인·코드 소유자 리뷰 필수 · "Require status checks to pass"(상태 검사 필수) · "Require signed commits" · "Restrict updates" · "Lock branch". (외부 지식, 이 저장소에서 시험하지 않음) 승인 흐름(3-17)을 켠 뒤에도 이력 커밋은 main에 직접 push하고 초안 브랜치(`ai/draft/…`)도 push하므로 같은 규칙이 적용됩니다.
> 개인 계정 저장소에서 봇만 이 규칙을 건너뛰게 하는 방법은 확인된 근거가 없습니다(미확인). 안전한 설정은 **삭제 금지 + 강제 push 금지**만 거는 룰셋입니다(5-2 A, 운영자 결정 2026-10-25). 봇은 일반 push만 하므로 이 둘은 막지 않습니다(코드 기준).

### 5-1. 점검표

| 항목 | 마지막으로 확인된 상태 | 할 일 |

### 5-2. 클릭 순서

**A. 룰셋 `main-safe` (삭제·강제 push 금지만)**
1. 저장소 → **Settings**(휴대폰은 More(⋯) 메뉴 안) → **Rules** → **Rulesets** → **New ruleset** → **New branch ruleset**.
2. Ruleset name `main-safe`, Enforcement status **Active**. Bypass list는 비워 둡니다.
3. Target branches → **Add target** → **Include default branch**.
4. Rules에서 **Restrict deletions**와 **Block force pushes**만 체크합니다. **나머지는 모두 체크하지 마세요.** → **Create**.
5. 이후 봇이 main에 커밋하는 다음 기회에 그 실행이 초록이고 커밋이 보이는지 확인합니다(예: Chance가 글을 만들 때 생기는 "🤖 자동 포스팅/이미지 수정" 커밋). 커밋 없이 끝난 초록은 push 경로를 검증하지 못합니다.
6. 그 실행이 빨강이면 즉시 룰셋을 **Disabled**로 바꾸거나 삭제합니다.

**B. 허용 액션 제한 (선택)**: Settings → **Actions** → **General** → **Actions permissions** → 선택한 액션만 허용(화면 이름 "Allow OWNER, and select non-OWNER, actions and reusable workflows") → **Allow actions created by GitHub**만 체크 → Save. 바꾼 뒤 Actions → `[공통] 사이트 자동 배포` → Run workflow(main)가 초록인지 확인하고, 문제가 있으면 "모두 허용"으로 되돌립니다. 같은 화면의 "Require actions to be pinned to a full-length commit SHA"는 켜지 마세요.

**C. 시크릿 스캔·푸시 보호**: Settings → **Security and quality** 구역(옛 이름: Code security, Code security and analysis) → **Advanced Security** → **Secret Protection**(옛 이름 Secret scanning)과 **Push protection**이 켜져 있는지 확인합니다. 꺼져 있으면 각각 **Enable**을 누릅니다. push가 막히는 화면이 나오면 **우회(bypass) 버튼을 누르지 마세요.** 키가 든 파일을 빼고 다시 올리고, 이미 올린 키는 폐기·재발급합니다. 저장소 **Security** 탭(2026-04-02부터 이름이 "Security & quality")의 알림도 가끔 봅니다.

**D. 알림 받기**
- Actions 실패 알림은 프로필 Settings → Notifications → System → Actions에서 켭니다(저장소 Watch 메뉴에는 Actions 항목이 없습니다).
- 예약(정기) 실행의 실패 알림은 예약(cron) 줄을 마지막으로 고친 사람(고친 적이 없으면 워크플로를 만든 사람, 비활성화했다가 다시 켠 사람)에게 가며, 저장소를 Watch 중이어야 합니다. 그 계정이 운영자 본인인지 확인하세요(미확인).
- 이슈·PR 알림은 저장소 상단 **Watch** → **Custom**에서 Issues·Pull requests를 고릅니다.
- 휴대폰 푸시를 받으려면 GitHub 앱을 설치하고 로그인해 "멘션 받았을 때·내가 담당자일 때" 알림을 켭니다([`OPS_INBOX.md`](./OPS_INBOX.md) §2).
- 워치독 알림과 `[운영] 확인 필요 모음`의 @멘션 코멘트가 운영자에게 닿는지는 미확인입니다. 안 올 때는 3-14.

**E. 협업자 확인**: Settings → **Collaborators**. 협업자는 사실상 쓰기 권한이라 워크플로를 고친 브랜치를 실행하고 시크릿을 쓸 수 있으며 이슈 수정 요청 자격도 됩니다. 꼭 필요한 사람만 두세요.

## 6. 워크플로별 상세

> **참고(AI·관리자용)**: 운영자는 3장의 안내에서 필요한 절로 찾아옵니다. 처음부터 읽을 필요는 없습니다.

공통: 파일은 `.github/workflows/`에 있습니다. 수동 실행은 Actions → 워크플로 → **Run workflow**입니다. "정상일 때"를 먼저 확인하세요.

### 6-1. `[Chance] 글 자동 작성·게시` (`chanceblog.yml`)

- **하는 일**: 신뢰 목록 게시자의 뉴스 기사로 한·영 글 한 쌍을 만들어 검증하고 main에 직접 커밋한 뒤 사이트 배포를 요청합니다(job `글 작성·게시`). 레지스트리 `publish_flow`가 `pr`이면(승인 흐름, 지금은 꺼짐 — 3-17) 직접 커밋과 배포 요청 대신 글을 초안 브랜치와 승인 PR 로 올리고, 병합이 공개입니다. 단계 순서: `발행 흐름 확인` → `AI 블로그 제너레이터 실행` → (직접 게시) `변경 사항 커밋`·`Pages 배포 실행` 또는 (승인 흐름) `초안 올리기와 승인 PR 열기`.
- **바꾸는 것**: `_posts/`의 글 2개와 `history.json`. 커밋 제목은 "🤖 자동 포스팅/이미지 수정". 승인 흐름에서는 main 에 이력(`history.json`)만 "🤖 이력: 제목 (승인 대기)" 커밋으로 올리고 글 2개는 `ai/draft/…` 브랜치("🤖 초안: 제목 (승인 대기)")와 PR 에만 있습니다.
- **언제 도나**: 자동 — cron `17 * * * *`와 `47 * * * *`(UTC, 매시 두 번). 수동 가능. 실행 제목 `[Chance] 글 작성·게시 · 정기`, `· 수동`, `· 수동(연습: 저장 안 함)`, `· 수동(연습: 실제 AI 호출·저장 안 함)`.
- **수동 입력**: `연습 실행`(`dry_run`)은 기본 체크(파일·커밋·게시 없음, **가짜 AI 응답**)입니다. `연습 실행에서도 실제 Gemini를 호출`(`real_ai`, 기본 꺼짐)을 체크하면 실제 호출로 연습하고, 실행 제목에 "실제 AI 호출"이 붙으며 요약에 `AI 응답` 줄이 남습니다(3-13).
- **권한·시크릿**: contents 쓰기 + actions 쓰기(배포 요청용) + pull-requests 쓰기(승인 흐름의 초안 PR 열기·라벨, 직접 게시에서는 쓰지 않음), `GEMINI_API_KEY`·`UNSPLASH_ACCESS_KEY`, 변수 `PIPELINE_PAUSE`. 제한 20분. `[Chance] 기존 글 이미지 교체(수동)`와 같은 대기열(`chanceblog`)을 씁니다.
- **정상일 때**: Summary(`Chance_Blog 실행 요약`)에 결과 코드와 분야 표(받은 기사·검증 통과·후보·탈락 사유), 호출이 있으면 `Gemini 호출: N회(실패 K회)`가 있습니다. 글이 생기면 봇 커밋("커밋: 해시" 줄) + "Pages 배포 실행 요청" 줄 + `[공통] 사이트 자동 배포` 실행 + 사이트의 한·영 글이 보입니다(승인 흐름에서는 대신 마지막 단계 요약의 `DRAFT_OPENED`와 PR 링크, Pull requests 의 `[초안][Chance]` PR 이 보이고, PR 을 병합해야 `[공통] 사이트 자동 배포`가 돌아 글이 열립니다). 글이 없는 정상 종료는 Summary와 로그의 `[SKIP] code=` 한 줄로만 남습니다.
- **실패하면**: 3-7의 "Chance가 빨강일 때".
- **수동으로 누르면 안 될 때**: 연습을 풀면 슬롯·하루 상한과 무관하게 글이 추가됩니다(3-1).

| 결과 코드 | 뜻 | 색 | 할 일 |
|---|---|---|---|
| `PUBLISHED` | 글을 만들었음 | 초록 | 사이트 확인 |

| `OUT_OF_WINDOW` | 첫 게시 시각(9시) 전 | 초록 | 없음 |
| `ALREADY_PUBLISHED` | 그 슬롯 글이 이미 있음(승인 흐름에서는 PR 을 병합해 글이 main 에 있음) | 초록 | 없음 |
| `DRAFT_PENDING` | (승인 흐름) 그 슬롯의 초안이 승인(PR 병합)을 기다리는 중이거나 닫혀 폐기됨. 같은 슬롯을 다시 만들지 않음 | 초록 | PR 이 열려 있으면 읽고 병합하거나 닫기(3-17) |

| `NO_CANDIDATES` | 시간 상한(480초)에 걸려 일부 분야만 시도하고 후보 없음 | 초록 + 노란 경고 | 다음 정기 실행을 기다림 |
| `ALL_LANES_EMPTY` | 모든 분야에 검증을 통과한 기사가 없음 | **빨강** | 3-7 |
| `SOURCES_UNREACHABLE` | 시도한 뉴스 소스에 모두 접속 실패 | **빨강** | 3-7 |

- 연습 실행은 결과 줄이 "연습으로 글을 만들어 봤습니다(저장하지 않았습니다)"로 나옵니다(코드는 `PUBLISHED`). Summary의 "실행" 줄에 "DRY_RUN: 파일·기록 저장 안 함"이 있으면 실제로는 저장되지 않은 것입니다.
- 기사 탈락 사유 코드(Summary 표와 로그의 소스별 줄): `AGE` 72시간 초과 · `UNTRUSTED` 게시자가 신뢰 목록에 없음 · `UNRESOLVED` 원문 주소를 못 얻었거나 주소 모양이 안전하지 않음(공백·꺾쇠·따옴표·괄호가 든 주소) · `HOST_MISMATCH` 게시자와 원문 주소가 다름 · `SHORT_SUMMARY` 요약 100자 미만 · `UNCHECKED` 소스당 5건 검사 한도 초과 · `NOT_TECH` 기술 키워드 아님 · `EXCLUDED` 소스별 제외 규칙(약관이 빼라고 한 것·글감이 못 되는 공지·퀴즈) · `OFF_TOPIC` 이 분야 주제어와 맞지 않음 · `NO_TITLE` 제목 없음 · `DUPLICATE` 기존 글과 제목이 비슷함.
- 분야 하나가 비면 `[SKIP] code=LANE_EMPTY lane=…` 한 줄을 남기고 다음 분야를 시도합니다(폴백으로 정상 발행한 실행에도 이 줄이 찍힘). 분야 대체는 **임시 조치**이고 같은 분야가 계속 비면 글이 소스가 많은 분야에서만 나올 수 있습니다. 2026-10-26부터 모든 분야가 약관을 읽은 직접 RSS에서 후보를 얻습니다(과학: NASA·EU 집행위원회 Environment·JRC, 경제: Federal Reserve·집행위원회 Energy·캐나다 통계청, 사회·정책: 집행위원회 소식·통계청(UN News는 유엔 쪽 조건을 채울 때까지 보류 — 로그에 `소스 UN News: 보류` 줄이 남음), 일상·마음: 통계청, 기술·미래: EU 디지털 전략, 문화: Pew). 공공기관 발표는 주말에 적어 주말과 월요일 아침(한국 시간)에는 72시간 창으로도 분야가 빌 수 있고 그때는 다른 분야로 대체됩니다. 기술·미래는 약 주 2건이라 드물게 뽑힙니다. 예: 2026-10-25 20시대 정기 실행은 "사회·정책" 후보가 없어 기술·미래 분야로 대체해 18시 슬롯 글을 정상 발행했고 `Gemini 호출`은 1회였습니다. 코드표는 [`ARCHITECTURE.md`](./ARCHITECTURE.md) §4-1에 있습니다.

### 6-2. `[Chance] 기존 글 이미지 교체(수동)` (`chance-fix-images.yml`)

- **하는 일**: 기존 글의 깨진(`broken`)·없는(`missing`)·중복(`duplicate`)·로컬 경로(`local-path`) 이미지만 교체합니다. 새 글은 만들지 않습니다(job `이미지 교체·커밋`).
- **바꾸는 것**: 교체한 `_posts/` 글 파일. **PR 없이 main에 직접 커밋**("🤖 자동 포스팅/이미지 수정")하고 사이트 배포를 요청합니다.
- **언제 도나**: 수동 전용. 입력 `연습 실행`(`dry_run`) 기본 체크(파일·커밋 없이 교체 대상만 로그로 확인, 가짜 AI 검색어 사용). 실행 제목 `[Chance] 기존 글 이미지 교체 · 연습(저장 안 함)`, `· 연습(실제 AI 호출·저장 안 함)`, `· 실제 교체`.
- **수동 입력**: `real_ai`(`연습 실행에서도 실제 Gemini를 호출`, 기본 꺼짐)는 Chance와 같은 뜻입니다. 이미지 교체 연습은 Gemini 한도는 쓰지 않아도 Unsplash 검색은 실제로 부릅니다. 실제 교체는 한 번에 최대 20건만 처리하고 나머지는 다음 실행으로 넘깁니다(3-13).
- **권한·시크릿·제한**: `[Chance] 글 자동 작성·게시`와 같습니다(20분, 같은 대기열).
- **정상일 때**: Summary에 "이미지 점검: 완료: …" 줄(대상·교체·건너뜀 건수, 연습이면 "DRY_RUN: 실제 변경 없음"이 붙음)이 있습니다. 교체한 뒤에는 봇 커밋과 `[공통] 사이트 자동 배포`가 따릅니다.
- **수동으로 누르면 안 될 때**: 연습을 풀면 확인 없이 main에 바로 커밋됩니다. 연타·정기 실행 시각 전후는 피합니다(3-3). 잘못 바뀌면 AI에게 해당 커밋을 되돌려 달라고 요청합니다.

### 6-3. `[Blogger] 글 자동 작성(초안함 업로드)` (`blogger.yml`)

- **하는 일**: 레지스트리(`pipeline/blogs.json`)의 Blogger 블로그를 하나씩 처리합니다. 주제 선정 → Gemini 글 → 검사 → 게시·Blogger 초안함 업로드·저장소 초안 저장 중 하나 → 기록. job은 `대상 블로그 계획`(plan) → `글 생성 (블로그key)`.
- **지금 상태**: `blogger_macat`이 정지(`mode: off`)입니다. plan 단계가 "대상 0개" 안내(`::notice::`)와 Summary(제목 줄 `### Blogger 글 자동 작성`, "결과: **대상 0개**" — 이 제목 줄은 워크플로 이름이 아니라 실행 안의 고정 문구라 이름을 바꿔도 그대로입니다)를 남기고 `글 생성` job은 건너뜁니다(초록). 글·커밋은 없습니다(`인증 점검만 실행`만 정지 중에도 대상에 넣어 점검하는 예외).
- **바꾸는 것(켜져 있을 때)**: `_blogger_drafts/` 초안과 `blogger_history.json`을 main에 직접 커밋("🤖 [블로그key] 생성/게시 기록", push 3회 재시도). 사이트 배포는 요청하지 않습니다.
- **언제 도나**: 자동 — cron `0 2 * * *`(UTC) = 한국 11:00. 수동 가능. 실행 제목 `[Blogger] 글 작성 · 정기`, `· 수동(…)`.
- **수동 입력**: `blog`(비우면 Blogger 전체, 오타면 plan 단계가 빨강)·`topic`(주제 지정, **하루 상한을 건너뜀**, 주제 가드레일에 걸리면 `TOPIC_BLOCKED`로 멈춤)·`연습 실행`(`dry_run`)·`publish`.
  - `연습 실행`(기본 켜짐)은 가짜 AI 응답으로 흐름만 확인합니다(저장·게시·하루 상한 소진 없음). **체크를 풀면** 실제 Gemini로 초안이 만들어져 저장소에 커밋되고 그날 하루 상한을 씁니다.
  - `publish`는 Blogger에 어디까지 보낼지 고릅니다. 건드리지 않으면 공개 게시는 하지 않습니다. 공개 게시를 고르면 게시용 시크릿이 있어야 하고, 없으면 빨강입니다.
- **권한·시크릿**: plan은 contents 읽기, 글 생성은 contents 쓰기. `GEMINI_API_KEY`, 게시용 4종 `BLOGGER_BLOG_ID`·`BLOGGER_CLIENT_ID`·`BLOGGER_CLIENT_SECRET`·`BLOGGER_REFRESH_TOKEN`, 변수 `PIPELINE_PAUSE`. **게시용 4종은 지금 모두 미등록이고 등록 금지입니다.**
- **정상일 때(켜져 있을 때)**: 이력 마지막 항목의 `status`가 `posted`(공개 게시, url 있음)·`draft_uploaded`(Blogger 초안함에 올림, 공개되지 않음) 또는 `draft`(저장소 초안만)입니다. 하루 상한은 1건이고 공개되지 않은 초안과 초안함에 올린 초안도 셉니다.
- **실패하면**: Summary·로그의 `[SKIP] code=` 줄로 판단합니다(아래 표). **수동으로 누르면 안 될 때**: `topic`은 하루 상한을 건너뛰어 하루 2건이 가능합니다. 공개 게시를 고르는 것은 시크릿 등록·승인 뒤에만 합니다.

| 코드 | 뜻 | 색 |
|---|---|---|
| `PAUSED` | `PIPELINE_PAUSE` 켜짐 | 초록 + 파란 안내 |
| `DAILY_CAP` | 오늘 상한 1건에 도달(수동 `topic`은 건너뜀) | 초록 + 파란 안내 |
| `NO_TOPIC`·`GATE_REJECTED` | 고를 주제 없음·재작성 3번 모두 검사 탈락 | 초록 + 노란 경고 |
| `TOPIC_BLOCKED` | 수동 `topic`이 주제 가드레일(질병·약·보충제·진단·임신·영유아·체중 감량·다이어트 등)에 걸림. Gemini·Blogger를 부르기 전에 멈추고 걸린 낱말이 요약에 보임(저장·이력 없음) | **빨강**(종료 2) |
| `SECRETS_MISSING` | 게시 대상인데 게시용 시크릿(또는 Gemini 키) 누락. 이름만 보이고 글을 만들기 전에 종료 2 | **빨강** |
| `EXPAND_FAILED`·`LLM_FAILED` | 주제 확장·글 생성 AI 호출 실패 | **빨강** |
| `PUBLISH_FAILED` | Blogger 게시 실패(인증·API) | **빨강** |

**초안함 업로드 모드**
- 레지스트리 `mode: draft`는 게시용 시크릿 4종이 **모두** 있으면 글을 Blogger **초안함에 업로드**합니다(공개되지 않음, 이력 `status`는 `draft_uploaded`).
- 시크릿이 **하나도** 없으면 저장소 파일에만 저장합니다(`UPLOAD_SKIPPED` 안내, 오류 아님). **일부만** 있으면 빨강(종료 2)입니다.
- 수동 입력 `publish`는 `off`(저장소 파일에만)·`draft`(기본, 초안함 업로드)·`publish`(즉시 공개 게시, 시크릿이 없으면 빨강) 3택입니다. 실행 제목은 `수동(저장소 파일만 저장)`·`수동(Blogger 초안함 업로드)`·`수동(즉시 게시)`입니다.
- 초안함의 글은 운영자가 Blogger 화면에서 확인한 뒤 직접 게시합니다.

**인증 점검만 실행**(`auth_check`, 수동, 기본 꺼짐)
- 글을 만들지 않고 인증만 확인합니다(3-12). 시크릿 4종이 있어야 하며 하나도 없으면 "시크릿 없음", 일부만 없으면 "시크릿 일부 없음"으로 빨강(종료 2)입니다.
- 실패하면 로그에 `[SKIP] code=AUTH_CHECK_FAILED reason=분류`가 남고 글 생성·업로드·게시는 하지 않습니다.
- `PIPELINE_PAUSE`가 켜져 있으면 점검하지 않고 `PAUSED`(초록, 종료 0)로 끝납니다. 통과 신호는 요약의 `AUTH_CHECK_OK`뿐입니다.

| 분류(`reason=`) | 뜻 | 종료 | 할 일 |
|---|---|---|---|
| `auth_expired` | 토큰 갱신이 만료·폐기로 거부됨 | 1 | 동의 화면이 "프로덕션"인지 확인하고 토큰을 새로 받아 `BLOGGER_REFRESH_TOKEN` 교체 |
| `auth_failed` | 클라이언트 ID·시크릿 불일치, 또는 블로그 조회가 401·403·404(권한 없음·블로그 없음) | 2 | `BLOGGER_BLOG_ID`·`BLOGGER_CLIENT_ID`·`BLOGGER_CLIENT_SECRET`, Blogger API 사용 설정, 계정의 블로그 권한 확인 |
| `blog_mismatch` | 인증은 통과했지만 돌려준 블로그 주소가 레지스트리 `url`과 다름 | 2 | `BLOGGER_BLOG_ID`가 이 블로그의 ID인지 확인 |
| `network`·`bad_response`·`api_error`·`unexpected` | 연결 실패·응답 이상·그 밖의 API 오류·예상 밖 예외 | 1 | 잠시 뒤 다시 실행, 계속되면 로그를 AI에게 |

### 6-4. `[공통] 사이트 자동 배포` (`pages.yml`)

- **하는 일**: 사이트(Jekyll)를 빌드해 공개하고, 새 글이 공개 주소에서 열리는지 확인합니다. 저장소는 바꾸지 않습니다.
- **잡 3개**: ① `사이트 빌드` ② `사이트 게시`(①이 끝나야 시작) ③ `사이트 반영 확인`(②가 끝나야 시작, 제한 15분).
- **언제 도나**: 자동 — main에 push될 때마다(경로 제한 없음). 수동 가능(입력 없음). Chance가 새 글을 커밋한 직후에는 Chance가 직접 실행을 요청합니다(봇 push는 자동 실행을 만들지 못하기 때문). 승인 흐름(3-17)의 초안 PR 을 내가 병합하면 사람의 push 라서 요청 없이 자동으로 돕니다(이력만 올리는 봇 커밋에는 돌지 않습니다). 새 배포가 오면 진행 중이던 이전 실행을 취소하므로 회색 "취소됨"은 정상입니다.
- **권한·시크릿**: 빌드 contents 읽기, 게시 pages 쓰기·id-token 쓰기, 확인 contents 읽기. 시크릿 없음.
- **정상일 때**: 세 잡이 모두 초록입니다.
- **`사이트 반영 확인` 요약 읽는 법**(Summary 제목 "공개 사이트 반영 확인")
  - 저장소 `_posts`에서 **공개될 가장 새 글**(`published: false`·미래 날짜 제외)의 공개 주소를 계산해 HTTP 200으로 열리는지 봅니다. 안 열리면 **마감 12분(720초)** 까지 다시 확인하는데, 대기는 10초에서 2배씩(10·20·40·80·160초) 늘고 시도마다 요청 모양(끝에 `index.html`, `Accept-Encoding` 등)을 바꿉니다. 공개 CDN이 404도 보관해서(최대 약 18분, 1회 측정이라 불확실) 같은 모양의 재시도는 같은 404를 받기 때문입니다.
  - `결과: **반영됨**` + "시도 1회·경과 0초"면 가장 정상입니다(첫 실제 실행도 이랬습니다). 시도가 여러 번이면 "시도 기록" 줄에 시도별 경과 초·요청 모양·상태가 나옵니다.
  - 응답 줄의 `X-Cache`(CDN이 보관한 응답인지)·`Age`(보관된 지 몇 초)·`Last-Modified`는 "캐시 때문에 늦은 것"과 "진짜 안 올라온 것"을 가르는 단서입니다.
  - `경고: 시도 1(정규 주소)에서 HTTP 404`가 있으면, 이 검사는 다른 요청 모양으로 열림을 확인했지만 독자가 정규 주소를 열면 CDN 보관이 끝날 때까지 404일 수 있다는 뜻입니다. 이 경우 시도 1의 `X-Cache`·`Age`와 열린 시각을 WORKLOG에 적도록 알려 주세요.
  - `결과: **건너뜀**`(초록)은 공개될 글이 없다는 뜻입니다(모든 글이 `published: false`이거나 미래 날짜).
- **빨강이면**: `결과: **반영 안 됨**`이고 "해석" 줄이 마지막 응답의 `Age`로 원인을 추정해 줍니다(`Age`가 검사 경과 시간보다 길면 검사 전부터 CDN이 들고 있던 응답, `MISS`·`Age 0`이면 원본이 직접 준 404라 진짜 미반영 가능성). 몇 분 뒤 새 글 주소를 직접 열어 보고, 계속 안 열리면 글의 `published`·`date`·permalink와 빌드 로그를 AI에게 확인시킵니다.
- **한계**: 가장 새 글만 봅니다(이미지 교체 같은 커밋의 반영은 못 봄. 승인 흐름에서 더 새 글이 이미 있는데 오래된 초안을 병합하면 그 글은 따로 확인되지 않습니다). 빌드가 실패하면 `사이트 빌드`가 먼저 빨강이고 `사이트 반영 확인`은 건너뛰어집니다. 워치독이 이 빨강을 "빌드 실패" 문구로 설명하는 알려진 문제가 있습니다(7장).
- **수동으로 누르면 안 될 때**: 위험은 낮습니다(같은 내용 재공개). "Use workflow from"은 main으로 둡니다.

### 6-5. `[공통] 발행 중단 감시·알림` (`watchdog.yml`)

- **하는 일**: 발행이 조용히 멈추는지 보고, 문제가 있을 때만 이슈를 엽니다. 글·파일은 바꾸지 않습니다(job `발행 상태 점검`).
- **언제 도나**: 자동 — cron `30 3,15 * * *`(UTC) = 한국 12:30·00:30. 보통 몇 시간 늦게 돕니다. 수동 가능(입력 없음). 실행 제목 `[공통] 발행 중단 감시 · 정기/수동`.
- **권한·시크릿**: contents 읽기, actions 읽기, pull-requests 읽기(승인 흐름의 열린 초안 PR 을 세기 위해, 읽기만), issues 쓰기. 시크릿 없음. 변수 `PIPELINE_PAUSE`가 켜지면 알림을 만들지 않습니다.
- **알림 방식**: (블로그, 코드)마다 이슈 하나를 유지합니다. 제목은 `[Watchdog] 블로그key: 코드`, 라벨 `watchdog`. 소유자를 담당자로 지정하고 본문에서 @멘션하며, 열려 있는 동안 본문을 최신으로 고칩니다. 심각 건이 48시간 지나도 풀리지 않으면 코멘트로 다시 알리고, 조건이 풀리면 코멘트를 남기고 자동으로 닫습니다. 한 번에 새로 만드는 이슈는 5건까지(심각 건 먼저).
- **정상일 때**: 초록, 로그에 "이상 없음", Summary에 점검 결과 표(블로그·모드·마지막 글·최근 7일 글 수). 정지(`mode: off`)한 블로그는 감시하지 않습니다.
- **빨강이면**: **이번 점검에서 새로 생긴 심각 건이 있다**는 뜻입니다(3-7). 이미 알린 건이 이어지는 동안은 초록입니다.
- **수동으로 누르면 안 될 때**: 없음(이슈를 열거나 닫을 수는 있음).

| 코드 | 수준 | 쉬운 말 | 운영자가 할 일 |
|---|---|---|---|
| `STALE` | 심각 | 마지막 글(또는 초안) 이후 Chance는 36시간, Blogger는 50시간이 넘게 새 글이 없음. 기준은 글 파일이 **추가된** 커밋 시각이라 이미지 교체는 세지 않음(승인 흐름에서는 PR 을 병합한 시각) | 3-2 순서로 원인을 찾습니다 |
| `NO_POSTS_DAY` | 경고/심각 | 자동 게시(`auto`) 블로그에서 한국시간으로 닫힌 하루 기준 어제 새 글이 0건이면 경고, 그제도 0건이면 심각. 오늘 새 글이 나왔으면 회복. `STALE`이 울리면 중복 알림 안 함 | 3-2 |
| `DRAFT_WAITING` | 경고 | (승인 흐름을 켠 뒤에만) 열린 초안 PR 이 있는 동안 위 `STALE`·`NO_POSTS_DAY` 대신 올라옵니다. 새 글이 없는 것은 멈춤이 아니라 내 승인을 기다리는 초안 때문이라는 뜻입니다(대기 건수·가장 오래된 초안이 기다린 시간이 본문에 있음) | 초안 PR 을 읽고 병합하거나 닫습니다(3-17). 닫거나 병합해 초안이 없어지면 자동으로 닫히고, 초안 없이 글이 안 나오면 `STALE`이 울립니다 |
| `FAIL_STREAK` | 심각 | 최근 3회 기록이 모두 실패(`publish_failed`·`llm_failed`; 이력에 상태가 있는 Blogger에만 해당) | 6-3의 코드표와 4-2의 키·토큰 만료를 확인하고 로그를 AI에게 전달합니다 |
| `RUN_FAIL_STREAK` | 심각 | 그 워크플로가 최근 3회 연속 빨강 | 3-7 |
| `PAGES_NOT_DEPLOYED` | 심각 | 글 커밋 뒤 30분이 지났는데 main의 성공한 `[공통] 사이트 자동 배포` 실행이 없음 | 3-7의 `[공통] 사이트 자동 배포` 줄 |
| `STATE_CORRUPT` | 심각 | 이력 파일이 손상되어 읽지 못함 | **직접 고치지 말고** AI에게 복구를 요청합니다(이력 파일은 중복 방지 기록이라 잘못 고치면 중복 글이 생길 수 있음) |
| `PAGES_FAILED` | 경고 | 가장 최근 `[공통] 사이트 자동 배포` 실행이 실패 | 3-7 |
| `REJECT_STREAK` | 경고 | 최근 5회 연속 검사 탈락(Blogger에만 해당) | 요약·로그의 `GATE_REJECTED` 사유(6-3)를 AI에게 전달합니다. 프로필·언어·톤을 바꾸는 일은 운영자 채팅 승인이 필요합니다 |
| `UNPUBLISHED` | 경고 | 자동 게시(`auto`)인데 가장 최근 실행이 게시 없이 저장소 초안만 남김 | 게시용 시크릿이 없어서일 수 있습니다(3-12). 지금은 Blogger가 정지라 열리지 않습니다 |
| `NO_ACTIVITY` | 경고 | 발행·초안 기록이 전혀 없음 | 그 블로그의 워크플로가 한 번이라도 성공했는지 Actions에서 봅니다(3-7) |

### 6-6. `[Chance] 이슈 수정 요청 처리(수정안 PR 만들기)` (`issue-edit.yml`)

- **하는 일**: 이슈 양식으로 접수된 수정 요청을 검사·수정해 **PR로** 올립니다. main에 직접 반영하지 않습니다(job `수정안 만들기`).
- **바꾸는 것**: 라벨 4개(`blog-control`·`edit:page`·`edit:image`·`issue-edit-done`) 만들기·갱신, 브랜치 `issue-edit/번호-대상-r실행번호` + 커밋 + PR(`Fixes #번호`), 이슈 코멘트와 표식 라벨 `issue-edit-done`, 그 브랜치의 `[공통] 저장소 규칙·테스트 자동 검사` 수동 실행 요청.
- **언제 도나**: 자동 — 이슈가 **새로 열릴 때만**. 작성자가 소유자·멤버·협업자이고 라벨 `blog-control`이 있거나 제목이 `[페이지 수정]`·`[이미지 변경]`으로 시작해야 합니다. 수동 가능.
- **수동 입력**: `issue_number`(필수, 1~999999999의 숫자, 아니면 첫 단계에서 실패)·`연습 실행`(`dry_run`, 기본 체크: 파일·PR·코멘트 없음).
- **권한·시크릿**: job에 contents·issues·pull-requests·actions **쓰기** 4종(축소는 예정, 7장). `GEMINI_API_KEY`·`UNSPLASH_ACCESS_KEY`는 AI 단계에만. 같은 이슈의 실행은 이슈별 대기열에서 차례로 돕니다.
- **한 이슈는 한 번만**: 번호 형식을 첫 단계에서 검사하고, 이미 처리했는지(원격 브랜치 `issue-edit/번호-…` 또는 표식 라벨 `issue-edit-done`)를 보고 코멘트만 남깁니다(연습 실행은 예외).
- **이슈에 달리는 응답 코멘트**
  - ✅ "수정안을 PR 로 만들었습니다": PR 링크가 있습니다. 검토 후 병합하면 반영됩니다.
  - ✅ "수정 브랜치를 만들었습니다": PR 자동 생성 권한이 없어 링크의 "Create pull request"를 눌러야 합니다(3-6).
  - ⚠️ "수정하지 않았습니다"(**거부**): 사유가 적혀 있고 저장소는 그대로입니다. 고쳐서 새 이슈로 올립니다(3-4 표).
  - ℹ️ "이미 처리한 이슈입니다"(**중복**): 새 브랜치·PR을 만들지 않았습니다. 기존 브랜치·PR을 확인하고, 더 고칠 것은 새 이슈로 올립니다.
  - ❌ "처리 중 오류가 발생했습니다"(**오류**): 저장소는 그대로이고 원인은 Actions 로그에 있습니다. ❌ "수정안은 만들었지만 브랜치·PR 단계에서 실패했습니다"도 로그를 봅니다.
  - **코멘트 없음**(**처리 안 함**): PR이거나 작성자 권한이 없는 이슈입니다.
- **수동으로 누르면 안 될 때**: 연습을 풀고 이미 처리한 이슈를 다시 돌리는 것(코멘트만 달림). 연습이어도 AI 호출과 로그의 요청문 출력은 있습니다(3-10).

### 6-7. `[공통] PR 변경 범위 검사` (`pr-scope-check.yml`)

- **하는 일**: PR 제목·본문의 `Fixes #번호`로 요청 이슈를 찾아 "요청한 범위만 바뀌었나"를 판정하고 PR에 코멘트 1개를 남깁니다(다시 돌면 고침). job `이슈 요청 범위 확인`.
- **언제 도나**: 자동 — PR이 열림·갱신·다시 열림·draft 해제될 때. 같은 저장소 브랜치의 PR만(포크 PR은 건너뜀). 수동: `pr_number`(필수).
- **권한·시크릿**: contents 읽기, pull-requests 쓰기, issues 읽기. 시크릿 없음. 항상 **기본 브랜치의 코드**로 실행하고 PR 쪽 파일은 읽기만 합니다.
- **정상일 때**: PR에 "요청 범위 검증" 코멘트. ✅ 통과 / ⚠️ 확인 필요(AI가 쓴 문장은 직접 읽기) / ❌ 요청 범위 밖(이때 실행이 빨강, 설계된 동작).
- **주의**: `Fixes #번호`가 없으면 검사 없이 초록입니다. 판정은 병합을 막지 못합니다. 봇이 만든 PR에서는 자동으로 안 돕니다(3-11).

### 6-8. `[공통] 이슈 양식 페이지 목록 갱신` (`sync-issue-form.yml`)

- **하는 일**: `pages.json`(고정 페이지 목록)과 이슈 양식의 "대상 페이지"·"수정 항목" 드롭다운을 최신으로 맞춥니다(job `목록 동기화`).
- **바꾸는 것**: `pages.json`과 `.github/ISSUE_TEMPLATE/page-edit.yml` 두 파일만 main에 직접 커밋합니다(바뀐 것이 없으면 "변경 없음"). 사이트 배포는 요청하지 않습니다.

- **권한·시크릿**: contents 쓰기. 시크릿 없음.
- **정상일 때**: 초록, 대개 "변경 없음". 새 페이지에 `editable: true`를 넣으면 "chore: pages.json·이슈 양식 자동 동기화" 봇 커밋이 생깁니다.

### 6-9. `[공통] 저장소 규칙·테스트 자동 검사` (`guardrails.yml`)

### 6-10. `[공통] 확인 필요 모음` (`ops-inbox.yml`)

- **하는 일**: 운영자가 해야 할 일·확인할 일(워치독 알림, 병합 대기 PR, 실패한 워크플로, 승인 대기 실행, 일시정지, Blogger 게시 설정 등)을 이슈 `[운영] 확인 필요 모음`(라벨 `ops-inbox`)과 이 실행의 요약에 모읍니다(job `확인 필요 항목 모으기`). 이슈 하나만 유지하고, 새로 해야 할 일이 생기면 소유자에게 @멘션 코멘트를 남깁니다.
- **바꾸는 것**: 이슈·코멘트·라벨뿐입니다(파일·브랜치는 바꾸지 않음). 권한은 코드·실행 기록·검사 결과·PR 읽기 + issues 쓰기입니다.
- **언제 도나**: 자동 — cron `40 */2 * * *`(UTC, 2시간 간격 예약이지만 GitHub가 늦추거나 건너뛰어 실제로는 보통 3~6시간 간격일 것입니다. 예상: 정기 실행의 실제 간격은 아직 관측 전). 수동 가능: `연습 실행`(`dry_run`, 기본 꺼짐)을 체크하면 이슈·코멘트를 쓰지 않고 실행 요약만 만듭니다. 실행 제목 `[공통] 확인 필요 모음 갱신 · 정기/수동/수동(연습: 이슈·코멘트 안 씀)`.
- **정상일 때**: 초록, 이슈 본문 맨 위에 요약 줄(`지금 해야 할 일 N건 · 확인하면 좋은 것 N건 · 참고 N건`)과 항목이 있는 구역이 나옵니다. 할 일이 없다는 신호는 "지금 해야 할 일 0건"입니다. 항목이 하나도 없을 때만 나오는 "지금 확인할 것이 없습니다" 문구는, 블로그별 마지막 글 현황이 늘 '참고'에 들어 있어 실제로는 거의 보이지 않습니다. 일부 소스를 읽지 못한 것은 빨강이 아니라 "조회 실패" 항목으로 남습니다. 같은 입력으로 바로 다시 실행하면 이슈 본문·코멘트가 바뀌지 않아야 합니다(요약에 "변경 없음").
- **빨강이면**: 이슈·코멘트를 쓰지 못했거나(권한·Issues 기능 꺼짐 등) 스크립트 오류입니다. Actions 실패 알림이 갑니다.
- **일시정지와의 관계**: `PIPELINE_PAUSE`가 켜져 있으면 "지금 해야 할 일"에 일시정지 항목이 올라옵니다. 정지 중에는 워치독이 새 알림을 만들지 않아 이 항목이 "아직 멈춰 있다"는 유일한 표시입니다.
- **한계**: 보통 3~6시간 늦을 것입니다(예상). **이 모음 자체가 멈춰도 이슈에는 표시되지 않으니**, 이슈가 갱신되지 않는 것 같으면 Actions에서 `[공통] 확인 필요 모음`의 마지막 실행 시각을 봅니다. 열린 이슈는 처음 100건, PR은 처음 8건의 상세만 봅니다.
- **끄려면**: Actions → `[공통] 확인 필요 모음` → "⋯" → **Disable workflow**. 이슈는 남으니 닫으면 됩니다.
- **켠 뒤 확인한 것**: 이슈 생성은 확인됨(#22, 2026-10-25 19:18 KST 첫 실제 실행). 후속 수정 뒤의 실제 실행에서 이름 표시가 고쳐졌고, 곧바로 한 번 더 실행하면 "변경 없음(이슈를 쓰지 않았습니다)"으로 끝났습니다(20:51).
- **아직 확인하지 못한 것**: 휴대폰 알림 도착, 닫은 이슈의 다시 열림(닫은 뒤 새 "해야 할 일"이 생겼을 때), 정기 실행의 실제 간격([`OPS_INBOX.md`](./OPS_INBOX.md) §8).

### 6-11. `pages-build-deployment` (GitHub 관리)

- **정체**: Pages 설정이 "브랜치에서 배포"일 때 GitHub가 돌리는 내장 워크플로입니다(외부 지식). 저장소에 파일이 없고 우리가 고칠 수 없습니다.
- **이 저장소**: Pages 소스가 **GitHub Actions**(2026-10-25 운영자 기록)라서 예전 흔적이며 지금은 쓰이지 않아야 합니다. 가장 최근 실행 날짜는 미확인입니다.
- `[공통] 사이트 자동 배포`와의 차이: `[공통] 사이트 자동 배포`는 우리 파일(`pages.yml`)로 직접 빌드·공개하고, 이 항목은 GitHub 자동 방식입니다. 둘이 함께 켜지면 이중 배포일 수 있습니다(동작은 미확인).
- **누르지 않습니다.** 새 실행이 계속 생기면 Settings → **Pages** → Source를 다시 확인합니다.

### 6-12. `[티스토리] 초안 패키지 만들기` (`tistory.yml`)

- **하는 일**: 레지스트리의 `platform: tistory` 블로그를 하나씩 처리합니다. 주제 선정 → Gemini 글 → 검사 → **GitHub 이슈 1개(초안 패키지)** → 기록. 글을 공개하지 않습니다(운영자가 3-19대로 직접 발행). job은 `대상 블로그 계획`(plan) → `초안 패키지 생성 (블로그key)`.
- **지금 상태**: 레지스트리에 티스토리 블로그가 없어(블로그 주소·주제 입력 대기) plan 단계가 "대상 0개" 안내(`::notice::`)와 Summary(제목 줄 `### 티스토리 초안 패키지 만들기`, "결과: **대상 0개**")를 남기고 `초안 패키지 생성` job은 건너뜁니다(초록). 이슈·커밋은 없습니다.
- **바꾸는 것(블로그가 있을 때)**: GitHub 이슈 1개(라벨 `초안`·`채널:티스토리`)와, 블로그별 이력 파일·`_…_drafts/` 저장소 사본을 main에 직접 커밋("🤖 [블로그key] 초안 패키지 기록", push 3회 재시도). 사이트 배포는 요청하지 않습니다.
- **언제 도나**: 자동 — cron `20 5 * * *`(UTC) = 한국 14:20. 수동 가능. 실행 제목 `[티스토리] 초안 패키지 · 정기`, `· 수동(초안 이슈 만들기)`, `· 수동(연습: 이슈 안 만듦)`.
- **수동 입력**: `blog`(비우면 티스토리 블로그 전체, 오타면 plan 단계가 빨강)·`topic`(주제 지정, 하루 상한은 건너뛰지만 열린 초안 3건 상한은 건너뛰지 못함, 주제 가드레일에 걸리면 `TOPIC_BLOCKED`)·`연습 실행`(`dry_run`, **기본 켜짐**). 연습은 가짜 AI 응답으로 이슈 본문을 만들어 Summary에 미리 보여 줄 뿐 **Gemini와 GitHub를 부르지 않습니다**(호출 0회, 이슈·커밋·하루 상한 소진 없음). **체크를 풀면** 실제 Gemini로 글을 만들어 초안 이슈 1개를 만들고 그날 하루 상한을 씁니다.
- **권한·시크릿**: plan은 contents 읽기, 생성은 contents 쓰기와 **issues 쓰기**(그 밖의 권한 없음). 시크릿은 `GEMINI_API_KEY` 하나와 워크플로가 자동으로 받는 `GITHUB_TOKEN`뿐이고, 변수 `PIPELINE_PAUSE`가 있습니다. **티스토리 계정 정보(아이디·비밀번호·쿠키·세션)는 저장하지도 쓰지도 않습니다.**
- **정상일 때**: 이력 마지막 항목의 `status`가 `package_issued`(`url`은 이슈 주소)이고 Summary "결과: **package_issued**"에 이슈 링크가 있습니다. 같은 날 다시 실행하면 `DAILY_CAP`으로 건너뜁니다.
- **실패하면**: 로그의 `[SKIP] code=` 줄로 판단합니다(아래 표). 이슈를 만드는 단계(`stage=issue`)에서 5xx·시간 초과처럼 **만들어졌는지 모르는** 실패였으면 안내에 따라 **재실행 전에 라벨 `초안` 이슈 목록을 먼저 확인합니다**(이슈가 만들어졌을 수 있습니다 — 이슈 만들기 요청은 한 번만 보내고 모호하면 다시 만들지 않고 멈춥니다). 권한 오류처럼 HTTP 4xx 로 거절된 실패는 만들어지지 않았으니 확인 없이 설정을 고치고 다시 실행하면 됩니다. 글이 비어 이슈를 만들 수 없는 `invalid_draft`·`too_long`은 `stage=build`입니다.

| 코드 | 뜻 | 색 |
|---|---|---|
| `PAUSED`·`MODE_OFF`·`DAILY_CAP` | 일시정지·정지된 블로그·오늘 상한 도달(수동 `topic`은 상한을 건너뜀) | 초록 + 파란 안내 |
| `PACKAGE_BACKLOG` | 같은 채널에 열린 `초안` 이슈(라벨 `폐기`가 붙은 것은 제외)가 3건 이상이라 새 초안을 만들지 않음(3-19) | 초록 + 파란 안내 |
| `NO_TOPIC`·`GATE_REJECTED` | 고를 주제 없음·재작성 3번 모두 검사 탈락 | 초록 + 노란 경고 |
| `TOPIC_BLOCKED` | 수동 `topic`이 주제 가드레일에 걸림. Gemini·GitHub를 부르기 전에 멈추고 걸린 낱말이 요약에 보임 | **빨강**(종료 2) |
| `INVALID_PUBLISH`·`AUTH_CHECK_UNSUPPORTED` | 이 채널에서 쓰지 않는 `BLOGGER_PUBLISH`·`--auth-check`를 씀(워크플로 입력에는 없어 로컬 실행에서만 생김) | **빨강**(종료 2) |
| `SECRETS_MISSING` | `GEMINI_API_KEY`(로컬 실행에서는 `GITHUB_TOKEN`·`GITHUB_REPOSITORY`도) 없음. 이름만 보이고 글을 만들기 전에 종료 2 | **빨강** |
| `EXPAND_FAILED`·`LLM_FAILED` | 주제 확장·글 생성 AI 호출 실패 | **빨강** |

| `HISTORY_WRITE_FAILED` | 이슈는 만들어졌는데 이력 파일을 쓰지 못함(종료 1). 같은 날 다시 실행하기 전에 라벨 `초안` 이슈 목록을 먼저 확인합니다(이번 결과의 이슈 번호·주소는 이 단계의 로그에 있습니다) | **빨강** |

### 6-13. `[네이버] 초안 패키지 만들기` (`naver.yml`)

- `[티스토리] 초안 패키지 만들기`(6-12)와 구조·입력·권한·코드표가 같고 채널만 다릅니다: `platform: naver` 블로그, 이슈 제목 `[초안][네이버] …`·라벨 `채널:네이버`, cron `20 6 * * *`(UTC) = 한국 15:20, 실행 제목 `[네이버] 초안 패키지 · …`.
- 이슈 본문의 본문 구역이 다릅니다: HTML 상자 대신 **서식 있는 글**(이슈 화면에서 선택·복사)과 **평문 상자**입니다(3-19). 글감은 Chance 글의 각색이 아니라 이 블로그의 자체 주제입니다(원고 변형 복제 금지).
- 지금은 레지스트리에 네이버 블로그가 없어 정기 실행은 "대상 0개"로 초록입니다.

## 8. 용어 풀이

|---|---|

| 초록 ✓ / 빨강 ✗ / 회색 | 오류 없이 끝남(할 일이 없어 끝나도 초록) / 오류로 끝남 / 취소됨(새 실행이 오면서 취소, 정상) |

| 연습 실행(dry run) | 파일·커밋·게시 없이 흐름만 보는 실행. 기본은 가짜 AI 응답이라 Gemini 한도를 쓰지 않음(`real_ai`를 체크하면 실제 호출. 이미지 교체 연습은 Unsplash 검색을 실제로 부름) |
| 슬롯 | 글을 만드는 시각 칸. Chance는 한국시간 9시·18시 |
| 승인 흐름·초안 PR | Chance 글을 main 에 바로 올리지 않고 `[초안][Chance]` PR 로 올려 내가 병합해야 공개하는 방식(레지스트리 `publish_flow: pr`, 지금 꺼짐, 3-17). 병합하면 공개, 닫으면 폐기 |
| 모드 | `off` 정지 · `draft` 초안(공개 안 함. Blogger는 게시용 시크릿이 있으면 Blogger 초안함에 올리고 없으면 저장소 파일에만 저장) · `package` 초안 패키지(티스토리·네이버 전용, 글을 GitHub 이슈로 보여 주기만 함) · `auto` 자동 게시. 블로그 항목에 직접 적어야 함(없으면 검증기 REG-1이 오류로 막음) |
| 게이트 | 게시 직전 자동 검사(길이·형식·금지 주제·중복·출처 등). 탈락하면 게시하지 않음 |
| 시크릿(Secrets)·변수(Variables) | 저장소에 넣는 비밀 값(API 키 등. 문서·이슈·채팅에는 이름만 적음) / 일반 설정 값(`PIPELINE_PAUSE` 같은 것) |
| 이슈(Issue) | GitHub의 게시판 글. 수정 요청·워치독 알림·`[운영] 확인 필요 모음`이 모두 이슈로 올라옴 |

| 라벨 | 이슈·PR에 붙이는 이름표(`watchdog`·`ops-inbox`·`초안`·`채널:티스토리` 등). 알림을 찾을 때 거름망으로 씀 |
