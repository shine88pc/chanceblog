## 먼저 읽기

1. **초록 체크는 "프로그램이 오류 없이 끝났다"는 뜻입니다.** "글이 올라갔다"는 뜻이 아닙니다.
   - 2026-10-25 진단에서 두 블로그 모두 글 없이 초록으로 끝난 날이 며칠 있었습니다.
   - 글이 올라갔는지는 5장의 "정상일 때"로 확인합니다.
2. 시간은 모두 **한국시간(KST)** 입니다. 설정 파일의 시각은 UTC라서 9시간을 더합니다. GitHub는 예약 실행을 제때 시작하지 않습니다(1장 시간표).
3. **미확인**은 코드·기록으로 확인하지 못했다는 뜻입니다. **예정**은 아직 반영되지 않은 계획이라 지금 동작이 아닙니다.
4. 이 문서는 **공개 사이트에 게시**됩니다. 비밀 값·개인정보·수익·방문자 수치는 적지 마세요. 시크릿 **이름**만 적습니다.
5. GitHub 메뉴 이름과 누르는 순서는 외부 지식이라 이 저장소에서 시험하지 못했습니다.
   - 화면이 다르면 **실제 화면에서 한 번 확인**하세요.
   - 모바일 앱에 없는 메뉴는 브라우저의 "데스크톱 사이트"로 엽니다(앱 지원 여부는 미확인).
6. 공통 이동: 저장소 → **Actions** → 워크플로 이름 → **Run workflow**(수동 실행). 웹에서는 왼쪽 목록에서 워크플로를 고릅니다.

## 2. 이럴 땐 이렇게

### 2-1. 글을 지금 한 편 올리고 싶다

**가능 여부**: Chance만 가능(주제는 고를 수 없음). Blogger는 정지라 불가.

1. 저장소 → **Actions** → **Chance_Blog Full-Auto Engine** → **Run workflow**
2. `dry_run`의 **체크를 해제**하고 `fix_images`는 꺼 둡니다 → **Run workflow**
3. 끝나면 그 실행을 열어 맨 위 **Summary**의 "결과" 줄을 봅니다.
4. `PUBLISHED`면 한·영 글이 만들어진 것입니다. 곧 **Deploy GitHub Pages**가 자동으로 뜹니다. 그것이 끝나면 사이트(`https://shine88pc.github.io/chanceblog/`)에서 글을 확인합니다.
5. 다른 결과는 5-1의 "결과 코드" 표에서 뜻을 찾습니다.

주의:
- Gemini를 실제로 호출합니다(사용량이 늘어납니다).
- 수동 글은 슬롯 기록이 남지 않습니다. 같은 시간대의 정기 실행이 글을 **한 편 더** 만들 수 있습니다(코드와 단위 테스트로 확인).
- 주제는 고를 수 없습니다. 그날의 분야를 추첨 순서대로 시도해 기사가 있는 첫 분야에서 만듭니다.
- 기사가 하나도 없으면 빨강으로 끝납니다(`ALL_LANES_EMPTY`). 시험 삼아 누르지 마세요.
- Blogger Generate는 눌러도 "대상 0개"로 끝납니다. **`BLOGGER_*` 시크릿을 등록하지 마세요.**
- 주제를 정해 쓰는 글 기능은 아직 없습니다(예정).

### 2-2. 기존 글의 이미지를 바꾸고 싶다

**가능 여부**: 가능. 단 2026-10-25 기준 Actions에서 실제로 처리한 기록이 0건이라 첫 결과는 **미관측**입니다.

1. 저장소 → **Issues** → **New issue** → **기존 게시글 이미지 변경** 양식
2. "게시글 주소 또는 제목"에 글의 공개 주소를 붙여 넣습니다(정확한 제목도 가능).
3. "원하는 이미지 설명"에 장면을 구체적으로 씁니다.
4. **Submit new issue**. 이슈가 열리면 **Issue Edit**가 자동으로 돕니다.
5. 이슈에 "✅ 수정안을 PR 로 만들었습니다" 코멘트와 PR 링크가 달리면 PR을 엽니다.
6. 2-10의 확인 항목을 본 뒤 **Merge pull request**. 병합하면 Deploy GitHub Pages가 자동으로 돕니다.
7. 사이트에서 이미지를 확인합니다.

참고:
- "⚠️ 수정하지 않았습니다"가 달리면 사유대로 고쳐 **새 이슈**를 만듭니다. 이미 만든 이슈는 고쳐도 다시 처리되지 않습니다.
- 이미지는 Unsplash에서 찾고, 주소가 `https://images.unsplash.com/`로 시작하는 것만 씁니다. 지금 이미지와 다른 글이 쓴 이미지는 피합니다.
- 미확인: 모바일 앱에서 이슈 양식이 보이는지, PR에 "Approve workflows to run" 버튼이 뜨는지.

### 2-3. 고정 페이지의 문구·제목·링크를 바꾸고 싶다

**가능 여부**: 가능(첫 실제 처리는 미관측). 대상은 소개(about)·카테고리(categories)·문의(contact)·개인정보처리방침(privacy).

1. 저장소 → **Issues** → **New issue** → **고정 페이지 수정** 양식
2. **대상 페이지**와 **수정 항목**을 고르고 아래 표대로 칸을 채웁니다.
3. **Submit new issue** → PR 링크가 달리면 2-10을 확인한 뒤 **Merge pull request**.

| 하고 싶은 일 | 수정 항목 | 쓰는 법 |
|---|---|---|
| 문구 바꾸기 | 문구 수정 | 변경 전=파일 원문 그대로, 변경 후=새 문장 |
| 링크 바꾸기 | 링크 변경 | 변경 전=현재 주소, 변경 후=새 주소 |
| 제목·설명(SEO) | SEO 메타 수정 | 변경 후=`title:` 또는 `description:` 줄 |
| 문단·구조 바꾸기 | 섹션/레이아웃 변경 | 원하는 결과를 구체적으로(AI가 일부만 수정) |

주의:
- "변경 전"은 화면에 보이는 글이 아니라 **파일 원문**(마크다운)과 글자까지 같아야 찾습니다.
- 소개·문의·개인정보처리방침은 광고 심사 대상이라 **소유자 요청만** 처리합니다. PR 본문에 "병합이 곧 승인" 경고가 붙습니다.
- 첫 화면(`index.html`)·레이아웃·워크플로·코드는 어떤 요청으로도 못 고칩니다. 한 요청은 한 파일만 고칩니다.
- 카테고리 페이지는 본문이 자동 목록이라 문구 교체 대상이 거의 없습니다(제목·설명은 가능).

### 2-4. 새 페이지가 수정 대상 목록에 없다

**가능 여부**: 가능. 단 저장소 맨 위 폴더(루트)의 `.md`·`.html` 파일만 됩니다. 하위 폴더 페이지는 수정 대상이 될 수 없습니다.

1. 새 페이지 파일 맨 위 `---` 줄 사이(front matter)에 `editable: true` 한 줄을 넣고 main에 저장(commit)합니다. 직접 하기 어려우면 AI에게 맡기세요.
2. **Sync Issue Form**이 자동으로 돕니다. 새 페이지면 "chore: pages.json·이슈 양식 자동 동기화" 봇 커밋이 생깁니다.
3. 이후 양식의 대상 페이지 목록에 나타납니다.

안 될 때:
- 자동 실행이 안 보이면 Actions → **Sync Issue Form** → **Run workflow**.
- 로그가 "변경 없음"이면 `editable: true`의 철자와 위치(front matter 안)를 확인합니다.
- 파일 이름이 영문·숫자·`_`·`-`(40자 이하)가 아니면 front matter에 `edit_id: faq`처럼 id를 적습니다.
- 기존 페이지 4개는 `edit-spec.yml`에 고정되어 있어 건드릴 필요가 없습니다.

### 2-5. 이슈를 만들었는데 아무 일도 없다 / PR 대신 링크만 왔다

확인 순서:
1. Actions에 **Issue Edit** 실행이 새로 생겼나? 없으면 아래 둘 중 하나입니다.
   - 작성자가 소유자·멤버·협업자가 아님.
   - 제목이 `[페이지 수정]`·`[이미지 변경]`으로 시작하지 않고 `blog-control` 라벨도 없음(양식을 안 쓴 이슈). 양식으로 새 이슈를 만드세요.
2. 이슈를 **나중에 고쳤거나 다시 열었다면** 처리되지 않습니다(이슈가 새로 열릴 때만 돕니다). 새 이슈를 만드세요.
3. 실행은 있는데 이슈에 코멘트가 없으면 실행을 열어 빨간 단계의 로그를 봅니다(2-6).
4. 코멘트가 "⚠️ 수정하지 않았습니다 + 사유"면 사유대로 고쳐 새 이슈를 만듭니다.
5. "수정 브랜치를 만들었습니다" 코멘트와 링크만 왔으면 링크의 **Create pull request**를 누릅니다.
   - 설정 "Allow GitHub Actions to create and approve pull requests"(Settings → Actions → General)가 꺼졌을 수 있습니다.
   - 2026-10-25 기록은 켜짐이라 보통은 PR로 옵니다.
6. 그 밖의 증상은 [`ISSUE_EDITS.md`](./ISSUE_EDITS.md)의 문제 해결표를 봅니다.

### 2-6. 빨간 ✗가 떴다

공통 순서:
1. Actions 목록에서 빨간 ✗ 실행을 엽니다. 맨 위 **Summary**의 "결과" 줄을 읽습니다.
2. 빨갛게 표시된 단계를 눌러 로그 끝의 `::error::`·`[SKIP] code=`·`ERROR` 줄을 읽습니다.
3. 아래 표에서 워크플로를 찾습니다.
4. 원인을 모르겠으면 그 줄들을 AI에게 보여 주세요(비밀 값이 섞였는지 먼저 확인).

| 워크플로 | 대표 원인 | 먼저 할 일 |
|---|---|---|
| Chance_Blog | 모든 분야에 기사 없음, Gemini 키·한도, push 거부 | Summary 결과 → 아래 목록 |
| Blogger Generate | 게시용 시크릿 누락, AI 실패, `blog` 오타 | 로그의 시크릿 이름 확인 |
| Deploy GitHub Pages | 사이트 빌드 오류(문서 속 Liquid 문법 등) | "Build Jekyll site" 로그 |
| Guardrails | 규칙 위반, 테스트 실패 | "ERROR [검사ID] 파일:줄" |
| Watchdog | 스크립트 오류(드묾) | 로그 확인 후 다시 실행 |
| Issue Edit | 처리 중 오류 | 이슈 코멘트와 로그 |
| PR Scope Check | 범위 밖 판정(설계된 빨강) | PR 코멘트 |
| Sync Issue Form | 페이지 id 중복, push 3회 실패 | 로그의 `[오류]` 줄 |

**Chance가 빨강일 때**: 같은 빨강이 하루에 여러 번 보일 수 있습니다. 정기 실행은 그 시간대 글이 생길 때까지 계속 다시 시도합니다.
1. 결과가 `ALL_LANES_EMPTY`: 6개 분야 모두 검증을 통과한 기사가 없었습니다. 운영자가 할 일은 없습니다. 며칠 계속되면 Summary 표의 탈락 사유를 AI에게 전달하세요.
2. 로그에 "GEMINI_API_KEY 환경 변수가 없습니다" 또는 "모든 Gemini 모델 호출 실패": 키·한도 문제입니다. 3-2를 봅니다.
3. 로그에 "대표 이미지를 2개 확보하지 못했습니다": 이미지 검색 문제입니다. `UNSPLASH_ACCESS_KEY`와 한도를 확인합니다.
4. 커밋 단계의 push 거부: 재시도가 없습니다. 다음 정기 실행이 다시 시도합니다.
5. **수동 실행**은 후보가 전부 탈락해도 빨강입니다("기존 글과 겹치지 않는 주제를 만들지 못했습니다").
6. 초록인데 노란 경고(`ALL_REJECTED`·`NO_CANDIDATES`)가 있으면 다음 실행을 기다립니다(5-1 표).

참고: 회색 "취소됨"은 정상입니다(새 실행이 이전 실행을 취소함). 오래된 빨강은 지난 일입니다: Deploy GitHub Pages #58·#59(문서 속 Liquid 문법, 결함 D-24, 해결됨), Blogger Generate #1·#2(2026-10-20, 이후 정상).

### 2-7. 글이나 이미지가 중복됐다

1. **더 만들지 않게 먼저 멈춥니다**(2-8). 고치려고 워크플로를 다시 누르지 마세요.
2. 원인을 봅니다. Actions에서 그 시간대 Chance 실행의 이벤트가 "Manually run"인지 확인합니다.
3. `history.json`에서 `slot` 값이 비어 있는(`null`) 항목이 수동 글입니다.
4. **글이 중복**이면 자동화는 글을 지우지 않습니다.
   - 해당 글 파일(한·영 2개)을 직접 삭제하거나 AI에게 명시적으로 요청하세요(삭제는 사용자 승인 사항).
   - `history.json`은 중복 방지 기록이라 그대로 둡니다.
5. **이미지만 중복**이면 한 글은 2-2의 이미지 변경 양식을 씁니다.
6. 여러 글이면 Chance_Blog → **Run workflow** → `fix_images` 체크 + `dry_run` **체크 유지**로 먼저 실행합니다.
   - Summary의 "이미지 점검: 완료: 문제 N건" 줄과 로그의 "문제(duplicate)" 줄을 봅니다.
   - 맞으면 `dry_run`을 해제해 다시 실행합니다. **이 방식은 PR 없이 main에 바로 커밋됩니다.**

참고: 새 글은 이미 쓴 이미지를 피해 고르고, 기존 글과 제목이 비슷하면 후보에서 버립니다(코드 확인). 그래도 겹치는 경로는 미확인입니다.

### 2-8. 자동 발행을 잠시 멈추고 싶다

**가장 안전한 방법**: 저장소 변수 `PIPELINE_PAUSE`. **Chance와 Blogger를 함께** 멈추고 수동 실행도 멈춥니다.

1. 저장소 → **Settings** → **Secrets and variables** → **Actions** → **Variables** 탭 → **New repository variable**
2. Name에 `PIPELINE_PAUSE`, Value에 `true` → **Add variable**
3. 확인: Actions → Chance_Blog Full-Auto Engine → Run workflow(`dry_run` 체크 유지). Summary에 "일시정지"가 나오면 멈춘 것입니다(로그는 `[SKIP] code=PAUSED`).
4. **되돌리기**: 같은 화면에서 변수를 삭제합니다.

알아 둘 점:
- 멈춘 동안에도 실행은 시작되고 초록으로 끝납니다. 글·커밋만 없습니다.
- 나머지 워크플로(Deploy·Guardrails·Watchdog·Issue Edit·PR Scope Check·Sync)는 멈추지 않습니다.
- 36시간이 지나면 Watchdog이 `STALE` 이슈를 열 수 있습니다. 재개 후 글이 생기면 자동으로 닫힙니다.
- 코드가 고장 나 빨강이 계속되면 대신 Actions → 해당 워크플로 → "⋯" → **Disable workflow**를 씁니다. 되돌리기는 Enable workflow입니다(모바일 앱 메뉴는 미확인).
- 외부 지식: 공개 저장소는 60일간 활동이 없으면 예약 실행이 자동으로 꺼질 수 있습니다. 오래 멈췄다면 재개 뒤 예약 실행이 다시 생기는지 확인하세요.

### 2-9. 이슈 수정 시스템을 dry_run으로 점검하고 싶다

중요: **새 요청 이슈를 만드는 순간 Issue Edit가 실제로 처리합니다**(브랜치·PR·코멘트가 생김). dry_run은 **이미 만든 이슈**를 다시 점검할 때 씁니다.

1. 저장소 → **Actions** → **Issue Edit** → **Run workflow**
2. `issue_number`에 이슈 번호를 적고 `dry_run`은 **체크 유지**(기본) → **Run workflow**
3. 실행을 열어 맨 아래 단계 "DRY_RUN 결과 출력"을 봅니다. 파일·PR·코멘트는 생기지 않습니다.
4. `status`를 읽습니다: `ok`(수정안 있음) · `rejected`(범위·형식 위반, 사유 표시) · `ignored`(처리 대상 아님) · `error`(처리 중 오류).

주의:
- dry_run이어도 키가 있으면 Gemini·Unsplash를 실제로 호출할 수 있습니다.
- 로그에 요청 내용이 찍힙니다. 공개 저장소의 로그는 누구나 볼 수 있다고 보세요. 요청문에 비밀·개인정보를 쓰지 마세요.

**처음 시험하는 방법(권장)**: 광고 표면이 아닌 `categories`에 "SEO 메타 수정"으로 `title: 카테고리 (시험)`을 요청합니다. PR이 생기면 **병합하지 말고 닫습니다**(Close pull request). 2026-10-25 기준 Issue Edit와 PR Scope Check는 실행 기록이 0건입니다.

### 2-10. PR을 병합하기 전에 볼 것

PR → **Files changed**와 하단 **Checks**에서 봅니다. 병합을 막아 주는 규칙이 없으니 **눈으로 막아야** 합니다.

| 확인 | 어디서 | 정상 |
|---|---|---|
| 변경 파일 수 | Files changed | 1개(이슈 수정은 한 파일만) |
| 바뀐 줄 수 | PR 본문 "바뀐 줄: N줄" | 문구 교체는 1~3줄 안팎 |
| 광고 표면 파일 | Files changed의 파일 이름 | 요청과 무관하면 병합 금지 |
| 금지 경로 | Files changed의 파일 이름 | 보이면 병합 금지 |
| 검사 결과 | Checks, PR Scope Check 코멘트 | ✅ 통과 / ⚠️ 직접 읽기 / ❌ 병합 금지 |
| `Fixes #번호` | PR 본문 맨 끝 | 있어야 이슈가 닫히고 검사가 동작 |

- 광고 표면 목록: `index.html`·`privacy.md`·`about.md`·`contact.md`·`robots.txt`·`ads.txt`·`_config.yml`·`_includes/`·`_layouts/`·사이트 인증 html 2개.
- 금지 경로(일부): `.github/`·`pipeline/`·`scripts/`와 `.py`·`.yml`·`.json` 파일.
- 파일 전체가 바뀐 것처럼 보이면(줄 끝 변경 가능성) 병합하지 마세요. Checks에 빨강이 있어도 병합하지 않습니다.
- 요청한 광고 표면 페이지(about·contact·privacy)면 PR 본문 둘째 줄에 "⚠️ 광고 표면 페이지… 병합이 곧 승인" 인용 상자가 있어야 정상입니다.
- ❌가 나오면 PR에 "요청한 부분만 바꾸고 나머지는 되돌려 주세요"라고 답글을 답니다.
- PR Scope Check 코멘트가 없으면 Actions → **PR Scope Check** → **Run workflow** → `pr_number` 입력.
  - 봇이 만든 PR에서 자동 실행되는지는 **미확인**입니다(`ISSUE_EDITS.md`는 안 돈다고 적고, 다른 근거는 "승인 대기"로 뜬다고 함).
- Copilot PR은 하단의 **Approve and run workflows**를 눌러야 검사가 돕니다(미관측).
- 병합: **Merge pull request** → 확인. 병합하면 Deploy GitHub Pages가 자동으로 돕니다.

| 매주 5분 | Pull requests | 처리 안 한 수정 PR 없음 | 2-10 후 병합·닫기 |

- **정상 신호**: Chance 결과가 9시·18시 시간대마다 `PUBLISHED`(하루 최대 2번), 나머지 실행은 `OUT_OF_WINDOW`·`ALREADY_PUBLISHED`(정상 건너뜀). Blogger는 "대상 0개"(정지 중).
- **이상 신호**: 빨강, 며칠째 같은 노란 경고, Watchdog 이슈, 마지막 글이 36시간 넘음.
- 글이 올라왔는지 빨리 보려면 저장소 → **Commits**에서 "🤖 자동 포스팅/이미지 수정"을 찾습니다.

### 3-2. 키·토큰 교체

공통 규칙:
1. 값은 이 문서·이슈·PR·채팅·로그에 쓰지 않습니다. 새 값은 발급 화면에서 복사해 곧바로 GitHub 입력칸에만 붙입니다.
2. 순서는 **새 키 발급 → GitHub에 갱신 → 동작 확인 → 옛 키 삭제**입니다.
3. 유출이 의심되면 확인 전에 옛 키부터 폐기합니다([`SECURITY_GUARDRAILS.md`](./SECURITY_GUARDRAILS.md) §4-A). 한 번 공개된 값은 지워도 유출로 봅니다.
4. 입력 경로: Settings → **Secrets and variables** → **Actions** → **Secrets** 탭 → 이름 옆 연필 → 값 붙여넣기 → **Update secret**.

| 값 | 증상 | 갱신 |
|---|---|---|
| `GEMINI_API_KEY` | Chance 빨강, Issue Edit 오류 | AI Studio에서 새 키 → 수정 → 옛 키 삭제 |
| `UNSPLASH_ACCESS_KEY` | 조용함(예비 이미지, 이미지 변경 거부) | 개발자 화면에서 재발급 → 수정 |
| `BLOGGER_*` 4종 | 미등록. 지금 등록하지 않음 | 예정: 초안 모드 이후 절차 갱신 |
| `GITHUB_TOKEN` | 해당 없음 | 실행마다 자동 발급. 교체 불필요 |

`GEMINI_API_KEY` 교체 순서:
1. Google AI Studio에서 새 키를 만듭니다. 옛 키는 아직 지우지 않습니다.
2. 위 입력 경로로 `GEMINI_API_KEY`를 새 값으로 바꿉니다.
3. Actions → Chance_Blog Full-Auto Engine → Run workflow(`dry_run` 체크 유지). 로그에 "Gemini 모델 호출 성공"이 보이면 새 키가 동작하는 것입니다.
4. 그 줄이 안 보이면(후보 기사 없음 등) 확인이 안 된 것입니다. 다음 정기 실행의 결과를 봅니다.
5. 동작을 확인한 뒤 옛 키를 삭제합니다.

`UNSPLASH_ACCESS_KEY`가 만료·오류면 새 글이 예비 이미지로 대체되고(로그 "[경고] 검색 결과 없음, 폴백 풀 이미지 사용") 이미지 변경 이슈는 "찾지 못했습니다"로 거부됩니다. 예비 이미지도 없으면 글 저장이 실패(빨강)합니다.

`BLOGGER_*` 4종은 **지금 하지 않습니다**(예정). 나중에 필요한 것:
- Git·Python 설치, Google의 `client_secret.json` 내려받기, `scripts/get_blogger_token.py` 실행.
- 그 스크립트는 값을 화면에 출력합니다. **본인 터미널에서만** 실행하고 AI 도구나 로그를 모으는 환경에서는 실행하지 않습니다.
- 작업 PC에서 파일을 꺼낼 수 없는 환경이면 다른 PC가 필요합니다([`HANDLER.md`](../HANDLER.md) §10의 전제와 같음).
- 동의 화면이 "프로덕션" 상태인지 먼저 확인합니다(결함 D-11). 옛 절차는 HANDLER §10 5번에 있고, Blogger 초안 모드가 생긴 뒤 다시 씁니다.

## 4. 보안 설정 점검표

코드로 못 바꾸고 운영자만 GitHub 설정에서 할 수 있는 항목입니다. "상태"는 2026-10-25에 운영자가 화면을 읽어 둔 **2차 기록**(캡처 없음)입니다. 바꾸기 직전에 같은 화면을 다시 확인하세요.

> **경고: main 브랜치 보호 규칙을 함부로 켜지 마세요.**
> 자동 발행 3종(Chance_Blog Full-Auto Engine · Blogger Generate · Sync Issue Form)은 `GITHUB_TOKEN`으로 **main에 직접 push**합니다.
> 아래 규칙 중 하나라도 main에 켜면 이 push가 거부되어 **자동 발행이 멈출 수 있습니다**(외부 지식, 이 저장소에서 시험하지 않음).
> "Require a pull request before merging" · 승인/코드 소유자 리뷰 필수 · "Require status checks to pass" · "Require signed commits" · "Restrict updates" · "Lock branch"
> 개인 계정 저장소에서 Actions 봇만 이 규칙을 건너뛰게 하는 방법은 확인된 근거가 없습니다(미확인). 저장소 문서(결함 D-07, `SECURITY_GUARDRAILS.md` §5)의 "github-actions 봇은 우회 허용" 안내는 시험 전에는 가정하지 마세요.
> 안전한 첫 단계는 **삭제 금지 + 강제 push 금지**만 거는 룰셋입니다(4-2 A). 봇은 일반 push만 하므로 이 두 규칙은 막지 않습니다(코드 기준).

### 4-2. 클릭 순서

**A. 룰셋 `main-safe` (삭제·강제 push 금지만)**
1. 저장소 → **Settings** → **Rules** → **Rulesets** → **New ruleset** → **New branch ruleset**
2. Ruleset name `main-safe`, Enforcement status **Active**. Bypass list는 비워 둡니다.
3. Target branches → **Add target** → **Include default branch**
4. Rules에서 **Restrict deletions**와 **Block force pushes**만 체크합니다. **나머지는 모두 체크하지 마세요.** → **Create**
5. 이후 봇이 main에 커밋하는 다음 기회에 그 실행이 초록이고 커밋이 보이는지 확인합니다.
   - 예: Chance가 글을 만들 때 생기는 "🤖 자동 포스팅/이미지 수정" 커밋.
   - 커밋 없이 끝난 초록은 push 경로를 검증하지 못합니다. Blogger가 정지라 지금은 매일 생기는 봇 커밋이 없습니다.
6. 그 실행이 빨강이면 즉시 룰셋을 **Disabled**로 바꾸거나 삭제합니다.

**B. 허용 액션 제한 (선택)**
1. Settings → **Actions** → **General** → **Actions permissions** → 선택한 액션만 허용 → **Allow actions created by GitHub**만 체크 → Save.
2. 지금 워크플로의 모든 `uses:`는 GitHub 제작(`actions/`)입니다. Actions → **Deploy GitHub Pages** → **Run workflow**(main)가 초록인지 확인하고, 문제가 있으면 "모두 허용"으로 되돌립니다.
3. 같은 화면의 "Require actions to be pinned to a full-length commit SHA"는 켜지 마세요.

**C. 시크릿 스캔·푸시 보호**
1. Settings → **Code security**(또는 Code security and analysis)에서 Secret scanning과 Push protection이 **켜짐**인지 확인합니다.
2. push가 막히는 화면이 나오면 **우회(bypass) 버튼을 누르지 마세요.** 키가 든 파일을 빼고 다시 올리고, 이미 올린 키는 폐기·재발급합니다.
3. 저장소 **Security** 탭의 알림을 가끔 확인합니다.

**D. 알림 받기**: 프로필 → Settings → **Notifications**에서 Actions 실패 알림과 수신 방식을 확인하고, 저장소 상단 **Watch**에서 이슈·Actions 알림을 받도록 고릅니다. Watchdog 이슈 #9·#10이 닿았는지는 모르는 상태입니다.

**E. 협업자 확인**: Settings → **Collaborators**. 협업자는 사실상 쓰기 권한이라 워크플로를 고친 브랜치를 실행하고 시크릿을 쓸 수 있으며 Issue Edit 요청 자격도 됩니다. 꼭 필요한 사람만 두세요.

### 5-1. Chance_Blog Full-Auto Engine (`chanceblog.yml`)

- **하는 일**: 신뢰 목록 게시자의 기사로 한·영 글 한 쌍을 만들어 main에 직접 커밋하고 사이트 배포를 요청합니다.
- **바꾸는 것**: `_posts/` 글 2개와 `history.json`. 커밋 제목은 "🤖 자동 포스팅/이미지 수정".
- **언제 도나**: 자동 cron `17 * * * *`(UTC, 한국도 매시 17분). 실제는 하루 5회 안팎. 글은 9시·18시 이후 첫 실행이 만듭니다. 수동 가능.
- **수동 입력**: `dry_run` 기본 **체크**(파일·커밋 없음, 키가 있으면 Gemini·Unsplash는 실제 호출). `fix_images` 기본 꺼짐(켜면 새 글 대신 기존 글의 이미지만 고침).
- **권한·시크릿**: contents 쓰기 + actions 쓰기(배포 요청용). `GEMINI_API_KEY`·`UNSPLASH_ACCESS_KEY`(생성 단계), 변수 `PIPELINE_PAUSE`. 제한 20분.
- **정상일 때**: Summary에 결과와 분야 표(받은 기사·검증 통과·후보·탈락 사유)가 있습니다.
  - 글이 생기면 봇 커밋 + Deploy GitHub Pages 실행 + 사이트에 한·영 글. Summary에 "커밋: 해시"와 "Pages 배포 실행 요청" 줄이 남습니다.
  - 글이 없는 정상 종료는 Summary와 로그의 `[SKIP] code=` 한 줄로만 남습니다.
- **실패하면**: 2-6의 "Chance가 빨강일 때".
- **수동으로 누르면 안 될 때**: `dry_run` 해제는 슬롯과 무관하게 글을 만들어 추가 글이 됩니다(2-1). `fix_images` + `dry_run` 해제는 기존 글을 고쳐 **PR 없이 main에 바로 커밋**합니다.

| 결과 코드 | 뜻 | 색 | 할 일 |
|---|---|---|---|
| `PUBLISHED` | 글을 만들었음 | 초록 | 사이트 확인 |
| `OUT_OF_WINDOW` | 첫 게시 시각(9시) 전 | 초록 | 없음 |

- `dry_run` 실행도 후보가 있으면 결과가 `PUBLISHED`로 보입니다. Summary의 "실행" 줄에 "DRY_RUN: 파일·기록 저장 안 함"이 있으면 실제로는 저장되지 않은 것입니다.

- 분야 대체는 **임시 조치**입니다. 뽑힌 분야에 후보가 없으면 추첨 순서대로 다음 분야를 시도합니다(Gemini 호출 없음). 코드표는 [`ARCHITECTURE.md`](./ARCHITECTURE.md) §4-1에 있습니다.

### 5-2. Blogger Generate (`blogger.yml`)

- **하는 일**: 레지스트리(`pipeline/blogs.json`)의 Blogger 블로그를 하나씩 처리합니다. 주제 선정 → Gemini 글 → 검사 → 게시 또는 초안 저장 → 기록.
- **지금 상태**: `blogger_macat`이 정지(mode off)입니다. plan 단계가 "대상 0개" 안내와 Summary를 남기고 generate 단계는 건너뜁니다(초록). 글·커밋은 없습니다.
- **다시 켜는 길(예정)**: 영어 프로필이 준비된 뒤 `pipeline/blogs.json`의 mode를 `draft`로 바꿉니다(코드 변경이라 AI 작업). `auto` 전환은 사용자 승인이 필요합니다.
- **바꾸는 것(켜져 있을 때)**: `_blogger_drafts/` 초안과 `blogger_history.json`을 main에 직접 커밋("🤖 [블로그키] 생성/게시 기록", push 3회 재시도). 사이트 배포는 요청하지 않습니다.
- **언제 도나**: 자동 cron `0 2 * * *`(UTC) = 한국 11:00. 실제는 16시경. 수동 가능.
- **수동 입력**: `blog`(비우면 Blogger 전체, 오타면 빨강) · `topic`(주제 지정, **하루 상한을 건너뜀**) · `publish`(기본 꺼짐=초안만, 체크하고 게시용 시크릿이 없으면 빨강) · `dry_run`(기본 **꺼짐**, 체크하면 가짜 글).
- **권한·시크릿**: plan은 contents 읽기, generate는 contents 쓰기. `GEMINI_API_KEY`, 게시용 4종 `BLOGGER_BLOG_ID`·`BLOGGER_CLIENT_ID`·`BLOGGER_CLIENT_SECRET`·`BLOGGER_REFRESH_TOKEN`, 변수 `PIPELINE_PAUSE`. **게시용 4종은 지금 모두 미등록이고 등록 금지입니다.**
- **정상일 때(켜져 있을 때)**: 이력 마지막 항목의 `status`가 `posted`(게시, url 있음) 또는 `draft`(초안만). 하루 상한은 1건이고 게시되지 않은 초안도 셉니다.

- **수동으로 누르면 안 될 때**: `topic`은 하루 상한을 건너뛰어 하루 2건이 가능합니다. 켠 뒤에는 `publish` 체크가 곧 공개 게시일 수 있습니다. 아무것도 안 고르면 `dry_run`이 꺼진 채 실제 실행됩니다.

| 코드 | 뜻 | 색 |
|---|---|---|
| `PAUSED` | `PIPELINE_PAUSE` 켜짐 | 초록 |
| `DAILY_CAP` | 오늘 상한 1건 도달(안내 표시) | 초록 |
| `NO_TOPIC`·`GATE_REJECTED` | 주제 없음·검사 탈락(노란 경고) | 초록+노란 경고 |

| `EXPAND_FAILED`·`LLM_FAILED` | 주제 확장·글 생성 AI 실패 | **빨강** |
| `PUBLISH_FAILED` | Blogger 게시 실패(인증·API) | **빨강** |

`SECRETS_MISSING`은 글을 만들기 **전에** 멈추고 시크릿 **이름**만 보여 줍니다(종료 코드 2).

### 5-3. Deploy GitHub Pages (`pages.yml`)

- **하는 일**: 사이트(Jekyll)를 빌드해 공개합니다. 저장소는 바꾸지 않습니다.
- **언제 도나**: 자동 — main에 push될 때마다(경로 제한 없음). 수동 가능(입력 없음). Chance가 새 글을 커밋한 직후에는 Chance가 직접 실행시킵니다(봇 push는 자동 실행을 못 만들기 때문).
- **권한·시크릿**: build는 contents 읽기, deploy는 pages 쓰기와 id-token 쓰기. 시크릿 없음. 새 배포가 오면 이전 실행을 취소합니다.
- **정상일 때**: build·deploy 둘 다 초록, 30~70초 안팎(관측). 회색 "취소됨"은 정상입니다.
- **실패하면**: 보통 build 단계(Jekyll) 오류입니다. 직전 성공본이 계속 공개되지만 새 글은 반영되지 않습니다.
  - "Build Jekyll site" 로그의 오류 줄을 확인하고, 원인 문서를 고쳐 push합니다.
  - 전례: 문서에 쓴 Liquid 문법(결함 D-24, 해결됨).
- **수동으로 누르면 안 될 때**: 위험은 낮습니다(같은 내용 재공개). "Use workflow from"은 **main**으로 두세요(다른 브랜치의 환경 규칙은 미확인).

### 5-4. Guardrails (`guardrails.yml`)

- **하는 일**: 읽기 전용 검사. 비밀 파일·키 모양, 워크플로 규칙, 레지스트리·cron 일치, 이슈 양식·명세, 문법, 깨진 링크, 문서 속 Liquid 문법, 광고 표면 무승인 변경(push·PR만), 단위 테스트, `actionlint`.
- **언제 도나**: 자동 — main push, 모든 PR. 수동 가능(입력 없음). 봇이 `GITHUB_TOKEN`으로 push한 커밋(Chance 글·Blogger 기록·Sync)에는 돌지 않습니다.
- **권한·시크릿**: contents 읽기만, 시크릿 없음. 파이썬 3.10과 3.12 두 번. 새 실행이 이전 실행을 취소합니다.
- **통과·실패 기준**: 검증기 **오류(ERROR) 1건 이상**, 단위 테스트 실패, `actionlint` 지적이면 빨강. **경고(WARN)는 통과**입니다.
- **정상일 때**: 두 파이썬 버전 모두 초록(20~30초 안팎, 관측). 이 가이드를 쓴 시점의 main 기준값은 오류 0·경고 2입니다.
- **실패하면**: "저장소 가드레일 검증" 단계의 `ERROR [검사ID] 파일:줄`을 읽고 그 파일을 고칩니다(AI에게 전달).
- **한계**: 알릴 뿐 막지는 못합니다(병합을 막는 규칙이 없음). 봇 커밋은 검사하지 않으므로 빨강이 없다고 안전한 것은 아닙니다.
- **수동으로 누르면 안 될 때**: 없음(수동 실행은 기준 커밋이 없어 광고 표면 검사를 건너뜁니다).

### 5-5. Watchdog (`watchdog.yml`)

- **하는 일**: 발행이 조용히 멈추는지 보고, 문제가 있을 때만 `[Watchdog] 블로그: 코드` 이슈(라벨 `watchdog`)를 엽니다. 조건이 풀리면 코멘트를 남기고 자동으로 닫습니다. 글·파일은 바꾸지 않습니다.
- **언제 도나**: 자동 cron `30 3 * * *`(UTC) = 한국 12:30. 실제는 17시 20~50분경. 수동 가능(입력 없음).
- **권한·시크릿**: contents 읽기, actions 읽기, issues 쓰기. 시크릿 없음.
- **정상일 때**: 초록, 로그에 "이상 없음", 약 10초(관측). **문제를 찾아도 실행은 항상 초록**입니다.
- **실패하면**: 스크립트 오류일 때만 빨강입니다(드묾). 로그를 보고 다시 실행합니다. 알림 이슈는 별개이며 이슈 본문의 코드를 봅니다.
- **한계**: 알림 통로는 GitHub 이슈뿐이고 운영자에게 닿는지는 미확인입니다. 정지(mode off)한 블로그는 감시하지 않습니다.
- **수동으로 누르면 안 될 때**: 없음(이슈를 열거나 닫을 수는 있음).

| 코드 | 뜻 | 기준 |
|---|---|---|
| `STALE`(치명) | 발행·초안이 오래 없음 | 마지막 활동 후 Chance 36시간·Blogger 50시간 초과 |
| `FAIL_STREAK`(치명) | 연속 실패 | 최근 3회 기록이 모두 실패 |
| `RUN_FAIL_STREAK`(치명) | 워크플로 연속 빨강 | 최근 완료 3회가 모두 실패 |
| `STATE_CORRUPT`(치명) | 이력 파일 손상 | 파일을 읽지 못함 |
| `REJECT_STREAK`(경고) | 연속 검사 탈락 | 최근 5회 기록이 모두 탈락 |
| `UNPUBLISHED`(경고) | 초안만 쌓임 | 자동 게시 모드인데 최근 3회 모두 초안만 |
| `NO_ACTIVITY`(경고) | 기록이 전혀 없음 | 이력·커밋 모두 없음 |

### 5-6. Issue Edit (`issue-edit.yml`)

- **하는 일**: 이슈 양식으로 접수된 수정 요청을 검사·수정해 **PR로** 올립니다. main에 직접 반영하지 않습니다.
- **바꾸는 것**: 라벨 3개(`blog-control`·`edit:page`·`edit:image`) 만들기·갱신, 브랜치 `issue-edit/번호-대상-r실행번호` + 커밋 + PR(`Fixes #번호`), 이슈 코멘트, 그 브랜치의 Guardrails 실행 요청.
- **언제 도나**: 자동 — 이슈가 **새로 열릴 때만**. 작성자가 소유자·멤버·협업자이고, 라벨 `blog-control`이 있거나 제목이 `[페이지 수정]`·`[이미지 변경]`으로 시작해야 합니다. 수동 가능.
- **수동 입력**: `issue_number`(필수), `dry_run` 기본 **체크**(파일·PR·코멘트 없음).
- **권한·시크릿**: job에 contents·issues·pull-requests·actions **쓰기** 4종(축소는 예정). `GEMINI_API_KEY`·`UNSPLASH_ACCESS_KEY`는 AI 단계에만.
- **정상일 때**: 이슈에 "✅ 수정안을 PR 로 만들었습니다" + PR 링크. 거부는 "⚠️ 수정하지 않았습니다 + 사유", 오류는 "❌ 처리 중 오류가 발생했습니다", 처리 대상이 아니면(`ignored`) 코멘트가 없습니다.
- **관측**: 실제 처리 기록은 0건(미관측)입니다.
- **실패하면**: 2-5의 확인 순서를 따릅니다.
- **수동으로 누르면 안 될 때**: `dry_run`을 끄고 이미 처리한 이슈를 다시 돌리면 **PR이 또 생깁니다**(브랜치 이름에 실행 번호가 붙음). `dry_run`이어도 AI 호출과 로그의 요청문 출력은 있습니다(2-9).

### 5-7. PR Scope Check (`pr-scope-check.yml`)

- **하는 일**: PR 제목·본문의 `Fixes #번호`로 요청 이슈를 찾아 "요청한 범위만 바뀌었나"를 판정하고 PR에 코멘트 1개를 남깁니다(다시 돌면 고침).
- **언제 도나**: 자동 — PR 열림·갱신·다시 열림·draft 해제. 같은 저장소 브랜치의 PR만(포크 PR은 건너뜀). 수동: `pr_number`(필수).
- **권한·시크릿**: contents 읽기, pull-requests 쓰기, issues 읽기. 시크릿 없음. 항상 **기본 브랜치의 코드**로 실행하고 PR 쪽 파일은 읽기만 합니다.
- **정상일 때**: PR에 "요청 범위 검증" 코멘트. ✅ 통과 / ⚠️ 확인 필요(AI가 쓴 문장은 직접 읽기) / ❌ 요청 범위 밖(이때 실행이 빨강, 설계된 동작).
- **실패하면**: 빨강은 판정입니다. 병합하지 말고 2-10을 따릅니다.
- **주의**: `Fixes #번호`가 없으면 **검사 없이 초록**입니다(코멘트 없음). 판정은 병합을 막지 못합니다. 봇·Copilot PR에서 자동으로 도는지는 미확인입니다(2-10).
- **수동으로 누르면 안 될 때**: 없음(코멘트만 남김).

### 5-8. Sync Issue Form (`sync-issue-form.yml`)

- **하는 일**: `pages.json`(고정 페이지 목록)과 이슈 양식의 "대상 페이지"·"수정 항목" 드롭다운을 최신으로 맞춥니다.
- **바꾸는 것**: `pages.json`과 `.github/ISSUE_TEMPLATE/page-edit.yml` 두 파일만 main에 직접 커밋합니다(바뀐 것이 없으면 "변경 없음"). 사이트 배포는 요청하지 않습니다.
- **언제 도나**: 자동 — main push 중 `edit-spec.yml`·`page-edit.yml`·`pages.json`·**루트의** `.md`·`.html`이 바뀐 때. 하위 폴더 파일은 대상이 아닙니다. 수동 가능(입력 없음).
- **권한·시크릿**: contents 쓰기. 시크릿 없음.
- **정상일 때**: 초록, 대개 "변경 없음". 새 페이지에 `editable: true`를 넣으면 "chore: pages.json·이슈 양식 자동 동기화" 봇 커밋이 생깁니다.
- **실패하면**: 로그의 `[오류]` 줄을 봅니다. 원인은 페이지 id 중복·이름 규칙 위반, 명세 오류, push 3회 실패입니다(2-4).
- **수동으로 누르면 안 될 때**: 거의 없음.

### 5-9. pages-build-deployment (GitHub 관리)

- **정체**: Pages 설정이 "브랜치에서 배포"일 때 GitHub가 돌리는 내장 워크플로입니다(외부 지식). 저장소에 파일이 없고 우리가 고칠 수 없습니다.
- **이 저장소**: Pages 소스가 **GitHub Actions**(2026-10-25 운영자 기록)라서 예전 흔적이며 지금은 쓰이지 않아야 합니다. 가장 최근 실행 날짜는 **미확인**입니다.
- **Deploy GitHub Pages와의 차이**: Deploy GitHub Pages는 우리 파일(`pages.yml`)로 직접 빌드·공개하고, pages-build-deployment는 GitHub 자동 방식입니다. 둘이 함께 켜지면 같은 사이트를 이중 배포할 수 있습니다(동작은 미확인).
- **확인(선택)**: Actions 목록에 이 항목의 새 실행이 계속 생기면 Settings → **Pages** → Source를 다시 확인합니다.
- **누르지 않습니다.**

## 7. 용어 풀이

| 말 | 쉬운 뜻 |
|---|---|
| 워크플로 | Actions 탭의 항목 하나. 정해진 때나 일이 생길 때 자동으로 도는 작업 묶음 |

| 노란 경고 | 초록이어도 실행 안에 남는 주의 표시 |
| 정상 건너뜀 | 지금 할 일이 아니라서 끝남(`[SKIP]` 한 줄) |

| 슬롯 | 글을 만드는 시각 칸. Chance는 9시·18시 |
| Secrets·Variables | 저장소에 넣는 비밀 값 / 일반 설정 값 |
| PR | 바뀐 내용을 보고 병합(승인)하기 전의 제안 |

| 광고 표면 | 광고 심사에 영향을 주는 파일. 승인 없이 못 바꿈 |
