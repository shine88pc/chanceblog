# 설치 버전 묶기(constraints) — 만드는 법·갱신 절차·검증 방법

> 규칙 문서입니다. 요구 파일 셋(`requirements-dev.txt`·`requirements-edits.txt`·`requirements-pipeline.txt`)의 **범위 표기는 그대로** 두고, 워크플로의 설치 줄이 파이썬 버전별 목록 파일 둘(`constraints-py310.txt`·`constraints-py312.txt`)로 **설치 버전을 묶습니다**. 검증기 규칙은 **DEP-3** 입니다.
> 운영자 결정: 2026-11-24 확인 034 보기 ① 승인(이슈 #258) — 변경안 A 한 건. 근거 조사(AP7): 격리 환경 둘에 범위 그대로 설치한 실제 버전·전체 시험 10,463개 통과·같은 설치를 한 번 더 해서 같은 버전과 해시. 결함 대장 D-461–D-465.

## 1. 한눈에

| 항목 | 내용 |
|---|---|
| 무엇이 바뀌었나 | 새 파일 둘(저장소 맨 위, 요구 파일 옆) + 워크플로 설치 줄 10곳에 `-c` 하나 + 검증기 규칙 DEP-3 + 시험. 요구 파일 셋은 한 글자도 바뀌지 않았습니다 |

| 목록에 없는 것 | `actionlint-py` — 요구 파일이 이미 `==` 로 정확히 고정했고, 미리 만든 설치 파일이 없어 이번 조사에서 설치하지 않았습니다(아래 6의 d) |

## 2. 설치 줄 10곳 — 어느 파이썬에 어느 목록인가

| 워크플로(job) | 파이썬 | 설치 줄 |
|---|---|---|
| `blogger.yml`·`naver.yml`·`tistory.yml` (generate) | 3.12 | `python -m pip install -c constraints-py312.txt -r requirements-pipeline.txt` |
| `issue-edit.yml`·`pr-scope-check.yml`·`sync-issue-form.yml` | 3.12 | `python -m pip install -c constraints-py312.txt -r requirements-edits.txt` |
| `chanceblog.yml`·`chance-fix-images.yml`·`chance-shadow.yml` | 3.10 | 따옴표 친 `google-genai>=2,<3` 앞에 `-c constraints-py310.txt` |
| `guardrails.yml` (검사, 3.10·3.12 두 칸) | 칸마다 다름 | 단계의 `env` 에 변수 `CONSTRAINTS` 를 두고 줄은 `python -m pip install -c "$CONSTRAINTS" -r requirements-dev.txt` |

- **매트릭스 칸**: 변수 값은 `constraints-py` 뒤에 GitHub 식을 두고 `.txt` 로 끝납니다. 식은 matrix 의 `python-version` 이 3.10 이면 310, 아니면 312 를 고릅니다. 식(달러 기호와 이중 중괄호)은 **`env` 안에만** 둡니다 — `run:` 에 식을 끼우면 검증기 WF-4 가 거절합니다. 새 파이썬을 matrix 에 더하면 식도 고치고 목록 파일도 만들어야 하고, 안 하면 DEP-3 이 그 칸에서 오류를 냅니다.
- **그대로 둔 것**: `python -m pip install --upgrade pip`(pip 자신은 이 변경 밖 — 항상 최신), 권한·시크릿·트리거·`name`·`if`·다른 `env` 칸·`uses`. 워크플로 파일에서 바뀐 것은 설치 줄(과 guardrails 의 `env` 한 칸)뿐입니다.
- **로컬에서**: 같은 버전으로 설치하려면 `python -m pip install -c constraints-py312.txt -r requirements-dev.txt`. `-c` 없이 설치하면 범위 안 최신이 깔려 CI 와 다를 수 있습니다. Windows 한글 환경에서는 pip 가 요구 파일·목록 파일을 시스템 인코딩으로 읽어 한글 주석에서 오류가 날 수 있습니다 — 환경 변수 `PYTHONUTF8=1` 을 먼저 켭니다(요구 파일 셋도 마찬가지인 기존 한계).

## 3. 검증기 DEP-3 — 무엇을 보나

`scripts/validate_repo.py` 의 `check_dependency_constraints`(기존 DEP-1 과 별개, DEP-1 은 경고 그대로). 모두 **오류**입니다.

1. **설치 줄에 `-c` 가 있나** — 요구 파일(`-r`)이나 패키지 이름을 설치하는 모든 `pip install` 이 대상입니다. 맨 앞 낱말이 `pip`·`pip3`·`python -m pip`(`-mpip` 처럼 붙여 쓴 것도)인 명령을 읽고, `install` 앞에 값을 받는 전역 옵션이 와도(`pip --cache-dir cache install …`, pip 가 받아 주는 줄임말 `--cache cache` 도) 설치로 읽습니다. 값을 받는 전역 옵션의 이름과 별칭(`--log`·`--log-file`·`--local-log`, `--timeout`·`--default-timeout` 등)은 손으로 적은 목록이라, 진짜 pip 의 옵션 파서와 견주는 시험으로 빠진 것이 없는지 확인합니다(pip 가 새 옵션을 더하면 그 시험이 먼저 알립니다). `pip` 자신만 올리는 줄(`--upgrade pip`)은 제외합니다. 따옴표 친 값과 단계·job·워크플로 `env` 변수(`"$CONSTRAINTS"`)를 읽습니다. 인라인 패키지(`google-genai>=2,<3`)는 그 파이썬용 목록에 있고 범위 안인지도 봅니다.
2. **번호가 맞나** — 같은 job 에서 그 줄 앞의 `actions/setup-python` 의 `python-version`(따옴표 친 글자 하나나 matrix 목록)과 목록 파일 번호가 같아야 합니다(3.10 은 py310, 3.12 는 py312). 칸마다 하나씩 따져 봅니다. 파일은 저장소에 있어야 합니다.
3. **목록 파일 모양** — 줄은 `이름==버전` 뿐입니다. 범위(`>=`·`<` 등)·주소·`-e`·옵션(`--hash` 등)·빈 이름·extras·환경 표식·지역 버전·와일드카드는 오류, 같은 이름(대소문자·`-`·`_`·`.` 를 가리지 않음)이 둘이어도 오류입니다.
4. **요구 파일과의 짝** — 요구 파일(맨 위의 `requirements*.txt` 와 설치 줄이 `-r` 로 가리키는 파일)의 모든 패키지가 각 목록에 있고 그 버전이 요구 파일의 범위 안이어야 합니다(`<3` 은 3.0 의 사전 릴리스도 받지 않습니다). 요구 파일에서 이미 `==` 로 고정한 줄은 목록에 없어도 됩니다 — 있으면 같은 값이어야 합니다.
5. **패키지를 받아 오는 곳**(확인 040 ① 승인) — `pip install` 줄에 `--index-url`(pip 가 같은 옵션으로 받아 주는 옛 별칭 `--pypi-url` 도)·`-i`·`--extra-index-url`·`-f`(`--find-links`)·`--trusted-host` 가 있으면 오류입니다. `install` 앞의 전역 위치도, pip 가 받아 주는 줄임말(`--extra-index`)·붙여 쓴 값(`-i` 바로 뒤에 주소)·합친 짧은 옵션(`-qi` 뒤에 주소)도 같습니다. `pip` 자신만 올리는 줄(`--upgrade pip`)도 대상입니다 — 그 줄에서 pip 자신이 다른 곳에서 오면 그 뒤의 모든 설치를 믿을 수 없습니다. 설치 대상을 주소·VCS·직접 참조로 지정한 것(`git+` 로 시작하는 글·`://` 가 든 글·`이름@주소`)과 `-e` 설치도 오류입니다(`-c` 가 없어도 따로 알립니다 — 설치 대상이 전부 주소인 줄도 같은 줄의 `-c` 없음·번호 어긋남 오류를 가리지 않고 함께 냅니다. 독립 검증 S 의 N6). 버전을 정확히 묶어도 다른 곳에서 같은 이름·버전을 받는 길이 열려 있으면 묶음이 무의미해서입니다 — 이 저장소는 기본 색인에서 이름과 버전으로만 받습니다. 값을 받는 전역 옵션을 읽는 목록(1번)은 그대로이고 그 위에 얹었습니다. 요구 파일(`-r`)과 목록 파일 안의 옵션 줄·주소는 3·4번이 이미 오류로 봅니다.

**새 모양만 허용**합니다(WF 규칙과 같은 방식): 읽지 못하는 모양은 통과가 아니라 오류입니다 — `bash -c` 로 감싼 설치·`eval`·`xargs`·`sudo`·`uv pip`, 셸이 파이프·here-string 으로 받은 글을 실행하는 줄(`echo '…' | bash`·`printf '…' | sh`·`bash <<< '…'`·`bash -s <<< …` — `sh`·`zsh`·`dash`·`ksh` 도 같고 `sudo`·`env` 를 앞에 붙여도 같으며 입력에 pip install 이 있든 없든 오류입니다. 독립 검증 S 의 R3), 정의되지 않은 변수, 지원하지 않는 식, `-e` 설치, setup-python 의 `pip-install` 입력, 따옴표 없는 `python-version: 3.10`(YAML 이 숫자 3.1 로 읽음).

**한계**: 한 파일 안의 길만 따라갑니다(재사용 워크플로·지역 복합 액션 안의 설치·`$GITHUB_ENV` 로 만든 값은 못 읽습니다). `run` 만 읽습니다. heredoc 은 알아보지 못해 본문의 줄도 명령처럼 읽습니다(그 안의 `pip install` 글은 오류가 될 수 있습니다). 단계의 `working-directory` 를 바꾸면 `-c`·`-r` 의 상대 경로가 어긋나도 이 검증기는 모릅니다(pip 가 실행 때 파일을 못 찾고 실패합니다). `echo`·`printf`·`git`·`gh` 말고 다른 명령의 인자에 `pip install` 글이 들어 있으면(예: `grep` 으로 그 글을 찾는 줄 — `<<<` 뒤의 here-string 글도 인자와 같게 읽습니다) 읽지 못한 설치로 보고 오류를 냅니다 — 글을 바꾸세요. `pip download`·`pip wheel` 은 대상이 아닙니다. 워크플로 읽기는 PyYAML 이 있어야 돕니다(없으면 건너뜁니다 — WF-0 이 그 경고를 냅니다. CI 는 `requirements-dev.txt` 로 설치합니다). 환경 변수 `PIP_CONSTRAINT` 로 묶는 방식은 인정하지 않습니다(`-c` 만). 위 5번의 색인·링크 옵션 거절은 설치 줄의 옵션 낱말만 읽습니다 — 같은 옵션을 환경 변수나 pip 설정 파일로 주거나 셸 변수에 담아 펼치면 읽지 못하고(아래 (a)·(e)), 값을 받는 옵션의 값 자리에 옵션처럼 생긴 글자가 오면(`--log -i`) 오류 쪽으로 읽습니다. pip 가 오류로 끝내는 겹치는 줄임말(`--e`)도 안전한 쪽으로 오류로 읽습니다. 받아 오는 곳이 아니라 신뢰·빌드에 닿는 옵션(`--cert`·`--proxy`·`--global-option`·`--install-option`·`--config-settings`·`--no-build-isolation`)은 이 규칙의 대상이 아닙니다.

**오류도 없이 지나가는 모양**(독립 검증이 찾았습니다. 일부러 돌려 쓰지 않으면 나오지 않는 모양이라 사고로 나올 가능성은 낮지만, 위의 '읽지 못하는 모양은 오류' 원칙에서 벗어나는 곳이라 적어 둡니다): (a) 명령 이름을 변수로 부르기 — `PIP=pip` 로 정한 뒤 `$PIP install …` 처럼 변수가 명령 자리에 오면 설치로 읽지 못하고 지나갑니다(`"$PYTHON" -m pip install …` 은 읽지 못한 설치로 오류입니다). (b) 다른 명령 뒤에 `-m` 과 모듈 이름을 붙여 쓰기 — `python -mpip install …` 은 읽지만 `sudo python -mpip install …` 처럼 `python` 이 맨 앞이 아니면 지나갑니다. (c) 따옴표 안의 명령 치환 — `echo`·`printf`·`git`·`gh` 의 안내문은 설치 글을 보지 않는 예외라 `echo "$(python -m pip install …)"` 가 지나가고, 큰따옴표로 감싼 대입 `x="$(python -m pip install …)"` 도 지나갑니다(따옴표 없는 `x=$(…)` 안의 설치는 보통 설치 줄처럼 읽어 `-c` 가 없으면 오류이고, `export X="$(…)"`·백틱은 읽지 못한 설치로 오류입니다). (d) 같은 단계의 스크립트 안에서 `-c` 가 가리키는 변수를 다시 대입하기(`CONSTRAINTS=/dev/null`) — 검증기는 단계·job·워크플로 `env` 에 적힌 값만 읽습니다. (e) 설치 줄의 옵션 밖의 길로 색인 바꾸기 — `pip config set`·pip 설정 파일·환경 변수 `PIP_INDEX_URL`(`PIP_EXTRA_INDEX_URL`·`PIP_FIND_LINKS`·`PIP_TRUSTED_HOST` 도 같은 길)와 `pip download`·`pip wheel` 줄의 색인 옵션은 지나갑니다. 설치(`pip install`) 줄에 직접 쓰는 `--index-url`·`--extra-index-url`·`-f`(`--find-links`)·`--trusted-host` 는 이제 오류입니다(확인 040 ① 승인, 위 5번). 환경 변수·설정 파일까지 거절하는 규칙은 이번 승인 범위 밖이라 두지 않았고, 필요하면 별도 변경으로 운영자 승인을 받아 더합니다. (f) `pip` 가 아닌 설치 도구 — `pipx install …` 은 지나갑니다(`uv pip`·`pipx run pip install` 은 읽지 못한 설치로 오류입니다). (g) 단계의 `shell:` 을 bash 가 아닌 것으로 바꾸고(예: python) 그 안에서 pip 를 부르기 — 이 검증기는 `run` 을 bash 줄로만 읽습니다(지금 저장소의 워크플로에는 `shell:` 을 쓰는 단계가 없습니다). (h) 다른 언어의 코드 안에서 pip 부르기와 감싸는 명령의 옵션 값 — `python -c "…"`·`python - <<< '…'` 처럼 파이썬 등 해석기의 코드 글 안에서 pip 를 부르는 것은 `pip install` 낱말이 따로 보이지 않으면 읽지 못하고 지나갑니다. 셸이 입력을 받는 줄(위 '새 모양만 허용')은 오류로 읽지만 감싸는 명령의 옵션에 값이 끼면(`sudo -u 사용자 bash`·`env -C 폴더 bash`) 셸 이름을 못 찾아 지나갑니다. 지금 저장소의 워크플로에는 둘 다 없습니다(독립 검증 S 의 R3). 셸 입력 줄의 판정은 셸 이름과 감싸는 명령(sudo·env·timeout·nice·exec·xargs 등) 목록으로 하므로 `| (bash)`·`| { cd /tmp; bash; }`·`tee >(bash)`·`while read` 루프·목록 밖 감싸는 명령(`flock`·`su -c`·`ssh` 등)·목록 밖 셸(`pwsh` 등)·`$SHELL`·`sh -c "$(curl …)"` 같은 모양도 지나갑니다(독립 재확인 S 의 권고) — 이런 줄도 지금 저장소의 워크플로에는 없습니다.

## 4. 만드는 법과 갱신 절차(월 1회, 보안 공지가 있으면 그때 바로)

1. **외부 접속이 필요한 일이라 번호 있는 확인이 먼저입니다.** 접속 대상은 패키지 색인 두 호스트의 읽기뿐이어야 하고, 승인 범위(호스트·설치 파일 크기·환경을 지우는 때)를 확인 요청에 적습니다. 승인 없이 설치하지 않습니다.
2. 저장소 밖에 새 가상환경 둘(파이썬 3.10·3.12)을 만들고 요구 파일 셋을 **범위 그대로**(고정 없이) 한 번에 설치합니다. pip 설정 파일의 `trusted-host`·프록시가 인증서 검사를 끄지 않는지 확인하고(`--isolated`), 미리 만든 설치 파일만 받습니다(`--only-binary=:all:`). `actionlint-py` 는 소스 설치라 빼고 돌립니다(아래 6의 d).
3. 각 환경에서 `pip check` 가 깨진 요구 없음으로 끝나는지, 접속을 막은 시험 러너(같은 컴퓨터 접속만 허용)로 **전체 시험이 실패 0** 인지 봅니다. 시험 대부분이 가짜 SDK 를 쓰므로 접속 없는 호출 모양 점검(`generate_content` 인자·`GenerateContentConfig` 필드)도 같이 합니다.
4. **같은 설치를 새 환경에서 한 번 더** 해서 버전·설치 파일 이름·해시가 같은지 봅니다(재현성).
5. 설치된 버전을 `이름==버전` 으로 적어 두 파일을 새로 만듭니다(맨 위 주석에 만든 날짜·방법·시험 결과). 이전 목록과 달라진 줄만 이유와 함께 변경 요청에 씁니다.
6. 목록 파일만 바꾸는 작은 병합 부탁(의존성 파일이라 T3 — 운영자가 직접 병합)을 보냅니다. 병합 전에 검증기(`python scripts/validate_repo.py`)가 DEP-3 오류 0 인지 봅니다.
7. 병합 전 한 번, 임시 가지(`NO-MERGE-` 이름)에서 GitHub 러너(리눅스, 실제 파이썬 3.10·3.12 패치 버전)로 같은 설치 줄이 설치·`pip check`·가져오기까지 통과하는지 봅니다. 윈도에서 만든 목록이 리눅스에서도 같은 버전으로 설치된다는 보장이 없기 때문입니다.

Dependabot 알림은 저장소 설정이라 운영자 몫입니다. 보안 공지가 목록의 버전에 걸리면 월 1회를 기다리지 않고 위 절차를 바로 돕니다.

## 5. 대안과 나중 일

- **요구 파일의 범위를 `==` 로** — 범위 유지 지시와 충돌하고 하위 의존성은 여전히 떠다니며, 3.10 이 `google-genai` 2.34.0 을 받지 못해 요구 파일이 파이썬마다 갈라집니다. 하지 않았습니다.
- **해시까지 담은 잠금(`--require-hashes`)** — 가장 강한 무결성이지만 설치 줄·도구가 커집니다. 확인 032 의 설치 고정·해시 항목과 같은 계열이라 보류했고, 지금 구조 위에 얹을 수 있습니다.

## 6. 위험과 되돌리기

- (a) 윈도에서 푼 목록이 리눅스 러너에서도 그대로 설치되는가 — 병합 전 임시 가지 검증(위 4의 7)으로 확인합니다.
- (b) 패치 버전 차이(조사한 PC 의 3.10.5·3.12.0 대 러너의 3.10.22·3.12.16) — 같은 검증이 확인합니다.
- (c) 보안 패치를 자동으로 받지 못합니다 — 월 1회 점검과 보안 공지 때 즉시 갱신으로 보완합니다.
- (d) `actionlint-py==1.7.12.25` 는 이 변경 밖입니다 — 미리 만든 설치 파일이 없어 검사 칸이 매번 소스에서 설치하며 그때 실행 파일을 외부에서 받습니다. 소스 설치의 빌드 도구에 `-c` 가 닿는지는 확인하지 못했습니다(미확인). 확인 032 의 설치 고정·해시 항목과 함께 다룹니다.
- (e) 시험이 가짜 SDK 를 써서 통과가 실제 SDK 호환을 보장하지는 않습니다 — 접속 없는 호출 모양 점검이 보완합니다.
- (f) **사이트 공개**: 목록 파일 둘은 저장소 맨 위에 있어 사이트의 정적 파일로 그대로 열립니다(`tests/test_site_cleanup.py` 의 `STATIC_EXPOSED`). 내용은 공개 패키지 이름과 버전뿐입니다. 사이트에서 빼려면 `_config.yml` 의 exclude 를 바꿔야 하는데 그 파일은 광고 표면이라 운영자 승인(T3)과 병합 정책의 내부 항목 목록 변경이 같이 필요합니다.
- 코드 소유자 지정(`.github/CODEOWNERS`)에는 요구 파일(`/requirements*.txt`)과 목록 파일(`/constraints*.txt`) 줄이 둘 다 있습니다(목록 파일 줄은 확인 040 의 승인으로 더했습니다).
- **되돌리기**: 설치 줄 10곳의 `-c`·새 파일 둘·검증기 DEP-3 과 시험을 한 커밋으로 되돌리면 지금까지와 같습니다(데이터 이관 없음).
